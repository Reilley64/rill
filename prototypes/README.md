# Syntax prototypes

Sample programs for [issue #2](https://github.com/Reilley64/rill/issues/2). They are for choosing syntax, not a final grammar.

## Decisions so far

Later tickets changed some of these. The ticket behind each change is in parentheses.

- Statements end with a semicolon. Semicolons are required.
- `import std::log;` imports an exported name; `::` separates path segments. Single/group imports, item/module `as` aliases, and `export import` re-exports preserve canonical type/family identity. Export functions/types directly on their declarations; ordinary declarations/import bindings are private by default. No bottom export lists, export-from form, wildcards, defaults, or string-path imports. (#17)
- Each source file defines a module. Application paths start at the entry directory; self/super paths stay within that origin root. `std` has an isolated toolchain root, used by its own unprefixed imports too. No inline modules, automatic index/mod fallback, or configurable package/search paths in v0. Load the entry/prelude/transitive import graph once, not unrelated files. Declaration cycles can work; unresolved aliases/impossible layouts fail. See [ADR 0010](../docs/adr/0010-file-modules-explicit-exports-and-privacy.md) and `10-modules/main.rill`. (#17)
- Import paths are case-sensitive origin-root paths, not lookup through prior local aliases. Grouped imports select exports from their module; competing distinct module/item identities in one namespace are errors, never precedence by filesystem/import order. Imported module qualification accesses exports, not implicit child-file loading. Types/modules and values/functions have separate namespaces; importing an exported name can bind both public halves, not a private counterpart. (#17)
- A fixed prelude supplies primitive types, compiler predicates, and canonical copy/dispose declarations, not the whole std library. Other source-level cross-module names require imports. Compiler metadata and automatic cleanup do not require source-visible private type names, and local shadowing cannot replace canonical ownership mechanics. (#17)
- `List<T>` and the key/value collection `Map<K, V>` belong to `std::collection`, along with the existing list helpers shown here. Use `Map` for the type, not `Dictionary`; lowercase `map(...)` remains the transformation function. Complete collection interfaces remain under #23.
- Ordinary top-level execution runs only in the file you run; there is no `main` function or implicit module initializer/exported runtime let. `rill test` runs independent expectations, including imported modules once, not ordinary startup code. Parse/type-check loaded startup and expectation bodies in both modes, but ordinary executables omit expectations and their test-only code. Expectations cannot capture startup lets. (#17, #27)
- `expect <expression>;` is a top-level, test-only declaration requiring a `bool`: `true` passes and `false` fails. It is a keyword, not an imported function, and is rejected inside ordinary functions, closures, or other nested blocks. Ordinary builds neither execute expectations nor include their test-only code in the executable. Failures report the source location, expression, and useful operand values without re-evaluating expressions or changing evaluation order or short-circuiting. Production checks still use `guard`, `Result`, or `panic`. See `06-expect.rill` for the syntax and rejection examples, and prototypes 2, 3, and 5 for expectations alongside the functions they test. Those expectations construct their own inputs rather than relying on ordinary top-level startup code. (#27)
- `x |> f(y)` means `f(x, y)`. `x |> f` means `f(x)`. `x |> pad(10, _)` means `pad(10, x)`. The right side is a name, a call, or a parenthesized arrow function. `|>` binds looser than arithmetic, comparison, and logical operators, groups left to right, and unary `&` binds tighter. (#12)
- `?` after a pipe step applies to that step's result: `text |> parsePort? |> toAddress` means `toAddress(parsePort(text)?)`. (#12)
- There is no ternary. `if (c) a else b` is an expression that always needs `else`. On its own line, `if` is a TypeScript-style statement with blocks and `else if`. (#12)
- `guard <condition> else { ... }` and `guard let x = <Result> else (error) { ... }`. `(error)` binds the `Err` value. `guard` also takes a `Result` or `Option` directly, as in `guard send(&jobs, n) else { return; }`. The `else` block must leave its scope with `return`, `break`, `continue`, or a `never` call. (#11)
- Postfix `?` returns an `Err` or `none` early. An unused `Result` is a compile error; `let _ = x;` drops one on purpose. (#11)
- No semicolon after a block, as in TypeScript.
- `let x = 1;` is immutable; `let mut x = 1;` permits reassignment and changes to owned fields. No `const` or per-field mutability declarations. Owned parameters are immutable bindings; move one into a mutable local to modify it. Loops may update mutable accumulators. (#15)
- A plain `T` parameter takes ownership, `&T` borrows read-only, and `&mut T` borrows exclusively for mutation. Callers explicitly obtain access with `&x` or `&mut x`, except for implicitly copied values such as `int` and `Point`. Existing copy classification is unchanged by mutability. `copy(x)` copies; neither copying nor moving erases borrowed dependencies, and exclusive access cannot be duplicated. `Shared<T>` gives several owners, not ordinary mutable access to the shared payload. (#7, #15)
- Check borrow conflicts statically until last use, including dependencies carried in other values and uses during disposal. Recognize disjoint named-field storage locally, not arbitrary indices or disjoint pointees merely from different field names. Forwarding mutable access to a borrowing parameter reborrows it. (#15)
- `=` and compound assignments such as `+=` are statements, not expressions; no `++` or `--` in v0. `*reference` accesses the referent, while field projection through borrows remains convenient. Replacement computes the destination/RHS once, frees/disposes the old value, then installs the replacement. Cancellation delivery is deferred from old-value disposal through installation, while scheduling remains allowed; deliver pending cancellation afterward against a valid destination and clean it up once. (#15, #16)
- Reference-containing results and retained storage carry conservative input dependencies, including borrows nested in owned inputs. Check function exits against both returned values and caller-owned mutable destinations. Borrowing never extends the source's owning scope, and temporaries may be borrowed only within their enclosing statement. See [ADR 0007](../docs/adr/0007-explicit-mutation-with-conservative-borrow-dependencies.md), `07-mutation.rill`, and `07-mutation-safety.md` for the approved design and validation cases. (#15)
- A name needs an overload declaration before it can have overloads: a body-less signature such as `function show<T>(value: &T): string;`. Implementations attach to the original family, including through aliases, and inherit its visibility; extending a family does not implicitly re-export the local import binding. The ordinary orphan rule permits the declaration's module or a module owning a type in the parameters; re-exporting is not defining that type. (#10, #17)
- Reject distinct implementations with identical canonical parameter patterns at collection; return types do not create overloads. Repeated paths to one implementation are deduplicated. Distinct generic/specific patterns still use most-specific dispatch; incomparable matches fail at a call. Orphan placement alone does not prevent conflicts, and neither import order nor dead-code elimination selects implementations. (#17)
- Required built-in ownership mechanics, such as genuine guard release, owner counts, and native-borrow retention, cannot be replaced by an ordinary overload. This is separate from replaceable ordinary defaults and the rejected blanket outermost-type placement rule for all copy/dispose overloads; #23/#28 must specify the exact protected-operation boundary. (#17)
- The most specific overload wins. `show(items: &List<Point>)` beats `show<T>(items: &List<T>)`, so a generic overload is the default for types without their own overload.
- A string, number, or `bool` literal can be a parameter type, as in `greeting(language: "fr")`. A literal beats its type, such as `string`.
- Every call resolves to one overload at compile time. If a literal overload could match a value the compiler doesn't know, the call is an error, so `fib` uses `match`. `match` is the only way to split a union at run time. (#10)
- A generic overload states what it needs with `where show(T)`. `noBorrow(T)`, `sendable(T)`, and `shareable(T)` are separate compiler-recognized intrinsics, not user-implementable overloads: borrow-freedom, transfer safety, and concurrent read-sharing are distinct from copyability and invocation mode. Derive properties from known structure/captures or explicit generic requirements before monomorphization; erased arrows cannot invent environment evidence. See [ADR 0009](../docs/adr/0009-concurrency-safety-and-cooperative-cancellation.md) for the recursive rules and trusted-type exceptions. (#10, #15, #16)
- Ordinary families named in exported generic requirements must have publicly nameable exported declarations; importing an operation does not implicitly bind its requirements in source. Private value types/implementation metadata remain allowed under opacity, and compiler metadata checks are not source imports. (#17)
- v0 has no named `where` constraint groups or aliases. List each requirement explicitly on every declaration that needs it, for example `where eq(T), hash(T), copy(T), show(T)`. Grouping can be reconsidered after v0; this does not change individual overload requirements or intrinsic `noBorrow(T)`. (#20)
- If no overload is the most specific, the call is a compile error.
- `spawn(() => f(x));` runs a zero-argument, void-returning callable in the background. Import `spawn` and `stop` directly from `std`; there is no `go` keyword or `std::process` module. `spawn` returns a `Routine`. `stop(&routine)` requests cooperative cancellation and waits for termination plus cleanup; repeated/concurrent calls share termination state, self-stop panics, and freeing the handle still does not stop it. (#8, #16)
- `spawn` owns its callable and requires a borrow-free, sendable capture environment. If the caller still needs a non-copying captured value, make an explicit `copy` before creating the closure, not inside it. Scoped waiting helpers may borrow under transfer/sharing and access rules, and return valid caller-dependent borrows, never references into destroyed child storage. (#7, #8, #16)
- `Mutex<T>` payloads and channel messages require `noBorrow(T)` and `sendable(T)`, not `shareable(T)`. Synchronized endpoints preserve concurrent operations and `Shared<Receiver<T>>`. `Shared<T>` itself requires both properties of `T` for cross-goroutine use; this still grants no ordinary mutable payload access. (#16)
- `lock(&counter)` acquires a goroutine-aware mutex and returns a non-copyable `LockGuard<T>` borrowing its source. `let mut held = lock(&counter); *held += 1;` uses built-in guard dereference, not a user-defined Deref trait or borrowMut accessor. Scope-exit/explicit disposal unlocks, not disposes the payload; protected borrows keep the guard needed. The guard is not sendable or borrow-free, but read-only sharing is allowed when T is shareable. Holding it across suspension/worker migration is allowed; self-reacquisition panics. There is no public raw unlock or callback-only withLock in v0. See `09-concurrency-safety.rill` and `09-concurrency-safety.md`; new library module/factory spellings remain provisional for #23. (#16)
- `channel<int>(10)` returns a `Sender<int>` and a `Receiver<int>`. The channel closes when its last `Sender` is freed. `select([tag(...), ...])` takes exactly one value from several receivers. It was called `first` in #8 and was renamed so it doesn't share a name with `std::collection`'s `first`, and `after(ms)` is a receiver for timeouts. Committed transfers are not rolled back on cancellation; each pending message/result must retain one owner. (#8, #16)
- `std::routine` has `all`, `allSettled`, `race`, and `any`. A winner or early error chooses the result, then cancels/joins remaining execution and cleanup before returning. Cancellation of a helper also joins its children. A race against a timer does not guarantee a hard return deadline; a race of receives can lose a message, so use `select` for one message commit. (#16)
- Native goroutines run on a parallel M:N scheduler and may migrate between OS workers; Wasm remains single-threaded. No user-visible OS-thread-affine resources, pinning interface, or public atomics in v0; runtime-internal atomics remain. (#16)
- Normal cancellation points include waits and compiler budget yields. Requests stay pending during disposal, invariant-sensitive replacement, and required cleanup joins; scheduling/completion continues, but cancellation cannot withdraw those deferred waits. Native jobs retain all borrowed sources until completion or confirmed abortion. Cleanup/blocking work/deadlock may delay stop/helpers indefinitely; no force kill or general deadlock prevention is promised. Panic remains immediate whole-program termination without cleanup. (#16)
- When top-level code ends, the program exits without an implicit global join or guarantee of background disposal. Use explicit stop/waiting when completion matters; a batch job or queue can keep the program alive by waiting on a channel. (#8, #16)
- `for (let x of &list)` loops over a list. `for (let x of &receiver)` receives until the channel is closed.
- Arrow expressions (`(x) => f(x)`), tuples (`[int, int]`), and destructuring (`let [a, b] = ...`) use TypeScript-style syntax. Callable types distinguish repeatable read-only `() => R`, repeatable exclusive `mut () => R`, and consuming `once () => R`. Infer the required mode; weakening is allowed, but annotations cannot strengthen invocation guarantees or erase borrow dependencies. Read-only invocation does not imply purity. Mutating owned captures requires mutable access to the closure. Invocation mode, borrow dependencies, and copyability are separate; erased arrows do not automatically prove `noBorrow` or `copy`. (#15)
- Named functions do not implicitly capture enclosing/top-level runtime `let` bindings, mutable or immutable. Pass state explicitly or use checked arrow closures; type/function declarations remain visible under module rules. Constant folding does not change binding access, and dispose/indirect calls cannot hide unchecked state. (#16)
- Every record has a declared nominal type and uses named construction, such as `let origin = Point { x: 0, y: 0 };`. No anonymous structural record types or values: neither a binding annotation nor a function parameter turns `{ ... }` into a named record. Inference from already typed expressions remains valid; no look-ahead or field-shape matching chooses a type. See [ADR 0008](../docs/adr/0008-records-require-named-construction.md) and `08-named-records.rill`. (#21)
- Record fields default to public; `private` fields are accessible only in their defining module. Any private field forbids external whole-record construction/rebuilding; aliases grant no new permissions. Genuinely private canonical types may cross exported operations as opaque inferred values, without external naming, construction, field access, or representation patterns. A public type lacking a local import name is not opaque. (#17)
- Tagged unions join separately named record variants, such as `type Shape = Circle | Rect | Empty;`, each retaining an explicit literal `kind` field. Construct the selected member with `Circle { ... }`, not `Shape { ... }`. Inline anonymous variant records are not allowed. There is no `enum`. Exported unions and inline union structure in public interfaces require public variant identities/discriminators at their origin, not re-exports through every facade. A named private union result remains opaque. (#17, #21)
- `match (value) { pattern => expression, ... }` is an expression. Patterns can pull out fields, check nested values, use `_`, and take an `if` condition. The compiler rejects a `match` that misses a case.
- Inside a `match` arm, the value has the type of the member it matched. Patterns such as `{ kind: "circle", radius }` remain brace-shaped: they inspect values, not construct records. `{` after `=>` starts a block; a named constructor such as `=> Circle { ...shape, radius: radius * by }` is an expression and needs no record-versus-block parentheses. A block arm in a `match` with a value must leave the function. (#11, #21)
- `Point { ...point, x: value }` rebuilds a named record, preserving the existing ownership/copy rules and same-type owned-value reuse guarantees. Bare `{ ...point, ... }` is not an alternative construction form. (#21)
- `std`'s `Option<T>` uses named variants, for example `type Some<T> = { kind: "some"; value: T };`, `type None = { kind: "none" };`, and `type Option<T> = Some<T> | None;`, not inline structural records. `receive` on a closed channel returns `none`. #23 owns the complete library definitions, including named record results and tagged messages. (#21)
- Errors have causes and traces by default, as in the Rust crate [ohno](https://crates.io/crates/ohno). `Err(message)` and `Err(message, cause)` make an `Error`. The `Error` records each place it was made or returned through, and printing it shows the trace and every cause.

## Open questions

- The combined checker/runtime is a proposal, not an implemented or demonstrated-sound system. ADR 0009 records #16's policies, but #28 still owes explicit checking, cleanup, and commit rules plus adversarial examples; the mutation/concurrency safety documents are hand-checked source material, not executed fixtures. ADR 0010 records #17's module/visibility policy; #23 still owns complete evidence-preserving interfaces and protected-operation contracts, #24 diagnostics, and #28 explicit resolver/checker/runtime validation. The new multi-file fixture is also hand-checked, not executed. (#15, #16, #17)
- Numeric and string types. The programs use `int`, `float`, and `string`. (#9)
