# Rill ri-vno research: TCP, addresses, DNS, platform limits and cancellation

This is factual primary-source research only. It does not establish accepted Rill contracts, API approval, a safety proof, implementation evidence or runtime test results.

## Evidence boundary and Rill context

This investigation read specifications, official platform documentation and first-party source. It did not build/run downloaded code, install tools, perform socket/network experiments, implement a Rill runtime/compiler, or validate backend support. Documentation retrieval is not a networking experiment. Only this research note is added; existing ri-636/#24 work and separate ri-kty/#23/#31/#41 artifacts are not modified.

Inputs are the supplied `/tmp/rill-34-input-{23,32,33,34,38,39,40,41}.json` and ri-fnk/#33 Markdown snapshots, plus the current confirmed ri-40y/#22 decisions. ri-fnk streaming I/O and ri-j60 clocks/deadlines remain OPEN and unsettled. Separate ri-1wl conversion work does not authorize implicit address conversions or parsing through a new family here. [R16][R22][R23][R32][R33][R34][R41]

The following constraints remain in force; this note does not decide them:

- Native scheduling is parallel M:N; routines can migrate between OS workers. Wasm's chosen execution model is single-threaded. No public thread-pinning/OS-thread-affine-resource interface is assumed.
- Cooperative cancellation requests and joins are distinct. Required cleanup and native borrowers must actually complete or confirm abort/release before their buffers, source storage, callback state, handles or stack storage are invalidated. Handle drop, timer victory, or an abort request is not confirmation. Cleanup may delay return indefinitely; there is no force-kill or hard latency guarantee.
- Preserve explicit ownership/copying, static callable/property/dependency evidence, protected native retention, exactly-once cleanup, typed errors and ri-8n7's retained-cause constraints. Standard input-dependent traversal/default cleanup must have bounded call-stack use under ri-636.
- No Rill compiler/runtime exists to test these obligations here. ri-dej's backend/ABI gates remain unvalidated; this note neither chooses a replacement architecture nor clears a target. [R16][R22][R23][R30]

## 1. Documented facts: TCP and native socket lifecycle

### 1.1 Byte stream, progress and EOF

1. TCP is a reliable, ordered byte stream, not a message protocol. There is no correlation promised between application write/read boundaries and TCP segment boundaries. Framing belongs to consumers. Delivery to the destination TCP endpoint is not proof that its application parsed a request, committed a transaction, or durably stored anything. [T1, §§2.2, 3.6, 3.7]
2. A native stream receive normally returns available bytes, up to the requested length; it need not fill the buffer. On an orderly peer shutdown, receiving from a drained stream returns zero. A zero-length receive request can also return zero, so that observation alone is not an EOF discriminator for every call. `MSG_WAITALL` can still return short on signal, error or disconnect; it does not provide an exact read with rollback. [Lrecv, DESCRIPTION, RETURN VALUE, `MSG_WAITALL`]
3. Sending returns a byte count on success. A nonblocking send may make only partial progress or encounter `EAGAIN`/`EWOULDBLOCK`; successful `send` has no implicit guarantee of delivery. Linux documents `EINTR` for interruption before any data was transmitted by that call. A wrapper that loops over sends can nevertheless fail/cancel after earlier calls committed a prefix. Replaying the whole buffer then risks duplication. Read loops similarly consume prefixes irreversibly. [Lsend, DESCRIPTION, ERRORS]
4. Backpressure is observable through finite send/receive capacity and would-block results. Writable readiness does not mean an arbitrary-sized write will complete. Reads/writes may encounter reset or other terminal errors rather than graceful EOF. Neither successful send nor a transient lack of errors is a connection-health proof. [Lsend][Lrecv][Lsocket, I/O events]

This creates a Rill dependency, not a contract. ri-fnk must settle how positive progress, zero requests, EOF, partial failure and retained buffers are represented. TCP cannot independently invent a competing reader/writer or byte-container contract. [R32][R23]

### 1.2 Half-close, descriptor close and abort are different

- RFC 9293's abstract `CLOSE` means "no more data to send"; the user may continue receiving. It is not identical to POSIX descriptor `close`. Native `shutdown(SHUT_WR)` disables further transmission; `SHUT_RD` disables reception; `SHUT_RDWR` disables both. `shutdown` does not itself release the descriptor. Peer send-side closure is compatible with local sends continuing. [T1, §3.6][Lshutdown]
- Graceful FIN handling, connection reset/abort, application/TLS shutdown and releasing the last descriptor are separate events. RFC 9293 §3.6.1 even permits a half-duplex close implementation to reset when closing would discard received data. Do not equate every full close with reliable draining of both directions. [T1, §§3.5.2, 3.6-3.6.1]
- `SO_LINGER` changes close behavior. Both Linux and Apple document that enabled linger can wait for queued data or an interval; a disabled linger can leave protocol work to the system after descriptor close. No blanket "close is instantaneous" or "close waits for remote application success" follows. Socket timeout options are not substitutes for a whole-operation deadline: Linux says they affect blocking socket I/O, not `select`/`poll`/`epoll_wait`. [Lsocket, `SO_LINGER`, `SO_RCVTIMEO`/`SO_SNDTIMEO`][Aopts]
- A listener and its accepted sockets are distinct resources. Accept creates a new connected socket and leaves the listening socket unaffected. Consequently, closing a listener alone is not a join/drain of the accepted connections already handed to handlers. [Laccept, DESCRIPTION]

### 1.3 Connect and accept completion races

| Operation | Documented platform fact | Consequence to account for, not a selected Rill policy |
| --- | --- | --- |
| Nonblocking connect | Linux reports `EINPROGRESS`; after writable readiness, inspect `SO_ERROR` for success/failure. Apple also documents writable readiness for completion. Linux says a failed connect leaves socket state unspecified and portable applications should use a new socket for another attempt. [Lconnect][Aconnect] | Readiness is not successful connection establishment. A cancellation/deadline race can coincide with a successful connect; the implementation must assign an owner to a late successful socket and release it. An external peer may already have observed a connection. |
| Accept | On success, accept returns a new descriptor. Readable readiness can become stale because another acceptor consumed the connection or an asynchronous error removed it; Linux recommends a nonblocking listener. [Laccept, NOTES] | A canceled wait is not proof that no accept completed. A late accepted connection needs one owner and exactly-once cleanup, rather than leaking or being handed to two continuations. |
| Accept errors | Linux passes pending network errors on the new connection through `accept`; its manual says to treat the listed TCP/IP network errors like `EAGAIN` and retry. `ECONNABORTED`, descriptor limits and invalid listener state are distinguishable failures. [Laccept, Error handling] | A connection-local failure need not terminate a server listener. This does not select an unbounded retry loop or classify every failure as transient. |
| Accepted flags | Linux does not inherit file-status flags such as `O_NONBLOCK` from the listener; BSD behavior differs. Linux `accept4` can set `SOCK_NONBLOCK`/`SOCK_CLOEXEC` atomically. [Laccept, VERSIONS, `accept4`] | Normalize/validate required flags in the platform layer; do not infer accepted-socket state from listener state or assume Linux `accept4` exists on macOS. |

### 1.4 Close, descriptor reuse and cancellation

On Linux, `close` releases the descriptor number early, even when later work reports an error. Retrying a failed close can close an unrelated descriptor that another worker has since obtained. The Linux manual explicitly warns against this, including its documented `EINTR` behavior. A blocking syscall in another thread can keep an open-file-description reference and successfully complete after another thread closes the descriptor. Thus cross-thread close is not a general cancellation/completion barrier. [Lclose, CAVEATS]

On macOS/Darwin, the archived close manual lists `EINTR` but does not fully settle ownership after every failure. In XNU `xnu-12377.1.9`, `sys_close` performs a pthread cancellation check and calls `close_nocancel`; `fp_close_and_unlock` marks the entry closing, removes knotes, drains fileproc I/O references, releases the descriptor slot with `fdrelse`, and only then drops the fileglob. The socket close path has an interruptible linger wait. This source ordering is evidence that an error from later teardown must not be interpreted as "the descriptor was never released." It is not a portable promise about every macOS release, libc cancellation path or blocked operation. That pthread check is OS cancellation machinery, not Rill cooperative cancellation or authorization to cancel/kill a runtime worker thread. [Xfd, `sys_close`, `close_nocancel`, `fp_close_and_unlock`][Xsock, `soclose_locked`]

POSIX versions differ. POSIX.1-2008 left descriptor state after interrupted close unspecified. POSIX.1-2024 introduces `posix_close`/`POSIX_CLOSE_RESTART` and specified alternatives: an allowed `EINTR` leaves the descriptor open; `EINPROGRESS` means it was closed but teardown continues asynchronously. The Linux 6.19 close manual explicitly records a mismatch between Linux's behavior and the newer standard. The new standard is therefore not evidence that currently deployed Linux/macOS implement that new interface or semantics. [Pclose][Lclose]

Existing Rill lifetime rules therefore require the implementation to synchronize resource identity, pending operations, poll registrations, completion publication and release. A recycled integer descriptor cannot identify an old logical operation safely on its own. Removing a readiness registration or requesting close/abort does not prove all queued events, callbacks or native borrowers have finished accessing their state. Keep every still-used buffer/resource/operation record alive until actual completion or confirmed abort; separately account for any native teardown that no longer accesses guest-owned state. This is an obligation to demonstrate, not a mandate for a particular generation-counter, poller or handle architecture. [Lclose][Lepoll, Q&A and event-cache pitfalls][Akqueue][R16][R22]

### 1.5 SIGPIPE and readiness portability

- Linux `send(..., MSG_NOSIGNAL)` suppresses `SIGPIPE` for that call while still returning `EPIPE`; ignoring `SIGPIPE` with `sigaction` instead changes process-wide behavior. Apple documents the socket option `SO_NOSIGPIPE`, returning `EPIPE` instead of raising the signal. A portable implementation must account for all sending paths and provider adapters; Linux's per-call spelling is not the macOS implementation plan. Process-global signal changes are not automatically authorized by ri-vno. [Lsend, `MSG_NOSIGNAL`][Aopts, `SO_NOSIGPIPE`]
- Linux epoll supports level/edge triggering and one-shot registration. Edge-triggered use requires nonblocking I/O and appropriate draining/rearming; sleeping before exhaustion can lose progress. Its interest identity involves both descriptor number and open file description; duplicate descriptors affect removal. Its event-cache example explicitly discusses an event for a descriptor closed while processing an earlier event. [Lepoll, Level-triggered and edge-triggered, Q&A, Possible pitfalls]
- Darwin kqueue's `EVFILT_READ`/`EVFILT_WRITE`, `EV_CLEAR`, `EV_ONESHOT` and `udata` are documented mechanisms, not epoll-compatible flags. `EV_EOF` can accompany unread buffered socket data. Events attached to descriptors are removed on last close, but that does not make already-returned userspace event records safe to dereference after freeing their state. [Akqueue]
- Native `EINTR`, would-block, readiness, hangup and actual completed I/O are different observations. Retrying must respect progress and cancellation arbitration; seeing hangup must not automatically discard remaining bytes. This follows from the documented receive and kqueue semantics, not from an executed runtime test. [Lrecv][Akqueue]

## 2. Documented facts: addresses, text and identity

### 2.1 Address values and endpoint text

- IPv4 and IPv6 binary address sizes are 32 and 128 bits; a native socket endpoint also carries a port and family. IPv6 native socket addresses have additional flow/scope fields; RFC 3493 specifies a 16-bit port in network byte order and a 32-bit `sin6_scope_id`. Native layout is not a portable public serialization: RFC 3493 describes differing BSD structure layouts, including length fields. [Linet][I1, §§2, 2.2][I4, §§3.3-3.4]
- `inet_pton` parses numeric addresses without host lookup. Linux documents four-component decimal IPv4 and the RFC IPv6 forms; older `inet_aton`/`inet_addr` also accept octal/hexadecimal and abbreviated IPv4 "numbers-and-dots" forms. Linux `getaddrinfo` can accept those more general forms too. A strict public literal grammar cannot be inferred merely by delegating to the resolver. Leading-zero policy, whitespace, signs, trailing garbage and legacy forms still require explicit grammar decisions. [Linet, DESCRIPTION, VERSIONS][Lgai]
- IPv6 input accepts multiple equivalent RFC 4291 spellings, including one `::` compression and embedded IPv4 notation. RFC 5952's canonical output suppresses leading zeroes, uses lowercase, compresses the longest zero run (leftmost on ties), and does not compress a single zero field. Its §5 discusses mixed notation for known IPv4-embedded prefixes. Canonical rendering is not permission to reject all valid noncanonical IPv6 input. [I1, §2.2][I2, §§4-5]
- A bare IPv6 address contains colons. RFC 3986 §3.2.2 uses brackets around IPv6 literals in URI authority, followed by a separate `:port` when present. Bare-address text, socket-endpoint text and a full URI are different grammars. A port number is transport addressing, not a DNS hostname, TLS server name, or proof of service identity. Resolver service-name lookup (`"http"`, etc.) is a separate optional OS facility; `AI_NUMERICSERV` requires a numeric port string. [I5][Lgai][I4, §6.1]

### 2.2 Zones and mapped addresses

- RFC 4007 §11 represents a scoped literal as `address%zone_id`; zone identifiers distinguish otherwise ambiguous non-global addresses and have local significance. A zone is not part of the 128 address bits and is not a portable global identity. Numeric indices and interface names require a host-specific mapping; their meaning cannot be assumed stable across machines or interface changes. [I3, §§6, 11-12][I6, §§3, 5-6]
- RFC 9844 corrects the earlier rule. It obsoletes RFC 6874, reverts its change to RFC 3986 URI syntax, and adds scoped-address UI requirements to RFC 4007. It explicitly distinguishes UI scoped-literal entry from browser URI handling. Do not present the old `%25zone` URI recipe as today's universal URI rule. It also explains that `inet_pton("fe80::1%eth0")` cannot perform the whole conversion: use suitable `getaddrinfo` handling or split the zone and map it separately with `if_nametoindex`. This does not select a Rill parser or HTTP origin policy. [I6, §§3, 5-6]
- IPv4-mapped IPv6 addresses (`::ffff:...`) are defined IPv6 values. That does not automatically make an IPv4 value and a mapped value identical for public equality, hashing, allowlists, rendering or connection selection. RFC 3493 describes `IPV6_V6ONLY` and mapped behavior; Linux exposes dual-family socket behavior. Whether a wildcard IPv6 listener also accepts IPv4 depends on platform/options. Explicitly validate intended dual-stack behavior rather than relying on a universal default. [I1, §2.5.5.2][I4, §§3.7, 5.3][Lipv6]

### 2.3 Hostname, lookup result and authenticated identity

- System name resolution is not necessarily "send a DNS query." Linux NSS configures host sources; local files and configured services can participate. Search domains, system policy and address sorting can influence results. `AI_CANONNAME` is a resolver facility, not an authenticated replacement for the caller's intended server identity. [Lnss][Lgai][S1, §6.1]
- IDNA is a distinct internationalized-domain processing boundary. RFCs 5890/5891 define A-label/U-label concepts and validity/protocol rules; they are not blanket permission to feed arbitrary UTF-8 to every platform resolver with identical results. Linux's `AI_IDN` behavior is a GNU extension, with input encoding tied to the current locale; POSIX does not specify that flag. A Unicode-to-ASCII policy, normalization/mapping/version and error boundary remain choices, not an inferred libc guarantee. [I7][I8][Lgai, Extensions to getaddrinfo for Internationalized Domain Names][Pgai]
- TLS reference identifiers are constructed from the application's intended service identity; RFC 9525 warns not to substitute intermediate names obtained through resolution. DNS-ID and IP-ID matching are different. RFC 6066 §3 defines DNS hostname SNI and excludes literal IPv4/IPv6 addresses from that `HostName`. Retaining the original hostname separately from the selected numeric endpoint is therefore a real TLS/HTTP consumer need. Numeric port selection does not settle certificate matching or application authority. [S1, §§6.1, 6.3-6.4][S2, §3][H1, §§4.2-4.3]

## 3. Documented facts: resolver behavior, retention and address selection

### 3.1 Blocking system resolution

`getaddrinfo(node, service, hints, &result)` returns a linked list of candidate address structures, or an `EAI_*` error. The call itself does not expose a portable operation handle, cancellation function, deadline argument or incremental-result stream. `freeaddrinfo` releases its returned allocation. The native input strings, hints, output storage and callback/job bookkeeping actually used by a chosen mechanism must remain valid for its documented duration; retaining only the high-level hostname value is not a complete lifetime argument. [Pgai][Lgai][R16]

The following details need an explicit resolution policy rather than a single undocumented "DNS" behavior:

- `AF_UNSPEC`, family/socket-type/protocol filters, `AI_PASSIVE`, `AI_ADDRCONFIG`, `AI_V4MAPPED` and `AI_ALL` affect results. `AI_NUMERICHOST` suppresses name lookup; `AI_NUMERICSERV` prevents service-name lookup. glibc's null-hints defaults include `AI_V4MAPPED | AI_ADDRCONFIG`, unlike POSIX's zero flags. Explicit settings and tests are needed for reproducibility; this note does not select those settings. [Lgai][Pgai]
- The returned list can contain multiple addresses and, depending on hints, socket types/protocols. System ordering need not be DNS wire order; Linux describes configurable sorting through `/etc/gai.conf`. Failure to connect one address is not proof all candidates fail. [Lgai]
- `EAI_AGAIN`, `EAI_NONAME`, `EAI_FAIL`, `EAI_SYSTEM` and resource failures have different documented meanings. `EAI_SYSTEM` requires inspecting `errno`; retain/capture that thread-local native error at the point of failure, not after routine migration. A resolver result does not promise fresh DNS data, a usable route, an authenticated peer, or connection success. [Pgai][Lgai]

### 3.2 Realistic cancellation and deadline limits

Running synchronous resolution on native workers is an option, not an architecture selection. It can avoid blocking a scheduler worker but cannot by itself make an already-running lookup abortable. Under ri-40y, a cancellation request must still wait for actual job completion/confirmed release before destroying borrowed inputs/job state. Copying input into independently owned job storage changes whose storage is retained; it does not automatically authorize detaching the work from structured joins, ignoring cleanup, or promising bounded return latency. A bounded worker queue can limit concurrency, but cannot create a hard latency bound for a stuck resolver. [Pgai][R16][R33]

The GNU extension `getaddrinfo_a(GAI_NOWAIT)` provides asynchronous submission and `gai_cancel`; its manual explicitly says requests currently being processed cannot be canceled. `EAI_NOTCANCELED` and `EAI_ALLDONE` are different from `EAI_CANCELED`. Request structures/strings/results and notifications still need their real completion lifetime. A GNU-specific async API is not a portable Linux/macOS cancellation contract. [LgaiA]

As a Darwin mechanism example, Apple's pinned `dns_sd.h` exposes `DNSServiceGetAddrInfo`, callback results, `DNSServiceRefSockFD`/`DNSServiceProcessResult` for event-loop integration and `DNSServiceRefDeallocate` for terminating operations. The descriptor must not be directly read/written; `ProcessResult` can block without readiness. The header warns against deallocation concurrent with processing, requires removing event monitoring before deallocation, and requires same-queue deallocation after dispatch-queue registration. This is evidence of a possible internal platform mechanism, not proof of equivalence to all `getaddrinfo` sources/policies or authorization of public raw descriptors/dispatch queues. No callback-quiescence or latency guarantee is inferred beyond the documented synchronization requirements. [Adns, named declarations and comments]

A timer may record that time expired while resolution/connect/cleanup still completes later. Whether timeout wins a completion race, whether any result is reported, and when the calling routine can finish belong to ri-j60/#32 and existing joined cleanup. A timer race cannot manufacture a successful abort acknowledgment. [R16][R32][R33]

### 3.3 Multiple addresses and RFC 8305 without selecting policy

RFC 8305 Happy Eyeballs v2 is a connection-establishment algorithm, not "resolve once, choose the first address," nor "race everything at once." Its documented pieces include:

- Start AAAA/A queries close together, AAAA first; do not wait for both before connecting. A positive A result arriving first gets a recommended 50 ms Resolution Delay to allow AAAA to arrive. It notes two synchronous family-specific queries on separate threads as a possible simulation if no async resolver exists. A single opaque `getaddrinfo(AF_UNSPEC)` result does not itself expose those incremental timing semantics. [D1, §§2-3]
- Sort destinations according to RFC 6724, then interleave families; local host preference/policy and network-specific history matter. RFC 8305 assumes IPv6 preference but explicitly allows adapting to different configured host preference. [D1, §§2, 4][D2]
- Stagger attempts, allowing overlap rather than simultaneous unbounded launch. RFC 8305 gives 250 ms as one recommended Connection Attempt Delay; it mandates a lower bound, specifically no subsequent start within 10 ms, recommends a 100 ms minimum and 2 s maximum, and discusses adaptation. These are RFC values, not approved Rill defaults. [D1, §5]
- When one attempt succeeds, cancel unfinished alternatives and stop launching unused candidates; DNS answers can change during setup. The RFC's use of "cancel" does not establish Rill's completion/retention semantics. A loser can succeed in a race, and all unused successful sockets still need ownership and release. Its allowance to continue DNS reply processing/cache population does not authorize detached Rill child work. [D1, §§5-6][R16]
- The algorithm addresses connection setup, not success at TLS authentication or application protocol/transaction completion. TCP success is not authority to replay an already-sent HTTP request or database command on another connection. [D1, §9.2][H1, §9.2.2][DB1, §§54.2.8-54.2.9]

Rill still needs to choose whether to expose numeric-address connection, hostname dialing or both, and whether the system or library orders addresses. Other design questions remain: serial fallback or a specified Happy Eyeballs algorithm, concurrency/resource limits, failure aggregation, cache policy and winner/error precedence. RFC 8305 is a concrete comparison standard if such behavior is chosen; citing it alone does not prove implementation conformance.

## 4. Target/platform limits: exact WASI comparison

### 4.1 Preview1 (`wasm32-wasip1`) is not preview2 networking

At pinned preview1 revision `fae981bae14809d91f9bc2d63852d461f331d161`, the module import namespace is `wasi_snapshot_preview1`. It defines the following socket-named functions: [W1]

| Preview1 operation | Parameters/result meaning |
| --- | --- |
| `sock_accept` | It takes an existing listening `fd` and requested `fdflags`, and returns a new connected `fd` or `errno`. |
| `sock_recv` | It takes an existing `fd`, scatter/gather receive buffers and `riflags`, and returns a byte count and `roflags`, or `errno`. |
| `sock_send` | It takes an existing `fd`, scatter/gather source buffers and `siflags`, and returns a byte count or `errno`. |
| `sock_shutdown` | It takes an existing `fd` and receive/send `sdflags`, and returns success or `errno`. |

Related descriptor facilities include `fd_close`, `fd_read`, `fd_write`, descriptor stat/rights/flag operations, and `poll_oneoff` subscriptions for descriptor read/write and clocks. The type definitions include socket file types, nonblocking flags, `fd_readwrite_hangup`, and rights for receive/send (`fd_read`/`fd_write`), `poll_fd_readwrite`, `sock_shutdown` and `sock_accept`. `sock_recv` has peek/wait-all flags; `siflags` has no defined flags. These are the preview1 WITX definitions, not POSIX signatures or an assumed host implementation. [W1][W2]

That standard interface has no socket creation, bind, listen, connect, getsockname/getpeername, general socket-option get/set, or hostname/DNS resolution. `sock_accept` consumes an already listening socket; it does not create or start listening. `path_open` does not dial network connections. The preview1 preopen type definitions describe directory preopens, not a universal discovery protocol for socket capabilities. Hosts can supply inherited/preopened sockets, but supplying/discovering their numbers, rights and setup is host configuration/extension territory, not a capability guaranteed by the target triple. [W1][W2]

The original `snapshot-01` WITX at `7256722d5d194be36842ba65d9983dff3718d87d` has `sock_recv`, `sock_send` and `sock_shutdown`, but no `sock_accept`. Therefore "preview1 has no accept" is too broad for later preview1, while "every preview1 host has accept" is also unwarranted. Pin and test the actual import set/host. [W0][W1]

A preview1 host could implement custom `sock_open`/`sock_connect`/resolver imports, or a compatibility adapter could arrange capabilities. Neither is an existing standard preview1 entitlement. Supporting them would require an explicit Rill target/host-import ABI and support decision, not an invisible implementation detail or silent move to `wasm32-wasip2`. This note makes no such selection. [W1][W3][R30][R34]

### 4.2 Preview2 capability comparison, not a new Rill target

The wasi-sockets `v0.2.0` WIT defines more operations and capabilities: [W3-W7]

- `network` is an opaque capability to a subset of networking, not necessarily one physical interface. `instance-network` supplies the default network resource when imported. Permission can fail with `access-denied`; an interface's existence does not grant unrestricted host networking.
- `tcp-create-socket.create-tcp-socket(address-family)` creates a resource. Binding/connecting use a borrowed network capability. TCP has `start-bind`/`finish-bind`, `start-listen`/`finish-listen`, `start-connect`/`finish-connect`, accept, local/remote address observation, options, subscribe and directional shutdown. Successful connect/accept provides wasi:io input/output stream resources; pending completion can report `would-block` and use a pollable.
- `ip-name-lookup.resolve-addresses(network, name)` immediately returns an asynchronous `resolve-address-stream` or error. `resolve-next-address` returns ordered candidates, `none` at exhaustion, or errors/`would-block`; `subscribe` exposes readiness. This version promises automatic Unicode IDNA-to-ASCII conversion and no IPv4-mapped results. Those are that interface's contracts, not portable native `getaddrinfo` behavior or a selected Rill Unicode policy.
- Its IPv6 socket-address record has `port`, `flow-info`, `address`, `scope-id`. Its TCP bind/connect explicitly reject IPv4-mapped IPv6 endpoints. Thus even an eventual adapter would need to reconcile representable address values versus endpoints accepted by that target; it cannot blindly copy native dual-stack behavior.
- Dropping resources, input/output stream semantics, pollables and capability denial are part of the component interfaces. They do not supply a universal hard cancellation latency or remove ri-40y's guest/native lifetime obligations. Preview2 WIT is not the preview1 fd/import ABI.

The research shows that standard wasm32-wasip1 does not provide native-style create/connect/listen/resolve operations. It cannot decide whether Rill should make networking native-only, expose only explicitly supplied socket capabilities, or approve a different target/host extension. Inherited-socket support itself needs a defined capability handoff and validated host; it is not already implementation-ready.

## 5. Native mechanisms and consumer evidence, without public raw handles

### 5.1 Mechanisms that exist, not a chosen runtime

Linux epoll and Darwin kqueue can drive nonblocking socket readiness. Blocking resolver jobs, GNU `getaddrinfo_a`, and Darwin DNS-SD callbacks are different resolver mechanisms with different completion, configuration and cancellation behavior. Choosing any combination requires worker admission, wakeup/race, teardown and native-error-capture validation under M:N migration. None requires exposing descriptors or native callbacks as public Rill APIs merely because the runtime uses them internally. Conversely, private fields alone do not prove safe lifetime retention. [Lepoll][Akqueue][LgaiA][Adns][R16][R23]

Linux io_uring is a separate completion-based candidate, not assumed necessary or selected. Its liburing cancellation documentation distinguishes successful cancellation, `-ENOENT` (possibly already complete) and `-EALREADY` (too far progressed); the latter requires waiting for the target request's completion event. Flags have kernel-version requirements. This is another concrete example of why submitting cancellation is not equivalent to releasing all buffers, and no basis to promise that macOS has an equivalent mechanism. [U1]

### 5.2 TLS (ri-irw), HTTP (ri-n5i) and database consumers (ri-dka)

| Consumer fact | Need to carry into later design, not an API/provider approval |
| --- | --- |
| TLS 1.3 uses `close_notify` to signal write closure. Transport EOF without it cannot establish absence of truncation. OpenSSL 3.5.0 separately classifies received `close_notify` and unexpected EOF. [S3, §6.1][Oerr] | Preserve transport EOF/error information; do not normalize all TCP closure into clean TLS message completion. TLS shutdown is not interchangeable with socket shutdown. |
| OpenSSL 3.5.0 nonblocking reads can need writes, and writes can need reads. A retrying write requires the same arguments/data; moving-buffer mode relaxes pointer identity, not data/length. [Oread][Owrite] | Per-direction TCP readiness alone does not prove independent concurrent operations on a TLS connection. Adapters need retained pending-operation data, progress/backpressure handling and explicit serialization/concurrency rules. |
| OpenSSL `SSL_get_error` reads the current thread's error queue, must run on the same thread as the I/O call with no intervening OpenSSL calls, and needs an initially empty queue. BIO pairs usually need both halves handled by the same application thread because they do not lock their internal structures. [Oerr][Obio] | Native bridge calls/error extraction cannot be separated by an unconstrained migrating suspension. This calls for a justified internal integration mechanism, not public pinning or an assertion that OpenSSL objects are inherently safe under arbitrary parallel access. ri-irw must select/validate its actual provider boundary. |
| BIO pairs allow TLS I/O under application control without their directly accessing a network socket; buffered output must be drained or a wait-for-read can deadlock. [Obio] | A provider-backed transport can in principle compose through byte pumping; raw socket extraction/public FFI is not logically required. This proves neither a workable Rill bridge nor a selected architecture. Bounded buffers, readiness and progress still matter. |
| HTTP/1.1 distinguishes message framing and incomplete messages; some responses are close-delimited, and premature closure of length/chunk-framed messages is incomplete. RFC 9110 restricts automatic retry of non-idempotent requests. [H2, §§6, 8][H1, §9.2.2] | Consumers need short-I/O handling, bounded framing/buffering, trustworthy EOF distinctions and control of connection reuse after abandoned bodies. A canceled TCP write is not permission to replay the HTTP request. |
| PostgreSQL 18 cancellation opens another connection and sends a keyed `CancelRequest`. No direct success reply is sent; the client must still await the original query response. Disconnect during an implicit-transaction command may be recognized only after commit. [DB1, §§54.2.8–54.2.9] | Transport cancellation/close cannot certify database rollback, nonexecution or reusable protocol state. A driver may need another connection and protocol resynchronization. Unknown external outcomes remain a consumer-level issue. |
| PostgreSQL 18's optional SSLRequest upgrade consumes a specific one-byte response and warns about extra buffered bytes; immediate TLS is another explicitly described mode with ALPN requirements. [DB1, §54.2.10] | A realistic adapter may wrap an already connected stream after plaintext negotiation. Ownership of buffered/unconsumed bytes must be explicit; this is evidence for composability, not a mandate to expose handles or adopt PostgreSQL-specific std operations. |

The ri-irw/#39/#40 snapshots explicitly require these provider/protocol questions to remain separate. ri-vno research does not select TLS, route HTTP, put a DB interface in std, add UDP/QUIC/Unix sockets, or authorize general FFI. [R38][R39][R40]

## Primary-source supplement: ASCII host input and native resolution boundaries

This factual supplement adds no Rill policy/API selection or implementation evidence. Earlier text remains historical research. ri-fnk is now CLOSED with a human-confirmed streaming contract and approved Q36 refinement [HN1]; its earlier OPEN/unsettled descriptions above are stale. ri-j60 remains open, with no approved deadline contract.

The user confirmed ASCII-only hostname input, explicit external IDNA conversion and no implicit Unicode/locale mapping. Resolution follows system host-resolution policy, not a bespoke DNS client/cache. Numeric IP parsers are pure and strict. IPv4 and mapped IPv6 remain distinct, and IPv6 socket metadata carries a `u32` scope ID, with `0` unspecified. These inputs do not settle the remaining hostname-acceptance questions.

### Facts: DNS names are not the application hostname grammar

- RFC 1034 §§3.1, 3.5 and RFC 1035 §§2.3.1, 3.1 distinguish the general DNS namespace from preferred application syntax. RFC 2181 §11 expressly allows arbitrary binary label contents subject to length limits, while permitting applications to impose their own restrictions. Thus "DNS permits it" does not establish suitability as a hostname, and an LDH hostname validator is not a general DNS-name validator. [HN2-HN5]
- The preferred host-label syntax uses letters, digits and hyphens, with an alphanumeric first and last character. RFC 1123 §2.1 relaxes the old initial-letter restriction to letter or digit. A label can be wholly numeric. That section separately discusses dotted-decimal address detection and assumes an alphabetic highest-level component for Internet hostnames; it is not a prohibition on arbitrary numeric DNS owner labels. A digit-initial rejection would be stricter than the updated hostname syntax. [HN2, §3.5][HN3, §2.3.1][HN4, §2.1][HN5, §11]
- The preferred grammar includes a single label; a dot is not required. An unqualified name can be completed by local search policy. The DNS root is the zero-length root label, conventionally printed `.`; it is a valid DNS name, not an ordinary nonempty host label or evidence of a connectable host. Accepting/rejecting `.` at an application hostname boundary is separate from recognizing DNS syntax. Empty caller input, a null native pointer and the explicit root string are not interchangeable portable lookup requests. Interior empty labels (`a..b`) are not the terminal root label. [HN2, §§3.1, 3.5][HN5, §11][HN7, DESCRIPTION]
- For ordinary unescaped ASCII labels, each non-root label is 1-63 octets. For `n >= 1` labels of lengths `L_i`, the expanded, uncompressed wire name occupies `sum(L_i) + n + 1 <= 255` octets, including every length byte and the final zero-length root byte. Consequently the dot-separated text has at most 253 ASCII bytes without the terminal root dot, or 254 with it, excluding a C terminating NUL. `.` itself is the special one-byte textual root, encoded as one zero byte. Compression does not enlarge the permitted expanded name. RFC 1123's "SHOULD handle ... 255 characters" is not an alternative 255-byte plain-text allowance; DNS escapes can also make presentation text longer than these unescaped bounds. A search suffix must itself fit the resulting name limits. [HN2, §3.1][HN3, §§2.3.4, 3.1, 4.1.4][HN4, §2.1][HN6, §2.1]
- RFC 1034 §3.1 distinguishes absolute `host.example.` from locally interpreted relative forms. In glibc 2.42's DNS search routine, a terminal dot triggers an as-is query and prevents suffix-search fallback; `ndots` and resolver options influence attempts for undotted/nonterminal-dot names. Even a name containing dots can undergo suffix search. Appending/removing a dot is therefore not semantics-neutral. This DNS behavior does not promise that every configured OS source treats dotted/undotted strings identically, nor does absolute DNS spelling imply a public/global destination. [HN2, §3.1][HN8, `__res_context_search`][HN9]
- Ordinary DNS-label matching folds only ASCII `A`-`Z` against `a`-`z`, not locale/Unicode case. Case-insensitive comparison is distinct from preserving caller spelling. RFC 4343 §4 requires output preservation with compression exceptions and describes input/database choices that can alter returned case; DNS replies are not guaranteed to echo the caller's casing. Linux NSS has configurable, extensible sources and source-order/actions, so DNS case/search rules cannot be imposed on every non-DNS host database by citing DNS RFCs. Preserving and forwarding caller bytes avoids adding an extra library rewrite, without guaranteeing native round-trip spelling or universal case equivalence. [HN3, §2.3.3][HN6, §§3-4][HN9]
- Accepting LDH syntax and length, including an ASCII `xn--...` prefix, does not establish a valid IDNA A-label. RFC 5890 distinguishes fake A-labels from valid Punycode/U-label round trips and requires more than ASCII syntax (including normalization, allowed characters/context and bidi constraints). RFC 5891 §5.3 explicitly discusses opaque handling by non-IDNA-aware lookup applications. Accepting such ASCII strings can therefore be described as syntax acceptance, not full IDNA validation, successful external conversion, registration validity or identity safety. GNU `AI_IDN` is a real locale-dependent extension, not a portable or necessary step for already-ASCII input. [HN10, §§2.3.1, 2.3.2.1][HN11, §§5.3-5.5][HN12, IDN extensions]
- `_service._tcp.example` is an SRV owner-name convention; RFC 2782 prepends underscores specifically to the service/protocol labels. This does not extend LDH host-label grammar to underscores, require SRV lookup in `getaddrinfo`, or turn an SRV owner name into the target hostname. An OS source's willingness to resolve underscore-containing input is a separate acceptance fact. [HN13, "The format of the SRV RR"][HN3, §2.3.1]

### Facts: numeric-looking input and actual native controls

- Portable `getaddrinfo` accepts address strings as well as names, so numeric interpretation is built in. Linux documents IPv4 numbers-and-dots forms; glibc 2.42 calls `text_to_binary_address` before host-source lookups. Its `__inet_aton_exact` requires complete consumption but retains the legacy one-/two-/three-/four-component grammar and C-style octal/hex bases. Thus examples such as `127.0.0.1`, `127.1`, `2130706433`, `0177.0.0.1` and `0x7f000001` can resolve numerically without a hostname lookup. This is source inspection, not an executed acceptance matrix. [HN7][HN12][HN14]
- The macOS evidence has an independent version pin. Apple Libinfo-600 `_gai_numerichost` tries IPv4 `inet_pton`, then `_inet_aton_check(..., 1)` (commented as supporting short forms), and also IPv6 `inet_pton`. `si_getaddrinfo` invokes numeric classification even without caller `AI_NUMERICHOST`. This verifies that clearing the flag is not "names only" on this source revision; it does not assert that every Apple release shares glibc's exact legacy grammar. Valid IPv6 address strings are also native numeric inputs; colon-containing IPv6 spellings are outside LDH hostname grammar. [HN15, `_gai_numerichost`, `si_getaddrinfo`][HN7]
- `AI_NUMERICHOST` requires numeric input and suppresses host-name resolution. Clearing it permits both names and numbers. `AI_NUMERICSERV` concerns the separate service/port argument only. `AI_CANONNAME` requests canonical-name information; `AI_ADDRCONFIG` filters by configured families; `AI_V4MAPPED`/`AI_ALL` affect family/result handling; `AI_PASSIVE` concerns binding/null-node defaults. None means hostname-only, no-numeric, strict-four-decimal-only or no-search. POSIX.1-2024 defines no `AI_HOSTNAME_ONLY`/`AI_NONUMERIC` or portable per-call no-search flag. Apple's documented extensions do not provide such a portable control. Do not confuse `getnameinfo`'s reverse-lookup controls with `getaddrinfo` input interpretation. [HN7, DESCRIPTION][HN12][HN15, `getaddrinfo.3`]
- Portable `getaddrinfo` cannot force a caller's unchanged numeric-looking string to be interpreted only as a hostname while also preserving system source/search/local-host semantics. Adding a trailing dot, escaping/altering labels, calling DNS directly, or using a different host-database interface changes the request or resolution path rather than supplying a missing flag. Family restrictions and canonical-name requests are not substitutes. Strictly parsing first does not change what libc does with the strings that fall through. [HN2, §3.1][HN7-HN9][HN14-HN15]

### Options and guarantee boundaries. Not selected Rill policy

- Pure literal parsing or direct literal handling can guarantee the chosen strict grammar, no lookup, exact family/address bits and checked scope/port metadata for successful parses. Constructing numeric socket addresses directly avoids libc reinterpretation or mapped-family synthesis on that path. It does not guarantee connectability. Invalid strict literals must not silently gain legacy acceptance through a resolver fallback if the intended guarantee is "strict literals only"; that guarantee needs an explicit fallback/acceptance rule. IPv4 and mapped IPv6 remain distinct under the supplied input.
- Prevalidation can guarantee ASCII, no embedded NUL, chosen LDH/label/total-length rules and preservation of the supplied case/root dot. LDH alone does not rule out numeric interpretation (`127.1` and `0x7f000001` pass its structural character rules); rejecting only strict-parser successes still misses legacy literals. Rejecting an explicitly defined broader numeric-looking set can protect a narrower accepted-input contract, but can also reject real local/relative names and is not the same as forcing hostname interpretation. A supported-libc classifier/rejection strategy would need a versioned grammar and evidence; no finite observed matrix establishes an unrestricted all-platform promise.
- Forwarding accepted ASCII unchanged to the system can retain OS resolution policy, including local sources and system caching, but cannot promise "a DNS query occurred," "this was a hostname rather than a number," a universal search sequence, or stable results. Choosing which ambiguous inputs to reject, whether literals belong at this boundary, and whether `.` is accepted remains a human policy decision. No bespoke DNS/cache workaround is selected. [HN7-HN9][HN12][HN14-HN15]

### Brief checks: interface names, scope metadata and TCP port zero

- Linux and Apple document `if_nametoindex(const char *) -> unsigned int`. It returns a positive interface index on success and 0 on failure, with documented native error reporting. RFC 3493 §3.3 defines `sin6_scope_id` as a 32-bit field; §§4-4.2 define name/index conversion. An implementation bridge can range-check into `u32`; lookup failure must not be silently turned into a successful unspecified scope merely because both use zero. Name lookup is OS metadata work, separate from a pure numeric-IP parser. [HN16][HN17][HN18, §§3.3, 4-4.2]
- These native interfaces expose C character strings, not a portable Unicode-normalization or UTF-8-transcoding contract. Apple documents `IF_NAMESIZE` including the terminating NUL. Inspected XNU `xnu-12377.1.9` defines it as 16; glibc 2.42's ordinary Linux lookup rejects names with `strlen >= IFNAMSIZ` (Linux v6.16 defines 16). Apple Libinfo-600 compares the full supplied name with `strcmp`. This supports checking encoded byte length, rejecting embedded NUL, supplying termination and never silently truncating in a bridge; it does not justify applying hostname/IDNA rules to interface names or assuming every other Linux naming facility has the same limits. No broader name-encoding policy is selected. [HN16-HN17]
- Interface indices/zone indices have local significance, not global identity. A returned integer neither owns/pins an interface nor promises persistence across removal, renaming, reassignment or later reuse; name-to-index success is a point-in-time observation, not an atomic guarantee for a later connect. General zone scopes need not all be reducible to an interface name. Preserve the confirmed `u32` scope metadata/zero-unspecified distinction without treating it as a stable cross-machine identifier. [HN16-HN18][HN19, §6]
- IANA's Service Name and Transport Protocol Port Number registry lists TCP 0 as Reserved, referencing RFC 6335. Reservation is an assignment/interoperability fact, not a claim that every kernel forbids every `connect` to destination port zero. It is also distinct from the documented use of local bind port zero for ephemeral allocation. Whether an application rejects remote port zero is an explicit policy choice, not a universal kernel fact established here. [HN20][Lbind]

This factual supplement selects no defaults, API, ABI or runtime architecture. Confirmed ri-vno inputs remain raw/unbuffered `TcpStream` with no-op flush, immutable numeric values/scopes, owned noncopyable split halves, and `shutdownWrite` as the only public directional operation. Write-half close/disposal attempts local send-direction release, not user-buffer flushing or TLS shutdown; cleanup retains actual native borrowers. Listener/address policy is still being interviewed.

Evidence scope: Linux man-pages 6.19 and Linux v6.16 source; Apple source pinned throughout to XNU `xnu-12377.1.9`. Apple archived manpages are explicitly historical, not evidence of every current macOS release. Pinned source establishes behavior of that revision, not a tested shipping OS/SDK matrix.

### Facts: reuse, restart and binding exposure

- `SO_REUSEADDR` is not `SO_REUSEPORT`. Linux documents address reuse subject to bind conflicts: an active TCP listener still prevents another bind to its address; a listener on `INADDR_ANY:port` prevents binding that port on any local address under this reuse rule. `SO_REUSEPORT` separately permits identical IPv4/IPv6 bindings, requires every participating socket to set it before bind, and requires the same effective UID to prevent port hijacking; Linux supports TCP accept-load distribution with separate listeners. Those permissions are not a portable load-balancing algorithm or an authorization boundary between same-UID processes. [OPT1]
- For restart/TIME_WAIT, Linux documents a bound TCP local address remaining unavailable after close unless reuse is enabled, and requires `SO_REUSEADDR` on both the earlier binder and its replacement. TIME_WAIT belongs to closed TCP connections/4-tuples, not a listener's accept queue; listener close does not erase accepted connections or their protocol state. Reuse can help with restart but does not promise every rebind or repeated connection to the same peer will succeed, terminate TIME_WAIT, or override a live conflicting listener. [OPT1][OPT2][OPT13]
- Darwin differs, including its security conditions. In pinned XNU IPv4 `in_pcbbind`, setting either reuse flag disables wildcard matching for the main local-conflict lookup; that lookup then considers an unconnected exact local-address/port match. Thus a wildcard and a specific-address binding can coexist where other checks permit, unlike the Linux active-wildcard-listener rule above. For ordinary unicast sockets, its exact-duplicate check requires intersecting `SO_REUSEPORT` bits on both sockets, apart from explicit external-port exceptions. Separate credential checks include root/share-UID/wildcard exceptions, and additional namespace/policy checks exist. Do not transplant Linux's simple effective-UID rule. Its receive lookup prefers an eligible specific local-address match over a wildcard; permitted overlapping listeners can therefore change who receives connections. Neither flag means exclusive ownership, authentication or an unconditional ability for another user to steal a port. [OPT3]
- No atomic multi-listener reservation follows. Native `bind` takes one socket and one local address; `listen` operates on one socket. Binding several addresses/families is a sequence, not a standard all-or-nothing transaction. A later failure can follow an earlier successful bind/listen, and closing earlier sockets cannot undo connections already observed externally. Port-zero allocation on one socket does not atomically reserve the chosen port on another. Reuse does not supply this missing transaction. This is an interface-derived limit, not a selected rollback/publication policy. [OPT2][OPT4][OPT6][OPT7]

### Facts: IPv6 family mode and accepted-peer values

- `IPV6_V6ONLY=1` restricts an IPv6 socket to IPv6; `0` permits IPv4-mapped operation as well. A dual-stack wildcard IPv6 listener can therefore cover IPv4 too; an explicit v6-only listener plus a separate IPv4 listener is a different setup with separate failure/race points. Linux's initial setting follows `/proc/sys/net/ipv6/bindv6only` (documented initial sysctl value 0), not a universal platform default. Pinned XNU accepts explicit setting/clearing before bind and rejects changes after a local port/address has been assigned. Neither setting bypasses address conflicts, family availability or host policy. [OPT5][OPT8]
- Linux documents IPv4 sources arriving through an IPv6 socket as mapped IPv6 addresses. Pinned XNU `tcp6_usr_accept` calls `in6_mapped_peeraddr`, which converts an IPv4 peer into `sockaddr_in6` mapped form. This is not a native `AF_INET` peer merely because its transport packets were IPv4. Public normalization, display and allowlist handling remain separate choices; the confirmed distinct IPv4/mapped-IPv6 value model must not silently collapse them. [OPT5][OPT8]

### Facts: backlog type, queue and caps

- The native signature is `listen(int socket, int backlog)`, not an unbounded unsigned count. A bridge must represent/check the actual C `int` range rather than silently narrow/wrap a larger value. POSIX calls backlog a hint, permits silent caps, permits incomplete connections in the queue, and says negative means zero; zero may still accept connections with an implementation-defined minimum. There is no omitted/default argument or portable inference that zero means "disabled," "use the maximum," or a particular capacity. `SOMAXCONN` is not a portable exact effective-capacity promise. [OPT6]
- On Linux, backlog limits completely established connections waiting for accept, not the application's live-handler count; the incomplete/SYN queue has separate controls (`tcp_max_syn_backlog`, with syncookie qualifications). Backlog is silently capped by `net.core.somaxconn`; its documented default is 4096 since Linux 5.4, formerly 128, but configuration can change it. Linux v6.16's entry path leaves zero as zero and compares backlog as unsigned when capping, so negative inputs can become the cap rather than a useful portable zero convention. [OPT7]
- In pinned XNU, `solisten` replaces `backlog <= 0` or `backlog > somaxconn` with `somaxconn`; the variable is writable through `kern.ipc.somaxconn` and initialized from `SOMAXCONN` (128 in this source header). Queue accounting defaults to incomplete plus completed connections; `kern.ipc.soqlencomp` and `soqlimitcompat` alter accounting/threshold behavior. Apple's archived `listen(2)` says "currently ... 128," but that historical sentence is not a current immutable cap. Neither successful listen nor a requested backlog reserves exactly that many successful future connections or bounds server concurrency. [OPT9]

### Facts: small writes and idle probes

- Fresh native TCP sockets in the inspected Linux/XNU source start with Nagle enabled. Enabling `TCP_NODELAY` disables Nagle's small-write coalescing delay, not congestion control, flow control, scheduling or peer delayed ACKs. Linux documents an explicit push of pending output when setting it (even with `TCP_CORK`); pinned XNU's setter changes `TF_NODELAY` without that same explicit output call. Do not elevate Linux's option-set side effect to a portable flush contract. Neither setting promises one packet per write, preserved message boundaries, peer delivery/application processing, or bounded latency. Raw Rill no-op flush is unchanged. [OPT10][OPT11][OPT13]
- `SO_KEEPALIVE` enables TCP idle probes; it is separate from the TCP-level idle/interval/count settings. Linux exposes `TCP_KEEPIDLE` (seconds), `TCP_KEEPINTVL` (seconds) and `TCP_KEEPCNT` (probe count). Linux v6.16 rejects idle/interval outside 1-32767 and count outside 1-127 with `EINVAL`. These native/versioned limits are not a portable public range. [OPT1][OPT10]
- Pinned XNU has tuning options beyond those in the old archive. `TCP_KEEPALIVE` names the idle time (not Linux's `TCP_KEEPIDLE`), alongside `TCP_KEEPINTVL` and `TCP_KEEPCNT`; setters consume `int`, seconds for the two times and a count for probes. The time setters accept 0 through `UINT32_MAX / TCP_RETRANSHZ` (`TCP_RETRANSHZ=1000`, hence 4,294,967 seconds); count accepts 0 through `INT32_MAX`. Zero selects system fallback through the effective-value macros, not immediate failure detection/zero probes. Accepted individual numbers do not prove safe combined timeout arithmetic or a useful liveness bound. These observations do not establish first-supported macOS versions or guarantee every deployed SDK exposes the same controls. [OPT11]
- RFC 1122 requires optional keepalives to default off and warns that loss of one probe is not proof of a dead connection. Probes can detect some idle transport failures, but a responding peer TCP does not prove a healthy/progressing application; partitions and transient loss confound failure attribution. Idle/probe tuning is neither an application request deadline nor a complete liveness proof, and supplies no hard operation/cleanup return time. [OPT12]

### Facts: SIGPIPE and linger/close hazards

- Linux `send(..., MSG_NOSIGNAL)` suppresses SIGPIPE for that call while retaining `EPIPE`; `sigaction(SIGPIPE, SIG_IGN)` instead affects the entire process/all threads. Pinned XNU implements socket-level `SO_NOSIGPIPE` via `SOF_NOSIGPIPE`, checked before raising SIGPIPE on an `EPIPE` send failure; the archived option manual describes the same intent. Every actual sending path/provider still needs coverage verification; suppression is not successful transmission or a replacement for error handling. [OPT14]
- `SO_LINGER` is not harmless cleanup tuning. Positive enabled linger can wait during close; disabled linger can leave native transmission/teardown in the background. Enabled zero linger takes an abortive TCP disconnect/drop path in both inspected kernels, risking reset and loss of unsent data rather than graceful FIN/draining. A native send/close success never certifies remote application receipt. Also beware Darwin header mode: pinned `sys/socket.h` maps ordinary Darwin `SO_LINGER` to the legacy ticks option, exposes `SO_LINGER_SEC` for seconds, and maps strict POSIX `SO_LINGER` to the seconds option; Linux's structure uses seconds. Copying a name/value without the target headers is not portable. [OPT1][OPT10][OPT11][OPT9]
- Pinned XNU's linger sleep is interruptible and its close path can return teardown errors. Timeout expiry there is explicitly not reported as an error. Linux warns that a close error can follow descriptor release and retry can close a recycled descriptor; earlier §1.4 records Darwin release ordering too. Neither a linger interval, nonblocking mode, successful close nor suppressed SIGPIPE supplies a hard Rill return deadline, remote-delivery proof, or confirmation that every native borrower has released. Preserve real completion/retention obligations; no ri-j60 policy is inferred. [OPT9][OPT15]
