## 3. Actual byte-pump facts and ordinary I/O implications

### Rustls: plaintext/ciphertext separation

At 0.23.46, `read_tls` ingests arbitrary ciphertext chunks; `process_new_packets` authenticates/processes them and may queue handshake/alert output; `reader` extracts plaintext. `writer` accepts plaintext and encrypts or buffers it. `write_tls` emits ciphertext and may return a short count. `wants_write` reports remaining output. `wants_read` applies backpressure when plaintext is pending. `complete_io` is an illustrative synchronous Rust Read+Write driver, **not a Rill suspension/cancellation adapter**. Provider Rust traits/`dyn io` are implementation details, not additions to Rill. [R3-R4]

- Plaintext acceptance does not mean ciphertext transmission. A successful `writer.write(n)` may leave records queued. Likewise, ciphertext input counts are not decrypted application counts. A pump must retain separate plaintext, ciphertext, transport-prefix and pending-output counters; never return the encrypted count as `std::io::write` progress.
- `set_buffer_limit(Some(n))` bounds the documented pre-handshake plaintext and outgoing TLS buffers; `None` permits unbounded output buffering. This is **not a demonstrated bound on every handshake/certificate/verification allocation or CPU path**. Drain plaintext/output and bound adapter queues/input admission independently. Positive-request zero progress/backpressure is an internal scheduling condition, not a valid Rill positive-request zero-success or a busy loop. [R3]
- Rustls `Writer.flush` itself does no I/O and can report an earlier fatal error. A Rill TLS flush must drive pending records and flush the underlying layer according to its chosen contract. Forwarding the Rust call alone would not flush the composed stream. `send_close_notify` only queues an alert: it must be pumped, and dropping state is not evidence it reached the peer. [R3-R4]
- Buffered plaintext drains before Rustls reports unclean transport EOF as `UnexpectedEof`; received `close_notify` is distinguished from transport EOF. Packet-processing errors are fatal/sticky, not permission to retry the same application bytes on a fresh connection. [R3]

### OpenSSL: memory BIOs really work, but retries are not ordinary short writes

The pinned 3.5.9 documentation explicitly describes an SSL BIO pair whose external half is controlled by the application and **never directly accesses a network connection**. BIO pair sizes are bounded (default documented as 17 KiB per write buffer); full/empty produces retry conditions and writes may be short. Independent memory BIOs are another mechanism, but writable `BIO_s_mem` grows while memory is available; it is not intrinsically a bounded queue. Empty input must be configured as retry until true transport EOF, not mistaken for EOF whenever no chunk has arrived. [O3-O4]

A pump would perform a TLS step and immediately capture its result and error. It would then drain queued ciphertext into retained output, send only the pending suffix through ordinary transport writes, feed admitted ciphertext chunks into the input BIO and retry the required TLS operation. Drain output before waiting for input, even after WANT_READ. OpenSSL documents a handshake deadlock otherwise. A short transport send advances only that ciphertext suffix; do not regenerate/replay the corresponding plaintext. Ordinary transport read/write/flush is enough in principle; no raw-FD API is logically required. [O3,O5]

- `SSL_read[_ex]` can need writing, and `SSL_write[_ex]` can need reading. WANT_READ/WANT_WRITE describes the engine/BIO state, not a guarantee that one transport readiness event completes the original application direction. Retry counts have no fixed upper bound. If a write returns WANT_WRITE, the documentation restricts intervening I/O-triggering operations to repeating that write; "serialize everything with a mutex" alone does not define a valid retry state machine. [O5]
- Default successful `SSL_write_ex` completes the supplied plaintext request; `SSL_MODE_ENABLE_PARTIAL_WRITE` permits a completed short plaintext prefix, after which a **new** request uses the remaining suffix. A WANT retry is different: repeat **the same arguments/data/length** because data may already have been partially processed. `SSL_MODE_ACCEPT_MOVING_WRITE_BUFFER` relaxes pointer identity only, **not bytes or length**. This requirement also appears in inspected 4.0.3 and 4.1.0 write docs; the rest of this integration analysis is pinned to 3.5.9, not presumed validated on 4.x. [O6]
- Consequently a suspended pending write cannot borrow a temporary buffer that disappears on token selection, reslice the request, or accept unrelated writes as though the engine were idle. A native-owned copy can preserve retry identity without public pinning, but requires bounded admission and a defined **plaintext acceptance point**. Ciphertext movement/WANT does not expose a recoverable exact application prefix. Do not guess zero merely because `SSL_write_ex` did not return success.
- There are two accounting options here, neither selected. A bounded wrapper-owned plaintext queue could credit bytes at copy-in and preserve them until consumption, error or owner release. Alternatively, a wrapper could retain caller data and finish the provider operation before releasing it. The latter may wait indefinitely on cancellation, and a terminal failure still needs a justified exact-prefix mapping. Neither provider return values alone nor "we copied it" proves canonical IoFailure semantics. This is a factual blocker for a naïve direct `SSL_write_ex → Rill write` translation. [O5-O6; ri-fnk/#34]

### Flush, close and reuse are separate state machines

Canonical flush must hand off all output accepted by that layer, including queued TLS records, then perform required lower-layer flush; it proves neither remote receipt nor TLS shutdown. A no-op raw TCP flush cannot drain TLS buffers. Zero/empty I/O operations need the established Rill no-probe behavior rather than provider-specific zero-call behavior. Controlled preflight still applies.

OpenSSL TLS shutdown exchanges `close_notify`. A return of 1 from `SSL_shutdown` means both alerts have been exchanged. A return of 0 means shutdown is incomplete; negative results need error/retry classification. The pinned page has inconsistent prose about nonblocking zero/error handling; inspected **`ssl3_shutdown` source** distinguishes unsent-alert WANT_WRITE and waiting-for-peer WANT_READ from zero. Do not infer complete closure from `SSL_SENT_SHUTDOWN`, which can be set on an unsuccessful send attempt, or mechanically call `SSL_get_error` on shutdown zero contrary to its RETURN VALUES section. Fatal SSL/SYSCALL errors prohibit further I/O/`SSL_shutdown`. [O7]

`SSL_free` decrements references and frees owned BIOs/other state at last reference; it neither implements a joined transport cancellation nor guarantees graceful TLS shutdown. `SSL_set0_rbio/wbio` transfer ownership, with separate reference rules when sharing a BIO; double-freeing an SSL-owned BIO is invalid. A consuming Rill close must separately resolve pending operations, whichever TLS shutdown policy is approved, transport close and exactly-once native release **on error too**. Automatic disposal must safely release without being advertised as implicit graceful flush/close-notify. No proposal here chooses whether explicit close waits for the peer's alert. [O7-O8]

A clean TCP FIN is not authenticated TLS closure; dropping unread data, canceling a write, receiving a TLS alert or freeing a native handle does not certify application-message completion or reusable HTTP/SQL state. No automatic reconnect/replay, session reuse or rollback guarantee is derived.

## 4. Native lifetimes, M:N migration and the narrowly trusted runtime question

The documentation imposes several constraints. OpenSSL `SSL_get_error` must run on the same OS thread as its associated TLS call, without intervening OpenSSL calls and with an initially empty error queue. Native errno and error data must be copied before overwrite/migration. BIO-pair documentation says both halves usually must be handled on the same application thread because internal structures are not locked. Thread-enabled OpenSSL does not make most objects safe for simultaneous mutation. Explicit async-engine mode imposes a same-thread retry requirement; it is not assumed enabled. OpenSSL explicitly says in-progress calls cannot generally be abandoned by thread cancellation/non-local exits, including language exceptions. [O3,O5,O9]

The following is a feasibility inference, not a proof or architectural choice. A narrowly scoped trusted runtime could own opaque backend, configuration and operation objects plus bounded native buffers. It could expose only checked byte counts and owned errors. One worker would complete each native step and extract its error before any Rill suspension. A private serialized executor could keep a BIO pair on one thread; another reviewed bridge could justify a narrower synchronization rule. Rill routines could migrate **between** such steps without exporting thread affinity. Neither immutable configuration sharing nor independent TCP split halves proves parallel TLS directions are safe. Rustls exclusive mutable access likewise needs a serialized engine owner even though its buffered pump is transport-independent. [R3,O9]

That inference depends on every condition below. This research establishes none of them for Rill:

1. **Explicit internal ABI/link boundary:** LLVM23-generated code must actually enter/return from the chosen runtime wrapper with supported calling conventions, widths/layouts, allocator/deallocator pairing, initialization and panic/unwind/trap policy. Rust's native ABI is not silently a stable C ABI; a purpose-built private bridge would itself require design/review. Native Rust/C implementations do not authorize general user FFI or imply the failed ri-dej containment mechanisms are usable.
2. **No suspended foreign frame by accident:** callbacks can synchronously feed/drain owned memory and return a retry indication; that does not permit arbitrary Rill suspension/unwind through C/Rust/dispatch frames. Entropy, trust loading, signing or provider initialization can block despite memory-only network BIOs. Private worker admission/scheduling and eventual joins are still required; copying into a job does not authorize detached cleanup.
3. **Retain the right storage:** SSL/config/keys/BIOs, pending write identity, caller borrows, registration records and callback contexts need lifetimes through actual last use. `BIO_new_mem_buf` is **read-only/noncopying** and requires supplied memory unchanged until BIO free; BIO internal-buffer pointers cannot outlive mutations/free. Prefer copied staging as an option, not a proof of pointer stability. Apple asynchronous dispatch data/completions likewise require native ownership, not a stack pointer smuggled into a closure. [O4,O8,P3]
4. **Real quiescence:** withdraw readiness/timer subscriptions safely, stop new native admission, wait for already-entered calls and in-flight callbacks, then release exactly once. OpenSSL's synchronous memory step has returned before it can be reclaimed, but pending engine state/transport jobs can remain. Network.framework's connection `cancel` is a connection-wide disconnect request, not a non-destructive per-read abort or acknowledgment that all callback storage is free. Completion/state notifications must be tied to the specific API's release contract and validated. [O9,P3]
5. **Preserve the borrowed connection:** a token cannot destroy SSL/BIO/underlying stream to escape a pending retry. Safe suspension/copying may let an operation stop waiting while retaining internal state, but exact accounting and subsequent permitted operations must be specified. Otherwise wait for completion; leave reuse unspecified. Owner disposal is a separate consuming obligation, not authority available to a borrowed controlled operation.

The provider APIs give concrete mechanisms to investigate a private runtime byte-pump boundary without public handles, pointers, pinning or `dyn`. They **do not establish that the current compiler/runtime can implement it safely**, nor select trusted runtime versus a future safe extension interface. If release, retry accounting or native entry cannot satisfy the approved contracts, return that blocker to the design map rather than relax them.

## 5. Trust roots, ambient initialization and entropy are independent decisions

### Roots and provider environment

Rustls protocol/verification configuration needs explicit trust material; it does not automatically import the OS store. **rustls-native-certs 0.8.5** is a separately inspected loader: Linux/Unix uses **openssl-probe** paths, not libssl; macOS uses the **security-framework** binding to enumerate User/Admin/System trust settings, honoring precedence and filtering trusted anchors. `SSL_CERT_FILE`/`SSL_CERT_DIR` override platform discovery; loading can be expensive and returns certificates **and errors**, not an all-or-nothing trust guarantee. Its repository lock pins openssl-probe **0.2.1**, security-framework **3.5.1**, security-framework-sys **2.17.0**; the last links Apple Security.framework, with CoreFoundation bindings in the closure. openssl-probe **0.2.2** was inspected separately and offers nonmutating `probe`; its environment-mutating initialization helpers are not needed/authorized. [T1-T2]

Exporting anchors into Rustls/webpki is **not the same as asking Apple's trust evaluator to verify each chain under current system policy**. Apple's TN3151 explicitly distinguishes using its trust infrastructure from independent trust evaluation. Native-root snapshot timing, distrust updates, partial loader failures, malformed entries, empty roots and private trust stores require policy; bundled webpki-roots/Mozilla roots would be another shipped/updateable input, not "OS roots." The security-framework 3.5.1 package also marks maintenance status `looking-for-maintainer`; verify the chosen wrapper's current maintenance instead of transferring Apple's support promise to it. [P1,T1-T2]

OpenSSL default trust locations are build paths (`cert.pem`, `certs`/store), overridable with `SSL_CERT_FILE/DIR`; CAfile is processed immediately, CApath can be lazy. A successful `SSL_CTX_set_default_verify_paths` can mean a default location is missing; it is not evidence of usable anchors. This API does not establish use of macOS Keychain/SecTrust. OpenSSL defaults to `SSL_VERIFY_NONE`; secure clients must deliberately enforce peer verification and the intended DNS/IP identity, separately from SNI. TCP numeric endpoint/canonical resolver name is not that identity. [O10-O11]

OpenSSL automatic initialization normally loads configuration; `OPENSSL_CONF`, includes, `OPENSSL_MODULES`, algorithm/provider selection and optional build-enabled `SSLKEYLOGFILE` are relevant ambient inputs. Explicit initialization/config controls and library contexts exist, but first-use/order and coexistence with other native consumers need review; no per-call global environment mutation or casual global cleanup. Loading a trust bundle, importing a private key or entering a provider may involve filesystem/native work beyond socket readiness. [O12]

ri-7ap does not solve this. Immutable application Inputs neither freeze libc/provider environment reads nor force them to use the snapshot. Possible future policies include explicitly supplied trust/configuration or a reviewed startup capture/initialization lifecycle; neither is chosen here. Pin environment/config/loader isolation in future integration fixtures. `rill test` synthetic Inputs do not isolate live native TLS or approve insecure verifiers/key logging.

## 6. Native versus actual wasm32-wasip1 capability

- **Native Linux/macOS:** credible maintained library/platform mechanisms exist, but no minimum OS/libc/SDK/CPU/build profile, actual Rill native entry, provider execution, scheduling or trust/entropy integration was validated. System packages, vendored/static copies and macOS frameworks have different patch responsibility and linkage/notice obligations; choose a deployment/update owner explicitly.
- **Ring path:** published ring 0.17.14 and getrandom 0.2.17 source show an actual WASI entropy route. Rust's old `wasm32-wasi` spelling in those docs is the preview1 lineage, not permission to substitute preview2. A Rill guest link, C crypto objects, time for certificate validity, roots/keys, linear-memory growth/reentrancy and trusted host imports remain unvalidated. This is a candidate for investigation, not provider support. [G1-G2]
- **AWS/OpenSSL paths:** AWS's observed platform page lists `wasm32-unknown-emscripten`, **not wasm32-wasip1**; AWS source `OPENSSL_WASM/getentropy` branches are not a WASI support promise. OpenSSL's `__wasi__` entropy branch likewise does not establish a supported TLS build/runtime, roots or network access. Network.framework/Security.framework are not WASI APIs. Do not invent host TLS imports, JS WebCrypto, preview2 adapters or a custom RNG to erase these gaps. [A2-A3,O13]
- **Transport is independently unavailable:** canonical ri-vno keeps names/types visible on wasm32-wasip1 but otherwise-valid live TCP/DNS operations return typed Unsupported; standard preview1 lacks general socket creation/connect/bind/listen/DNS and a TLS/trust service. Its random_get and existing-fd operations do not grant a dialable TLS connection. A memory engine might later compose over an explicitly provided ordinary byte transport, but no inherited-socket handoff/custom host capability was approved by ri-vno. Preserve input/control validation and the target; ri-irw must explicitly resolve its own TLS capability/Unsupported profile without fabricating support or dropping wasm32-wasip1. [ri-vno §§4,10; W1]

## 7. Choices, unknowns and future validation (NOT RUN)

The interview needs to weigh these tradeoffs; this note accepts no recommendation. Rustls offers the clearest explicit buffer-pump separation but needs separately approved Rust/native crypto dependencies, lifecycle and roots. OpenSSL 3.5 has the longest published support horizon observed here and bounded BIO-pair integration, but adds retry, thread-error and configuration complexity. OpenSSL 4.x branches are maintained alternatives with shorter listed horizons and a major-ABI boundary. Network.framework offers current Apple system TLS/trust integration but is a platform connection architecture, not a demonstrated generic stream-upgrade engine. SecureTransport is not a current TLS-1.3 solution; BoringSSL/LibreSSL do not remove ownership/ABI/update obligations.

Several factual blockers remain. Rill has no delivered provider bridge or backend approval. Interrupted or failed provider writes lack an exact-prefix mapping. Native calls, error capture and callback release have no proven migration-safe implementation. No secure entropy, build, configuration and roots lifecycle has been selected, and no wasm32-wasip1 TLS transport/provider capability has been established. Rustls's policy-date inconsistency and transitive-wrapper maintenance need explicit support confirmation. These are separate from certificate/protocol/security-policy choices; none is fixed by ri-3id, standalone source inspection or a successful future handshake.

Future work **only after authorization and provider/policy selection**:

1. Pin full dependency/features/SBOM/notices, OS/CPU/libc/SDK/host/imports, linkage, initialization/environment and security-update process; verify maintained branch eligibility and advisory fixes, including transitive crypto/root bindings. No "latest forever," FIPS or legal-compliance inference.
2. Establish LLVM23 native entry/return and ri-dej-supported scheduling/unwind/stack/pointer/reclamation mechanisms. Exercise migration at every permitted suspension, adjacent calls on worker threads, nested provider callbacks/error queues, worker saturation and blocking trust/entropy initialization.
3. Instrument one-byte/short plaintext and ciphertext, full queues, partial BIO feed/drain, WANT_READ while output is pending, read-needs-write/write-needs-read, write-retry pointer/data/length identity and terminal failure after partial wire effects. Check exact current-input acceptance/prefix accounting, no duplicate prefix or positive zero-success; bound handshake/input/output memory and processing under hostile input.
4. Exercise explicit Clock/domain/deadline/token preflight; repeated readiness/retries using the original absolute deadline; ManualClock registrations; token/deadline/native completion races and late final progress; intrinsic cancellation masking; non-destructive abort-or-wait. Track callback/job/registration quiescence before freeing any argument, with no hard return/reuse promise.
5. Separate flush, local close-notify queued/sent, peer close-notify, buffered plaintext, TCP EOF/truncation, fatal alert, failed handshake, consuming-close failure and default disposal. Verify last-reference/BIO/transport release exactly once and preservation of primary/secondary error envelopes; never infer remote execution, rollback or replay safety.
6. Validate trust/identity/SNI/ALPN, roots missing/partial/stale/distrusted, native-config changes and entropy denial/early boot/failure under approved fixtures. For WASI independently validate actual guest crypto build, secure random_get host, time/root/byte-transport capabilities and memory.grow/reentrancy lifetimes, with honest Unsupported cases.
