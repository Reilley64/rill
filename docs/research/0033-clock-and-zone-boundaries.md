# Clock and zone boundaries. Remaining facts for Rill #33

**Status:** primary-source research, **not approved Rill policy**. Checked 2026-11-15 UTC.

**Scope:** clock/host facts needed to choose elapsed-time semantics, followed by small source-level zone-database gaps. Read alongside [0033-jiff-api-model.md](0033-jiff-api-model.md) and [0033-jiff-wire-and-differences.md](0033-jiff-wire-and-differences.md); this note does not repeat their wire audit or change them. The user's choice is a **Jiff-inspired, Rill-native API**, not a Rust FFI/dependency/backend selection.

**Evidence boundary:** official specifications, vendor documentation and pinned upstream source inspection; **no executable Rill tests, browser suspend experiments, native probes, safety/proper-tail proof or LLVM/Wasm pipeline validation**. In particular, a host API existing does not discharge [#30](https://github.com/Reilley64/rill/issues/30). Implementation examples below are static source observations, not measurements or claims about every installed release. Jiff citations are all **0.2.44**, commit **`95f343d3f137e5596288d862f4a04dc3be52b07b`**. Other source versions are explicitly identified in the references.

## 1. Distinctions that the clock contract must keep separate

- **Monotonic** means readings do not go backwards; it does not mean strictly increasing, constant-rate, UTC-accurate, suspend-inclusive or infinitely representable. Linux explicitly permits repeated identical readings and frequency correction; Rust explicitly separates monotonic from steady and leaves suspend behavior unspecified across platforms/versions. [L1, R1]
- **Resolution** is the reported tick/granularity; **representation precision** is the unit/range of a value; **accuracy** is closeness to the intended physical timescale. A nanosecond field or `clock_getres` result is not a nanosecond accuracy or wakeup guarantee. POSIX makes resolution implementation-defined; Apple's manual even warns its reported resolution can be smaller than the underlying clock's actual precision. Browser privacy coarsening adds another, deliberately less precise observation layer. [P1, A2, H3]
- **Suspend exclusion** is not process CPU time. A system elapsed clock can advance while this process is descheduled and still stop for whole-system sleep. CPU-time clocks instead measure CPU consumption; they are not substitute elapsed timeout clocks. Nor is freezing a browser context the same event as suspending the OS. [L1, A2, W1, H1, H4]
- **Read time, timer eligibility, callback execution and API return are different events.** A clock may include suspended time without waking the machine. Timers can become overdue during sleep and execute later. Linux's separate alarm clocks require wake authority; HTML timers can be padded/throttled and depend on document/worker activity. No source here establishes a finite upper bound on Rill return latency. [L3, H4, B1]

These are factual distinctions, not a recommendation to expose every host clock or every host limitation as a public Rill operation.

## 2. Native: POSIX, Linux and macOS

### POSIX baseline, not a universal suspend policy

POSIX.1-2024 requires `CLOCK_MONOTONIC`: system monotonic time since an unspecified point that does not change after system startup, not settable with `clock_settime`. This revision made support mandatory; do not retroactively assume every older POSIX deployment has it. Its clock interface does **not choose Linux's suspend-excluding behavior for all implementations**. Linux and Apple provide the concrete counterexample below. [P1, L1, A2]

For `clock_nanosleep`, an uninterrupted successful relative wait lasts at least the requested interval **in the selected clock**; an absolute wait lasts at least until that clock reaches the deadline. An already-reached absolute deadline returns without suspension. Signals can interrupt either wait, and rounding up/scheduling can extend it. Linux documents absolute-deadline retry as a way to avoid drift from repeatedly restarting relative waits; availability of a readable clock does not establish that every waiting API accepts it. These are lower-bound/eligibility facts, **not completion-time upper bounds**, and do not specify Rill cancellation behavior. [P2, L2]

### Clock matrix: similar names do not select similar semantics

| Platform/source | Clock | Suspend counted? | Wall steps / rate correction | Boundary |
| --- | --- | --- | --- | --- |
| Linux | `CLOCK_MONOTONIC` | **No** | No discontinuous wall-clock jumps; subject to frequency adjustments, including the documented `adjtime`/NTP class of correction. | Nonsettable, system-wide; repeated values possible. [L1] |
| Linux | `CLOCK_BOOTTIME` | **Yes** | Otherwise identical to Linux `MONOTONIC`, thus not a promise of an uncorrected/raw rate. | Clock since Linux 2.6.39; timer API support has its own history. [L1–L3] |
| Linux | `CLOCK_MONOTONIC_RAW` | **No** | Raw hardware-based time, not subject to frequency adjustments. | Linux-specific since 2.6.28. Not interchangeable with an arbitrary timer backend's clock. [L1, L2] |
| macOS | `mach_absolute_time` / `CLOCK_UPTIME_RAW` | **No** | Apple's raw-clock documentation excludes frequency/time adjustments. | Mach returns ticks; uptime clock returns converted time. [A1–A3] |
| macOS | `mach_continuous_time` / `CLOCK_MONOTONIC_RAW` | **Yes** | Raw, unaffected by frequency/time adjustments. | Continuous API available from macOS 10.12; **Apple RAW is not Linux RAW's suspend policy**. [A1–A3] |
| macOS | `CLOCK_MONOTONIC` | **Yes** | Apple reserves the explicit no-frequency/time-adjustment promise for RAW; do not infer RAW rate semantics here. | Apple manual's sleep-inclusive statement differs from Linux's identically named clock. [A2, A3] |

**Linux wait capabilities:** `clock_nanosleep` documents `MONOTONIC` and `BOOTTIME` support (BOOTTIME since 2.6.39), but can reject an unsupported clock with `ENOTSUP`. `timerfd_create` supports BOOTTIME since Linux 3.15; its `*_ALARM` clocks, distinct from ordinary BOOTTIME, can wake a suspended system and require `CAP_WAKE_ALARM`. Suspend inclusion therefore does not imply wake-from-suspend permission or prompt execution after wake. [L2, L3]

**Apple source corroboration and units:** XNU's header says continuous time is like absolute time but advances during sleep. Its implementation uses a continuous hardware clock when available, otherwise absolute ticks plus accumulated sleep time. The inspected Libc maps `CLOCK_UPTIME_RAW` to `mach_absolute_time` and `CLOCK_MONOTONIC_RAW` to `mach_continuous_time`; its ordinary `CLOCK_MONOTONIC` path subtracts boot time from `gettimeofday`, with consistency sampling. These are facts of the cited releases, not a proof that every Apple implementation has identical internals. Use Apple's documented contract, not a deduction that ordinary MONOTONIC is raw because of its name. [A1-A3]

Mach values are `uint64_t` **ticks**, with conversion using `mach_timebase_info`'s `numer/denom`; Apple's nonportable `clock_gettime_nsec_np` returns `uint64_t` nanoseconds. A multiplication/division conversion must preserve range and chosen rounding; ticks are not inherently nanoseconds. Apple's pinned Libc shows the conversion expression, not a general overflow-proof conversion recipe for Rill. POSIX `timespec` separates seconds and nanoseconds; it does not give Rill one target-independent integer range. [A1-A3, P1]

**Identity/comparability:** POSIX fixes the monotonic origin for a system startup, but that is not a durable timestamp or cross-machine identifier. Linux additionally virtualizes MONOTONIC (including RAW/COARSE) and BOOTTIME with **time-namespace offsets**. Consequently, even same-machine raw numbers need a shared clock/namespace/boot identity before comparison. Apple's RAW manual says not to compare it to other system time sources. A deliberately narrower process/runtime-local Rill instant domain is an available design choice, not a restriction proven necessary by all native APIs. [P1, L4, A2]

### What Rust `Instant` does. And does not. Settle

Rust 1.91.0 documents an opaque, monotonically nondecreasing `Instant`, not a steady-rate or portable suspend contract; arithmetic range varies by target, checked operations are available, and ordinary addition can panic. Its "around one hundred years" guidance is **Rust portability guidance**, not a Rill promised deadline range. `duration_since`/elapsed subtraction can saturate to zero to mask clock anomalies or reversed operands; the docs explicitly warn this obscures programming mistakes. Rill still needs its own failure/ordering/overflow choice. [R1]

The pinned Unix implementation selects **`CLOCK_UPTIME_RAW` on Apple** and `CLOCK_MONOTONIC` otherwise; therefore the generic docs table's Darwin "Monotonic Clock" description must not be read as a literal selection of Apple's sleep-inclusive `CLOCK_MONOTONIC`. At this pin the Apple and Linux selections both exclude suspend, but differ in rate-correction properties. Rust's WASIp1 source calls the host monotonic clock; WASIp2 calls `wasi:clocks/monotonic-clock.now`. None of these Rust choices selects a Rill implementation or guarantees browser unknown-unknown Wasm support. [R1, R2]

## 3. WebAssembly: host contracts, not one clock

The relevant interfaces differ: browser JavaScript timing, legacy WASI Preview 1 imports, component-model WASI 0.2 interfaces, and custom embedders. Treat the **chosen host interface and its available capabilities** as part of the support contract. WASI's own clock proposal describes an API and its worlds; it is not evidence that every Wasm embedder provides it or that Rill's backend can import it. [W1-W4, R2]

### Browser `performance.now`: specification versus implementations

**Specification:** High Resolution Time Level 2 (Recommendation, 2019-11-21) requires same-time-origin readings to use the same monotonic clock and their chronological differences never to be negative. Level 3's inspected **2026-11-06 Working Draft** describes a shared monotonic clock within a user-agent execution, time origins, and comparable moments only from the same clock. `performance.now()` is milliseconds relative to a context's time origin; direct subtraction across different origins is wrong. Origin translation is specified for communicating contexts, not indefinite persistence across browser restarts/profiles/machines. A time-origin epoch estimate is not a clock resynchronized to future wall-clock adjustments. [H1, H2]

**Suspend wording needs qualification:** the published Level 2 and inspected Level 3 text contain an *informative note* saying throttling/freezing callbacks should not affect the clock's resolution/accuracy. They do not supply an unambiguous explicit normative OS-suspend sentence. The owning standards repository's [issue #115](https://github.com/w3c/hr-time/issues/115) records the earlier intent/consensus that it should tick during sleep, explicitly identifies the normative-text gap, and contains an implementer's acknowledgment of inconsistent implementations. Thus neither "the spec clearly permits stopping in sleep" nor "every conforming deployment necessarily has verified suspend inclusion" is an honest basis for Rill portability. The distinction is **intended/spec-discussed behavior versus actual host capability**, with a documented specification clarity gap. [H1, H2, H5]

**Documented implementation evidence, not our experiments:** in Chromium **131.0.6778.85**, Blink's `Performance::now` uses its tick clock and subtracts/clamps the time origin; the default is `DefaultTickClock`. Its Apple tick implementation uses `mach_absolute_time`, and its non-Apple POSIX implementation uses `CLOCK_MONOTONIC`. Together with the OS contracts above, this is source-level evidence of **suspend-excluding browser timing on those paths**, despite the standards discussion's sleep-inclusive intent. The standards issue also records historical cross-browser/platform reports; these are dated implementer/reporter statements, not a fresh all-browser conformance matrix. No claims here establish current Firefox/Safari/Windows behavior or validate any browser version by observation. [H5, H6, A1, L1]

**Rate and precision:** HRT says the clock is not subject to system clock adjustments; the standards issue specifically identifies ambiguity concerning small monotonic rate corrections versus wall steps. Do not convert that wording into a proven universal "NTP cannot affect rate" property. The Level 3 coarsening algorithm starts at **100 µs**, or **5 µs** for cross-origin-isolated contexts, and permits coarser implementation-defined resolution and jitter. These are not minimum available accuracy promises. `DOMHighResTimeStamp` is a WebIDL `double` in milliseconds, not an exact integer nanosecond counter; floating precision and intentional coarsening remain even after numeric conversion. [H2, H3, H5]

**Timers are a different capability:** HTML says timers are not guaranteed to run exactly on schedule. The waiting algorithm counts document fully-active time or worker not-suspended time, permits additional implementation-defined padding, and applies a 4 ms minimum after sufficiently nested timers. A readable monotonic clock does not promise callbacks execute while a context/OS sleeps, or promptly after resume. A Rill adapter would need an explicit reading/eligibility/wakeup policy, rather than equating `setTimeout` with a precise nanosecond deadline or replacing monotonic time with `Date.now` to recover sleep time. [H4, H1, B1]

### WASI Preview 1 and WASI 0.2

| Interface | Guaranteed/described facts | What it does **not** settle |
| --- | --- | --- |
| **Preview 1, `snapshot-01`** | `timestamp` is `u64` nanoseconds. `clockid.monotonic` is **store-wide**, has undefined epoch, cannot be adjusted or jump negatively. `clock_res_get` requires a nonzero resolution for supported clocks and returns `INVAL` for unsupported ones. `clock_time_get`'s requested precision is a maximum permitted lag, **not** a timer deadline. [W1] | No explicit suspend inclusion or precise NTP-rate contract in this clock definition; not every listed clock must be supported. A store-wide identity does not authorize comparing independent stores/hosts or persisted readings. [W1] |
| **Preview 1 subscriptions** | `poll_oneoff` waits on subscriptions; clock events mean the clock reached the requested timeout. `subscription_clock` supports absolute versus relative time, selected clock ID, and a `precision` allowance for **additional coalescing delay**. [W1] | Coalescing allowance is not an end-to-end scheduler/return upper bound. An event/error/cancellation mechanism must not be confused with forced abort of unrelated I/O. [W1, B1] |
| **`wasi:clocks/monotonic-clock@0.2.0`** (also checked 0.2.6) | `instant` and `duration` are `u64` nanoseconds; unspecified initial value; reads nondecreasing; instants comparable **only from the same monotonic-clock**. `resolution` describes a clock tick. `subscribe-instant` and `subscribe-duration` create pollables resolving once the instant occurs / duration elapses from subscription. [W2] | No specified suspend policy, NTP/raw-rate contract, cross-instance identity protocol, or chosen wrapping/overflow recovery behavior in this WIT. No precision parameter equivalent to Preview 1's coalescing field. [W2] |
| **`wasi:io/poll@0.2.0`** | A pollable has readiness/block operations; polling waits for one or more ready indices; a timeout is another clock-created pollable. I/O errors can appear as readiness to inspect at the source. [W3] | Readiness alone is not a successful I/O result, release confirmation, or permission to invalidate borrowed sources; a timer in the list does not kill other work. [W3, B1] |

**Representation limit:** a full `u64` nanosecond interval is about **584.5 years** (arithmetic from `(2^64−1)/10^9` seconds). This is a numeric capacity, not a promised future deadline horizon: the current reading consumes headroom, its origin is unspecified, and the host's wait representation can be narrower. Existing Rill `u64` **millisecond** inputs cannot all fit in a `u64` nanosecond conversion. Checked multiplication/addition, rounding, overflow and the handling of long waits remain Rill decisions; neither raw WIT types nor Rust `Duration` settles them. [W1, W2, R1, B1]

**Concrete host differences:** Wasmtime **29.0.1** allows an embedder to replace `HostMonotonicClock`; its default clock reports elapsed time from a clock-construction `initial` instant, not necessarily machine boot. That implementation converts elapsed nanoseconds to `u64` with `unwrap`. Its timer implementation uses **Tokio's timer clock**, deriving a relative interval from the configured clock for `subscribe-instant`; zero becomes ready, and unrepresentable Tokio deadline addition becomes a **never-ready wait**, not an overflow error. These are pinned host behaviors, **not WASI or Rill policy**. In particular, replacing just this host's clock-read object does not automatically provide deterministic manual-clock timer subscriptions: the wait path must be controlled too. No executable host check was performed. [W4]

**Capability conclusion:** named imports/interface versions, clock identity, suspend semantics, wait support, runtime resource limits and errors/traps require explicit target/host investigation. Browser HRT does not imply WASI, WASI does not imply a browser clock, and a custom embedder may supply another clock entirely. Missing/unverified capability must not silently become a wall clock, incompatible suspend policy or falsely supported Rill target. This is a proposed honesty boundary, not a selected error API or backend implementation. [W1-W4, H1-H6]

## 4. Honest policy choices and deterministic testing questions

The following are **alternatives for human selection**, not approvals:

1. **Include suspend:** elapsed deadlines continue across whole-system sleep. Linux BOOTTIME and Apple's continuous clock supply relevant native read semantics; clock-compatible waiting/resume behavior remains necessary. Browser/WASI support must be checked rather than inferred from "monotonic." No wake-from-suspend or timely-return promise follows. [L1-L3, A1-A3, H5, W2]
2. **Exclude suspend:** elapsed deadlines pause during whole-system sleep, though ordinary descheduling still counts. Linux MONOTONIC and Apple's absolute/uptime clocks supply relevant native reads. Some pinned browser paths match, but that is not a portable browser/WASI selection rule; reject or mark unsupported hosts that cannot establish the chosen behavior. [L1, A1-A3, H6, W2]
3. **Explicitly unsupported/unavailable where the selected contract cannot be met or verified:** choose a documented target subset, or explicit capability-specific clock domains if separately approved. A weaker "host-dependent suspend behavior" contract is also possible **only if deliberately approved and named**, not hidden beneath one supposedly uniform elapsed-time guarantee. API shape, failure mode and whether multiple domains belong in v0 remain decisions. [R1, H5, W2]

Independently decide whether frequency slewing is allowed, how anomalies are surfaced, clock-domain identity/comparability, instant opacity/persistence prohibition, range/conversion/rounding, and whether a deadline is anchored once versus recomputed from a wall appointment. Wall time and Jiff zone rules cannot manufacture a missing monotonic guarantee. [P1, L1, R1, H2, W2; prior Jiff notes]

**Candidate fake/manual-clock requirements. Not a selected testing API:**

- Couple `now`, instant/deadline domain identity, registration, expiration and wake scheduling to the **same controllable clock**. A fake read with real timers is insufficient; the Wasmtime example makes that distinction concrete. Reject mixed real/fake or different fake-instance comparisons if the chosen identity contract requires it. [W2, W4]
- Test repeated readings, coarse ticks, upward deadline rounding, maximum duration conversion/addition, already-expired/zero deadlines, and backward-reading anomaly handling separately from negative elapsed arithmetic. Tests should not rely on wall sleeps or assume every `now` advances. These are proposed cases derived from P2/L1/R1/H3/W2, not executed tests.
- Model wall steps/slews separately from elapsed progression, and model **OS suspend**, **context/process inactivity** and **scheduler delay** separately. Advance a suspend-inclusive versus exclusive fake according to the policy selected later; do not encode the answer in a supposedly neutral fixture. [L1, A2, H4, H5]
- Explicitly drive registration-before/after-expiry, simultaneous operation/timer readiness, unregister/abort acknowledgments, committed side effects and cleanup completion. Advancing time makes a deadline eligible; it must not magically complete unabortable work or a cleanup join. Winners/fairness need the existing unspecified simultaneous-ready boundary or an explicit future decision. [B1]

**Rill invariant retained:** [#33](https://github.com/Reilley64/rill/issues/33), [ADR 0009](../adr/0009-concurrency-safety-and-cooperative-cancellation.md) and the standard-library contracts require cooperative cancellation and joined cleanup. Requests/handle drops are **not force kill or confirmed abort**. Native registrations retain sources until completion/confirmed abort; scoped races join losing execution and cleanup before returning. A timer winning can trigger result selection/cancellation, but unabortable work or cleanup can postpone return indefinitely. A better monotonic clock changes none of that. [B1]

## 5. Jiff 0.2.44: remaining database/source qualifications

### ASCII case, "canonical" names and aliases

`TimeZoneDatabase::get` documents **ASCII-case-insensitive** lookup; its example normalizes `america/NEW_YORK` to `America/New_York`. The zoneinfo backend compares against names collected from the database directory, the concatenated backend compares against indexed names, and the bundle binary-searches its generated name table. This is not Unicode case folding or arbitrary path normalization. `iana_name()` returns the loaded name (or special UTC); it does not independently resolve a tzdb alias graph. [J1-J4]

In `jiff-tzdb`, "canonical" is explicitly **canonical capitalization**. The pinned generated table has both **`America/New_York`** and **`US/Eastern`**, pointing at the **same byte range `190195..191939`**, while lookup returns the table entry's own name. Therefore, by source deduction, bundled lookup of `us/eastern` retains **`US/Eastern`**, not `America/New_York`. The zoneinfo path similarly retains the discovered relative entry name rather than canonicalizing a symlink's target name. **Alias acceptance is database-content dependent; accepting an alias is not canonicalizing it to a primary IANA Zone name.** No executable lookup was run here. [J2-J4]

`UTC` and `Etc/Unknown` receive special case-insensitive treatment in usable backends; `iana_name()` returns `Some("UTC")` for UTC but **None** for unknown, which is explicitly not IANA. An explicitly empty database's `get` errors before backend special lookup. Preserve these distinctions rather than assuming any string resembling an identifier supplies an immutable rule snapshot. [J1, J5]

### Path-escape protections: scope the positive claim narrowly

The checked zoneinfo `get(query)` **does not join an arbitrary caller query to the database directory**. It resolves a query against its enumerated, case-insensitively searched names and opens the stored path. The paths/names originate from the directory walk and `strip_prefix(start)`; separator-bearing traversal/absolute query strings do not introduce fresh filesystem paths through this lookup route. Bundle and concatenated lookup likewise select table/index entries, not query-named files. These are source-level protections against **query-based traversal**, not a demonstrated filesystem sandbox. [J2-J4]

The walk treats symlinks as files, does not descend symlink directories, and later uses ordinary `File::open` for stored paths. Consequently symlink targets may be outside the configured root; the inspected path provides no no-follow, descriptor-relative confinement or race-free immutable snapshot guarantee. Root selection, trusted directory contents, symlink/replacement authority, explicit file-loading/system-discovery APIs and OS permissions remain separate trust boundaries. Do not call `from_dir` safe confinement for an attacker-controlled tree just because name lookup avoids `../` concatenation. No adversarial filesystem tests or security audit were performed. [J2, J6]

### Equality: actual implementation versus the docs' strong wording

The public docs say equal zones are guaranteed to have the same rules, describe IANA equality as identifier plus rules checksum, and describe POSIX equality as byte-for-byte original rule-string equality. **The source requires narrower claims:** [J7]

- `TimeZone` derives equality over its private `Repr`. That implementation first rejects **different representation tags**; UTC equals UTC, unknown equals unknown, fixed offsets compare offsets, and **static TZif versus runtime/Arc TZif compare unequal even if name/rules agree**. Same-tag TZif values compare `MaybeNamedTimeZone`; its derived comparison includes the optional name and its zone's equality. It is not simply pointer identity or offset-at-one-instant equality. [J7, J8]
- Core TZif `TimeZone::eq` compares **only `u32 checksum`**. The parser computes masked **CRC32C/Castagnoli** over the TZif bytes actually consumed, ignoring any unused trailing bytes. It does not compare all transitions/rules after a checksum match. A 32-bit checksum admits collisions; therefore "equal guarantees identical rules" is **not a collision-proof/adversarial guarantee of this implementation**. Conversely differing encoded bytes/checksums or names can yield unequal values despite equivalent rules. The core docs themselves call it "best effort." Do not adopt that checksum as Rill snapshot/security identity without a separate decision. [J8, J9]
- POSIX source equality is **derived structural equality on parsed abbreviation/offset/DST-rule fields**, not original-string equality: the core `TimeZone` stores no original input string, and `Repr` compares that parsed value. Thus the public original-string statement does not describe the pinned mechanism. Any Rill requirement for lexical identity, rule identity or equivalence needs an explicit definition. [J7, J10]

This qualifies the earlier notes' prose about conservative/same-rules equality without editing them. No collision was constructed or equality fixture executed. Representation distinctions and CRC limitations alone suffice to reject a stronger proof claim.

### Resource limits and caches: useful inputs, not Rill quotas

- **Zoneinfo:** initialization walks directories with an explicit stack (not recursive Rust calls), collects/sorts names, and skips top-level `posix`/`right` trees. The inspected walk has no explicit total entry/depth/byte budget. Loading a selected TZif uses **`read_to_end` into a Vec**, without an explicit byte cap at that site; cached zones grow in a sorted Vec on first successful lookup. This is not an explicit bounded-memory database service for arbitrary roots. [J2]
- **Disk cache:** zoneinfo and concatenated defaults are **five-minute TTLs**. Expiration triggers lookup-time revalidation/reload, not a periodic eviction or five-minute propagation guarantee. Zoneinfo can retain a zone when its modification timestamp is unchanged; its source explicitly assumes unchanged metadata means unchanged bytes. `reset` clears caches, but retained immutable `TimeZone` values survive. Neither TTL nor reset proves immediate global refresh, total-memory reclamation or external-file atomicity. [J2, J6, J11]
- **Bundle cache:** with `std`, parsed zones live in a **global RwLock/sorted Vec cache**; source says it "can never contract" in ordinary use, with explicit clear/reset available. Distinct alias names may occupy distinct entries even when their raw byte ranges match. The bundled universe is finite, but there is no user-selected cache-entry/byte budget here; without `std`, that parsed global cache is absent. [J3, J4]
- **Concatenated database:** the index format has **40 bytes for an IANA name** plus three `u32` fields. Its allocation helper rejects an individual request above **10 MiB** (`10 * 1 << 20`), uses `try_reserve_exact` and checked length addition. This is **not** a 10 MiB total DB/process/cache limit: separate index/data buffers, parsed zones, names and retained scratch capacities exist. The source warns large data can still cause proportionally large allocations. These format/helper limits must not become a universal Rill zone-name or database quota by accident. [J12, J11]
- **TZif parser:** documents allocation proportional to input, uses checked header size arithmetic and input-slice bounds, and heap-allocates transitions/types. Optional `tz-fat` generation has a `FATTEN_MAX_TRANSITIONS = 300` guard and a target year of 2038; this is a guard on **additional generated transitions**, not a total imported transition-count budget. None of these local checks constitutes a total load/retention/CPU/stack/latency bound for Rill. [J9]

**Needed database decisions, not selected limits:** authority/source and immutable snapshot provenance; ASCII case/alias policy; equality versus canonical identifier versus rule-content identity; trusted versus untrusted roots/data; maximum input bytes, entries, identifier bytes, transitions, generated expansion and retained snapshot/cache memory; eviction/reset/update semantics; and error boundaries when those limits are exceeded. Resource budgets must include simultaneous retained old/new snapshots and temporary parse buffers, not just one TZif blob. These are proposed design dimensions derived from the cited allocation/cache behavior, not approved numeric quotas or a request to add Rust machinery.

## 6. Decisions to take back to #33

1. **Suspend and rate:** include or exclude OS suspend; whether monotonic rate slewing is allowed; explicit unsupported hosts versus a separately approved weaker/variable contract.
2. **Domains and numbers:** clock identity/comparability and persistence boundary; value range/precision; checked conversions/deadline addition; coarsening/rounding/anomaly behavior. Preserve existing zero/expired and no-wrap obligations.
3. **Wait meaning:** clock-compatible eligibility versus actual execution/return; completion/cancellation races and source retention remain joined-cleanup obligations, never hard return deadlines.
4. **Testing seam:** whether/how a manual clock controls reads **and** registrations/wakeups, with separately driven operation and cleanup completion.
5. **Zones:** capitalization versus alias normalization; explicit snapshot/equality identity rather than CRC proof; authority and aggregate database/cache/parse limits.

None is settled by choosing Jiff's calendar API. This note contributes factual inputs only: no policy acceptance, Rust FFI choice, executable Rill testing, safety/proper-tail proof or #30 backend proof.
