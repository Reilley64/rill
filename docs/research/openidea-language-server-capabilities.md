## Main findings

1. OpenIDEA has source-wired LSP completion/resolve, signature help, hover, navigation, references, highlights, symbols, code actions/resolve, rename, file-move updates, formatting, semantic tokens, inlay hints, code lenses/resolve, links/resolve, and **both call and type hierarchies**. This is substantially more than a diagnostics-only client. See the inventory below.
2. A capability name or language-definition option is **not** proof of a working LSP feature. At this revision, `folding-range`, `selection-range`, and on-type formatting appear in capability filtering, but actual folding and selection use syntax/plugin paths; there is no corresponding generic LSP request path in the inspected client. [Capability filter][feature-filter] versus [actual document operations][doc-ops].
3. Diagnostic capability advertisement is richer than the display model: related information and code-description URLs are advertised, but the diagnostic converter does not carry them into the IDE diagnostic record. Diagnostic `data` is also not carried into that display record, although raw diagnostics are retained for code-action context. This matters directly to #24's multiple labels, notes, documentation links, and fixes. [Advertisement][caps-diagnostics], [conversion][diagnostic-conversion], [raw code-action context][code-actions].
4. Language recognition, lexical syntax/structure, LSP semantic features, plugin providers, run/test output, and debugging are distinct integration surfaces. A server alone does not supply every OpenIDEA language feature. [Language definition][language-definition], [plugin syntax][plugin-syntax], [plugin language features][plugin-features], [run/test API][plugin-runs].

## 1. Language recognition, syntax, and external-server registration

### Recognition is not supplied by LSP

OpenIDEA's language definitions are TOML: `id`, `name`, extensions, exact/pattern file names, and optional first-line regex. Comments, indentation, scratch templates, CodeMirror `ui-mode`, bundled `tree-sitter`, language servers, debugger, and external formatter are separate fields. User definitions live in the configuration directory's `languages/` folder and are read at startup; the documented override replaces a built-in definition as a whole. Plugins can contribute the same language-definition format, including through a **data-only** plugin. Built-in/user ids and detection mappings take precedence over plugin claims; users can also map file types explicitly. [Definition and detection fields][language-definition], [plugin registration][plugin-languages], [registry precedence][registry-precedence].

Consequently, recognizing `.rill` and choosing the correct LSP language id require a language definition/mapping. An LSP executable appearing on `PATH` does not itself register a file type.

### Syntax grammar is a separate deliverable

- `ui-mode` selects an existing instant-highlighting CodeMirror mode. `tree-sitter` names a **bundled** grammar used for outline, folding, project symbols, and highlighting when no UI mode exists. The documented grammar list does not include Rill. A new tree-sitter grammar must be compiled into OpenIDEA; a plugin declaration does not install an arbitrary grammar. [Syntax fields and grammar list][language-definition].
- For an unbundled language, a WASM plugin's `syntax-provider` can supply highlight tokens, outline symbols, and folds. Tokens/symbols use UTF-8 byte offsets; folds use lines. Results are validated and cached per document version. This is **not LSP semantic tokens** and is not a complete tree-sitter parser API. [Plugin syntax contract][plugin-syntax], [source representation][external-syntax].
- Semantic highlighting through LSP can augment lexical highlighting, but does not automatically supply the editor's syntax-node/expression/local-symbol operations. A Rill syntax-provider or future bundled grammar and an LSP therefore address different parts of the editor experience. [Semantic capability advertisement][caps-diagnostics], [syntax operations exposed to the editor][syntax-api].

### Starting and configuring a server

Each `[[language-servers]]` entry specifies a server `name`, executable `command`, args, env, optional required env vars, root markers, initialization options/settings, and install hint. Regular servers run side by side; a fallback is used only when earlier servers are missing. The root-marker rule selects the outermost matching ancestor within the project, with an optional requirement that a marker exist. A `features` allow-list and `code-action-kinds` filter can deliberately restrict a particular server. **Empty `features` means all available features, not a minimal set.** Users can override executable/args/env/options/configuration in Language Servers settings. [Server definition][server-definition], [restriction implementation][feature-filter].

The default launcher resolves and starts the executable with **stdio LSP**, using the server root as working directory; `connect` enables a TCP connection/start path. A plugin server uses its approved executable pin instead of arbitrary subsequent resolution. [Launcher][launcher]. Initialization supplies client identity, root URI, workspace folders, capabilities, and initialization options. [Initialize parameters][initialize].

### Permissions and trust

A plugin-contributed server/debug adapter requires `process:<program>` approval, even for a data-only plugin. Declared programs derive optional process capabilities: refusing one preserves language recognition but omits that server/adapter. Approval resolves an absolute executable and records a content hash; it is checked again before launch. Remote project programs are resolved/pinned on the remote host. These external processes must not be confused with the sandboxed WASM component itself. [Capability/grant documentation][plugin-permissions], [effective-language source][plugin-policy], [pin verification at launch][launcher].

The host initializes LSP execution permission from project trust. A project-local plugin is also documented as requiring project trust and capability approval. A separately granted plugin editor provider has its own supplied-document and host-import permission rules; these are not extra LSP server capabilities. [Host trust wiring][host-trust], [plugin installation/trust][plugin-install], [provider policy][plugin-features].

[Capabilities][caps], [sync][document-sync]. |

Treat as **not evidenced here**, not as a Rill feature-exclusion decision or claim about future OpenIDEA versions. ## 3. Editor composites and language-specific extensions are not separate standard LSP methods

- **Refactor menus:** Extract/Introduce, Inline, Move, Change Signature and Generate are UI adapters over code-action kinds/titles and workspace edits, sometimes with language-specific syntax fallbacks. "Extract Method" is an editor label, not a standardized LSP request or proof Rill has methods. A Rill extraction of a free function could be meaningful, but mapping it to this UI remains a design/integration question. Safe Delete combines definition/outline/references and client editing; it is not a standard `textDocument/safeDelete`. [Refactor catalogue][refactor-catalog], [query adapter][refactor-query], [safe-delete source][safe-delete], [actions][editor-actions].
- **Pull Members Up / Push Members Down:** explicit app-owned Java extension commands, `openidea.java.hierarchy.members` and `.refactor`, over `workspace/executeCommand`. They must not be counted as generic Rill type-hierarchy or ordinary code-action support. [Java extension implementation][java-hierarchy].
- **Implement/Override Methods:** menu actions query actions matching appropriate titles, with some per-language semantic fallbacks. Their existence is not a generic traits/methods requirement for every language. Navigation to implementation and type hierarchy remain separate features with potentially meaningful Rill semantics. [Actions][editor-actions].
- **Expression Type Info, code vision, imports on paste and cleanup:** composites of hover, symbols/references, diagnostics/quick fixes and code actions. In particular, imports-on-paste queries/resolves quick fixes rather than a standard "paste imports" LSP request. [Type info][type-info], [code vision][code-vision], [paste imports][imports-on-paste], [intentions][intentions-ui].
- **Interactive command forms:** `command/resolve` and interactive resolve capability handling are specifically gated to `gopls`, not a generic server-input-form API Rill can assume. [Command resolver][interactive-command]. Other source paths specialize Java, Kotlin, TypeScript/Vue, C#, Angular, etc.; shipping an LSP with similarly named commands is insufficient to acquire those integrations. [Manager][lsp-manager].

## 4. Non-LSP/plugin language features and run/test/debug integration

### Plugin editor providers

The plugin API independently supplies completion/inline completion, quick fixes, navigation, line/gutter markers, semantic tokens, hover, diagnostics while typing, inlay hints, and the additional providers listed below. Documentation describes how results are merged with or fall back from LSP. This proves an **extension route**, not standard LSP support for every provider of the same name. [Provider overview][plugin-providers], [semantic/hover/diagnostic/inlay contracts][plugin-semantic], [additional features][plugin-features].

Additional providers cover formatting, signature help, document highlights/links, lenses, selection ranges, folding, colors/presentations, document symbols, implementation/type-definition and gutter actions. Syntax providers separately provide lexical highlights/outline/folds for unbundled languages. Snippets are a manifest contribution, independent of a server's completion snippets. [Additional features][plugin-features], [syntax provider][plugin-syntax], [snippet contribution][plugin-snippets].

Embedded-language injection providers can create bounded virtual documents whose language servers answer selected features within an injected range; this is host/plugin orchestration, not automatic parsing of Rill embedded languages. [Injection contract][plugin-injections].

### Run and test

- `runDetectors` can declare a marker-detected argv; dynamic `runConfigurations` can return programs/args/cwd/test/framework. Both require approved programs and use the Run tool window. A `framework = "plugin"` test-results export parses sequential output chunks into the test tree and can select tests for reruns. The host owns Stop/Rerun and executable verification. [Run detectors][plugin-syntax], [run/configuration/test API][plugin-runs].
- A Rill LSP's diagnostics or code lenses do not automatically implement `rill run`, `expect` execution, test discovery, structured test result parsing, or debugger launch. A lens can invoke a command, but that command still needs a supported action/launch route.
- Rill's top-level test-only `expect` and its failure-report requirements belong to #24's testing-report context, but mapping those results into OpenIDEA's test tree is a separate integration question. A compiler diagnostic and a runtime failed expectation are not automatically the same LSP publication. [Rill issue][rill24], [plugin test protocol][plugin-runs].

### Debugging

`[debugger]` declares an adapter/command/args, stdio or TCP transport, optional connection address and install hint; registering one enables breakpoints in that language. These are **DAP/debugger** facilities, not LSP requests. Debugging plugin run configurations additionally depends on the selected/source language debugger and approved launch configuration. Rill backend debug information, stepping, variable representation and adapter compatibility are unvalidated by this research. [Debugger definition][debug-definition], [plugin debug-launch rules][plugin-runs].

## 5. Rill semantic relevance and unresolved questions. Not policy decisions

The absence of methods/traits must not silently reduce the inventory to procedural editing basics. Conversely, OpenIDEA's OO-labelled actions do not create language constructs Rill lacks. ### Diagnostics and positions: stronger claims would be incorrect

1. **Actual position advertisement is only `general.positionEncodings: ["utf-16"]`.** `Encoding::parse` also understands UTF-8/UTF-32 internally, defaulting to UTF-16; that is not negotiation of those encodings. Client text coordinates are UTF-16. Rill's approved original UTF-8 byte-span model therefore still needs correct source/CRLF/Unicode mapping to UTF-16; internal conversion code is not a reason to send byte offsets to this release. [Release capability lines 9-20][rel-caps], [encoding implementation][rel-text], [approved source-position context][rel-decisions].
2. **Push version support does not mean stale publications are discarded.** For normal open documents, `params.version < current version` calls `set_obsolete_diagnostics`, which **replaces/shows** that pushed set but preserves the prior `last_published` timestamp. There is no diagnostic UI stale/version flag in the converted record/event. Unversioned pushes cannot be compared; ordinary closed-file pushes can be retained (special transient/external/injected-document filters exist). A delayed older publication can therefore replace newer visible results. "Obsolete" here is a freshness-bookkeeping distinction, not guaranteed stale suppression or a stale badge. [Release publish handler lines 221-261][rel-handler], [server storage lines 768-844][rel-server], [conversion][rel-convert], [UI replacement storage][rel-diagnostic-ui].
3. **Pull is independently protected, but bounded:** a new scheduled pull supersedes the older per-path token; response checks token, server generation and whether the path is still open. Close removes pulled data. Edit-triggered pulls debounce 300 ms; open/save/refresh pull, saves can re-pull other **open** documents for inter-file-dependent providers. `previousResultId`, optional provider identifier, `full`/`unchanged` reports and bounded server-cancellation retries are implemented; only top-level `items` are read, not `relatedDocuments`. This is not workspace-wide pulling, nor an explicit version embedded in the displayed diagnostic. Old visible diagnostics can remain until replacement, and push's stale policy still applies to the merged set. [Entire identical release pull implementation][rel-pull], [storage][rel-server], [sync scheduling][rel-manager].
4. **Rich diagnostic loss persists byte-for-byte:** advertised `relatedInformation`, `codeDescriptionSupport`, `dataSupport` and `versionSupport` exceed the display conversion. The IDE record carries range, severity, message, source, code, unnecessary/deprecated tags and server, **not related locations/messages, code-description URL, data or publication version**. Raw server diagnostic sets are retained for intersecting code-action context, so `data` can travel back there even though not in hover/Problems display. Preserve richer Rill information in the common model; valid server output alone cannot demonstrate multi-label/link rendering. [Advertisement][rel-caps], [converter lines 1064-1087][rel-convert], [raw action context][rel-manager], [diagnostic UI][rel-diagnostic-ui].
5. **No blanket freshness/retry guarantee:** `general.staleRequestSupport.cancel` and `retryOnContentModified` for full tokens/hints/lenses are advertised. The generic release `call` wraps timeout/RPC and injected-document checks, not a universal ordinary-document version comparison or automatic retry loop. Individual consumers check text/generation and schedule again (e.g. hints/tokens/lenses/formatting), and rename/pull have their own retry logic. Acceptance must exercise concurrent edits, cancellation, push ordering and clearing rather than infer correctness from these flags. [Generic call/rename][rel-manager], [pull][rel-pull], [inlay][rel-inlay-ui], [semantic][rel-semantic-ui], [lens][rel-lens-ui], [format][rel-format-ui].

### Workspace edits: negotiated contract versus actual safeguards/failure paths

This expands the development note's incomplete "version-aware workspace edits" description. The core engine is **already present in the release**; its existence is not new Rill functionality.

| Boundary | Release facts and limits |
| --- | --- |
| Negotiated contract | `workspace.applyEdit: true`; `workspaceEdit.documentChanges: true`, resource operations create/rename/delete, **`failureHandling: "abort"`**, `normalizesLineEndings: true`, `changeAnnotationSupport: {groupsOnLabel: false}`. Code-action and rename capabilities separately say **`honorsChangeAnnotations: false`**. The LSP definition of **abort permits earlier operations to remain applied** after a later failure; it is not `transactional`. [Release caps][rel-caps], [pinned first-party protocol definition][rel-edit-protocol]. |
| Conversion fidelity | Document-change operation order and text-document version are retained; `changes` maps become sorted unversioned edits. Annotated edits become plain edits and the `changeAnnotations` map is discarded: label/description/`needsConfirmation` cannot drive the application UI. Create keeps only `overwrite`; delete only `recursive`; create/delete ignore-if-exists/not-exists flags and rename options are lost. Non-convertible edit/resource URIs are skipped rather than forcing whole-edit failure. Thus an empty/partial **converted** edit can report success without proving the original protocol edit's intent was honored. [Identical converter lines 651–713][rel-convert], [application engine empty-edit path][rel-edit-engine]. |
| Open-document versions | Before mutation, each `FileEdit::Edit` with a version must match an open buffer's current version, else the **whole converted edit** is rejected as out of sync. Initiating-document checks also surround host rename and code-action preparation. Versionless edits have no server-provided text-version protection. [Engine lines 397–447][rel-edit-engine], [host preparation/rename][rel-host]. |
| Closed-file versions | A versioned edit to a file with no open buffer is rejected unless **preconditions were already captured on the incoming internal edit**. With those captured fingerprints it is allowed based on content, not by comparing a closed file to a meaningful LSP document version. Direct inbound applyEdit conversion supplies no preconditions, so an unprepared versioned closed-file edit is refused; host-prepared rename/actions can pass that gate. [Engine `captured`/version branches][rel-edit-engine], [converter][rel-convert], [handler][rel-handler], [unexecuted source tests lines 219–247][rel-edit-tests]. |
| Preview protection / timing | `prepare_workspace_edit` fingerprints disk trees plus unsaved-buffer content; it preserves existing preconditions. Application validates them, preflights on staged copies, then validates again. This detects changes **since capture**, including closed-file disk changes and unsaved open-buffer edits; saving unchanged content need not invalidate. For direct unversioned applyEdit, first capture occurs **at application**, not at server computation; even a prepared action's dependent-file fingerprints are captured after the response. These are not proofs all returned edits were computed from current text. [Engine lines 335–455][rel-edit-engine], [host preparation][rel-host], [source tests][rel-edit-tests]. |
| Open/closed and unsaved content | Text operations open the target temporarily. Clean/already-saved buffers and closed files are saved; genuinely unsaved buffers are edited but left unsaved, avoiding saving unrelated user work. Clean open buffers are compared with disk in case the watcher missed an external write. Resource overwrite/rename/delete check affected dirty buffers and refuse changes needing those buffers saved. Library/virtual documents are read-only. [Engine normalize/apply/preflight/resource checks][rel-edit-engine]. |
| Preflight/application | Normalizes/validates paths, expands host resource rules, snapshots touched disk/buffers, preflights the sequence on a private copy and checks fingerprints before a real **sequential** apply. This is materially stronger than blindly executing each edit, but not a filesystem transaction or a lock against external processes changing files after the last check. Preview filtering/grouped undo are client facilities, not preservation of LSP annotations. [Engine lines 175–257, 387–490, 561–707][rel-edit-engine], [preview summaries][rel-edit-ui]. |
| Application failure / rollback | Errors before live apply reject without applying the edit to user files. A live-operation or post-apply bookkeeping failure calls `recover`: attempts disk/buffer restoration; success returns the original error. **Rollback itself can fail**: error includes rollback details and retained recovery directory; restored buffers whose disk restore failed are marked dirty. Earlier changes or partial restoration can then remain. Crash recovery markers/snapshot retention and successful grouped undo do not establish unconditional atomicity. Source has injected mid-apply and failed-rollback tests, which were read **but not executed**. [Engine `apply_workspace_edit_inner`, `restore`, `recover` and tests][rel-edit-engine]. |
| What the server learns | `workspace/applyEdit` invokes a boolean host hook (`apply_workspace_edit(...).is_ok()`), replying `applied: false` with only **`failureReason: "edit could not be applied"`** on failure; it does **not** return `failedChange`, detailed rollback state, recovery path, or whether some changes remain. The result schema permits `failedChange`, but this implementation does not populate it. On true, converted edit is queued as applied. “Applied true” is not annotation/option fidelity; “false” is not proof nothing changed. [Hook wiring][rel-project], [handler lines 324–345][rel-handler], [protocol result][rel-apply-protocol]. |
| User action versus command failure | User-initiated workspace-edit/rename paths propagate host errors for UI reporting. Code-action execution applies its edit **before** executing its command; a later command failure does not roll back that earlier successful edit. Server commands can send further applyEdit requests with their own outcomes. Completion and lens command failures use their consumer error/logging paths, not a transaction spanning editor insertions and server commands. [Host `lsp_execute_code_action`][rel-host], [rename UI][rel-rename-ui], [completion][rel-completion-ui], [lens][rel-lens-ui]. |

**Consequence:** the negotiated minimum is **abort**, while the implementation adds content/version guards, preflight and best-effort rollback/undo. Neither "no safeguards" nor "all edits are guaranteed atomic/version-safe" is accurate. The unresolved integration constraint is how accepted Rill operations and tests account for the release's annotation/option loss, unversioned/stale computation window, prepared versus direct closed-file edits, and partial-failure observability. No client patch is approved or proposed here.

### Lifecycle/capability constraints and remaining acceptance questions

- **Sync/configuration:** initialize/initialized, versioned open/full-or-incremental change/save/close, configuration requests/settings notifications, initial workspace folders and folder-query responses exist. `willSave`/`willSaveWaitUntil` are false; no general live `didChangeWorkspaceFolders` path is established. File-watch dynamic registration/relative patterns and rename file filters are supported, but do not define Rill entry/build-context semantics. Minimal registration is an `id`/`name`/extension mapping plus executable/args/options/server definition loaded at startup; the default launcher is stdio. Empty `features` means all available features, not none. Root markers are optional client configuration, not a newly mandated Rill manifest. [Registration docs][rel-language], [launcher][rel-launch], [manager sync/config/watch/reconfigure][rel-manager], [handler][rel-handler].
- **Lifecycle/UI:** graceful shutdown/exit with forced owned-process fallback, manual restart, crash/status UI and bounded crash-restart behavior exist; an externally connected process is not owned/shut down. Release lacks development's explicit expired-build no-restart refinement. Work progress/create/cancel and request cancellation exist; Task UI consumes progress. These do not prove generic partial-result streaming. Most text-document dynamic flags are false, though registration handlers exist (inline completion is advertised dynamic); accepting a registration cannot create a missing method. [Manager lifecycle][rel-manager], [server state][rel-server], [handler][rel-handler], [status UI][rel-server-ui], [task UI][rel-task-ui], [release JSON-RPC cancellation][rel-rpc].
- **Command dispatch is constrained:** generic `execute_command` chooses the first ready attached server listing the command in `executeCommandProvider.commands` (unless an injected command pins a server). Completion/lens/inline UI command paths therefore must not be assumed to preserve the originating server when names overlap; code-action execution has a separate server-aware route. Completion locally handles trigger-suggest/parameter-hints commands and ignores other `editor.*` IDs. Arbitrary editor/native Run/Test commands are not implied by standard `workspace/executeCommand`. [Manager command routing][rel-manager], [host action execution][rel-host], [completion command consumer][rel-completion-ui], [lens consumer][rel-lens-ui].
- **Refresh/messages:** token/hint/lens refresh emits events consumed by UI, diagnostic refresh schedules open-file pulls. `window/showMessageRequest` returns null rather than an interactive choice; `window/showDocument` reports `success: false` and is advertised unsupported. Informational messages are logged; error/warning messages notify. `command/resolve` interactive forms are gopls-specific, not a generic Rill contract. [Handlers][rel-handler], [manager][rel-manager], [availability/refresh][rel-availability].
- **Acceptance questions, not exclusions:** define meaningful Rill semantics for **every used applicable family above**, including nominal enum type edges, overload/function-family call/navigation/rename identity, useful inline completion, actions/lenses/commands, incomplete files, unsaved dependency graphs and entry/target separation. Explicit semantic non-applicability needs evidence/reason; a missing client LSP route is a different classification. The acceptance matrix still needs per-feature delivery owner, expected observable result, tests and protocol/version prerequisites. No row is "passed" by this research.
- **Highest-risk tests still unperformed:** rich related labels/docs/data round trips; Unicode/CRLF positions; late/unversioned push and pull/refresh/clear ordering; lazy symbols with URI-only locations; hierarchy expansion identities; multi-file versioned and versionless rename/actions; closed/dirty/clean buffer edits; stale preview; annotated/resource option edits; preflight failure, live failure and failed rollback; edit-success/command-failure; capability changes, cancellation, crash/restart and multi-server merging. The release baseline is now selected, but the old note's runtime-validation questions are not resolved by selecting it.
