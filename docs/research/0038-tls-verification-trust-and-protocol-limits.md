## 2. Standards currency and protocol profiles. Facts, not a Rill decision

The [RFC Editor index][index] now records [RFC 9846][r9846] (July 2026) as obsoleting RFC 8446. Its §1.2 says this is a backward-compatible TLS 1.3 clarification/tightening, **not TLS 1.4**. Below, RFC 8446 sections preserve the requested baseline; corresponding current sections are supplied where significant. [RFC 9852 §§4-5][r9852] and [RFC 10015 §§2-6][r10015] update RFC 9325; treating its 2022 wording as the entire current policy would be wrong.

| Question | Primary-source finding |
| --- | --- |
| Old versions | RFC 9325 §§3.1.1, 3.1.3 and RFC 8996 §§4–5 prohibit negotiating TLS 1.0/1.1; SSLv2/v3 are also prohibited. No retry-driven weakening to an old version. |
| TLS 1.3 versus 1.2 | RFC 9325 §3.1.1 originally required 1.2 support and recommended/preferred 1.3. RFC 9852 §§4–5 now requires **new protocols** to default to 1.3, permitting 1.2 as an additional non-default deployment option. This is not a blanket declaration that all deployed HTTPS/database TLS 1.2 is insecure or forbidden. Rill's library compatibility floor is still a human choice, distinct from a new application-protocol profile. |
| TLS 1.2 secure profile | RFC 9325 §4.2 recommends ECDHE_RSA/ECDHE_ECDSA with AES-128/256-GCM. §4.1 rejects NULL/RC4/weak suites and discourages CBC without encrypt-then-MAC. RFC 10015 now **prohibits finite-field DH, including ephemeral FFDHE, and static RSA key exchange in TLS 1.2**; static ECDH remains discouraged. This does **not** prohibit RSA signatures/certificates, or TLS 1.3 FFDHE. ChaCha20-Poly1305 suites are separately specified by RFC 7905 §2. |
| TLS 1.2 extra obligations | RFC 9325 §3.5 requires secure-renegotiation signaling (RFC 5746), even when renegotiation itself is not implemented, and support for extended master secret (RFC 7627). Merely setting a minimum version/cipher list does not establish all extension, renegotiation or resumption policy. |
| TLS 1.3 profile | RFC 8446 §§1.2, 4.1.1, 9.1 / RFC 9846 §§1.3, 4.2.1, 9.1: AEAD-only record protection; cipher suite names select AEAD/hash, **not** certificate signatures or key-exchange groups. Absent an overriding application-profile standard, AES-128-GCM-SHA256 is mandatory to implement; AES-256-GCM-SHA384 and ChaCha20-Poly1305-SHA256 are recommended. Separately constrain groups, authentication algorithms and certificate algorithms/strength; RFC 9325 §4.5 requires RSA authentication keys of at least 2048 bits, rejects SHA-1/MD5 and prohibits curves below 224 bits. |
| Crypto lifetime | RFC 9325 §§4.4–4.5 and RFC 9846 §§4.7.3, 5.5 require key-usage limits/update-or-close; the latter tightens the former TLS 1.3 guidance. RFC 9846 §1.2 also forbids cross-connection KeyShare reuse. Listing supported suites does not establish that an integration enforces these rules. |

[RFC 9325][r9325] §§3.2-3.3 also distinguish strict TLS from opportunistic fallback and forbid TLS-level compression. Certificate compression is different (§3.3.1; RFC 8879); if supported, expanded-certificate resource limits still need review. None of these facts authorizes plaintext fallback on authentication failure or implementation of crypto inside Rill.

## 3. What an authenticated connection establishes

To authenticate a server identity, a certificate-based full handshake validates the certificate path, verifies the reference identity and proves key possession and transcript integrity. [RFC 8446][r8446] §§4.4.2.4, 4.4.3-4.4.4 / RFC 9846 §§4.5.1.3, 4.5.2-4.5.3 separate these jobs. Receiving a certificate, negotiating encryption or finishing a provider handshake without enforcing verification is insufficient.

Even correct authentication establishes the configured peer identity under the selected trust policy, **not** that the server application is honest, healthy, authorized for a particular resource, or has received/executed a write. [RFC 9525][r9525] §7.7 explicitly excludes rogue-server/buggy-application detection. TLS record acceptance/flush/close-notify is not an application acknowledgment; higher protocols must define message completion, authorization, unknown outcomes and retry safety. Client-side completion need not mean that the peer has consumed the final handshake flight (RFC 8446 §2).

| Verification component | Requirements and limits |
| --- | --- |
| Chain and trust anchor | RFC 5280 §§6.1.1–6.1.4 take an independently trusted anchor and prospective path as inputs; the peer's supplied root is **not** automatically trusted. Check signatures, CA/basic/path-length constraints, applicable name constraints and critical extensions. Path construction is not the same operation as validating one candidate path. A self-signature is not an authority grant. RFC 6818 §§2, 4 clarifies trust-anchor treatment; do not assume every root field is processed like a path certificate. |
| DNS reference identity | RFC 9525 §§2, 6.1.1–6.3: construct reference identifiers independently of the server certificate from intended/configured application input. Compare DNS-ID to `subjectAltName.dNSName`; **subject CN/RDN fallback is forbidden** (§2). Do not replace the intended hostname with a CNAME, PTR, `getaddrinfo` canonical name or resolved address. Intermediate DNS identifiers are not reference identifiers absent a separately specified authenticated derivation. |
| IP reference identity | RFC 9525 §§6.2, 6.4: direct numeric reference identity matches `subjectAltName.iPAddress` **octet-for-octet**, not textual `dNSName`, CN, a network prefix or a DNS hostname derived from the address. A connection dialed numerically on behalf of a DNS service still verifies that DNS service. IPv6 zone/scope and socket port are routing metadata, not bytes in the certificate IP-ID. |
| IDNA and text | RFC 9525 §§2, 6.3, 7.3 and RFC 9549 §§2.2–2.4: DNS matching uses case-insensitive ASCII A-labels; supported U-label input must be converted under an explicit IDNA policy before comparison. Certificate matching does not solve confusables/UI deception. #34's ASCII hostname acceptance does not validate `xn--` labels or choose TLS IDNA/root-dot normalization. IDNA mapping and the relation between DNS input, identity input and SNI require an explicit boundary, not resolver-canonical identity. |
| Wildcards | RFC 9525 §6.3 permits a supported wildcard only as the **entire left-most label**, exactly one `*`, matching exactly one reference-name label; ignore invalid presented patterns. No partial-label/multi-label/reference-side wildcard interpretation. §7.1 discusses risks; this is not a public-suffix registry algorithm or a guarantee against CA misissuance. |
| Certificate purpose | RFC 5280 §§4.2.1.3, 4.2.1.9–4.2.1.10, 4.2.1.12: apply KU, CA constraints and EKU restrictions; when KU and EKU both exist, use must satisfy both. `serverAuth` and `clientAuth` are different purposes. EKU absence is not universally forbidden by RFC 5280; applications may require its presence. Trusting an issuer does not establish the certificate's permitted purpose. |
| Validity time | RFC 5280 §§4.1.2.5, 6.1.1, 6.1.3: validity is inclusive `notBefore`–`notAfter` evaluated against date/time. A trusted/current wall-time source is a separate dependency from elapsed handshake deadlines. A manual Rill `Clock` does not automatically control provider certificate time; `Instant` is not a timestamp. Do not disable time checks to cope with bad host time. Long-lived connections/resumption need separately stated revalidation policy; initial validation is not continuous certificate monitoring. |
| Revocation | RFC 9325 §7.5 requires a strategy to distrust revoked certificates, while documenting CRL/OCSP scaling, availability, privacy and soft-fail gaps. TLS support for stapled status does not mean it is requested, cryptographically validated, fresh or required. OCSP acceptance/signature/authority/freshness checks are RFC 6960 §3.2; must-staple client processing is RFC 7633 §§4.2.3.1, 4.3.3. RFC 9608 §§2, 4 specifies `noRevAvail`/the revocation-check exception, **not a blanket skip for ordinary certificates**. |

Relevant PKIX updates are not all implemented by every validator: RFC 9549 replaces RFC 8399's internationalization update; RFC 9598 replaces RFC 8398 for internationalized email identities (not a DNS/IP matcher mandate); RFC 9618 §§3-6 replaces exponential policy-tree processing and discusses bounded mitigations. RFC 10007 §4 tightens CRL-issuer KU checking. RFC 9925 §4's unsigned-certificate form must **fail** wherever a path signature must be verified; trust-anchor self-signature treatment is a different context. Provider conformance to these updates remains a validation question, not implied by a "PKIX" label. [Sources: RFC 5280 update list][index].

## 4. SNI and ALPN are separate from verification

- SNI uses the name to route a connection. RFC 6066 §3 specifies ASCII DNS hostname/A-labels **without terminal dot** and forbids literal IPv4/IPv6 in `host_name`. It assists routing/certificate selection; it does not authenticate the name. DNS hostname verification remains necessary with or without SNI. RFC 9325 §3.7 updates the older unknown-name advice: servers **should fail** an unrecognized name rather than continue with a default service. Ordinary SNI is not a confidentiality guarantee. No ECH feature/profile is selected here. [RFC 6066][r6066], [RFC 9325][r9325].
- ALPN negotiates an application protocol. RFC 7301 §§3.1-3.2 carries nonempty opaque identifiers of 1-255 bytes; the server selects one offered protocol, or fails `no_application_protocol` if there is no overlap. ALPN is per connection, including resumed connections (§3.1). In TLS 1.3 its selection is in EncryptedExtensions (RFC 8446 §4.3.1 / RFC 9846 §4.4.1). RFC 9325 §3.8 stresses enforcement against cross-protocol attacks. [RFC 7301][r7301].
- A peer omitting ALPN is different from a negotiated mismatch: the **application profile** decides whether absence is fatal or a defined legacy mode. TLS/ALPN success is not a license to parse a different application protocol. RFC 9525 §§2, 6.5 also distinguishes unrestricted DNS/IP identity from service-restricted URI/SRV identity; supporting a DNS matcher does not implement every service identity type.

- **Apple Security-61901.120.67**, commit `97c3a4296c1ea06b0fe1877a7e616aa84450b5b2`: public `SecPolicy.h`/`SecTrust.h` source contracts. This is a **trust evaluator**, not evidence for a complete Network.framework/SecureTransport TLS backend or a tested macOS release/security-update state.

### OpenSSL 3.5.9

1. **Default is `SSL_VERIFY_NONE`.** In client mode the handshake continues despite certificate-validation failure; in server mode no client certificate is requested. Enforce peer verification explicitly. Default verification callback returns the preverification decision, but only an enforcing mode aborts on it; an always-success callback defeats authentication. Mandatory mTLS needs `SSL_VERIFY_PEER | SSL_VERIFY_FAIL_IF_NO_PEER_CERT`, not just `PEER`. [Verification manual][ossl-verify], [`SSL_CTX_new_ex` source][ossl-lib].
2. **Identity is not automatic.** Configure nonempty DNS/IP reference input (`SSL_set1_host`) and SNI separately. Default hostname flags permit **partial-label wildcards** and CN fallback if an applicable SAN is absent: a concrete mismatch with RFC 9525. `X509_CHECK_FLAG_NEVER_CHECK_SUBJECT` and `NO_PARTIAL_WILDCARDS` address those two defaults; this is not a complete assertion of RFC 9525 conformance for every input/flag combination. [Host setup][ossl-host], [matching flags][ossl-match].
3. A fresh context creates an `X509_STORE`; it does not thereby load OS roots. Trust loading is separate. `SSL_CTX_set_default_verify_paths` uses compiled locations overridable by `SSL_CERT_FILE`/`SSL_CERT_DIR`; **missing default locations can still return success**. A directory lookup may be lazy, unlike loading a PEM CAfile. This is not automatic macOS Keychain evaluation, an immutable root snapshot, or proof that usable anchors exist. [Initialization][ossl-lib], [trust-loading manual][ossl-roots].
4. When enabled, TLS verification chooses server/client purpose and normally checks current system time; general X.509 verification and TLS context defaults must not be conflated. CRL checks need flags and CRLs; built-in defaults do not provide complete online revocation. Requesting stapling additionally needs an application status callback to judge the response. "Has OCSP APIs" is not automatic OCSP/must-staple enforcement. [Validation/purpose][ossl-validation], [default flags][ossl-vpm], [CRL flags][ossl-param], [stapling][ossl-status].
5. Default TLS≤1.2 cipher expression is `ALL:!COMPLEMENTOFDEFAULT:!eNULL`, **not** an ECDHE+AEAD allow-list. Default TLS 1.3 suites are AES-256-GCM, ChaCha20-Poly1305, AES-128-GCM; the two lists are separate. Security-level default is compile-time configurable (otherwise level 2); a level alone does not implement the complete profile above. Explicit settings, configured modules and vendor builds matter. [Cipher source][ossl-ciphers], [security-level manual][ossl-level].
6. `SSL_get_verify_result == X509_V_OK` can mean **no certificate was presented**; session reuse restores the prior result. Never turn that single observation into fresh verified identity. Default TLS 1.3 server behavior sends two tickets; early-data acceptance is disabled unless configured. [Result semantics][ossl-result], [initialization][ossl-lib], [early-data manual][ossl-early].

### Rustls 0.23.46 / webpki 0.103.17

1. The normal client builder requires an explicit root-store/verifier choice. `with_root_certificates` installs webpki verification: chain/signatures, supplied verification time, server EKU and DNS/IP reference identity; handshake-signature checks are additional verifier operations. webpki DNS matching reads SAN, not CN, and supports whole-left-label wildcards; IP uses IP SAN. Unsupported name types are not automatically URI/SRV verification. [Client builder][rustls-client], [server verifier][rustls-verifier], [verification helpers][rustls-verify], [DNS matching][webpki-dns], [subject-name dispatch][webpki-subject].
2. **Normal root-store shortcut performs no revocation checking; supplied OCSP is logged as unvalidated, not verified.** CRL-enabled builders default to chain checking (excluding anchor) and reject unknown status, but **ignore CRL expiration unless `enforce_revocation_expiration` is requested**. No CRLs means no revocation checking, regardless of the unknown-status setting. These are substantive gaps, not equivalent to an OS/browser trust evaluation. [Server verifier][rustls-verifier], [client-certificate verifier][rustls-client-verifier].
3. **KU versus EKU is a real limitation:** webpki's `check_issuer_independent_properties` explicitly ignores certificate `KeyUsage` for certificate validation; it does check basic constraints, validity and EKU. Default server/client EKU checks require the appropriate purpose **if EKU is present**, not mandatory extension presence. Do not describe this as enforcing every RFC 5280 purpose restriction. It also rejects directory-name constraints rather than implementing their general matching. [Validation source][webpki-validation], [name-constraint source][webpki-constraints].
4. Default Cargo features include TLS 1.2 and AWS-LC cryptography; default versions are 1.3 and feature-enabled 1.2. The inspected AWS-LC suite list is TLS 1.3 AEAD and TLS 1.2 ECDHE+AES-GCM/ChaCha20-Poly1305 (feature/FIPS-dependent). Non-FIPS client `require_ems` defaults false: **supporting EMS is not requiring it for every peer**. These defaults still do not choose Rill policy or authorize an entropy/provider hook. [Cargo features][rustls-cargo], [versions][rustls-versions], [suite source][rustls-suites], [client configuration][rustls-client-config].
5. Client defaults enable SNI, leave ALPN empty, disable early data, key logging and secret extraction, and enable an in-memory resumption store for up to 256 server names under `std`. Client credentials are an explicit builder choice, not inferred from roots. Server builder separately chooses no client auth or a verifier: `WebPkiClientVerifier` requires authentication by default; `allow_unauthenticated` permits missing certificates, whereas `no_client_auth` does not request them. Server defaults include stateful session storage, two TLS 1.3 tickets and zero accepted early data. [Client builder/configuration][rustls-client], [resumption configuration][rustls-client-config], [server builder][rustls-server], [client verifier][rustls-client-verifier].

### "Native roots" is not "native validation"

`rustls-native-certs` returns **certificates plus independent loading errors**, not an all-or-nothing trust-verification result. Its normal entry point reads ambient `SSL_CERT_FILE`/`SSL_CERT_DIR`; configured locations replace platform loading. On macOS it enumerates user/admin/system settings, applies precedence and extracts TrustRoot/TrustAsRoot certificates; it does **not** call SecTrust for each connection. A DER-root set alone cannot reproduce per-host, purpose or application constraints. Nor does it reproduce all distrust metadata, platform revocation/CT policy or dynamic policy updates. Explicit failure/partial-store acceptance, root provenance, replacement-versus-addition, reload and ambient-environment rules remain choices. [Loader][native-lib], [macOS extraction][native-macos].

Apple's `SecPolicyCreateSSL(server, hostname)` distinguishes server/client purpose and only requires hostname matching when the hostname is supplied. `SecTrust` SSL-policy evaluation **permits missing-intermediate network fetches by default**; evaluation can block for network fetch/revocation. The revocation policy is best-attempt unless positive-response enforcement is selected. `SecTrustSetAnchorCertificates` alone restricts trust to those anchors; adding system anchors back requires the separate `...Only(false)` setting. Thus even platform evaluation needs explicit name/anchor/network/revocation policy and lifecycle review; these headers do not establish exact hostname/IDNA/CT behavior for every supported OS. [Policy header][apple-policy], [trust header][apple-trust].

Server authentication and mTLS need separate anchor scopes and purposes. Each also needs a policy for missing client certificates, certificate/key ownership and application authorization. RFC 9525 §1.4.2 excludes client/end-user identity matching: a valid client chain is not an account/role authorization algorithm. TLS 1.3 permits an empty client certificate response, with server acceptance or rejection policy (RFC 8446 §4.4.2.4 / RFC 9846 §4.5.1.3). Do not reuse DNS-server identity rules for arbitrary client subjects.

## 6. Hostile input, records, EOF and ongoing control traffic

- **Bounds differ by layer.** RFC 8446 / RFC 9846 §§5.1-5.2 limit plaintext record fragments to 2^14 bytes and TLS 1.3 ciphertext to 2^14+256, excluding the five-byte header. A handshake message has a 24-bit length and may span records; the Certificate list has its own 24-bit length (§4.4.2 / current §4.5.1). Record bounds therefore do not bound a chain, accumulated flights, path search, pending plaintext or total connection work. RFC 8449 §§1, 4's `record_size_limit` addresses protected-record size, **not all handshake/resource bounds**.
- Providers impose concrete limits, but these do not prove a global memory or time bound. OpenSSL's default certificate-list cap is **102400 bytes** and default verification depth is **100 intermediates** (`x509_vpm.c`, `SSL_CTX_set_verify`); the [max-cert-list manual][ossl-maxcert]'s parenthetical "10" is inconsistent with those sources. Rustls caps joined handshake messages at `0xffff` bytes; `set_buffer_limit` affects send plaintext/TLS queues, **not all memory**. Its default received-plaintext limit is 16 KiB and send-buffer limits 64 KiB. webpki caps path intermediates at six and budgets 100 signature checks, 200000 chain-building calls and 250000 name-constraint comparisons. [OpenSSL constants][ossl-constants], [verification][ossl-verify], [parameters][ossl-vpm], [Rustls deframer][rustls-deframer], [buffers][rustls-conn], [state][rustls-state], [webpki budgets][webpki-validation].
- Future limits must account for raw ciphertext, authenticated plaintext, handshake/certificate reassembly and decompression, certificate count/size/graph shape, trust-store parsing, signature/path-search work, output/backpressure, repeated empty/control records and concurrent handshakes. Bounded individual records do not prevent an infinite slow/drip or control-only peer. RFC 9618 §§3-6 is a specific warning against assuming certificate policy evaluation is naturally linear. Do not expose unverified record fragments as authenticated plaintext (RFC 8449 §1).
- **TCP EOF is not authenticated TLS EOF.** RFC 8446 / RFC 9846 §6.1: transport close without preceding close-notify cannot establish that all sent data arrived. Drain already authenticated plaintext before reporting clean closure/truncation as appropriate; reset/fatal alerts are not clean EOF. Rustls returns `UnexpectedEof` on unclean EOF once pending data is read; OpenSSL 3.x reports `SSL_R_UNEXPECTED_EOF_WHILE_READING`, unless the application enables the explicitly weakening ignore-unexpected-EOF option. [Rustls reader][rustls-conn], [OpenSSL error semantics][ossl-error].
- Half-close behavior depends on the TLS version. TLS 1.3 close-notify closes the sender's TLS write side without itself closing its read side. TLS 1.2's RFC 5246 §7.2.1 requires the recipient to respond/close immediately and discard pending writes. Neither raw FIN nor raw write-half disposal substitutes for a generated/flushed TLS alert. Alert enqueue, transport write completion, peer close-notify receipt and final native release are separate events. Application framing may detect a complete message despite later truncation, but that does not retroactively make TLS closure clean or prove delivery.
- Handshake completion is **not cessation of TLS control I/O**. RFC 8446 §§4.6.1-4.6.3 / RFC 9846 §§4.7.1-4.7.3 permit tickets, negotiated post-handshake authentication and key updates; requested key updates can require a response before more application data. Renegotiation is TLS 1.2-only, not a TLS 1.3 feature. Rill must decide which optional mechanisms to enable/reject, not discard unknown control traffic or call it application EOF.
- A provider may accept plaintext into a queue **before the handshake completes** (Rustls `Writer` does so); that is not verified-channel publication or peer delivery. Rill's eventual admission/prefix policy must distinguish accepted plaintext from emitted ciphertext and handshake state, rather than expose a provider byte count unchanged. [Rustls writer][rustls-conn].
- OpenSSL `SSL_read` can write control traffic; read/write retries can require either direction. `SSL_get_error` must inspect the result/error queue **on the same native thread, without intervening OpenSSL calls**, with queue preconditions satisfied. This demands a narrow internal scheduling/error-capture design, **not public thread pinning**. Shared TLS state and emitted control traffic invalidate any inference that TCP owning halves permit independently operated TLS halves. [Read manual][ossl-read], [error manual][ossl-error].

## 7. Tickets, resumption, replay and secret/context ownership

RFC 8446 §§2.2-2.3, 4.6.1, 8 / RFC 9846 §§2.2-2.3, 4.7.1, 8 distinguish ordinary resumption from **0-RTT**. A resumed PSK handshake may not send or freshly validate certificates; it authenticates continuity of previously established secret state. Both OpenSSL (saved verification result) and Rustls TLS 1.3 (explicit "don't reverify" resumed path) implement that distinction. Certificate expiry, revocation or changed trust policy cannot be assumed freshly enforced on every resumed connection. [OpenSSL result][ossl-result], [Rustls resumed path][rustls-resume].

- Tickets/PSKs, session caches, traffic secrets, long-term private keys, ticket-encryption keys, retained certificate chains and verification configuration have different owners/lifetimes. RFC 9846 §4.7.1 limits ticket use to at most seven days and recommends limiting total inherited keying-material lifetime; RFC 9325 §3.4 requires protected resumption state and ticket-key rotation/destruction. Session storage cannot be casually copied into an unrelated trust/identity/client-auth context.
- Rustls keys client sessions by server name and requires shared stores to use the **same verifier and client-credential resolver identities**; its docs explain the insecure-to-secure configuration confusion otherwise possible. OpenSSL requires server session-id contexts to separate application contexts, with specific client-auth resumption consequences. These mechanisms are facts to preserve/review, not permission for a public cache/provider hook. [Rustls configuration][rustls-client-config], [OpenSSL session-id context][ossl-context].
- Context segregation/reload/invalidation choices must cover intended name, SNI, current ALPN selection, trust-policy generation, application protocol/tenant and client-auth policy. RFC 7301 §3.1 renegotiates ALPN per connection; early-data acceptance has stricter saved-parameter rules (RFC 8446 §4.2.10 / RFC 9846 §4.3.10). Sharing tickets across servers changes the security boundary (RFC 9325 §3.9).
- **0-RTT has no inherent cross-connection replay protection or forward secrecy.** RFC 8446 §§2.3, 8 and Appendix E.5 / RFC 9846 equivalents describe replay and retry duplication, including distributed-server limits. RFC 9325 §3.10 says applications must avoid early data absent an explicit safe application-protocol specification. OpenSSL's optional single-use-cache defense has deployment/external-PSK limits; it is not an end-to-end exactly-once guarantee. Ordinary resumption does not itself require early data. [OpenSSL early-data/replay manual][ossl-early].
- Cancellation does not erase already emitted handshakes/records, un-send a client certificate, revoke a ticket already delivered, erase all provider copies or prove application nonexecution. Keep secret/configuration owners and native borrowers alive through safe completion/abort; define log/export/persistence/zeroization policies separately. No universal secure-memory/zeroization promise is established by source reading or #37.

## 8. Open choices and future validation (all NOT RUN)

No recommendation below is accepted policy. The v0 scope still needs a choice between client-only support and server/mTLS support, and between TLS 1.3-only support and reviewed TLS 1.2 compatibility. The exact version, suite, group and signature floor remains open.

Identity decisions include DNS/IP input, A-label and root-dot rules, wildcard support, required ALPN and behavior for unknown SNI. Verification decisions include trust sources, custom anchors, addition versus replacement, refresh, purpose strictness, wall-time failure behavior, revocation availability/freshness and network policy.

Other choices concern certificate/key formats and ownership, resumption/context lifetime, optional post-handshake features and resource bounds. EOF, shutdown, disposal, cancellation and connection reuse also need defined behavior. No insecure or testing override is authorized here.

Future evidence must use the actual pinned provider/build/OS plus the proposed narrow integration, not merely these notes:

1. Verification fixtures: unknown/missing anchor/intermediate, path alternatives/cycles/depth, malformed DER/critical extensions, CA/path/name constraints, KU/EKU conflicts, expired/not-yet-valid boundaries and failed wall-time acquisition; revoked/unknown/stale/missing CRL/OCSP, must-staple and `noRevAvail` policy.
2.
