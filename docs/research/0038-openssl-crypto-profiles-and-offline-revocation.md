## 1. Current standards: implementation obligations are not optional profile preferences

- [RFC 9846][R13] (July 2026) **obsoletes 8446** without changing the TLS 1.3 wire version; §§1.2, 4.3.8, 4.7.3, 5.5 tighten key-share reuse, key updates and usage limits. [RFC 9852][RNEW] §§4-5 updates RFC 9325: new protocols MUST default to/support TLS 1.3; TLS 1.2 MAY be an additional non-default option. [RFC 10015][RKX] §§2-6 prohibits static RSA and finite-field DH, including ephemeral FFDHE, in TLS 1.2; RSA **signatures** and TLS 1.3 FFDHE are not thereby prohibited. [RFC 9851](https://www.rfc-editor.org/rfc/rfc9851.html), referenced by 9852 §3, records TLS 1.2 feature freeze, not a promise of PQ upgrades there.
- **Do not silently omit current mandatory interoperability:** absent an overriding **application-profile standard**, RFC 9846 §9.1 requires `TLS_AES_128_GCM_SHA256`, P-256 key exchange, `rsa_pkcs1_sha256` **for certificates**, `rsa_pss_rsae_sha256` for CertificateVerify/certificates, and `ecdsa_secp256r1_sha256`. AES-256-GCM and ChaCha20-Poly1305 suites and X25519 are SHOULDs. A private library allow-list is not automatically such an overriding standard; an RSA-PSS-only *certificate-chain* policy or X25519-only group policy omits MTI capabilities even if its primitives are sound.
- RFC 9846 §9.2 additionally makes `supported_versions`, `cookie`, `signature_algorithms`, **`signature_algorithms_cert`**, `supported_groups`, `key_share`, and SNI mandatory to implement, with use requirements conditional on the feature. This is distinct from enabling optional PSKs, PHA, compression or OCSP. §9.3 requires extensibility-compatible ignoring of unrecognized ClientHello offers/appropriate unrecognized extensions; "disable optional features" does not mean reject every unknown offer or discard mandatory control messages.
- Current [IANA TLS registry][IANA] and [RFC 9847](https://www.rfc-editor.org/rfc/rfc9847.html) §3 distinguish **Y** (recommended), **N** (not necessarily flawed; limited applicability or no consensus), **D** (discouraged; consult normative reference). Registration is neither MTI status nor evidence a build implements a feature. [RFC 10024][RPQ] (August 2026) standardizes the three ECDHE/ML-KEM hybrids below; calling all OpenSSL 3.5 hybrid groups "unstandardized drafts" is now wrong. Its construction references informational [RFC 9954](https://www.rfc-editor.org/rfc/rfc9954.html), not an obligation to deploy PQ everywhere.

These are explicit modern certificate-authenticated suite sets whose inclusion/order is still a choice. TLS 1.3 suites select **AEAD + transcript/KDF hash**, not authentication or group; TLS 1.2 names also select ECDHE and RSA/ECDSA authentication. All nine entries below have IANA Recommended=Y. **3.5.9 defaults, not Rill policy:** `TLS_DEFAULT_GROUP_LIST` is `?*X25519MLKEM768 / ?*X25519:?secp256r1 / ?X448:?secp384r1:?secp521r1 / ?ffdhe2048:?ffdhe3072`. `*` predicts a client key share; `/` separates server preference tuples; `:` groups algorithms treated as comparable. Thus hybrid and X25519 shares are predicted, hybrid is in the first server tuple, and additional groups beyond the narrow inventories above remain available by default. `SSL_CTX_set1_groups_list` can express different tuples; merely putting PQ first in a single comparable tuple is not a require-PQ guarantee. A classical-only list is technically configurable but **explicitly excludes a maintained standardized PQ option**, not an upstream capability gap. Final wire-format conformance, HRR behavior, CPU/build availability and failure policy still need validation. ([O-T1] `TLS_DEFAULT_GROUP_LIST`, [O-GROUP] DESCRIPTION/HISTORY, [O-CAP]; [RPQ])

**Signatures require three separate inventories: handshake, chain, revocation-object.** Concrete classical TLS tokens are `ecdsa_secp256r1_sha256`, optional `ecdsa_secp384r1_sha384`/`ecdsa_secp521r1_sha512`, `rsa_pss_rsae_sha256/384/512` (rsaEncryption SPKI), `rsa_pss_pss_sha256/384/512` (RSASSA-PSS SPKI), `ed25519`, `ed448`, and `rsa_pkcs1_sha256/384/512`. RFC 9846 §§4.3.3,4.5.2 normally excludes PKCS#1 v1.5 from **TLS 1.3 CertificateVerify**, not from certificates; PSS salt/parameters and ECDSA scheme/curve restrictions matter. TLS 1.2 can use RSA PKCS#1 signatures with ECDHE without static RSA key exchange. [RFC 9963](https://www.rfc-editor.org/rfc/rfc9963.html) defines optional distinct `rsa_pkcs1_*_legacy` client-auth schemes; this does not make ordinary `rsa_pkcs1_sha256` a 1.3 CertificateVerify scheme. ([O-SIG], [O-T1] `sigalg_lookup_tbl` / `find_sig_alg`, [IANA])

**New PQ authentication status:** 3.5.9 builtin provider capabilities advertise `mldsa44/65/87` (`0904/0905/0906`, TLS≥1.3) and libssl discovers them; not merely libcrypto primitives. IANA currently lists N with reference `RFC-ietf-tls-mldsa-06`, not a numbered TLS RFC. [RFC 9881](https://www.rfc-editor.org/rfc/rfc9881.html) standardizes ML-DSA X.509/CRL identifiers separately; [RFC 10073](https://www.rfc-editor.org/rfc/rfc10073.html) now standardizes composite ML-DSA for PKIX (November 2026 index entry), not mandatory TLS interoperability or proof that 3.5.9 implements those composite algorithms. These optional capabilities/statuses must not be confused with the classical MTI set. ([O-CAP] `param_sigalg_list`, [O-T1] `ssl_load_sigalgs`; [IANA], [INDEX])

**Strength is not selected by suite names.** RFC 9325 §4.5 requires RSA authentication modulus≥2048, excludes curves<224 bits and SHA-1/MD5 signatures. OpenSSL default security **level 2** means 112-bit floor (RSA≥2048, EC≥224); level 3 means 128-bit (RSA≥3072, EC≥256), disables non-forward-secret suites/tickets; level 4 means 192-bit (RSA≥7680, EC≥384) and therefore filters P-256/X25519/AES-128; level 5 is 256-bit. Level 1 already rejects SHA-1/MD5 signatures in this pin. Floors intersect explicit lists and provider properties; filtering an MTI capability needs recognition, not a claim that a stricter level is unconditionally more conformant. TLS `ssl_verify_internal` sets chain `auth_level` from TLS security level; standalone X.509/OCSP stores do not automatically inherit a TLS connection's settings. `check_auth_level` checks every certificate key but omits the anchor's signature-strength check. Hybrid group capability strength is reported from the ML-KEM component (768→192 bits, 1024→256), not simply the classical curve's strength; this does not make all authentication/record protection equally strong. Neither sigalg lists nor chain `auth_level` alone establish a named algorithm allow-list for CRLs/OCSP responses. ([O-LEVEL], [O-CERT], [O-VFY], [O-CAP], [O-MLKEM])

**Concrete signature-control gap:** `SSL_CTX_set1_sigalgs_list` plus client-auth counterpart controls TLS advertisements/selection, not a complete independent peer-chain signature algorithm policy. `extensions.c` accepts `signature_algorithms_cert` but explicitly says **"We do not generate signature_algorithms_cert at present"**. RFC 9846 §9.2's current implementation requirement cannot be silently dropped; assess this receive-only implementation and absence of separate generation/control against the required application profile. A strict SHA-2/PSS/ECDSA/EdDSA chain inventory needs explicit provider-backed enforcement/validation, while retaining mandatory RSA-PKCS1-SHA256 certificate support unless a real overriding profile applies. ([O-EXT], [O-SIG], [O-T1])

## 4. Offline CRLs: what checking means and what it does not

An offline profile can consume retained application-supplied revocation objects without fetching. It still needs defined coverage, age, supported forms, update provenance and failure behavior. RFC 9325 §7.5 requires a strategy to distrust revoked certificates; "no online I/O" alone is not that strategy, nor does an immutable snapshot stay fresh indefinitely.

| Area | Source-established behavior / additional obligation |
| --- | --- |
| Loading/formats | `d2i_X509_CRL` decodes ASN.1 DER **and BER forms**; `PEM_read_bio_X509_CRL` supports PEM `X509 CRL`; `X509_STORE_add_crl` retains an object reference. Parse success is not signature/status validity or strict-DER/full-input consumption: `d2i` advances the input pointer. Public format choice, exact consumption, duplicate handling, object/entry/byte limits and immutable snapshot ownership remain undecided. ([O-PARSE], [O-PEM], [O-STORE], [O-XCRL]) |
| Leaf versus chain | `X509_V_FLAG_CRL_CHECK` checks leaf; `CRL_CHECK_ALL` only works **with** CRL_CHECK. `check_revocation` iterates the actual built chain **including final anchor**, not “all except roots”. Partial-chain termination therefore changes coverage; checking a non-self-issued final anchor can require an unavailable CRL issuer (`UNABLE_TO_GET_CRL_ISSUER`). Decide/document scope rather than assuming ALL means browser-style coverage. ([O-PARAM], [O-VFY] `check_revocation`/`check_crl`) |

## 5. Stapled OCSP is transport of evidence, not automatic validation

**Request/availability:** client `SSL_CTX_set_tlsext_status_type(...,TLSEXT_STATUSTYPE_ocsp)` requests status; `SSL_get_tlsext_status_ocsp_resp` returns bytes or −1/NULL. A private `SSL_CTX_set_tlsext_status_cb` can reject unacceptable/missing status (client 0=failure, negative=internal error, positive=accept). It does not validate it automatically. Server callbacks merely choose/supply response bytes. No public Rill callback or permission to override chain failure follows. ([O-STATUS]; [O-EXC]; [O-CLNT] `tls_process_initial_server_flight`)

A private validation layer, if stapling is in scope, owes **all** these checks, not "callback installed":

1. Bounded, complete decoding; successful outer response and supported BasicOCSPResponse; supported version/critical extensions; authenticated response signature and approved signature/key strength. `OCSP_basic_verify` verifies signature and signer path/authority, **not freshness, target status or all application restrictions**. Do not enable NOSIGS/NOVERIFY/NOCHECKS/TRUSTOTHER bypasses. Configure its store/time/authentication/purpose deliberately: it creates its own store context, selects OCSP-helper purpose/trust, and does not inherit the connection's per-SSL parameters. ([O-OCSP], [O-OVFY])
2. Match **CertID** issuer name hash, issuer key hash and serial for the certificate/actual issuer; require an applicable authoritative `GOOD`, distinguish `REVOKED`, `UNKNOWN`, no matching entry and responder errors. Issuer CA or directly delegated responder (`id-kp-OCSPSigning`, same issuing key), or separately scoped explicit responder trust, are distinct authorization cases. A chain to some TLS anchor is not itself OCSP authority. `OCSP_basic_verify` includes delegation/issuer checks and optional explicit OCSP trust fallback; `ocsp-nocheck` clears CRL checking for responder validation, requiring explicit supported-policy review. ([RFC 6960][ROCSP] §§3.2,4.1.1,4.2.2.2; [O-OVFY])
3. Fresh thisUpdate/nextUpdate, producedAt semantics and signer-certificate validity at checked wall time; explicit missing-nextUpdate/max-age/skew policy. **`OCSP_check_validity` calls unchecked `time(&t_now)` internally**, accepts NULL nextUpdate, and uses maxsec only if configured; it is not Q19's checked explicit timestamp path. Its RETURN VALUES prose misdescribes maxsec; `ocsp_cl.c` actually limits thisUpdate age. Equivalent provider-backed explicit-time checks/additional enforcement remain owed, without disabling native certificate checks. ([O-OCL], [O-OCSP]; [ROCSP] §§2.4,3.2,4.2.2.1)
4. Nonce binding **when a nonce-bearing request was actually made**; ordinary cached staples need not contain a client nonce and do not gain per-handshake freshness from being stapled. RFC 9654 §2.1 (obsoletes 8954) requires requester nonce≥32 octets, permitted range 1-128; OpenSSL nonce helper's default is 16. `OCSP_check_nonce` returns several different positive cases, and −1 means requested nonce missing, not a cryptographic mismatch. Do not blanket-require random nonces on offline pre-produced staples or treat any nonzero return as matched request evidence. ([RFC 9654](https://www.rfc-editor.org/rfc/rfc9654.html), [O-NONCE]; [ROCSP] §4.4.1)

**Provider support limits:** TLS 1.3 permits per-certificate status and client-certificate status requests (RFC 9846 §4.5.1.2); 3.5.9 `tls_parse_stoc_status_request` **ignores chainidx≠0**, server construction sends only index 0, and CertificateRequest/client-certificate status is not implemented on these paths. Thus leaf stapling is not intermediate/mTLS revocation coverage. Missing staple, invalid staple and no supported mechanism must remain distinguishable where evidence exists. ([O-EXC], [O-EXS])

**Must-staple / unsupported features:** RFC 7633 §§4.2.3.1,4.3.3 differentiates SHOULD reject inconsistent status_request, alternative validation cases, and MUST enforce features in the intersection of ClientHello and TLS Feature. It is not honest enforcement to avoid requesting status and silently ignore a noncritical TLS Feature extension. A **deliberately narrower CRL-only profile can reject certificates requiring stapling or other unhandled revocation/TLS features**, including unknown TLS Feature values, rather than claim to satisfy them with CRLs. This is an availability/interoperability restriction, not implementation of stapling or a forced profile choice. It needs explicit detection beyond strict-X509's unknown-*critical*-extension check, for received chains and supplied server credentials. ([RFEATURE], [O-PURP])

**`noRevAvail` is not "serial absent ⇒ good":** RFC 9608 §§2-4 defines noncritical OID **2.5.29.56**, DER NULL; forbids CA use and conflicts with CRLDP/freshestCRL/OCSP-AIA; violations MUST invalidate; understood valid use skips revocation. Pinned `check_revocation`/extension cache does not implement that general exception/conflict policy. An ordinary CRL could omit such a certificate forever. A profile can explicitly reject noRevAvail/unsupported revocation exceptions; if accepting it, implement the RFC exception and conflicts rather than requiring nonexistent status or calling it CRL-verified. `ocsp-nocheck` has specific responder semantics, not permission to skip arbitrary TLS leaf checks. ([RNOREV], [O-VFY], [O-PURP], [O-OVFY])

## 6. No hidden fetching: reachable calls, not a magic offline flag

Default X.509 verification consumes supplied chains/store lookups; ([O-PARAM] BUGS) explicitly says it **does not download CRLDP CRLs**. Inspected `build_chain`/`get1_issuer` and `check_revocation` do not perform automatic AIA-issuer or OCSP HTTP retrieval. Merely parsing AIA/CRLDP or requesting a peer staple is not fetching their URLs. This claim is scoped to the pinned builtin paths, not arbitrary lookup/provider/application callbacks.

Actual fetch-capable paths include `X509_load_http`/`X509_CRL_load_http` → `OSSL_HTTP_get` (connects when BIOs not supplied); `OCSP_sendreq_bio`/request-context exchange performs HTTP over its supplied BIO; application helper `store_setup_crl_download` installs `crls_http_cb` through **`X509_STORE_set_lookup_crls_cb`**, then follows CRLDP/freshestCRL with `X509_CRL_load_http`. That helper is **apps code**, not a libssl default. Store `get_issuer`/`get_crl`/lookup/check-revocation callbacks can introduce I/O; `X509_LOOKUP_store` invokes `OSSL_STORE_open_ex/load` for configured URIs, and hash-directory lookup is lazy filesystem I/O. A future AIA callback can fetch too. ([O-FETCH], [O-HTTP], [O-OHTTP], [O-LOOKUP], [O-HOOK])

**Offline-policy enforcement owed:** populate only retained in-memory certs/CRLs; no default paths/CAstore/URI/lazy-directory loaders, network lookup/download callbacks, OCSP-request HTTP calls, ambient modules/config, or implicit fallback fetches. A private status callback, if used, validates already-received bytes only. Reviewed `no-http`/`no-sock` builds can remove builtin mechanisms but do not constrain arbitrary callback/provider code or prove all ambient I/O absent. No single per-SSL "disable AIA+CRLDP+OCSP networking" flag was established; exact linked-call/build audit and hostile URL/lookup reachability tests remain owed. Source-research HTTP retrieval here is not a TLS runtime policy experiment.

## 7. Anchor model, strict X.509 and purpose are independent choices

| Question | Pinned behavior / consequence |
| --- | --- |
| Self-signed CA roots only? | App anchor grant is independent of self-signature. For an explicitly root-only profile, admission must check self-issued **and cryptographically self-signed**, CA/basic constraints and intended KU/EKU restrictions, and reject unsupported AUX trust grants/forms. `X509_self_signed(cert,1)` can verify signature; subject==issuer alone cannot. `CHECK_SS_SIGNATURE` requests final self-signature checking during path validation but does not define root-only admission or grant trust. Default omits that check; enabling it can reject old/unsupported root self-signatures without adding trust security. ([O-VFY], [O-PARAM], [O-VALIDATE]) |
| Partial chains / explicit trust | `PARTIAL_CHAIN` makes store intermediates terminal anchors and shortens the built path. Leaving it clear is **not alone root-only**: positive AUX purpose trust can anchor a non-self-signed certificate; a store-provided self-signed leaf can also need separate exclusion. Ordinary self-signed certificates without AUX are compatibility-trusted for all uses inside that store. `check_purpose` can let positive AUX trust **trump certificate purpose restrictions** before `X509_check_purpose`; this is not simply another embedded EKU. Keep app grants/purpose-separated stores distinct from peer untrusted intermediates. Root-only versus explicitly granted intermediates is still a choice, with revocation-coverage consequences above. ([O-VALIDATE] Trust Anchors/Path Building, [O-PARAM]) |
| CA / KU / EKU | Strict flags add critical CA basicConstraints, CA KU-presence/keyCertSign, path-length, AKID/SKID, empty-name/SAN and signature-algorithm-consistency checks, with conditions such as chain length>1. TLS purpose checks accept **absent EKU**, do not require explicit serverAuth/clientAuth extension presence. Pinned `check_purpose_ssl_server` accepts serverAuth **or legacy SGC**, client checks clientAuth; generic purpose KU permits several bits and is not itself proof the selected signing key permits digitalSignature. TLS signature-use checks and any stricter credential admission must be audited separately. `anyExtendedKeyUsage` alone is not a replacement for these source functions' specific TLS EKU tests. ([O-PURP], [O-VFY], [O-VALIDATE]) |
| Anchor fields / name constraints | RFC 5280 §6.1.1's abstract trust anchor is outside the prospective path; OpenSSL represents it as a certificate and checks anchor validity time, applicable CA/purpose extensions including EKU subject to the AUX trust override above, and uses name constraints along the built chain (`check_name_constraints`/`NAME_CONSTRAINTS_check`). Therefore not every external anchor policy equals “run normal RFC path rules over root DER”. Retain/reject external restrictions as already accepted; neither CN-disabled matching nor root self-signature checking establishes complete DNS/IP/name-constraint conformance. ([RPKIX]; [O-VFY], [O-VALIDATE] Extended Key Usage) |
| Strict ≠ complete RFC conformance / bounded work | STRICT does not enable all certificate-policy processing (`POLICY_CHECK` is separate), fix RFC 10007/noRevAvail/stapling gaps, guarantee all DER/version/duplicate-extension rules or impose global CPU/memory/path-search bounds. Unknown critical certificates/CRLs reject unless IGNORE_CRITICAL; unsupported *noncritical* revocation features require explicit admission logic. RFC 9618's policy-validation update and RFC 9925's unsigned-certificate form also require implementation-specific review wherever used, not assumptions from a flag name. ([O-PARAM], [O-VFY]; preceding verification note §3) |

## 8. Blockers and choices to return, not decisions

1. **Crypto inventory:** exact suite order, classical versus hybrid inclusion/requirement, group tuples/shares, handshake versus chain/revocation signatures, strength floor and stricter credential KU/EKU presence. Preserve current MTI support or identify an actual overriding standard; settle the signature_algorithms_cert generation gap and new KeyUpdate/usage-limit enforcement, rather than merely documenting their omission.
2. **Offline status contract:** leaf/chain/anchor coverage; CRL-only versus validated leaf staple plus chain CRLs; supported base/delta/indirect/reason forms; maximum age/nextUpdate/refresh/rollback rules; must-staple/noRevAvail/unknown-feature explicit rejection versus understood processing. Missing/stale/unknown failure must not masquerade as revoked or success. Retained snapshots need fresh per-handshake evaluation, not frozen "now".
3. **Anchor/verifier contract:** root-only admission versus explicit partial anchors/AUX grants; root self-signature/extension rules; required-purpose presence versus absence-tolerant restrictions; provider-backed additional validation without public callbacks or success overrides. Offline I/O reachability, native evidence ownership and resource limits remain separate gates.

**All validation NOT RUN:** effective-build inventories and negotiation; EMS/RI initial/renegotiation cases; fragmented control traffic/KeyUpdate/request/epoch/GCM limits; key-share freshness; root/partial paths, KU/EKU/name constraints/strict fixtures; missing/stale/future/malformed/wrong-issuer/bad-signature/revoked CRLs, delta/reasons/indirect/partial coverage; OCSP wrong CertID/signature/delegation/status/time/nonce/critical extensions; must-staple/noRevAvail conflicts; hidden fetch/ambient inputs and hostile resource graphs. No integration, compiler/backend, ABI, security or bounded-work proof; #30 remains OPEN. Only this research document was written; no issue/spec/Serena edits, children, commits or pushes.
