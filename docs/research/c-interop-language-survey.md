# C interoperability lessons for Rill

Source review, 2026-11-19. This note compares 19 implementations or projects. The links document capabilities or show upstream source and tests. This survey did not run a compiler, native test or benchmark. A documented callback is evidence that C can call back into a language, not evidence that the language can ship a standalone library for a C host.

## Findings

- Rust is a useful model for safe wrappers over trusted C calls. Zig and D provide models for C translation and build integration. Swift checks whether an exported signature can cross a C boundary. Rill can use these ideas without exposing raw pointers or C++ classes.
- Header ingestion checks declarations and helps keep bindings current; it does not establish who owns a buffer, when a callback stops, or which thread may make a call. Java's Foreign Function & Memory API checks segment bounds, scope and confinement on the managed side. Go checks parts of its garbage collector's pointer contract. Rust can enforce ownership and thread restrictions in a safe wrapper whose unsafe implementation honors the foreign contract. These are different guarantees.
- Rill can use the fixed entry points and generated marshalling in its existing provider designs as precedents. Roc's native host and restricted application API are a useful design comparison. Neither precedent requires general header import, user-defined ABI declarations or a public plugin registry.

## Usable open-source implementations

Versions below are evidence baselines, not a claim about every compiler, target or package release. Where a project publishes a rolling manual, pin the actual compiler, bindings and dependency build before evaluating it.

### Native libraries and C-oriented toolchains

**Rust.** Use handwritten `unsafe extern "C"` declarations or generate them with libclang-based `bindgen`. Rust 2024 requires `unsafe` on the extern block. Export C-compatible functions with `extern "C"` and a deliberate symbol name; use a written header or `cbindgen`. A `repr(C)` record establishes layout rules, not the validity or lifetime of foreign memory. The safe wrapper can make an owner non-copyable, restrict its thread use, and unregister callbacks before dropping state. C still has to honor the pointer and unregister contracts, including calls from C-created threads. Use `staticlib` for the existing executable or `cdylib` for a shared library; Cargo build scripts declare native link inputs, and a C/C++ host linking a static library may need additional native dependencies. [FFI guide](https://doc.rust-lang.org/nomicon/ffi.html), [Rust 2024 extern rules](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-extern.html), [bindgen](https://rust-lang.github.io/rust-bindgen/), [cbindgen](https://github.com/mozilla/cbindgen), [linkage](https://doc.rust-lang.org/reference/linkage.html), [Cargo](https://doc.rust-lang.org/cargo/reference/build-scripts.html), [license](https://github.com/rust-lang/rust#license).

**Zig 0.17.1.** This was the latest stable release in the [download index](https://ziglang.org/download/index.json) at review time. In [0.15.2](https://ziglang.org/documentation/0.15.2/), `@cImport` translated includes into a Zig namespace. In [0.16.0](https://ziglang.org/download/0.16.0/release-notes.html), the recommended route moved to the build system and translation moved off libclang to Aro and `translate-c`. In [0.17.0](https://ziglang.org/download/0.17.0/release-notes.html#C-Translation-Moving-to-External-Package), `@cImport` was removed and `std.Build.Step.TranslateC` deprecated in favor of the [Zig Software Foundation package](https://codeberg.org/ziglang/translate-c). The [0.17.1 manual](https://ziglang.org/documentation/0.17.1/) still documents the `zig translate-c` CLI. Use the package for build-integrated translation of a C include file, or declare a small ABI by hand with `extern`. Match the target and C flags used for the actual library. `export fn` with C-compatible types gives a C entry point; the [C library example](https://ziglang.org/documentation/0.17.1/#Exporting-a-C-Library) uses a C-side declaration and shows shared and static outputs. Translation can preserve pointer and function-pointer shapes. It does not check foreign retention, allocator pairing, callback registration lifetime or thread affinity. The [build system](https://ziglang.org/learn/build-system/) handles C sources and native link inputs; pin the translation package as well as the [compiler](https://codeberg.org/ziglang/zig/src/tag/0.17.1/LICENSE).

**Swift 6.3.** Swift imports C declarations via its Clang importer. `@convention(c)` function values can represent C callbacks; captured Swift state needs a separate context instead of a capturing closure. Swift 6.3 shipped `@c` for C-compatible global functions and enums and emits their C declarations in the compatibility header. `@c @implementation` checks the definition against an existing imported C declaration. This is distinct from the older underscored `@_cdecl` and from the C++ export route. Pointer retention, unmanaged references and the calling thread remain boundary obligations. Annotated C/C++ APIs can get stronger Swift-side lifetime checks, but plain imported pointers do not. SwiftPM can use C-family targets or system-library module maps with `pkgConfig` and build static or dynamic library products. Check the generated header, runtime dependencies and final link on the actual host. [C imports](https://developer.apple.com/documentation/swift/using-imported-c-functions-in-swift), [calling conventions](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/attributes/#convention), [6.3 release](https://www.swift.org/blog/swift-6.3-released/#c-interoperability), [SE-0495](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0495-cdecl.md), [safe interop](https://www.swift.org/documentation/cxx-interop/safe-interop/), [SwiftPM manifest](https://docs.swift.org/package-manager/PackageDescription/PackageDescription.html), [license](https://github.com/swiftlang/swift/blob/main/LICENSE.txt).

**D and ImportC.** A D module can import a C translation unit that includes the vendor header. The compiler uses a C preprocessor and parses the result; it does not make arbitrary preprocessor macros into D functions. Handwritten `extern(C)` declarations are an alternative. Export `extern(C)` definitions and provide matching C declarations. C callbacks use `extern(C)` function pointers, not D delegates. Pointers visible only to C need explicit rooting if they refer to D garbage-collected data. If a foreign-created thread needs the D runtime, follow the thread attach/detach contract. A native host must account for runtime initialization and shutdown. DMD documents object/library builds; DUB records native libraries and linker flags. Pin the D compiler and test its ImportC support against the selected headers and preprocessor. [ImportC specification](https://dlang.org/spec/importc.html), [C ABI and callbacks](https://dlang.org/spec/interfaceToC.html), [runtime](https://dlang.org/phobos/core_runtime.html), [threads](https://dlang.org/phobos/core_thread_osthread.html), [DMD](https://dlang.org/dmd-linux.html), [DUB](https://dub.pm/dub-reference/build_settings/), [license](https://github.com/dlang/dmd/blob/master/LICENSE.txt).

**Nim.** `importc` declarations are normally handwritten or generated by an external tool such as Futhark. `header` includes the real header in generated C; it does not populate Nim declarations on its own. For C callers, use `exportc` with `cdecl`, and `dynlib` for shared-library exports. The backend guide documents `NimMain`, static-library builds and global teardown when Nim does not own `main`. `passL`, `compile` and `dynlib` cover linking, compiling companion C, and dynamic imports. C function pointers do not carry a Nim closure environment. The caller must honor the memory manager and foreign-thread requirements of the chosen build; Nim's normal thread checks do not validate what C retains or where it calls. [Pragmas and FFI](https://nim-lang.org/docs/manual.html#foreign-function-interface), [backends and embedding](https://nim-lang.org/docs/backends.html), [system and foreign threads](https://nim-lang.org/docs/system.html), [Futhark](https://github.com/PMunch/futhark), [license](https://github.com/nim-lang/Nim/blob/devel/copying.txt).

**Odin.** `foreign import` selects system libraries, local artifacts or a library collection. Bind the C types and procedures in a `foreign` block or use a maintained binding such as `vendor:sdl2`; the compiler syntax does not import C headers. Export with `@(export)` and a `proc "c"` signature. The compiler has static and shared library modes. Its C calling convention keeps Odin's implicit context out of the signature; it does not supply an allocator or control where a foreign callback runs. Use explicit context handling and lifetime rules when the exported implementation needs them. [Foreign declarations and context](https://odin-lang.org/docs/overview/#foreign-system), [export and link names](https://odin-lang.org/docs/attributes/), [library build modes](https://github.com/odin-lang/Odin/wiki/Compiler-Flags), [SDL2 bindings](https://pkg.odin-lang.org/vendor/sdl2/), [license](https://github.com/odin-lang/Odin/blob/master/LICENSE).

**C3, checked against the v0.8.6 release and upstream manual.** Declare C functions with `extern`, using `@cname` for a different native name. The documented baseline is an explicit declaration, not C header ingestion. Export a C-compatible definition with `@export("name")` and a matching C declaration. Raw C pointers and ABI-compatible function pointers do not encode ownership, callback lifetime or thread affinity. The project supports static and dynamic library targets, native `-l` and `-L` inputs, and `.c3l` packages with target-specific native artifacts. These are useful properties for a C-shaped port; they do not establish the breadth of a particular target's bindings. [Release](https://github.com/c3lang/c3c/releases/tag/v0.8.6), [C interop](https://c3-lang.org/language-common/cinterop/), [project configuration](https://c3-lang.org/build-your-project/project-config/), [library packaging](https://c3-lang.org/misc-advanced/library-packaging/), [license](https://github.com/c3lang/c3c/blob/master/LICENSE).

**V.** Declare `fn C.*` and C types in V. `#include` brings declarations into generated C, not directly into V's type checker. `v translate wrapper` is a separate generation path. `#flag` passes native compiler/linker inputs. Export named functions with `@[export: 'name']` in a `-shared` build. The C guide includes function-pointer callbacks and, on Windows, documents DLL runtime init/cleanup including when the host supplies `DllMain`. Neither the generated declarations nor the runtime init check C's retention or thread promises; decide which pointers are borrowed, rooted or freed at the boundary. [C interop and shared libraries](https://docs.vlang.io/v-and-c.html), [memory modes](https://docs.vlang.io/memory-management.html), [license](https://github.com/vlang/v/blob/master/LICENSE).

### Managed runtimes and embedding

**Go with cgo.** The `import "C"` preamble can include real C headers. cgo generates wrappers, and `//export` plus the generated header and `-buildmode=c-archive` or `c-shared` make Go callable from a native host on supported targets. The `//export` file's preamble cannot contain C definitions. `#cgo` flags and `pkg-config` carry link inputs; cross-compilation needs a target C compiler. Go pointers passed to C must be pinned, normally for the call only. `runtime.Pinner` permits eligible longer retention, and `runtime/cgo.Handle` lets C keep an opaque token instead of a Go pointer. Go performs dynamic checks within limits; it cannot validate C's behavior. `runtime.LockOSThread` is explicit when a goroutine must stay on an OS thread. It does not let a callback arbitrarily choose which thread a native host calls from. [cgo](https://pkg.go.dev/cmd/cgo), [build modes](https://pkg.go.dev/cmd/go), [pinning](https://pkg.go.dev/runtime#Pinner), [thread locking](https://pkg.go.dev/runtime#LockOSThread), [license](https://go.dev/LICENSE).

**.NET P/Invoke and Native AOT.** Write a managed `[DllImport]` or `[LibraryImport]` signature. The latter generates marshalling code from the managed declaration, not from a C header. Export Native AOT methods with `[UnmanagedCallersOnly(EntryPoint = "name")]` and provide the C signature; the attribute also supports native calls through suitable static function pointers. Use blittable types for the baseline export. For callback delegates, root them until C can no longer call them. `SafeHandle` and pinning help with managed ownership but cannot check C retention or impose native thread affinity. Native AOT can link selected C dependencies directly with `DirectPInvoke` and `NativeLibrary`. The supported native library publishing path is shared; static libraries and unloading are not officially supported. Only exports in the published assembly are considered, not methods from its NuGet or project dependencies. [Import](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke), [source generation](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke-source-generation), [ownership practices](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices), [Native AOT linking](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/interop), [library publishing](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/libraries), [license](https://github.com/dotnet/runtime/blob/main/LICENSE.TXT).

**OpenJDK Java FFM, final in JDK 22.** A downcall uses a symbol address and a Java `FunctionDescriptor`. `jextract` is a separate Clang-based header generator; match its JDK version. `SymbolLookup.libraryLookup` loads a native library, and an arena controls its scope. An `upcallStub` gives C a callable function pointer while its arena stays alive. FFM does not publish Java methods as ordinary C library exports. To start a JVM from a C host, consider the separate JNI Invocation API. Java checks spatial and temporal bounds for segment access and enforces confined-arena thread access. C can violate the contract by retaining an address or calling a stub after its arena closes. An incorrectly described ABI or a wrong native thread is still a boundary bug. [JEP 454](https://openjdk.org/jeps/454), [Linker](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/Linker.html), [Arena](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/Arena.html), [jextract](https://github.com/openjdk/jextract), [JNI host invocation](https://docs.oracle.com/en/java/javase/22/docs/specs/jni/invocation.html), [license](https://github.com/openjdk/jdk/blob/master/LICENSE).

**Kotlin/Native.** `cinterop` processes C headers using a `.def` file and generates Kotlin declarations. The current guide marks C library import Beta with `@ExperimentalForeignApi`. `.def` records compiler/link options and can bundle a native archive with the binding. Kotlin/Native can produce a native library with a generated C header; the dynamic-library example uses an exported symbol-table accessor and generated disposal functions. A `staticCFunction` callback cannot capture. Pass a `StableRef` as user data and dispose it only after deregistration and quiescence; lexical `memScoped` and pinning cover narrower lifetimes. The current shared heap does not mean that an SDL call can migrate or that a C pointer remains valid. [C interop](https://kotlinlang.org/docs/native-c-interop.html), [definition files](https://kotlinlang.org/docs/native-definition-file.html), [C-callable library](https://kotlinlang.org/docs/native-dynamic-libraries.html), [native binaries](https://kotlinlang.org/docs/multiplatform/multiplatform-build-native-binaries.html), [memory manager](https://kotlinlang.org/docs/native-memory-manager.html), [license](https://github.com/JetBrains/kotlin/blob/master/license/LICENSE.txt).

**Crystal 1.22.** Bind C with `lib` and `fun` declarations. `@[Link]` uses native linker options and can query `pkg-config`. The compiler does not ingest the header as a Crystal module; external tools such as Bindgen generate bindings. Crystal can pass non-capturing C callbacks. Its docs show how to box and root captured data explicitly when C accepts a context pointer. Compiler tests show that top-level `fun` definitions have external linkage. That does not establish a supported general-purpose C-host library workflow: the standard entry point initializes the runtime, including the GC. Treat host initialization, foreign-thread entry and shutdown as unverified here. Crystal is a better-supported choice when Crystal owns the process and calls C. [C bindings](https://crystal-lang.org/reference/latest/syntax_and_semantics/c_bindings/index.html), [linking](https://crystal-lang.org/reference/latest/syntax_and_semantics/c_bindings/lib.html), [callbacks](https://crystal-lang.org/reference/latest/syntax_and_semantics/c_bindings/callbacks.html), [Bindgen](https://github.com/crystallabs/bindgen), [export linkage test](https://github.com/crystal-lang/crystal/blob/1.22.3/spec/compiler/codegen/fun_spec.cr), [runtime entry](https://github.com/crystal-lang/crystal/blob/1.22.3/src/crystal/main.cr), [license](https://github.com/crystal-lang/crystal/blob/master/LICENSE).

**Julia.** `@ccall` names the function and declares ABI types; `Clang.jl` can generate wrappers from headers. `@cfunction` produces a C function pointer. A C executable can link `libjulia` and initialize the Julia runtime; a callback address is not an independent C ABI library product. Use `GC.@preserve` when a raw pointer would otherwise outlive Julia's visible use of its owner. Root any closure callback object until deregistration, and note platform limits on closure trampolines. The embedding guide restricts `jl_*` calls to the initializing thread or Julia-created threads. Do not infer foreign-thread entry from a `qsort` callback example. [C calls, libraries and callbacks](https://docs.julialang.org/en/v1/manual/calling-c-and-fortran-code/), [embedding](https://docs.julialang.org/en/v1/manual/embedding/), [Clang.jl](https://github.com/JuliaInterop/Clang.jl), [license](https://github.com/JuliaLang/julia/blob/master/LICENSE.md).

**LuaJIT 2.1 line.** `ffi.cdef` parses supplied C declarations, not a general platform header/preprocessor environment. `ffi.load` and `ffi.C` look up libraries and symbols. C can call Lua through callback pointers or through the Lua 5.1 C API after the host links LuaJIT and creates a `lua_State`. The latter is the better fit for scripting an existing executable. `ffi.gc` can attach a finalizer, but raw access is unchecked. Keep explicit callbacks alive until C stops invoking them, and then free them explicitly. The host must serialize access to a state and keep SDL calls on the proper thread; Lua coroutines are not OS-thread permissions. LuaJIT documents target-specific embedding/link options and restrictions on callbacks. [FFI API](https://luajit.org/ext_ffi_api.html), [FFI semantics](https://luajit.org/ext_ffi_semantics.html), [embedding and linking](https://luajit.org/install.html), [Lua C API](https://www.lua.org/manual/5.1/manual.html#3), [license](https://luajit.org/luajit.html).

## Emerging implementations and limits

These projects have open source, but a specific native path may still be experimental or unverified. No proprietary-only toolchain is recommended or counted as a verified open-source implementation. In particular, a historical description of Mojo as a partial open-source toolchain no longer describes the current release.

**Mojo 1.2.0.** Modular [opened the compiler and build tooling](https://www.modular.com/blog/mojo-open-source) in 2026, beyond the previously published standard library. The [1.2.0 release](https://mojolang.org/releases/v1.2.0/) has both directions in source. `external_call` names a C symbol and uses a manually typed call; `OwnedDLHandle` loads shared libraries, and `abi("C")` supports thin callbacks. `@export("name")` on an `abi("C")` function with `--emit shared-lib` produces a named C export. The tagged [library test](https://github.com/modular/modular/blob/mojo/v1.2.0/Mojo/test/mojo-integration/shared-lib-c-host/test_shared_lib_runtime_init.mojo) and [C host](https://github.com/modular/modular/blob/mojo/v1.2.0/Mojo/test/mojo-integration/shared-lib-c-host/c_host.c) show the host supplying the signature and the library explicitly initializing its parallel runtime. Mojo's pointer origins check lifetimes it can see, not pointers that C retains. The [FFI manual](https://mojolang.org/docs/manual/c-ffi/) documents the limits of signature and aggregate checking. This is enough to justify an embedding experiment, not to assume a stable generated header workflow, arbitrary foreign-thread callbacks or the same host integration on every target. [Build CLI](https://docs.modular.com/mojo/cli/build/), [source and license](https://github.com/modular/modular).

**Roc.** Open-source alpha/nightly. Roc applications call typed platform operations implemented by a native host; the native host starts first and calls an application function exposed through `provides`. This is bidirectional through a platform, not arbitrary C header import or a generic application-written `extern`. The current Zig template shows a generated platform ABI and explicit host allocation/deallocation and entry points. Packaging builds a target-specific host for the compiler to link with the application. The platform chooses ownership and scheduling; the current platform docs mark some platform-implemented concurrency pieces as missing. The design is relevant to Rill, but the alpha and newer nightly toolchains have different platform support. [Platform model](https://www.roc-lang.org/platforms), [compiler releases](https://github.com/roc-lang/roc/releases), [compiler source and license](https://github.com/roc-lang/roc), [Zig host](https://github.com/lukewilliamboswell/roc-platform-template-zig/blob/main/src/host.zig), [ABI and build instructions](https://github.com/lukewilliamboswell/roc-platform-template-zig/blob/main/docs/host-development.adoc).

**Vale.** Open-source pre-release; the release page lists v0.2.0. The project guide shows both `extern func` calling a C companion and C calling `exported func` through headers generated by `valec`. This is a Vale-declared boundary, not vendor-header import. Its immutable aggregate example requires C to free a copy. Its mutable-object example uses an opaque reference and Vale accessors. This is a useful design distinction, not evidence that C obeys release, callback or thread contracts. A reusable library distribution and foreign-thread lifecycle are unverified; the examples establish a companion linked with a Vale program. [FFI guide](https://vale.dev/guide/externs), [pre-release](https://github.com/ValeLang/Vale/releases), [source and license](https://github.com/ValeLang/Vale).

**Carbon.** Open-source experimental compiler and linker with a C++ migration goal. Current compiler tests cover [importing `extern "C"` declarations through C++](https://github.com/carbon-language/carbon-lang/blob/trunk/toolchain/check/testdata/interop/cpp/function/import/extern_c.carbon) and [exporting selected functions to C++](https://github.com/carbon-language/carbon-lang/blob/trunk/toolchain/check/testdata/interop/cpp/function/export/function.carbon). The latter does not establish a stable plain-C library export. Do not treat the [bidirectional design](https://docs.carbon-lang.dev/docs/design/interoperability/) as a delivered package, lifetime or thread model. The project still lists broad C++ interop as a [milestone](https://docs.carbon-lang.dev/docs/project/milestones.html); a deployable C library workflow and foreign-thread callback rules are unverified here. [Project status and license](https://github.com/carbon-language/carbon-lang).

## Native libraries with thread and lifetime requirements

SDL2 illustrates a requirement that a C signature does not express. [Event polling](https://wiki.libsdl.org/SDL2/SDL_PollEvent) must run on the thread that set the video mode. [Presentation](https://wiki.libsdl.org/SDL2/SDL_RenderPresent) requires the main thread. Rill goroutines can migrate between workers. A binding needs a platform service that uses the required thread for initialization, polling, rendering and release.

An `SDL_Event` is a C union, not an owned Rill message. [User events](https://wiki.libsdl.org/SDL2/SDL_UserEvent) can hold pointers. [Drop events](https://wiki.libsdl.org/SDL2/SDL_DropEvent) can hold a string that the recipient must free with `SDL_free`. Keep those obligations in the adapter. Pass selected event fields as owned Rill values.

[zlib](https://zlib.net/manual.html) illustrates a smaller boundary. A decompression adapter can check input and output sizes, supply a bounded output buffer and return owned bytes. It does not need a window, a callback or a persistent native owner. A successful link does not show that the adapter honors the buffer bounds.

If a later binding needs callbacks, define the permitted thread, context lifetime and unregister procedure. Keep the callback code and state alive until no callback remains in flight. No calling convention establishes those guarantees.

## Lessons for Rill

| Design question | Useful comparison |
| --- | --- |
| How can native code stay behind ordinary application operations? | Rust wrappers separate a safe interface from the code that trusts C. Keep the Rill-facing types and ownership rules separate from C layouts. |
| How can the build keep declarations and libraries consistent? | Zig and D show ways to consume C declarations during a build. Pin the target, headers and native inputs. Header translation cannot prove ownership or thread rules. |
| How can a compiler reject invalid boundary types? | Swift checks `@c` signatures and emits C declarations. Rill can apply a narrow boundary type check to admitted imports without adding public exports. |
| How can a runtime restrict native memory or owner lifetimes? | Java FFM arenas and .NET handles give scoped access or release contracts. Go constrains which managed pointers can remain in C. Compare these rules before exposing any retained pointer. |
| How can a platform supply a narrow native service? | Roc separates typed application operations from native platform code. Rill can keep platform setup in an adapter without moving application logic there. |

Direct C++ interop is a separate choice. Swift imports supported C++ headers. Rust CXX generates glue for selected types. A C ABI alone does not specify C++ object layout, exception behavior or ownership. See the [Swift constraints](https://www.swift.org/documentation/cxx-interop/status/) and [CXX supported signatures](https://cxx.rs/bindings.html). Neither capability is necessary for the first Rill-to-C bindings.

## Proposed first checks

The [SQLite provider contract](../sqlite-provider-contracts.md) and [TLS native boundary](../tls-native-boundary.md) cover specific admitted providers. Neither grants access to arbitrary native packages. [Draft RFC 0011](../rfcs/0011-trusted-native-c-bindings.md) proposes a separate mechanism for a Rill executable to call explicitly approved C adapters.

1. Compile a Rill executable that links a real zlib adapter. Check exact decoded bytes, an insufficient output limit, and invalid input. Reject a missing approval or mismatched binding before producing a usable executable.
2. Run a Rill executable that supplies a frame to SDL2 and reads a copied event. Record the actual video backend and thread. A headless event-only test does not prove that presentation works.
3. Check release and cancellation independently. A request to cancel cannot end a buffer or handle dependency. Wait until native work stops accessing it.

These are proposed checks. This survey did not run them or establish runtime, platform or performance results.
