## 2. Shared values: facts an interface cannot erase

- **Methods:** extensible, case-sensitive `token`, not only a closed list of known verbs ([9110 §9.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.1)). **Status:** three decimal digits, valid range 100–599; unknown codes are handled by class as specified, not rejected merely because unnamed ([§15](https://www.rfc-editor.org/rfc/rfc9110.html#section-15)). An HTTP/1 reason phrase is optional explanatory material that clients SHOULD ignore, not the status identity ([9112 §4](https://www.rfc-editor.org/rfc/rfc9112.html#section-4)).
- **Field names:** case-insensitive tokens. Values are not universally UTF-8: `obs-text` octets 0x80–FF are allowed and SHOULD be treated as opaque; field-specific syntax still matters. CR/LF/NUL in a value are invalid: the recipient MUST reject or replace each with SP before further processing/forwarding. This is not permission for an emitter to inject line breaks ([9110 §§5.1–5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.1)).
- **Repetition:** retain all field-line values and same-name order. A proxy MUST NOT reorder them. Senders MUST NOT generate repeated same-name lines except where list combination is allowed, with the well-known **Set-Cookie exception**: it cannot be comma-folded into one value. Commas inside quoted values/dates are not generic split points. Order between different field names is not semantically significant. A unique-key string map, unconditional comma join, or “last value wins” loses required information ([§§5.2–5.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.2), [§5.6.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.1)). No cookie engine follows from preserving bytes.
- **Version-specific validation remains necessary:** HTTP/2 and HTTP/3 require lowercase field names on wire, constrained pseudo-fields before regular fields, and prohibit connection-specific fields; request `TE` is limited to `trailers`. Transfer-Encoding is not their body framing ([9113 §§8.1–8.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.1), [9114 §§4.1–4.3](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.1)). A shared field representation cannot alone certify every protocol's valid message.
- **Bounds:** HTTP specifies no universal field-size ceiling. A server exceeding its chosen request-field limit MUST return an appropriate 4xx, not silently omit fields and route the remainder. Checked length arithmetic and bounded retention are required interface capabilities, but exact local limits are still choices ([9110 §5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.4)).

## 3. URI, authority and request-target are different things

[3986 §3](https://www.rfc-editor.org/rfc/rfc3986.html#section-3) separates scheme, authority (`[userinfo@]host[:port]`), path, query and fragment. Generic `reg-name`, IP literal, TCP lookup name, numeric socket address, TLS reference name/SNI, and HTTP authority are not interchangeable. URI IPv6 brackets are not bare IP syntax; the ri-vno socket scope syntax explicitly is **not** URI percent-decoding. The ri-irw reference-name constructor is deliberately narrower than a generic URI host. Neither DNS canonical names nor dialed endpoints replace the application's authority/reference identity.

HTTP/1.1 has four request-target forms ([9112 §§3.2–3.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2)):

| Form | Standard constraint |
| --- | --- |
| origin-form | Absolute path plus optional query for normal direct requests; empty URI path becomes `/`. No fragment. |
| absolute-form | Proxy requests normally carry an absolute URI; origin servers **MUST accept** absolute-form too. Proxy/origin recipient uses its authority instead of received Host; forwarding proxy regenerates Host from the target. |
| authority-form | CONNECT carries host and mandatory port, not a whole URL or path. Empty/invalid port is rejected. |
| asterisk-form | Server-wide OPTIONS uses `*`; not a general wildcard path. |

A client MUST send Host on **every HTTP/1.1 request**, including absolute-form; it matches the target authority excluding userinfo (or is empty if authority absent). A server MUST respond 400 for missing Host, more than one Host field line, or invalid Host. Absolute-form authority precedence is not permission to ignore those validity checks ([9112 §3.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2)). HTTP/2/3 `:authority` has its own rules; copying a raw Host over a conflicting pseudo-field is unsafe ([9113 §8.3.1](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.3.1), [9114 §4.3.1](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.3.1)).

Fragments are client-side and excluded when forming the target URI; a sender MUST NOT generate userinfo in an HTTP(S) URI reference within a message ([9110 §§4.2.4, 7.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2.4)). Percent-decoding reserved delimiters can change interpretation; repeated decoding is not safe equivalence ([3986 §§2.2–2.4](https://www.rfc-editor.org/rfc/rfc3986.html#section-2.2)). Reference resolution (§5), syntax comparison (§6), application routing and HTTP(S) normalization ([9110 §4.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2.3)) are separate operations. **No automatic normalization, filesystem safety, browser/WHATWG URL compatibility, IDNA conversion or general URL-library scope is selected here.**

## 4. HTTP/1 framing: exact precedence and invalid inputs

A parser MUST process **octets**, not decode an undelimited stream as Unicode first. Start-line/field syntax has security-relevant whitespace rules: sender emits CRLF, a recipient MAY recognize bare LF; whitespace before a request field colon MUST cause server 400; obsolete folding cannot be emitted, and role-specific recipient alternatives are rejection or replacement, not arbitrary preservation ([9112 §§2.2, 5.1–5.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-2.2)). Stricter rejection of permitted robustness cases is a policy choice, not a fabricated RFC MUST.

**Evaluate [9112 §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3) in this order**, not by whichever header is encountered first:

1. Response to **HEAD**, or status **1xx / 204 / 304**: ends at header terminator, **no message body or trailer section**, regardless of fields present. This precedence also covers 101's HTTP message; subsequent upgraded-protocol bytes are not its body.
2. **2xx to CONNECT:** tunnel begins immediately after headers. Client MUST ignore Content-Length/Transfer-Encoding in it; those bytes belong to the tunnel, not an HTTP response body.
3. **Transfer-Encoding + Content-Length:** TE overrides CL. The RFC says this “ought to be handled as an error,” not “every recipient MUST reject.” A forwarding intermediary MUST remove CL and process TE before forwarding. A server MAY reject or process TE alone, but **MUST close after responding** ([§6.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.1)). A sender MUST NOT generate both ([§6.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.2)).
4. TE with final **chunked**: decode to the chunked terminator. Response with non-final/nonexistent chunked final coding: close-delimited. Request whose final transfer coding is not chunked: **400 then close**.
5. Without TE, **invalid CL** is an unrecoverable framing error, with the identical valid comma-list exception below. Server: 400 and close. Proxy receiving such a response: close upstream, discard response, send 502. User agent: close and discard response.
6. Valid CL without TE: **exactly that many octets**. Premature closure/timeout is incomplete and requires closure, not successful short-body EOF.
7. Otherwise a request has **zero** body length. Requests are never close-delimited, regardless of method or transport half-close.
8. Otherwise a response is close-delimited. This cannot distinguish success from interruption except available underlying errors; servers SHOULD prefer explicit framing.

Additional constraints:

- CL syntax is `1*DIGIT`, decimal nonnegative octets: no sign, fraction or exponent. Decimal leading zeros are not forbidden. Prevent overflow/precision loss for arbitrarily long numerals; representability/size rejection must not wrap. Identical repeated decimal values (e.g. `42, 42`) **MAY be rejected or collapsed to one** under [9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6); conflicting/invalid values do not qualify. “Always first/last CL wins” is invalid. Forwarding known-incorrect CL is forbidden.
- Chunked MUST be parseable; sender MUST NOT apply it twice. Request transfer coding must end in chunked. A server receiving an unsupported request transfer coding SHOULD respond 501, distinct from invalid framing's mandatory 400. HTTP/1.0 plus TE is faulty framing and requires closure ([9112 §6.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.1)). Transfer-Encoding describes applied body coding; **TE** negotiates acceptable response transfer codings/trailers, and MUST NOT name chunked. Its sender MUST also send `Connection: TE` ([§7.4](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.4)). Neither is Content-Encoding.
- Chunk sizes are checked hexadecimal; no allocation of the entire declared chunk is required to stream it. Completion includes the zero chunk, trailer parsing and terminating empty line, not just delivery of the last nonempty data. Unknown syntactically valid chunk extensions MUST be ignored; limits still apply. Parameters on the **chunked coding** SHOULD be errors, unlike per-chunk extensions ([§7.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1)).
- Servers MUST NOT emit CL or TE on 1xx/204/2xx CONNECT. HEAD/304 may carry hypothetical GET metadata under the precise constraints in [9110 §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6) and [9112 §6.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.1); that metadata does not authorize a body. Request framing is independent of method semantics; neither GET nor HEAD means “ignore a framed request body” ([9112 §6](https://www.rfc-editor.org/rfc/rfc9112.html#section-6)).

**Smuggling implication:** complete header validation must precede applying a request to its resource (a MUST in [9110 §5.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.3)). Rejecting/closing ambiguous framing, keeping one authoritative framing state and validating output against it are feasible requirements; the parent must choose any permitted recovery policy explicitly. Do not route one interpretation and forward another. Parser leniency disagreement, newline injection, header truncation and method/status conversion are attack surfaces ([9112 §§11.1–11.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-11.1)).

## 5. Completion, abandonment, trailers and switching protocols

**Body data EOF is a protocol fact, not “one short read,” raw EOF, flush, handler return or disposal.** HTTP/1 persistence requires self-delimiting messages. A server **MUST read the entire request body or close after responding**; a client **MUST read the entire response body if it intends to reuse** ([9112 §9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)). Early body abandonment therefore needs explicit drain-to-verified-boundary evidence or non-reuse/closure. Draining may block, exceed limits or fail; automatic unbounded drain is neither required nor safe to assume. Full consumption is necessary, not sufficient: Connection: close, framing fault, poison, upgrade/tunnel and outstanding message state also matter. Pooling remains open.

A client MUST record incomplete responses as incomplete. For close-delimited responses, intact headers plus closure count as completion **unless the lower connection indicates error**, including incomplete TLS closure ([9112 §8](https://www.rfc-editor.org/rfc/rfc9112.html#section-8), [§9.8](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.8)). Under ri-irw raw EOF without close-notify is truncation, not clean TLS EOF. A length-delimited body can finish before TLS closure; a later TLS error must not silently become clean EOF, nor erase the distinct already-observed HTTP boundary.

Trailers are a separate late field section. A recipient MUST NOT merge them into headers unless that field's definition explicitly permits and specifies the merge. Sender MUST NOT generate a trailer field unless its definition permits trailers; essential framing/routing/authentication or other pre-content decisions cannot be deferred there. Dechunking recipients MAY selectively retain/discard trailers; applications must not depend on mandatory delivery of every trailer ([9110 §§6.5–6.6.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-6.5), [9112 §7.1.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1.2)). An interface claiming trailer access needs a way to distinguish “not reached yet,” terminal failure, and successfully completed late fields, without choosing a callback shape here.

**1xx** responses are interim, not the final response (101 switches); clients MUST be able to parse one or more interim responses before final, including unexpected ones, and MAY ignore unexpected informational responses ([9110 §15.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.2)). HTTP/1 outstanding responses correlate in request order ([9112 §9.2](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.2)).

**101/CONNECT:** successful protocol transition requires preserving all unread suffix bytes, not treating read-ahead as the next HTTP message or discarding it. Upgrade requires the request's Upgrade offer and protocol rules; a client cannot begin the upgraded protocol until permitted ([9110 §7.8](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.8)). Current **9931 §8** additionally requires a proxy client forwarding untrusted TCP data over HTTP/1.1 CONNECT to **wait for 2xx or send `Connection: close` (or both)**. A rejecting proxy server **MUST close without processing more requests**, with the specified MAY optimization only when the client is known to wait for 2xx. This prevents rejected optimistic tunnel payload becoming smuggled requests. Supporting CONNECT/101, external WebSocket protocols or transport handoff remains an explicit human scope/ownership decision; ri-irw has no TLS raw-owner extraction escape.

## 6. Critical feasibility trap: sequential TLS versus early responses

### Actual requirements, not an invented universal duplex MUST

[9110 §7.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.5) permits **any response, including final, before the request completes**; response completion can precede request completion. A client receiving a response while still sending SHOULD continue unless explicitly indicated otherwise. More specifically, [9112 §9.5](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.5) says an uploading client **SHOULD monitor for an error response while transmitting**, and SHOULD immediately cease sending/close its side when told the server will not receive the body and is closing. These are **SHOULD**, not an RFC sentence demanding simultaneous language-level read/write calls. The server is not required always to consume a request before starting its response.

### Why bounded write-then-read is not general streaming

Consider a client streaming an arbitrarily large upload while a server rejects it early, stops consuming upload and emits a response. Client output can block on finite buffers while it never reads the response; server output can also block while it never drains upload. Or a server waits in a whole-stream body read while its application needs to send a response to unblock the peer. This is an adversarial liveness scenario permitted by the standards, **analysis rather than an executed proof of any particular stack**.

The closed ri-irw contract has **one exclusive generic application I/O driver**: no TLS split/reunite, no independent simultaneous app read/write, no public readiness/poll facility. TLS read/write/flush may pump opposite-direction **TLS protocol** traffic and retain bounded authenticated data, but that does not expose an HTTP early-response parser or guarantee a blocked app write returns so HTTP can inspect it. TCP split does not split the TLS owner. A mutex around that owner still leaves the lock held by a suspended operation. Alternating small writes and reads also fails: either operation can suspend indefinitely awaiting a peer that needs the opposite direction. Buffering the whole body merely narrows the problem, violates general unbounded streaming, and does not remove transport backpressure.

Racing a blocked TLS write against a timer is **not** a benign yield: admitted interruption poisons the TLS session; actual release may wait indefinitely, and accepted-prefix semantics do not authorize replay or recovery. Therefore **the existing sequential TLS app-I/O surface does not establish a generally live HTTP/1.1 streaming client/server**. A deliberately restricted sequential exchange may be feasible, but needs its restrictions and omitted SHOULD behavior acknowledged; it is not evidence of general HTTP support. Generality requires a **new explicit transport/driver capability decision and validation**, or an honestly narrower HTTP scope. No such capability or exception is selected by this note, and ri-irw is not silently reopened.

### What Expect: 100-continue solves — and does not

[9110 §10.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.1):

- Client MUST NOT generate the expectation without content; a client that waits for 100 before content MUST send the expectation. It MAY send content without waiting any particular time and SHOULD NOT wait indefinitely (notably through HTTP/1.0 intermediaries).
- Given HTTP/1.1+ headers containing that expectation and content indication, origin server MUST send **immediate final**, if determinable from method/target/headers, or **immediate 100**; it MUST NOT wait for content before sending 100. Omission is permitted if some/all content already arrived or framing says none. Proxies have separate forward/immediate-final rules.
- A 100 encourages upload; it is **not** a promise no later rejection will occur. The server ultimately owes a final response unless prematurely closed. A final-before-body-complete server SHOULD indicate whether it will close or keep reading. A 417 retry-without-expectation is a specific SHOULD, not blanket permission to retry arbitrary interrupted uploads.

Thus 100-continue avoids *some* unnecessary uploads and supplies an initial headers/decision phase, but **does not serialize the rest of HTTP**. Later rejection, ordinary clients without Expect, clients sending before 100, informational responses and simultaneous streaming remain possible. Waiting forever for 100 fails interoperability; timing out a TLS read by interruption poisons it, so “wait briefly then reuse the stream to upload” is **not supplied by ri-irw**. A source-correct 100 policy still needs a transport decision.

## 7. HTTP/2, HTTP/3, HTTPS and effects

- **HTTP/2 is not just new start-line encoding.** Binary frames multiplex streams on a connection; DATA is controlled by **both stream and connection windows**, while connection/control frames and HPACK state need coordinated progress. Endpoints **MUST read/process frames as soon as available**, explicitly to avoid deadlock on WINDOW_UPDATE ([9113 §5.2.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-5.2.2)); a blocked generic TLS app write plus no application-level receive drive is a concrete missing seam. Stream count/window/field-compression bounds and terminal stream errors require evidence. Neither TCP halves nor TLS's internal WANT handling supplies an HTTP/2 multiplexer.
- HTTP/2 over TLS uses ALPN **`h2`** and connection prefaces, TLS 1.2+ with further restrictions, and domain-name SNI requirements ([9113 §§3.1–3.4](https://www.rfc-editor.org/rfc/rfc9113.html#section-3.1), [§9.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-9.2)). ri-irw's optional SNI/ALPN modes cannot all be blindly reused as a conforming h2 profile. Absence of negotiated ALPN does not imply h2. No version is chosen here.
- **HTTP/3 requires QUIC**, not HTTP/2 atop `TlsStream<TcpStream>`. QUIC incorporates TLS 1.3, independent bidirectional request streams, flow control and transport security; HTTP/3 adds control streams and QPACK. Establishment selects **`h3`** ([9114 §§1.2, 3.2, 6](https://www.rfc-editor.org/rfc/rfc9114.html#section-1.2)). QUIC v1 is UDP-based ([RFC 9000 §1](https://www.rfc-editor.org/rfc/rfc9000.html#section-1)); ri-vno selects no UDP/QUIC foundation, and ri-irw's stream TLS provider is not QUIC integration. H3 delivery would need new explicit prerequisites and evidence, not merely adding an enum case or ALPN ID.
- **HTTPS authority:** verify the intended service identity and authority, not just encryption, TCP reachability or SNI. HTTP(S) origin includes scheme/host/port ([9110 §§4.3.1–4.3.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.3.1)). ri-irw requires explicit maintained, purpose-bound CA grants and strict offline CRL evidence (including the built root); no OS/browser/default CA import, online fetching/softfail, or insecure verifier. Configured snapshots age and need application refresh. Public-web compatibility cannot be assumed from common browser behavior. ALPN offer/selection and any no-ALPN fallback remain HTTP choices; do not advertise an unimplemented protocol.
- **Targets:** ri-vno intends native Linux/macOS networking; ri-irw intends Linux/macOS x86-64/AArch64 TLS, all unvalidated. Standard `wasm32-wasip1` has portable value construction/type visibility and typed Unsupported for unavailable live operations, not working HTTPS. Browser fetch, preview2, inherited sockets and custom imports are not implied support. ri-ei7/#30 gates remain.
- **Control:** NetControl captures an ordinary by-value descriptor snapshot retaining clock/token borrows; forward the **same absolute** budget through DNS, dial, TLS and applicable HTTP work, not freshly renewed durations. Basic/domain validation precedes already-requested token and needed clock checks. Selection is once; ready ties unspecified; keep real late prefixes and original errors through release. `withDeadline` joins and preserves nested Result, not force-close or hard return. Pre-admission rejection differs from admitted TLS poison.
- **No execution inference:** TLS writes count current plaintext accepted into bounded owned storage, not server execution; flush/notify/close are not receipt or body completion. Transport failure or zero progress does not prove nonexecution. [9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) permits retry of idempotent operations in defined circumstances, but **SHOULD NOT** automatically retry non-idempotent requests absent knowledge of idempotence/non-application, **SHOULD NOT** retry a failed automatic retry, and a proxy **MUST NOT** automatically retry non-idempotent requests. HTTP/2/3 have specific refusal/GOAWAY evidence ([9113 §8.7](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.7), [9114 §§4.1.1, 5.2](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.1.1)); those facts are not general transport-progress evidence. No automatic retry, redirect, proxy or replay policy is selected.

## 8. Candidate evidence inventory (all NOT RUN)

“Positive” means standards-permitted input/scenario, not a promised feature. “Rejected” distinguishes mandatory source rejection from parent-policy alternatives above. This inventory is for later design/RFC/implementation validation, **not a claim that writing examples proves security**.

| Class | Cases and facts to preserve |
| --- | --- |
| Positive values | Extension method with exact case; unknown valid status; empty field value; opaque non-UTF-8 value; repeated list field in order; separate Set-Cookie lines with Expires commas; CL `0` and decimal leading zeros. |
| Positive framing | One-byte/fragmented headers and chunks; known length; unknown length chunked; unknown valid chunk extensions; trailer completion; HEAD/304 hypothetical CL with zero body; multiple 1xx then final; request without CL/TE ends at headers regardless of method. |
| Rejected framing | Conflicting/invalid CL; signed/overflowing numerals without wrap; request TE not ending chunked; repeated chunking; HTTP/1.0 TE; whitespace before field colon; missing/duplicate/invalid Host; incomplete header/body/chunk/trailer; emitting forbidden body/framing fields. Identical CL and TE+CL exercise the **explicit permitted alternatives**, not invented reject-MUSTs. |
| Injection/smuggling | CRLF/NUL value; obs-fold/bare LF agreement across proxy/backend; CL.TE/TE.CL; oversized fields never silently dropped; absolute-target/Host mismatch; extra bytes after final response not accepted as an unsolicited response; CONNECT rejection followed by HTTP-looking optimistic payload (9931). |

## 9. Questions requiring human decisions, not research answers

1. What HTTP versions/roles and streaming scope are actually required? If general HTTPS streaming is required, what **new, explicitly approved transport/driver decision** addresses early responses and bidirectional liveness while preserving ri-irw's exclusive-driver/poison contract? If unavailable, which restrictions and omitted behaviors will be stated honestly?
2. Which shared values and version-specific validators, module placement, generic/callable evidence and owner-retention boundaries are selected? How are headers, late trailers, interim/final responses, body completion/failure and original errors observable without inventing methods/traits/public dyn?
3. Which resource/field/body/chunk-extension/interim/work/time bounds, strictness alternatives, drain/abandonment and graceful shutdown guarantees are selected? How are response/request/upload state and non-reuse represented? Pooling, handoff/upgrade support and callback shapes remain open.
4. How will authority parsing, HTTP target forms and narrower DNS/TLS identities compose without silent normalization? Which HTTP(S) ALPN/profile/trust provisioning and unsupported-target behavior are documented?
5. Which convenience policies, if any, exist for redirect, retry, proxy, decompression, URI normalization, cookies, multipart or WebSockets? Standards facts do not choose these. Routing/middleware/authentication/serialization remain external per ri-n5i; no first-party API comparison is necessary to establish the constraints above.

**Bottom line:** shared bytes/repetition and exact framing/completion can be specified independently, but a general streaming HTTPS claim currently lacks a transport liveness seam. `100-continue`, TCP split, bounded buffers and timeout races do not supply that seam. Keep this unresolved dependency explicit rather than approve an imaginary concurrent TLS interface or assert compliance from source reading.
