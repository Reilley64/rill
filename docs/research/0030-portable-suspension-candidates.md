# #30: portable suspension candidates. Research follow-up

2026-11-15. Recommendation: prototype checked explicit records first; do not adopt an architecture or close the support gate. This is new static primary-source research, not an executed candidate, compiler/checker proof, performance measurement or support decision. The researcher ran no runtime probes, installed nothing and changed no earlier evidence. The parent agent is responsible for experiments. Read alongside [executed experiments](0030-backend-experiments.md) and [the earlier mechanism audit](0030-backend-mechanisms.md); this note does not amend either.

## 1. Scope and source discipline

- [#13's confirmed pipeline/target decision][R13] explicitly lists x86-64/AArch64 Linux/macOS and `wasm32-wasip1` with Wasm 3.0 tails. Windows and `wasm32-unknown-unknown` come later. A required browser target cannot be inferred from "portable Wasm," Asyncify's JavaScript examples, or earlier reports mentioning browsers. Browser compatibility is an optional additional compatibility check here, not a new acceptance requirement. Non-JavaScript WASIp1 hosts remain relevant; choosing one embedding's fibers is not portable WASIp1 suspension.
- [#22's final confirmation][R22] governs the imprecise "saved budget is program-wide" wording in #30: initial addressable and saved defaults are each 1 MiB per routine; the saved-size setting/override is program-wide, not an aggregate quota shared by all routines. Addressable entry/sized-spawn overrides do not override saved capacity. Ordinary heap data, explicit causes and legitimate cleanup worklists are not total-memory-quota subjects; retained activation state cannot escape saved accounting by being renamed.
- [#30][R30] requires bounded activation growth for eligible self/mutual/indirect tails in all builds, ordinary lifetimes when storage/disposal/joins survive a call, pre-corruption managed bounds, stable borrows and completion-based reclamation. The user's current authorization permits continued mechanism investigation preserving those semantics/targets, not replacement-architecture adoption or target narrowing. No architecture choice is needed merely to run the proposed standalone prototype.
- Existing toolchain pins remain LLVM 23.1.5 `392dfff97d29b59d77e5cac6d4b6ef2585fe7117`, Binaryen 133 `fba5005a132d85d578be5bd010e0487ed8e2ce3e`, Wasmtime 50.0.1 `c307ec81de02852d815e9849f7c89d955c03c30d`. Sources below were fetched afresh at these revisions. Additional proposal/compiler/document snapshots have their own immutable revisions in the references; they are evidence, not tool upgrades.

Upstream specifications establish semantics, and source establishes available mechanisms and limitations. The designs and costs below are engineering deductions, not upstream guarantees about Rill. The previous finite Wasmtime-fiber positive result remains host-specific; its unresolved `opaqueSavedStateBudget` problem is not solved by this research.

## 3. Concrete candidate mechanisms

### A. Explicit records, nonrecursive dispatch, defunctionalized CPS

In the proposed minimal machine, a routine owns a checked saved arena, a fixed addressable arena and a descriptor for its currently runnable activation. A generated step reads a function/PC tag and executes a bounded segment, then returns an action to an iterative dispatcher: `continue`, `ordinary-call`, `tail-transfer`, `return`, `yield`, or cleanup/wait progress. These are conceptual actions, not proposed public Rill APIs. Never implement "CPS" as unrestricted recursive calls to continuation functions.

The mechanism is concrete rather than dependent on a new Wasm feature: Rust's compiler already documents transforming MIR coroutines into state/layout/switch-based resume functions that return `Pending`/`Ready`; LLVM documents comparable split resume functions and frames. These sources demonstrate available implementation patterns, not this Rill lowering or its tail eligibility. [Rust-transform], [L-coro]

Required invariants for a parent prototype:

1. For an ordinary call, retain the caller's return PC, live values, initialized/cleanup state and stable addressable slots. Check capacity before pushing the callee's record. Returning copies/moves results to valid caller-owned storage and removes only the completed record. A suspended callee must not erase its ordinary ancestors.
2. For an eligible tail, evaluate arguments/target once while their sources remain valid. Preserve the earlier ordinary return continuation/result destination, and replace the current record. Do not append a continuation, trace node, promise, awaiter or bookkeeping node per transfer. Self/mutual/indirect transfers use the same rule. Variable record sizes need checked replacement and bounded staging; merely freeing old records after constructing an ever-growing linked chain is not bounded behavior.
3. To suspend, publish PC/live values/wait-registration state and return from the step and dispatcher to the scheduling boundary. Later, dispatch the saved descriptor. No engine activation may remain parked invisibly in the prototype. Returning a status while leaving recursive nested `poll`/resume calls active is not this design.
4. A borrowed caller slot must occupy a fixed offset arena, not a temporary C step local or a movable record vector. Keep its owner record/slot until execution, required cleanup and borrowers complete. A live caller-local dependency or post-call action makes the source call ordinary; never relocate/release that storage just to label the transfer tail.
5. Charge all retained PC/function/continuation descriptors, arguments, results retained across steps, live scratch, record headers, padding and activation-specific runtime metadata to Saved. An out-of-line resume packet/allocator side table is still retained state. Addressable locals use their fixed checked arena. If a design merges the storage domains, explicitly specify charging; do not invent an unapproved exemption for dual-purpose bytes. A constant program dispatch table is not a growing per-activation allocation.

The semantic invariant is "one current record plus genuinely live ordinary ancestors," not "one record for every function ever visited." Costs are more loads/stores, tag dispatch, explicit call/return marshalling and possible loss of cross-segment optimization. Native synchronous islands might reduce these costs later, but arbitrary recursion or hidden suspension inside an island invalidates a fixed-headroom argument. No quantitative speed claim is supported here.

Hand-written C is an executable model of this protocol. It does not show that LLVM invents it automatically, that a Rill compiler emits correct spill/ownership/cleanup state, or that the checker soundly identifies eligible tails. Native Rill lowering and the approved whole-program pipeline are not changed by testing a Wasm model.

### B. LLVM 23 coroutine machinery and Rust async frames

LLVM 23 has several useful, distinct interfaces. [L-coro]

- Switched-resume `llvm.coro.id`: compiler-generated frame with resume/destroy pointers, promise where present, suspend index and values crossing suspension. `coro.size`/`coro.align` expose frame requirements after lowering. Allocation can be supplied by the frontend. The exact source also handles `byval` spill payloads, padding, dynamic-alignment slack and final frame rounding: charging only source locals or the promise is wrong. [L-frame]
- Returned-continuation `coro.id.retcon`: takes constant buffer size/alignment and a continuation prototype; suspension returns yielded values and a continuation function. A dispatcher can invoke that function after the previous invocation returned, avoiding recursive resume calls. If the frame does not fit in the supplied buffer, the ABI uses an allocation and retains a pointer in the buffer. The allocator must not return null or throw; a checked allocator must terminate fatally on exhaustion, not use null as ordinary failure. LLVM's docs explicitly say allocation elision after full inlining is ineffective for this lowering. [L-coro-retcon], [L-retcon-allocator]
- Async-context `coro.id.async`: frontend-managed context carrying arguments/results and caller-context projection; frames live at the tail of that context. This is machinery for an explicit ABI, not automatic stack capture. The frame builder rejects frame alignment higher than the async-context guarantee. [L-coro], [L-frame]
- Symmetric transfer: `coro.await.suspend.handle` resumes a returned coroutine handle. At this pin, `CoroSplit` marks that call `musttail` only when `TTI.supportsTailCallFor` says yes; it still creates call+return otherwise. Wasm's TTI tail support depends on its tail-call feature. Thus the intrinsic alone is not an all-build mandatory-tail contract, and a `+tail-call` codegen probe must inspect the resulting IR/Wasm, not infer support from intrinsic acceptance. [L-split], [L-wasm-tti]

Machine-frame and coroutine-object storage are separate. A musttail resume can eliminate its machine frame while the coroutine object still retains the parent/awaiter/continuation. Repeated `return await child` with one heap object per eliminated caller is not Rill proper-tail behavior. Generic allocation elision cannot be the guarantee in development builds. A frontend still needs a deliberate tail replacement/lifetime protocol, or to drive returned continuations using candidate A's dispatcher.

Exact documented LLVM 23 limitations, not a claim of blanket Wasm failure: coroutine compatibility across LLVM releases is not guaranteed; `CoroElide` depends on ramp inlining; elision across ABI boundaries remains work; `inalloca` coroutine parameters are unsupported; the docs list alignment ignored by `coro.begin`/`coro.free` and LTO optimization work among open areas. The frame-layout source *does* track alignment, so the alignment note must not be exaggerated into "all coroutine alignment is ignored." Neither these docs nor frame-size constants establish checks before every generated write or runtime/C-ABI temporary. [L-coro-limits], [L-frame]

Rust async is a pattern/reference, not LLVM `coro` reuse. At Rust revision `41089d07a0a2afc16adfe28a760d94d73d7298a4` (the installed compiler revision inventoried by the parent), `rustc_mir_transform/src/coroutine/mod.rs` directly describes the MIR state-machine transform, captures, suspend-live locals and drop shim. Its own `Pin` docs identify async state machines as potentially self-referential. Pinning a Rust object does not pin the host base of Wasm linear memory, bound its allocation, flatten recursive futures, guarantee proper tails or implement Rill's suspendable masked cleanup/join contract. Boxed recursive futures merely trade native recursion for retained heap state unless explicitly flattened/replaced. [Rust-transform], [Rust-pin]

Useful second probe: `retcon` with a checked arena-backed allocation path, deliberately undersized/overaligned buffers, and a returned-continuation trampoline; inventory every generated byte and every fallback allocation. Do not begin with C++ coroutine library behavior or Rust executor conventions and assume they implement Rill.

### C. Tail-aware Asyncify is a redesign, not removal of two checks

Fresh inspection of Binaryen 133 establishes four relevant facts:

1. Analyzer visitors reject direct and indirect `isReturn` calls. Assert instrumentation separately assumes those calls return to its post-call check. [B-analysis], [B-assert]
2. The documented saved format contains a per-frame call-site index and saved locals; resumption begins by calling the same initial entry function. [B-format]
3. `makeCallSupport` admits the original static call when normal or when the rewind index matches, then performs a post-call unwind check. `AsyncifyLocals` loads the current function's locals on rewind and saves its own call index/locals in a postamble on unwind. A `return_call` cannot execute that eliminated caller's postamble. [B-control], [B-save]
4. `makeCallIndexPush` still contains the pre-end-check TODO; local saving stores/advances without complete pre-write containment. Control-export end checks occur too late for adjacent in-bounds storage. [B-save], [B-format]

A concrete rewind counterexample tests the naïve proposal to leave tails unchanged. `root` ordinarily calls `A`. `A` performs effect α and tails to `B`; `B` performs effect β and tails to `C`; `C` suspends. The surviving engine caller relationship is a call from `root` to `C`, not a chain through `A` and `B`, because core tail semantics remove the current frame. But root's existing saved call-site index identifies its static call to A. [W-tail], [B-control]

Re-entering A and simply running the uninstrumented tail-entry path would repeat α/β. Treating A as a normal rewind frame instead would try to consume C's saved layout/index as A's; skip guards do not reconstruct the missing target identity, argument values or layout. Saving A and B to make that replay work restores forbidden tail-history growth. This is a source-derived counterexample to those proposed shortcuts, not an executed result from a patched Binaryen.

A plausible redesign must carry the actual surviving target/resume descriptor across each ordinary edge (and at a tail-called exported root): target identity/signature, correct live argument/state representation, saved-layout/PC identity and return destination. Each tail updates/replaces that descriptor in bounded space, including indirect targets; rewind must enter the actual live target without replaying eliminated entries. It also needs checked saved pushes/local stores/alignment/overflow and complete addressable-stack checks. This starts to overlap explicit-record/CPS lowering at the binary level, where source ownership/liveness information is less available. No inspected official source supplies a proven patch or low-cost implementation; reject stock Asyncify and rejection-only patches as supported candidates, not the possibility of future redesign.

### D. JSPI, core stack-switching/WasmFX and host fibers

These are different mechanisms, not interchangeable names for a portable host facility.

- JSPI is real, not merely an old experimental proposal: the pinned WebAssembly proposal index places it at Phase 5, while core stack-switching is Phase 3. V8's pinned first-party introduction reports availability in Chrome 137 and Firefox 139; its old Phase-4 wording is older than the proposal index and does not demote the latter. This is documented availability, not browser execution here or a claim about Safari/all hosts. [P-status], [J-v8]
- JSPI wraps imports with `WebAssembly.Suspending` and exports with `WebAssembly.promising`, changing the JS boundary, not Wasm instructions. Thus it need not rewrite/remove valid core `return_call`s; actual engine composition still requires validation. It prohibits suspension across intervening JS frames. Neither API is a WASIp1 non-JS import contract, nor exposes per-routine retained-byte enumeration/pre-write saved limits. Optional JS deployment would need an explicit host/accounting strategy, not a promise-count proxy. [J-overview], [W-tail]
- Core stack-switching: the inspected explainer has `cont.new`, `resume`, `suspend`, `cont.bind`, symmetric `switch` and exceptional resumption. Continuations are one-shot; producing a suspension reuses the continuation, and consumed handles trap if reused. These are useful resource/control semantics, not a byte-budget API. `resume_throw` cancellation examples are not Rill's deferred-delivery/masked-cleanup/join implementation. Core tail calls remove frames; a future composition should preserve that, but no source inspected proves bounded retained implementation state for all combinations. [S-overview], [W-tail]
- WasmFX is a research/prototype lineage informing typed stack-switching. Its own site describes an instruction-set extension rather than a core-Wasm software fallback; its spec repository describes prototype specification/implementation. Do not count that as a separate deployed portable runtime. [FX-site], [FX-spec]
- Pinned Wasmtime availability: its proposal matrix calls core stack-switching Tier 3, unfinished, not Phase 4, with no finished API/C API, and implementation currently x86-64 Linux only. This does not supply the parent's macOS/AArch64 mechanism. The same matrix's component-model async support is a different ABI/proposal layer, not a Preview1 stack-suspension facility. [T-status]
- Wasmtime native async fibers: the C API and Rust implementation execute on a separately allocated stack and park it; untouched return calls are a legitimate control, consistent with the parent's positive evidence. `max_wasm_stack` and `async_stack_size` govern host mechanism limits/headroom, not the two Rill managed budgets. A custom stack allocator can observe whole allocations but does not inventory every live activation, host frame, alignment gap or external continuation object. Charging a whole fiber conservatively is a possible accounting *question*, not a demonstrated per-routine Saved policy, and remains host-specific. [T-async], [T-fiber], [T-config]

JSPI/native fibers likely minimize guest transformation and avoid Asyncify's unwind/rewind walk; core continuations could support efficient switching. Those qualitative benefits do not establish portable deployment, deterministic Saved accounting or safe native leases. No candidate is entitled to exempt engine-retained activation state just because the engine owns it.

### E. Credible lower-implementation-cost variants

Returned-continuation lowering plus an explicit trampoline is the strongest compiler-assisted variant to investigate after A: reuse LLVM spill/layout code, retain Rill control of records and dispatch. It reduces one implementation task, not the ownership/ABI/accounting tasks, and must expose fallback allocations. See B.

Selective interpretation / state-machine islands: Binaryen's own historical design discussion describes Emterpreter-Async as a bytecode VM where suspension is trivial, avoiding pathological rewrite code-size growth but paying interpretation cost; selective interpretation kept non-suspending computation compiled. This is concrete published primary-source precedent, not evidence to adopt that old toolchain. A small Rill bytecode interpreter could make PC/frame layout and pre-write checks uniform; it still needs tail replacement, stable addressable slots, full cleanup state and charged interpreter/runtime metadata. [B-history]

Later, proven non-suspending, statically bounded-call-depth helpers can remain direct compiled calls inside either variant. "Cannot suspend" alone does not bound recursive native stack growth, and imported/runtime callbacks can reenter/suspend. An effect/call-graph analysis would be another compiler obligation. This is an optimization research direction, not permission to narrow which Rill calls may suspend. No inspected source establishes a cheaper drop-in portable combination meeting every #22 requirement.

## 4. Prototype design recommendation and bookkeeping traps

The parent agent should first probe A with a minimal manually lowered C machine, compiled through LLVM 23 to `wasm32-wasip1`. It should use no `return_call`, Asyncify or host fibers. Tail *semantics* come from replacement, not optimization. Inspect generated Wasm in development and optimized builds to establish this mechanism and account for all live ordinary records. A module with the intended triple and test imports is not automatically a complete WASI command/provider implementation.

Use a per-routine ledger and report current/peak addressable, Saved and temporary reservations separately, plus allocated/retained backing and metadata. Avoid these omissions:

- Count Saved records, headers, PCs, function IDs and ordinary-return links. Also count argument copies, suspend-live scratch, aggregate results, pending registrations, resume payloads, activation-specific allocator headers, alignment slack and side tables. Count any transient old+new record overlap or bounded staging during replacement before writing it, including an allocation outside the arena. No per-tail heap trace/sample log.
- Count addressable borrowed slots and live caller storage, oversized alignment padding, outgoing indirect/byval arguments, aggregate/return buffers, compiler-generated memcpy/memmove temporaries, C/runtime entry frames and dispatcher/helper frames. A result pointer into the replaced record is not a valid earlier-caller result destination.
- Fixed addressable arenas do not eliminate the transient C-ABI linear stack. Conservatively reserve and charge a bounded slice of that routine's addressable capacity, established by the full linked call graph and generated frames, including worst live outgoing/return areas, alignment and the ABI's 128-byte leaf red zone. Reserve/admit it before the first prologue/store; a check inside an already-writing callee is too late. Helpers with unknown recursion, dynamic alloca or unbounded reentry invalidate that bound. Reject that probe configuration or instrument it; do not silently exempt runtime frames. Binaryen `stack-check` only instruments SP assignments and cannot cover red-zone stores. [W-abi], [B-stack]
- At a real yield, the proposed C stack has fully returned and is not Saved. If any implementation retains C/runtime frames across suspension, it must add them to the retained-state inventory rather than call them "transient." Engine-native stack/host function limits are still a separately configured fatal boundary; a charged guest C stack is not a guard on arbitrary host-native recursion. [W-abi], [T-config]
- Test fixed-size record replacement with varying/aligned callees. Account for free-list fragmentation/caches and temporary copies. Test allocation failure, double completion, stale resume, and result/cleanup state after ordinary returns. "Current live record count is constant" does not prove allocated capacity or hidden bookkeeping stays bounded with transfer count.

Reserving records from entry rather than serializing only on suspension is a candidate implementation policy. Exact capacity/admission effects, minimum usable capacities, double-purpose storage classification and maximum-record-versus-variable-record layout remain architecture choices, not settled source facts. Record conservative overheads explicitly; do not market the nominal 1 MiB as 1 MiB of user locals plus free runtime space.

## 5. Shared containment, borrow and cleanup protocol

### Checks before writes, not eventual traps

For every record/slot/temporary reservation, validate alignment, checked upward rounding and representability when converting u64 to wasm32. Compute padding and total bytes without wrapping. Require `offset <= limit` and `needed <= limit - offset` before stores/copies or pointer publication. Check the complete live peak at calls and tail argument shuffles, including outgoing and return storage. Exact-fit is valid only after alignment/headroom accounting. Fail fatally with bounded best-effort reporting; do not resume normally or attempt recursive formatting/cleanup on exhausted capacity. Overall Wasm bounds protect the whole memory, not adjacent logical routine regions. These are implementation requirements from #22, not checks automatically supplied by LLVM `coro`, interpreter dispatch or a host stack limit. [R22], [W-abi], [B-stack]

### Stable guest slots are not stable host pointers

Stable guest offsets survive suspension/dispatch and can remain valid after linear-memory relocation. Wasmtime's pinned memory docs explicitly warn that growth/reentry can invalidate native base pointers and aliasing assumptions; keeping a store/memory handle or pinning a guest frame does not prevent this. [T-memory]

For a portable prototype, prefer a copy/completion protocol:

1. Validate extents and access mode; synchronously copy inputs to independently owned native storage before the worker retains access. Mutable/out results need an explicitly owned output copy and an exclusive logical destination lease.
2. During normal execution/cancellation, retain source/destination owners, registration identity and dependent borrowed slots through actual completion/confirmed abort. A request/handle drop is not completion. For fatal guest termination, the worker must independently retain everything it actually accesses; only independent copies may outlive store destruction, never raw guest pointers. Store destruction is unsafe if any foreign borrower still accesses guest backing.
3. A pending operation carries offsets/lengths/generation/ownership state, not a cached guest base. After completion, reacquire current memory/base/extent under sanctioned exclusive store access; validate the operation/destination is still live and perform copyback once. No post-fatal copyback into a destroyed store. Free copies only after foreign access ceases.
4. If testing zero-copy later, specify a whole-memory no-growth/no-conflicting-access lease covering every guest/embedding/reentrant growth route and storage lifetime, or a host's demonstrated stable-backing mechanism. Wasmtime reservations/pooling can prevent movement, but are host-specific and do not eliminate aliasing/completion rules. A lease that forbids growth does not demonstrate successful growth during an outstanding raw-pointer borrow; the copied-buffer case does permit legal guest growth. [T-memory], [T-memory-config]

Candidate A's return-to-driver scheduling avoids a parked engine future, making legal memory access between completed core calls easier to express. It is not permission for concurrent access to one store. With Wasmtime's existing async-fiber C API, only one call future may be alive per store and its parameters/context must remain alive/unmodified until deletion; retaining a temporary `caller` or growing the store from an unrelated outer API call while pending violates the API. Use guest growth after the copy handoff, or a legal between-call explicit-record interleaving. [T-async]

### Cleanup, joins and masks

Represent initialized fields, disposer progress, protected actions, child/native join progress and cancellation-delivery mask state explicitly across every yield. Continue iterative cleanup in dependency/order-correct phases, defer cancellation delivery during mandatory cleanup, and reclaim records/slots only when execution and required cleanup/borrowers have completed or confirmed release. A native callback finalizer/continuation drop is not necessarily foreign-job completion. [R22], [R30], [T-fiber]

Legitimate cleanup/cause worklists may grow with pending semantic data; they must not disguise one activation per eliminated tail. Their allocation failure is fatal, not recursive fallback. LLVM destroy functions, Rust drop shims, JS Promise rejection and `resume_throw` are mechanisms to integrate, not implementations of Rill's ordering/masking/joins. Pending obligations preserve ordinary calls, even if a dispatcher could mechanically overwrite the record. [R22], [L-coro], [Rust-transform], [S-overview]

## 6. Exact next validation cases and remaining decisions

The parent should first run A with finite counts and explicit invariants, in O0/development and optimized modes; retain every build command, tool hash, IR/WAT and result. Suggested minimal matrix:

1. Tail-only: self/mutual/indirect transfers at increasing counts (including a million), yields before/after target changes, varying argument/record sizes and alignments, aggregate result via an earlier live caller. Assert results/effect counts, bounded live and allocated activation storage, unchanged retained-record high-water versus chain length, and bounded native/engine nesting. No per-transfer observer allocation.
2. Ordinary ancestor + tail chain: root ordinarily calls A. A tail cycle through A, B and C mutates arguments and effect counters; C yields repeatedly, then returns. Assert effects run once, actual live target/PC resumes, caller result/slots survive and the chain never reappears as retained records. This also specifies the critical future Asyncify-redesign counterexample; do not claim it tests an unimplemented patch.
3. Ordinary negative controls: caller-local borrow used across yield, pending guard/disposer, child/native join, explicit error wrapping. Retain caller record/slots; assert expected growth for live ordinary depth, fatal Saved exhaustion at a small configured capacity, and no early release. Manual classification is not a checker test.
4. Pre-write limits: exact-fit and one-byte-over cases; huge/near-u32 and u64 alignment/size overflow; simultaneous old/new tail-argument staging; oversized/outgoing/indirect/byval arguments and aggregate return buffers; high-alignment leaf red zone and runtime-helper entry at almost-exhausted addressable capacity. Place canaries adjacent to each logical region; failure must precede any out-of-budget store. Verify admission includes the C-ABI reserve in both build modes.
5. Separate resources/multiple routines: two routines may each approach 1 MiB Saved under the same program-wide setting without an invented aggregate 1 MiB quota. Independently exhaust each routine's addressable and Saved regions; separately test host engine exhaustion in isolated invocations, fatal to Rill but not necessarily the embedding process. No normal cleanup guarantee on fatal failure.
6. Growth/foreign completion: hold an independent worker copy, grow/relocate guest memory legally while the operation is pending, resume by offsets and copy back only after completion/exclusive reacquisition. Cancel/drop/fatally terminate guest before worker completion; worker touches only its retained copy, releases once after actual cessation, and never uses a stale base or destroyed destination. If a later zero-copy lease is tested, try every prohibited growth/reentry route and confirm enforcement rather than assuming it.
7. Cleanup: deeply nested initialized/partially initialized structures and full explicit cause chains; suspended disposer/join callbacks; cancellation requested during masking; order/once-only observations; stale/double wakeup; worklist/record allocation failure. Measure bounded standard traversal call depth while preserving legitimate worklist data. Arbitrary user callback recursion is not transformed into a standard-library guarantee.
8. Machinery comparison only after the baseline: a small LLVM `retcon`/switched-resume case with checked allocator, over-aligned frame and fallback allocation; symmetric-transfer IR/Wasm inspection with/without tail feature. Compare frame/header/padding and native call peaks, not just success. Preserve the existing Wasmtime-fiber control; no inference that any model replaces the approved runtime.

Not resolved by authoritative sources or this research: automated Rill MIR transformation and eligibility/checker soundness; complete aggregate/callable/runtime ABI; record layout/admission/charge classification; native-target integration/migration; provider-specific copy-versus-zero-copy semantics; full cleanup/masking/join implementation; universal engine allocation observability; performance or arbitrary-depth proofs. Adopting a replacement pipeline, a host-specific profile or any target change still needs an explicit decision. Proceed with a standalone explicit-record prototype without asking the user to select an architecture first; keep #30 open and #28's affected support gate unresolved.
