# Polymorphism without traits

Research for [issue #5](https://github.com/Reilley64/rill/issues/5). Sources were read on 2026-10-21. Links to source code are pinned to the commit that was read.

## Question

Rill has generics and overloading but no traits, classes, or type classes. This note answers two questions:

1. How do other languages let one operation behave differently per type?
2. How does a generic function say that it needs an operation on its type parameter, for example `sort<T>` needing comparison?

It covers C++, Zig, Julia, Gleam, OCaml, and Roc, and then looks at how overload resolution interacts with type inference.

## Summary

| Language | Per-type behavior | How `sort<T>` gets comparison | When a missing operation is reported |
| --- | --- | --- | --- |
| C++ | Overloading, templates, ADL | Unconstrained name lookup at instantiation, or a concept such as `std::sortable` plus a default comparator object | At instantiation; with concepts, at the call site |
| Zig | Separate functions, no overloading | `comptime` comparator function argument | When the instantiation is analyzed |
| Julia | Multiple dispatch on all arguments | Calls the generic function `isless`; `lt` keyword overrides it | At run time (`MethodError`) |
| Gleam | Separate functions, no overloading | Comparator function argument | Ordinary type checking of the argument |
| OCaml | Separate functions, modules, functors | Comparator argument, or a functor over a module with `compare` | Ordinary type checking |
| Roc | Methods on the argument's type (static dispatch) | `where [item.Sort]` clause, or `sort_with` comparator | At the call site and in the body |

## C++ templates and concepts

**Per-type behavior.** C++ uses function overloading. When a call names an overloaded function, the compiler does name lookup, which may include argument-dependent lookup (ADL), then template argument deduction, then picks the candidate whose parameters match the arguments most closely ([cppreference: overload resolution](https://en.cppreference.com/w/cpp/language/overload_resolution)). A function template is not a function by itself. No code exists until the template is instantiated with concrete arguments ([cppreference: function template](https://en.cppreference.com/w/cpp/language/function_template)).

**How a generic body finds the operation.** A template body can call `a < b` or `swap(a, b)` on a dependent type without declaring anything. Lookup of a dependent name is postponed until the template arguments are known. At that point ordinary lookup sees declarations visible at the template definition, and ADL also sees declarations visible at the point of instantiation ([cppreference: dependent names](https://en.cppreference.com/w/cpp/language/dependent_name)). ADL is why the generic-code idiom is `using std::swap; swap(obj1, obj2);`: a qualified `std::swap` call would not find a user-defined `swap` in the type's namespace ([cppreference: ADL](https://en.cppreference.com/w/cpp/language/adl)). So in C++, overloads defined next to a type act like trait implementations.

The lookup rules have a sharp edge. cppreference's example defines `operator<<` for `std::vector<int>` in a user namespace `P1`, then calls a library template that prints its argument. The call fails to find `P1::operator<<`, because that namespace is neither visible from the template definition nor associated with `std::vector<int>` ([cppreference: dependent names](https://en.cppreference.com/w/cpp/language/dependent_name)).

**Before concepts: SFINAE.** If substituting deduced types into a function template's signature fails, the specialization is dropped from the overload set instead of causing an error ([cppreference: SFINAE](https://en.cppreference.com/w/cpp/language/sfinae)). Library authors used this to enable or disable overloads by type.

**Concepts (C++20).** A concept is a named set of requirements, used in `requires` clauses or as a constrained parameter such as `Hashable auto` ([cppreference: constraints](https://en.cppreference.com/w/cpp/language/constraints)). Satisfaction is structural. The compiler substitutes the template arguments into the constraint expressions, and if any substitution is invalid the constraint is not satisfied ([cppreference: constraints](https://en.cppreference.com/w/cpp/language/constraints)). Types never declare that they model a concept. Violations are reported early in instantiation, which gives shorter messages than an error deep inside `std::sort` ([cppreference: constraints](https://en.cppreference.com/w/cpp/language/constraints)).

`std::ranges::sort` shows both halves of the `sort<T>` answer. It takes a comparator `Comp` that defaults to `ranges::less` and a projection, and requires `std::sortable<I, Comp, Proj>` ([cppreference: ranges::sort](https://en.cppreference.com/w/cpp/algorithm/ranges/sort)). `sortable` is defined as `std::permutable<I> && std::indirect_strict_weak_order<Comp, std::projected<I, Proj>>` ([cppreference: sortable](https://en.cppreference.com/w/cpp/iterator/sortable)). So the comparison is a function argument with a default, and the concept checks that the argument works.

**No definition checking.** C++ checks constraints at the call site but does not check the template body against them. Stroustrup writes that he first thought generic code should be checked in isolation, now considers that a mistake, and that "C++ concepts don't offer definition checking even though we know how to implement it" ([Stroustrup, Concept-Based Generic Programming in C++, section 7.7](https://www.stroustrup.com/Concept-based%20GP.pdf)). His reason is that templates often call things not named in the interface, such as logging.

**Concepts and overloading.** Constrained overloads are ranked by subsumption: an overload whose constraint implies another's is more specific. Subsumption works on the identity of atomic constraints, not on meaning, so `N > 0` does not subsume `N >= 0`, and two concepts that spell the same check separately make a call ambiguous ([cppreference: constraints](https://en.cppreference.com/w/cpp/language/constraints)).

## Zig comptime

**Generics.** Zig implements generics with compile-time parameters, and the language reference calls this "compile-time duck typing" ([Zig reference: compile-time parameters](https://ziglang.org/documentation/master/#Compile-Time-Parameters)). `fn max(comptime T: type, a: T, b: T) T` compiles for any `T` that supports `>`. Calling it with `bool` fails with `operator > not allowed for type 'bool'` when that instantiation is analyzed ([same section](https://ziglang.org/documentation/master/#Compile-Time-Parameters)). Parameters can also be `anytype`, with the type inferred at the call ([Zig reference: function parameter type inference](https://ziglang.org/documentation/master/#Function-Parameter-Type-Inference)).

**No overloading.** Zig has no operator overloading; an operator always means one of the built-in operations ([Zig reference: operators](https://ziglang.org/documentation/master/#Operators)). It also has no function overloading. Andrew Kelley closed a 2018 proposal for it, replying "No function overloading, no functions with default values" ([ziglang/zig#1251](https://github.com/ziglang/zig/issues/1251)).

**How `sort` gets comparison.** The standard library passes the comparison explicitly. `std.sort.insertion` takes `comptime T: type`, the slice, a `context: anytype`, and `comptime lessThanFn: fn (@TypeOf(context), lhs: T, rhs: T) bool` ([lib/std/sort.zig](https://codeberg.org/ziglang/zig/src/commit/c8bb44618a9c3c7bfff4a9f672a451fdeda1bb02/lib/std/sort.zig#L13-L40)). `std.sort.asc(T)` builds a comparator that uses `<` for types that have it ([lib/std/sort.zig](https://codeberg.org/ziglang/zig/src/commit/c8bb44618a9c3c7bfff4a9f672a451fdeda1bb02/lib/std/sort.zig#L131-L138)). The lower-level `insertionContext` takes any `context` that "must have methods `swap` and `lessThan`", stated only in a doc comment and checked by duck typing ([lib/std/sort.zig](https://codeberg.org/ziglang/zig/src/commit/c8bb44618a9c3c7bfff4a9f672a451fdeda1bb02/lib/std/sort.zig#L37-L42)).

**Stating requirements.** There is no constraint syntax. Authors can test a type with `@hasDecl`, which reports whether a type has a public declaration with a given name ([Zig reference: @hasDecl](https://ziglang.org/documentation/master/#hasDecl)), and fail with `@compileError` ([Zig reference: @compileError](https://ziglang.org/documentation/master/#compileError)). A proposal for compile-time interfaces was closed as not planned. Andrew Kelley's reply suggests users accept that Zig "may never gain an interface-like feature" ([ziglang/zig#1268](https://github.com/ziglang/zig/issues/1268)).

**Runtime polymorphism.** This is done by hand with a struct of function pointers. `std.mem.Allocator` holds a context pointer and `vtable: *const VTable` ([lib/std/mem/Allocator.zig](https://codeberg.org/ziglang/zig/src/commit/c8bb44618a9c3c7bfff4a9f672a451fdeda1bb02/lib/std/mem/Allocator.zig#L23-L25)). The long-running vtable proposal was closed with "the plan is to not add an additional dynamic dispatch language feature" ([ziglang/zig#130](https://github.com/ziglang/zig/issues/130)).

## Julia multiple dispatch

**Per-type behavior.** A Julia function is a generic function with many methods. Dispatch chooses a method using the number of arguments and the types of all arguments, not only the first ([Julia manual: methods](https://docs.julialang.org/en/v1/manual/methods/)). The manual's motivation is arithmetic: `x + y` does not belong to `x` more than to `y` ([same page](https://docs.julialang.org/en/v1/manual/methods/)). Julia is dynamically typed. A call with a combination of concrete argument types not seen before triggers specialization in a just-in-time compiler, and inlining can turn a dispatched call into a direct one ([Bezanson et al., Julia: dynamism and performance reconciled by design, OOPSLA 2018](https://janvitek.org/pubs/oopsla18b.pdf), [DOI](https://doi.org/10.1145/3276490)).

**How `sort` gets comparison.** Sorting calls `isless` by default, and the `lt` keyword replaces it with any function ([Julia manual: sorting](https://docs.julialang.org/en/v1/base/sort/)). A user type becomes sortable by adding an `isless` method. Nothing in `sort`'s signature states the requirement. Julia calls these "informal interfaces": define a few methods and generic code works with your type ([Julia manual: interfaces](https://docs.julialang.org/en/v1/manual/interfaces/)). A missing method shows up as a `MethodError` when the call runs ([Julia manual: methods](https://docs.julialang.org/en/v1/manual/methods/)).

**Ambiguity.** With `g(x::Float64, y)` and `g(x, y::Float64)`, the call `g(2.0, 3.0)` matches both and neither is more specific. Julia raises a `MethodError` instead of picking one, and the fix is to add `g(::Float64, ::Float64)` ([Julia manual: method ambiguities](https://docs.julialang.org/en/v1/manual/methods/#man-ambiguities)). The manual warns that the more methods a function has, the more ambiguities appear, and that adding intersection methods mechanically can be counterproductive ([Julia manual: avoiding ambiguities](https://docs.julialang.org/en/v1/manual/methods/#man-method-design-ambiguities)).

**Grouping types.** To dispatch on a set of types that does not follow the type hierarchy, Julia code uses the "Holy-trait" pattern: a function maps each type to a singleton value, and methods dispatch on that value ([Julia manual: trait-based dispatch](https://docs.julialang.org/en/v1/manual/methods/#Trait-based-dispatch)). Iteration uses this, for example `Base.IteratorSize` ([Julia manual: interfaces](https://docs.julialang.org/en/v1/manual/interfaces/)).

**Open method tables.** Any module can add methods to any function. The style guide names adding methods to functions you do not own, on types you do not own, "type piracy", and warns that it causes hard-to-predict incompatibilities ([Julia style guide](https://docs.julialang.org/en/v1/manual/style-guide/#avoid-type-piracy)).

## Gleam

**No ad hoc polymorphism.** Gleam's FAQ lists "Function and operator overloading" and "Type classes or traits" among features that are not planned ([Gleam FAQ](https://gleam.run/frequently-asked-questions/#What-features-are-not-planned-for-Gleam)). The stated reasons for leaving out type classes: they make hard-to-understand code easy to write, give confusing errors, make the code hard to use from other languages, cost compile time, and cost run time unless the compiler does whole-program monomorphization ([Gleam FAQ](https://gleam.run/frequently-asked-questions/#Will-Gleam-have-type-classes)).

**Per-type behavior.** Each type gets its own functions and operators. Float arithmetic uses `+.`, `-.`, `*.`, `/.`, and `<.`, because "Gleam's numerical operators are not overloaded" ([Gleam tour](https://tour.gleam.run/everything/)). Equality is the exception: `==` works on any type ([Gleam tour](https://tour.gleam.run/everything/)).

**How `sort` gets comparison.** The caller passes it: `pub fn sort(list: List(a), by compare: fn(a, a) -> Order) -> List(a)`, called as `list.sort(xs, by: int.compare)` ([gleam_stdlib list.gleam](https://github.com/gleam-lang/stdlib/blob/13359e53d6256c4f1ccf1a60e62dbfa3f1de2d57/src/gleam/list.gleam#L1125-L1137)).

**Possible future.** Asked about ad hoc polymorphism, Louis Pilfold wrote that such features "open the door to code that is very difficult to understand and modify" and that Scala 3's `given`/`using` looked closer to what Gleam might have one day ([gleam-lang/gleam discussion #1244](https://github.com/gleam-lang/gleam/discussions/1244)).

## OCaml modules and functors

**Per-type behavior.** The core language does not overload arithmetic: `(+)` is `int -> int -> int` and `(+.)` is `float -> float -> float` ([OCaml Stdlib](https://ocaml.org/manual/5.2/api/Stdlib.html)). Comparison is the exception. `compare` and `<` are polymorphic structural orderings over all types. Comparing functional values raises `Invalid_argument` at run time, and cyclic values may not terminate ([OCaml Stdlib](https://ocaml.org/manual/5.2/api/Stdlib.html)).

**How `sort` gets comparison.** `List.sort : ('a -> 'a -> int) -> 'a list -> 'a list` takes the comparison function ([OCaml List](https://ocaml.org/manual/5.2/api/List.html)).

**Functors.** Functors are functions from modules to modules ([OCaml manual: module system](https://ocaml.org/manual/5.2/moduleexamples.html)). A module type lists the operations a parameter must provide. `Set.Make` takes `Ord : OrderedType`, whose signature is a type `t` and `val compare : t -> t -> int` ([Set.Make](https://ocaml.org/manual/5.2/api/Set.Make.html), [Set.OrderedType](https://ocaml.org/manual/5.2/api/Set.OrderedType.html)). This is the closest OCaml equivalent of `T: Ord`, with the instance named and applied explicitly. Functor signatures can keep the result type abstract, so a set built from one ordering has its own type ([OCaml manual: functors and type abstraction](https://ocaml.org/manual/5.2/moduleexamples.html)).

**First-class modules.** A module can be packed into an ordinary value and unpacked later, so a bundle of operations can be passed at run time ([OCaml manual: first-class modules](https://ocaml.org/manual/5.2/firstclassmodules.html)).

**Modular implicits.** White, Bour, and Yallop proposed modular implicits: implicit module parameters chosen by type, which elaborate into OCaml's first-class functors and give type-class-like overloading ([arXiv:1512.01895](https://arxiv.org/abs/1512.01895)). The OCaml 5.2 manual's language extensions chapter does not include them ([OCaml manual: language extensions](https://ocaml.org/manual/5.2/firstclassmodules.html)).

## Roc abilities and static dispatch

Roc is the closest match to Rill's question, because it replaced a type-class-like feature with something lighter.

**Abilities (the earlier design).** An ability defined a set of functions that different types implement, and type variables were constrained with `where a implements Encoding` ([Roc abilities doc, 2025](https://github.com/roc-lang/roc/blob/67c6c66f22567873e90d4c683968aed07db8dc58/www/content/abilities.md)). Builtin types got builtin abilities automatically. Opaque types opted in with `implements [Eq, Hash]` or gave custom functions such as `Eq { isEq: colorEquality }` ([same doc](https://github.com/roc-lang/roc/blob/67c6c66f22567873e90d4c683968aed07db8dc58/www/content/abilities.md)). A `Sort` ability with `compare` was only a proposal ([same doc](https://github.com/roc-lang/roc/blob/67c6c66f22567873e90d4c683968aed07db8dc58/www/content/abilities.md)). The implementation tracking issue listed dictionary passing versus monomorphization as an open choice ([roc-lang/roc#2463](https://github.com/roc-lang/roc/issues/2463)).

**The switch.** In January 2025 Roc opened "Move to Static Dispatch in place of Abilities", describing it as letting trait-like code "simply use functions instead of having to define abilities" ([roc-lang/roc#7458](https://github.com/roc-lang/roc/issues/7458)).

**Static dispatch (current).** Methods are functions defined in a block after a nominal type's declaration. `value.method(a, b)` means `Type.method(value, a, b)`, where `Type` is the compile-time type of `value` ([Roc langref: static dispatch](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). Operators desugar to methods on the left operand, for example `a + b` calls `a.plus(b)` and `==` calls `is_eq` ([same page](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). The langref says these "aren't interfaces or traits that a type implements": a type just has a method with the right name and type ([same page](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). Number and string literals also go through methods (`from_numeral`, `from_quote`) ([same page](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)).

**How `sort` gets comparison.** A generic function lists the methods it calls in a `where` clause: `show_all : List(a) -> Str where [a.to_str : a -> Str]` ([Roc langref: where clauses](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). Named groups of constraints are "where aliases", and any type with the methods satisfies them without declaring anything ([same page](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). The builtin is `item.Sort : where [item.order_relative_to : item, item -> [Before, Same, After]]` ([Builtin.roc](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/src/build/roc/Builtin.roc#L3894)), and `List.sort : List(item) -> List(item) where [item.Sort]` sits next to `sort_with`, which takes an explicit comparator ([Builtin.roc](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/src/build/roc/Builtin.roc#L4186-L4203)).

**Checking.** Unlike C++, Roc checks both sides. Calling a method on a type variable without listing it in the annotation's `where` clause is an error, and each call site is checked for the method ([Roc langref: where clauses](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). Without an annotation, the compiler infers the `where` clause ([same page](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)).

**Cost.** A function with a `where` clause is compiled separately for each type it is used with, and each method call is a direct call, with "no table of methods passed around at runtime" ([Roc langref: performance](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). Roc's FAQ says Roc compiles by monomorphizing and rejects rank-2 types partly because they would block full monomorphization ([Roc FAQ](https://github.com/roc-lang/www.roc-lang.org/blob/f10bbbdcae18f28fdc8ca59655f47825bbccddeb/website/content/faq.md#L129-L155)).

**Derived methods and defaults.** Structural records, tuples, and tag unions get `is_eq`, `to_hash`, and encoding methods automatically when their contents support them. Nominal types opt in with `is_eq : _` ([Roc langref: compiler-derived methods](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)). When nothing fixes a number literal's type, the compiler picks the first type in a fixed list that works, starting with `Dec`, and warns if that made a function's inferred type more specific ([Roc langref: number literal defaulting](https://github.com/roc-lang/roc/blob/534956997e8e5c62888bc14cbc763f60109d0b72/docs/langref/static-dispatch.md)).

Roc's dispatch looks only at the type of the value before the dot. It is not overloading on all parameter types, which is what Rill's glossary describes.

## Overload resolution and type inference

**Why the two conflict.** Hindley-Milner inference works out a variable's type from how it is used. Overload resolution works out which function a name means from the argument types. If the argument types are themselves being inferred, the resolver has to search. Palsberg proves that overload resolution in a lambda calculus where bound variables have no annotations is NP-complete, by reduction from 3SAT ([Palsberg, Overloading is NP-complete](https://web.cs.ucla.edu/~palsberg/paper/dedicated-to-kozen12.pdf)). The same paper shows that Java, which requires every formal parameter to have a type, can resolve overloading in polynomial time, by induction over expressions whose argument types are already known ([same paper, section 8.1](https://web.cs.ucla.edu/~palsberg/paper/dedicated-to-kozen12.pdf)). Type classes were introduced as a way to add overloading to Hindley-Milner, generalizing Standard ML's `eqtype` variables ([Wadler and Blott, How to make ad-hoc polymorphism less ad hoc](https://homepages.inf.ed.ac.uk/wadler/topics/type-classes.html)).

**Swift: inference blowup.** Swift type-checks with a constraint solver. An overloaded reference becomes a fresh type variable plus a disjunction with one branch per overload ([Swift TypeChecker.md](https://github.com/swiftlang/swift/blob/db53009c0ef28309fd5d840d7b62f81af4e422c6/docs/TypeChecker.md)). The document says solving can take exponential time in the worst case, that overload resolution adds to this, and that Swift limits inference to a single expression or statement for performance and diagnostics ([same document](https://github.com/swiftlang/swift/blob/db53009c0ef28309fd5d840d7b62f81af4e422c6/docs/TypeChecker.md)). When the solver gives up, users see "the compiler is unable to type-check this expression in reasonable time; try breaking up the expression into distinct sub-expressions" ([DiagnosticsSema.def](https://github.com/swiftlang/swift/blob/db53009c0ef28309fd5d840d7b62f81af4e422c6/include/swift/AST/DiagnosticsSema.def#L202-L204)). When several solutions remain, Swift scores and ranks them instead of always reporting ambiguity ([Swift TypeChecker.md](https://github.com/swiftlang/swift/blob/db53009c0ef28309fd5d840d7b62f81af4e422c6/docs/TypeChecker.md)).

**C++: resolution per call.** C++ resolves each call by matching its candidates against the types of the argument expressions ([cppreference: overload resolution](https://en.cppreference.com/w/cpp/language/overload_resolution)). Function parameters have declared types or are template parameters deduced from the arguments, which is the same shape as Palsberg's polynomial-time Java case. Ambiguity is a hard error: with `f(long)` and `f(float)`, `f(0)` is ambiguous ([cppreference: overload resolution](https://en.cppreference.com/w/cpp/language/overload_resolution)). An overloaded name used as a value, not called, needs a target type from context, such as the variable being initialized or the parameter it is passed to ([cppreference: address of an overload set](https://en.cppreference.com/w/cpp/language/overloaded_address)).

**TypeScript: first match wins.** TypeScript picks the first matching overload signature in declaration order, so a general signature listed first hides later ones ([TypeScript: do's and don'ts](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html)). It resolves a call to a single overload, so `len(cond ? "hello" : [0])` fails even though each overload accepts one branch. The handbook advises union-typed parameters over overloads where possible ([TypeScript handbook: functions](https://www.typescriptlang.org/docs/handbook/2/functions.html)).

**Standard ML: overloading without generalization.** SML has a fixed set of overloaded operators, and programs cannot add more ([SML Basis: top-level environment](https://smlfamily.github.io/Basis/top-level-chapter.html)). When context does not fix the type, the operator defaults to `int` (or `real` for `/`). So `fun f(x,y) = x <= y` gets type `int * int -> bool`, not a generic type ([same page](https://smlfamily.github.io/Basis/top-level-chapter.html)).

**Known pitfalls, collected.**

- Ambiguity. Two overloads match and neither is more specific (C++ `f(0)`, Julia `g(2.0, 3.0)`, C++ concepts with separately spelled constraints). Languages either reject the call (C++, Julia) or break ties by order (TypeScript).
- Hidden overloads. With first-match rules, a general overload declared early makes later ones unreachable (TypeScript).
- Inference blowup. With unannotated parameters, resolution is NP-complete in general (Palsberg). Swift shows the practical cost even with inference limited to one statement.
- Defaulting surprises. When nothing fixes a type, a default is picked (SML `int`, Roc `Dec`), which can make a function less generic than it looks.
- Visibility. Which overloads a generic body can see depends on lookup rules (C++ ADL and the `operator<<` example; Julia's open method tables and type piracy).
- Late errors. If requirements are not declared, a missing operation appears inside the generic body (C++ without concepts, Zig) or at run time (Julia).

## Implications for Rill

The follow-up grilling ticket needs to decide the points below. Each lists the options seen above and their trade-offs.

1. **How a generic function states that it needs an operation.**
   - No declaration. The body calls `compare(a, b)` and each instantiation is checked (C++ templates, Zig). Simple to specify. Errors appear inside the generic body, and the signature does not document the requirement.
   - A structural constraint that names the overloads it needs, for example something like `where compare(T, T): Ordering` (Roc `where` clauses, C++ concepts). Types do not declare conformance. Sub-choice: check only call sites (C++), or also check that the body uses nothing else (Roc). Body checking gives earlier errors; Stroustrup argues it makes templates harder to use.
   - Pass the operation as an argument (Gleam, OCaml `List.sort`, Zig `std.sort`, Roc `sort_with`). Needs no new feature. More verbose at call sites. Roc and C++ combine this with the constrained form (`sort` plus `sort_with`, or a defaulted comparator argument).
   - Pass a bundle of operations as a value (OCaml functors and first-class modules, Zig's hand-written vtable). Explicit, and allows several orderings for one type. Heavier syntax.
2. **Where satisfying overloads are looked up.** Options: only next to the type (Roc's methods block), the caller's scope, anywhere in the program (Julia, with the type-piracy risk), or the C++ mix of definition scope plus the argument type's namespace. This decides whether two libraries can give conflicting `compare` overloads for one type.
3. **What an overload dispatches on.** All parameter types (C++, Julia, and Rill's glossary today) or only the first argument (Roc). All-argument dispatch handles `Vector * Scalar` and `Scalar * Vector` naturally but has more ambiguity cases.
4. **Ambiguity policy.** Reject ambiguous calls (C++, Julia), pick by declaration order (TypeScript), or rank by specificity (Julia's most specific method, C++ subsumption, Swift's scores). Ranking reduces errors but makes the chosen overload harder to predict.
5. **Inference boundaries.** Whether overloaded functions, top-level functions, and lambda parameters must have type annotations. Required annotations keep resolution polynomial (Palsberg's Java argument). Inferring across larger regions risks Swift-style blowup. A related choice: when an unannotated generic function uses an overloaded operation, infer a constraint (Roc) or default to a concrete type (SML).
6. **Literal defaulting.** Whether an unconstrained literal gets a default type, which one, and whether the compiler warns when defaulting narrows a function's type (Roc).
7. **Compilation strategy.** Monomorphize each instantiation (C++, Zig, Roc) or pass operations at run time (OCaml functors, explicit function arguments). Monomorphization gives direct calls, larger binaries, and longer builds. Gleam's FAQ cites the run-time cost when a compiler does not monomorphize. Rill emits LLVM IR, so both are possible.
8. **Runtime polymorphism.** None of the static options gives heterogeneous collections. Without traits, Rill would need explicit records of functions (Zig's `Allocator`) or closures. This may belong in a separate ticket.
