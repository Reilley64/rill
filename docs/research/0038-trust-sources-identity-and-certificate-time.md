## 1. Bundled roots: maintained inputs are not interchangeable policy

| Candidate input | Facts established by primary sources | What a flat certificate export does not establish |
| --- | --- | --- |
| Mozilla NSS `certdata.txt` | Pinned Mozilla source contains certificate objects **and separate trust objects**, purpose-specific `CKA_TRUST_*`, `CKA_NSS_MOZILLA_CA_POLICY`, and server/email distrust-after attributes. `CKA_VALUE` alone is not the trust decision. [N1–N3] | The source's presence of a certificate, or its self-signature, does not authorize it for server TLS, client TLS or every purpose. |
| curl's Mozilla CA extraction | Maintained first-party converter defaults to `SERVER_AUTH:TRUSTED_DELEGATOR`; the hosted service checks daily and publishes SHA-256. Its official CA Extract page explicitly warns that browser-applied name/other constraints are **not carried into the PEM bundle**. [C1–C2] | A convenient PEM is not Firefox policy equivalence; a checksum delivered beside an artifact is not an independent authenticity guarantee. The inspected converter is not a general distrust-after evaluator. |
| CCADB-derived `webpki-roots` / `webpki-root-certs` | Pinned project has generation tooling, TLS trust-bit filtering, DER-versus-metadata SHA-256 checks, exclusions and explicit Mozilla applied-constraint handling. One output carries webpki trust anchors with constraints; the other carries full X.509 DER certificates. [W1–W3] | Do not transplant the constrained trust-anchor representation into a DER-only OpenSSL store and claim equivalent policy. The DER generator emits certificate bytes, not the external constraint field. |
| CCADB reports themselves | Official resources distinguish **operator-specific** reports from community reports containing roots trusted by **at least one** participating operator. Community trust bits aggregate stores; “constrained” booleans signal that constraint information exists. [D1] | “All included”, CT-log roots, all disclosed intermediates, an aggregate trust bit or a constraint boolean is not a selected Mozilla/Apple/Microsoft policy or the constraint's executable meaning. |

**Trust semantics to preserve or explicitly reject:** NSS defines `CKT_NSS_TRUSTED_DELEGATOR`, `TRUSTED`, `MUST_VERIFY_TRUST`, `NOT_TRUSTED`, `TRUST_UNKNOWN`, and `VALID_DELEGATOR`; these are not one true/false root bit. `TRUSTED` is not a delegation grant; absent/unknown/non-delegator purpose must not accidentally become an anchor grant. The inspected data distinguishes `CKA_TRUST_SERVER_AUTH`, email and code-signing; a server-auth bundle does not define mTLS client-anchor policy. Certificate-embedded KU/EKU/name constraints remain in DER, but **external** trust/reject/purpose/issuance-cutoff metadata does not. Whether a validator enforces an anchor's embedded extensions is a separate verifier setting/algorithm question. [N1–N3; RFC 5280 §§4.2.1.10, 4.2.1.12, 6.1.1]

**Distrust-after is not simply root expiry or “remove this root when today's date passes X”.** NSS exposes per-purpose UTCTime/false attributes. Pinned Firefox `IsDistrustedCertificateChain` compares the **end-entity `notBefore`** against the builtin root's cutoff: `notBefore <= cutoff` survives this particular test; later issuance is distrusted, with builtin/third-party-root distinctions. This is evidence about that implementation, not every consumer of NSS. [N3, F1] The CCADB generator instead keeps a website-trusted root while its generation date is before `cutoff + 398 days`; it does not encode a per-leaf issuance check in either output. Its constraint parser expressly calls multi-constraint syntax a “best guess”. This is a concrete reason to audit an extraction rather than call it policy-equivalent because it checks fingerprints. [W2–W3]

**Maintenance/provenance/security choices still required:** identify an operator and use case; pin upstream revision/report bytes, schema, extractor version, exclusions, constraint interpretation and output digest; record acquisition/generation date and generation-time dependencies (including wall date); retain reproducible inputs and an auditable update diff. Authentic delivery, rollback/staleness limits, emergency distrust/removal, release/advisory monitoring and a rebuild/redeployment owner are separate obligations. The webpki project warns that its bundles suit applications that can be promptly recompiled/deployed. An immutable snapshot intentionally does not update existing configurations when upstream changes; refresh/generation semantics and stale-source failure need explicit decisions. These are design options/validation requirements, not evidence of a Rill updater. [W1–W3, C2, D1]

**Licensing is source-specific, not certified here:** NSS data has an MPL-2.0 notice; curl identifies its converted bundle as MPL-2.0, while its converter code has the separate curl license. Review MPL §§3.1–3.4 source/executable distribution, notice and source-availability obligations for covered files/modifications; do not infer that all Rill code must become MPL. CCADB-derived data/tooling must not be assigned the NSS license by association: pinned webpki README identifies data as CDLA-Permissive-2.0 and tooling as MIT/Apache. CDLA §2.1 requires making its agreement text available with shared data; current CCADB usage terms additionally state attribution and non-endorsement requirements. Review the actual shipped artifacts, license copies/notices and applicable terms; no legal/FIPS/security certification follows. [N1, C1–C2, W1, D2, L1]

## 2. Native snapshots: avoid silently promoting constrained trust

**Linux:** a source must name its distro/service/paths and provenance, not just “Linux roots”. The inspected p11-kit trust module exposes PKCS#11 anchors, blocklists and other policy; paths/priority are build/configuration inputs. Ordinary DER/PEM contains no independent trust policy; `TRUSTED CERTIFICATE` can carry OpenSSL AUX trust/reject information. Location also matters: p11-kit treats plain certificates in an input file as anchors, while plain certificates in a directory are not automatically anchors unless under `anchors/`; `blocklist/` has distrust semantics. Copying every discovered certificate into one root set changes this meaning. [P1]

The extractor recognizes OpenSSL bundle/directory formats as purpose-policy capable. For plain formats it requires/filter-defaults to one purpose (server-auth); it refuses a combined anchors-plus-blocklist export to a format that cannot represent policy. Enumeration prevents matching blocklisted issuer/serial or public-key entries from becoming anchors. But its manual explicitly says **no available extraction format preserves blocklist entries lacking a full certificate**, e.g. issuer+serial-only distrust. Such a leaf/intermediate could still chain through another retained anchor: subtracting roots is not a complete substitute for chain-wide distrust. OpenSSL AUX exports carry trust/reject OIDs, not an arbitrary native-policy interpreter; conversion to ordinary certificate DER discards AUX. No complete translation of attached constraints or NSS distrust-after into OpenSSL verification was established. [P2–P4]

A distro-generated purpose-filtered PEM can be a deliberately narrower, named **PEM-source** contract, but neither its freshness/completeness nor equality with the live p11-kit policy follows from successful parsing. Loading a mutable/lazy directory is not an owned immutable snapshot; copy/parse the selected material and retain provenance if that model is chosen. Missing, empty, partially parsed or unrecognized-policy sources need explicit failure, not provider-default fallback. This note did not inspect live native stores or establish race-free snapshot acquisition. [P1–P4; prior provider note §5]

**macOS:** pinned `SecTrustSettings.h` documents User/Admin/System domains and arrays of usage-constraint dictionaries. Within a dictionary **all supplied components must match**; across dictionaries any matching usage can apply. Components include policy, application, policy string (**hostname for SSL**), key usage, result and allowed error. Results distinguish `TrustRoot`, `TrustAsRoot`, `Deny`, `Unspecified`; absence of a result defaults to `TrustRoot`. An **empty settings array** means always-trust-root, whereas **no settings** means verify to a known trusted certificate; empty settings on a non-root are invalid. Thus neither “certificate enumerated” nor “some setting says TrustRoot” means unconditional TLS trust. [A1]

`SecTrustCopyAnchorCertificates` returns default system root certificates, not a serialized policy engine. `SecTrustSettingsCopyCertificates` enumerates certificates with settings in a domain; the copy-settings API retrieves the dictionaries. The supplied rustls-native-certs example is extraction, not per-chain `SecTrust`. `SecPolicyCreateSSL(server, hostname)` and `SecTrustEvaluateWithError` evaluate a concrete purpose/name/chain; evaluation can involve intermediates/revocation/network and further platform policy. No claim that every Apple policy restriction, host constraint, precedence rule, deny or runtime update can be enumerated losslessly into DER is justified by these headers. [A1–A3; prior verification note §5]

**Fail-closed extraction — possible requirement, not a proved portable algorithm:** accept only understood grants, apply applicable denials/precedence, and preserve all restrictions in an enforcement layer or exclude affected grants; if restrictions/denials cannot be conservatively represented, fail the source as unsupported. Unknown metadata must not be ignored and conditional host/purpose/application trust must not be promoted to unconditional trust. Even excluding a root can be insufficient when a distrust rule targets a leaf/intermediate reachable by alternate paths. Native evaluator equivalence, conservative-subset correctness, complete enumeration and cross-domain atomicity remain **unestablished**. A separate per-connection native evaluation would be another design/lifecycle policy, not an implicit property of an OpenSSL root snapshot. No native source is selected.

## 3. Validated DNS identity is not an opaque ASCII resolver name

- **Standards distinction:** RFC 9525 §§2, 6.3 uses preferred-syntax FQDNs and ASCII A-label comparison; supported U-label input must first become A-labels. RFC 5890 §§2.3.1–2.3.2.1 distinguishes an `xn--` **XN-label**, a valid A-label and a fake A-label: valid Punycode alone is insufficient; a valid U-label/NFC/context/bidi/round-trip relationship is part of the definition. A separate “validated A-label” value must not be advertised on the strength of LDH syntax alone. [R1–R3]
- **Do not overstate IDNA lookup obligations:** RFC 5891 §3.1 says comparison need not validate and successful equality does not imply validity. §5.3 permits IDNA-unaware/opaque lookup without decoding; decoding is **MAY**, validation **SHOULD** in the stated cases, and if decoded, §§5.4–5.5 processing and round-trip equality are **MUST**. Lookup checks differ from registration (§4); do not silently impose every registration restriction as a universal lookup requirement. Rill may choose stricter TLS identity construction, but that is a separate policy from #34's non-IDNA-aware ASCII lookup. [R2–R3]
- **Minimum DNS-host identity syntax/profile:** nonempty hostname labels, ASCII letters/digits/hyphen with no leading/trailing hyphen, label length ≤63 octets and DNS wire name ≤255 octets (normally ≤253 presentation bytes without the root dot); RFC 1123 §2.1 permits a leading digit. Reject NUL, empty internal labels, wildcard reference input and leading-dot suffix-search input. Underscores are valid in other DNS uses, but not this preferred hostname syntax/IDNA label class; RFC 9525 §6.5's SRV service underscore is not permission for underscore DNS-host identities. Numeric reference identity uses the separate IP route, not textual dNSName. [R1–R5]
- **Case/root dot/SNI:** compare ASCII case-insensitively, not locale/Unicode case folding. RFC 1034 §3.1 distinguishes absolute names with a terminal root dot from relative/search-list forms; RFC 9525 does **not** specify a general input-repair/strip-all-dots algorithm. Accept-and-remove **one** root dot for the TLS representation versus reject terminal-dot identity input is an explicit constructor choice; reject resulting empty/multiple-dot forms. Never use search-list expansion or resolver canonicalization as reference identity. RFC 6066 §3 requires SNI ASCII fully qualified hostname/A-label form **without a trailing dot** and prohibits literal IP addresses. Preserve routing's absolute-name intent separately if needed; normalizing TLS identity is not authorization to change DNS lookup behavior. [R1, R4, R6]
- **Minimum matcher enforcement:** SAN dNSName only, no CN fallback; independently supplied reference identity; whole-label ordered ASCII comparison. If supported, exactly one `*` as the entire leftmost **presented** label, matching exactly one reference label; invalid presented wildcard patterns ignored. IP-ID matches IP SAN octets, not DNS text. Public-suffix checking is outside RFC 9525's matcher (§7.1), not an implied requirement implemented by a wildcard flag. [R1 §§2, 6.1–6.4, 7.1]
- **OpenSSL isn't the constructor:** 3.5.9 documents A-label input, but does not promise IDNA validation. `NEVER_CHECK_SUBJECT` and `NO_PARTIAL_WILDCARDS`, without `MULTI_LABEL_WILDCARDS`, address important default mismatches; reject its leading-dot reference-search mode rather than treating `SINGLE_LABEL_SUBDOMAINS` as a substitute. `valid_star` additionally requires at least two dots in a wildcard pattern (so `*.com` is not accepted there); exact comparison is not routed through a full hostname validator. Flags alone establish neither reference syntax nor complete RFC conformance. Root-dot behavior, malformed SANs, wildcard suffixes and IDNA/version policy require later fixtures; none run. [O1]

## 4. Checked certificate time: precision and equality are real gaps

**Rill boundary:** `SignedDuration` is an elapsed quantity; `Clock`/`Instant` are elapsed clock-domain values, not Unix wall timestamps. `timestampNow():Result<Timestamp,TimeError>` supplies wall time; its exact-nanosecond value is not a claim of physical clock accuracy. `unixSecondsExact` errors on a fraction; `unixSecondsTrunc` explicitly truncates **toward zero**. A manual elapsed clock does not control certificate wall time. Do not add fake-wall-time provider injection or call a lossy conversion “exact”. [time contracts §§2–3](../time-contracts.md), [clock contracts §§1, 4](../clock-cancellation-contracts.md)

**Actual 3.5.9 path:** `X509_VERIFY_PARAM_set_time(param, time_t)` is a **void assignment**, setting `USE_CHECK_TIME`, not a checked conversion or wall-clock health check. The bridge must check acquisition/conversion before supplying it, and ensure the per-verification parameter is actually inherited/applied. Otherwise `X509_time_adj_ex` calls `time(&t)` and does **not check its return for failure**; conversion failure can surface later as a certificate-time-field error, but a representable failure sentinel is not a reliable typed wall-clock failure. Never infer fail-closed wall acquisition from that default path. [O2–O3]

The input is **integral seconds**, with no nanosecond parameter; native current time follows `time()`, and explicit Rill timestamps lose any fractional nanoseconds unless rejected. `X509_cmp_time` requires fixed `YYMMDDHHMMSSZ` / `YYYYMMDDHHMMSSZ` certificate forms (no fractional seconds); converts reference seconds through native `gmtime` and ASN.1; invalid formats/conversions return error. RFC 5280 §§4.1.2.5.1–.2 itself requires seconds and forbids GeneralizedTime fractions, but that does **not** make a nanosecond wall sample exactly representable in `time_t`. [O3–O4, R7]

**Bounds:** check the selected ABI's actual `time_t` signedness/width and representability **before** narrowing, then the provider/native UTC-calendar conversion range; do not assume signed 64-bit seconds or that every Rill Timestamp fits. Signed 32-bit Unix seconds, if selected, end at 2038-01-19 03:14:07 UTC. Native `gmtime` can reject otherwise representable seconds; certificate/reference ASN.1 conversion has additional format/calendar limits. Rill admits negative years while RFC 5280's four-digit GeneralizedTime does not represent them. No blanket portable supported range was proved here; the exact Linux/macOS ABI/libc range remains a distribution validation gate. [O2–O4; time contracts §2]

**Boundary discrepancy (source-established, not experimentally tested):** RFC 5280 §4.1.2.5 says `notBefore` through `notAfter`, **inclusive**. OpenSSL's `X509_cmp_time` returns `-1` for certificate time **≤** reference time, `+1` for later, `0` for error. `ossl_x509_check_cert_time` rejects `notBefore > reference` and `notAfter <= reference`: effective **[notBefore, notAfter)** at integer-second precision, including its trust-anchor time check. In particular, equality with `notAfter` is expired, not an inclusive success. This supplements/corrects any inference that the prior note's inclusive RFC statement describes OpenSSL's equality behavior. [O3, R7]

**Unselected policy options:** (a) checked native wall sampling with an explicitly seconds-granular provider contract; (b) checked Rill wall sample with a named quantization rule and documented boundary effects; (c) exact-only conversion, which fails on ordinary fractional samples; (d) a separately reviewed higher-precision validity enforcement design. Floor, ceil, nearest and truncation differ; truncation of negative epochs is **not floor**. Rounding upward can admit a not-yet-valid certificate; one-second adjustments cannot simultaneously restore both exact inclusive endpoints. Extra high-precision rejection can narrow acceptance, but cannot by itself recover an equality OpenSSL already rejects. No disable-time flag, success-returning verification callback, tolerance window, wall-failure fallback or boundary workaround is authorized. Sampling point, per-handshake versus immutable-config time, wall jumps/staleness, CRL/OCSP time and error mapping remain choices; never freeze “now” accidentally when freezing trust roots.

## 5. OpenSSL ambient inputs: private libctx is not an environment sandbox

| Input/path in pinned 3.5.9 | Controls actually supported / limits |
| --- | --- |
| Default configuration and includes (`OPENSSL_CONF`, `OPENSSL_CONF_INCLUDE`) | Early `OPENSSL_init_crypto(NO_LOAD_CONFIG, ...)` suppresses automatic config through a process/library-instance **once** decision; it cannot undo another consumer's earlier loading. Build `no-autoload-config` suppresses automatic default config. Neither prohibits explicit config loads. An independent `OSSL_LIB_CTX_new` with no config load plus `SSL_CTX_new_ex` can scope provider/property/RAND state; NULL/default-context APIs and global initialization remain distinct. [O5–O7] |
| Provider/engine discovery (`OPENSSL_MODULES`, `OPENSSL_ENGINES`) | Explicit per-libctx provider search path overrides the environment fallback; builtin providers avoid that dynamic module path. Reviewed `no-dso` / `no-engine` builds remove corresponding mechanisms, not all native loader/environment behavior. Explicit provider/property allowlists and no unreviewed modules are possible; libctx is not a process isolation boundary. [O6–O8] |
| `SSL_CERT_FILE/DIR`, optional CT/HTTP paths | Do not invoke default trust loaders: construct from the approved owned snapshot. Other optional APIs have their own inputs (`CTLOG_FILE`, HTTP proxy variables, etc.); inventory **reachable** paths. The environment manual includes application/script-only settings too; listing a name there is not evidence that every TLS handshake reads it. [O8; prior note §5] |
| `SSLKEYLOGFILE` | In an `enable-sslkeylog` build, `SSL_CTX_new_ex` reads it even with a private libctx, and key-file output is separate from the application keylog callback. `NO_LOAD_CONFIG` or leaving that callback NULL does **not** disable it. Keep the optional feature disabled/compile `no-sslkeylog` if this control is chosen; separately prohibit application logging callbacks. [O7–O9] |
| CPU capability environment | x86 `OPENSSL_ia32cap` and ARM `OPENSSL_armcap` are read by process-global CPU setup, not libctx configuration. ARM has a constructor; x86 assembly has startup initialization. A late bridge init cannot undo these reads. In the inspected x86/ARM build rules, `no-asm` removes the capability-object/reader paths; that is a concrete build option with performance/profile implications, **not** a proved all-platform all-environment switch. Otherwise process environment control before library load or a separately reviewed distribution is needed. [O10] |
| Seed sources and seed files | `RAND_set_DRBG_type` / `RAND_set_seed_source_type` are per-context, must be called before first RAND use and select algorithms/sources, not arbitrary OS syscall policy. Build `--with-rand-seed=getrandom` versus `os` controls native paths: inspected Unix `os` enables getrandom **and device fallback**. `RANDFILE`/`HOME` are read by `RAND_file_name`, not evidence of automatic file loading on normal TLS RAND. Avoid that API/manual seed-file path; preserve a secure approved automatic seed source, never choose `none` just to avoid ambient I/O. Device/kernel readiness, native entropy and optional JITTER/provider paths remain beyond config suppression. No custom RNG hook is authorized. [O7, O11] |

`ossl_safe_getenv` means privilege-aware getenv (`secure_getenv` / set-ID handling), **not “use Rill Inputs” or “ignore all environment”**. CPU readers even use plain getenv on the inspected paths. Debug/test/instrumented builds and third-party providers can add behavior; dynamic loader inputs are outside `OSSL_LIB_CTX`. A documented “no inherited trust-path env” guarantee is narrower than “OpenSSL never reads the process environment”. A complete suppression claim needs a pinned target/build/reachable-call audit and initialization/coexistence evidence; no universal per-libctx ignore-environment switch was established. Never mutate global environment around concurrent provider calls. [O5–O11]

## 6. Concise blockers / choices for the interview (not decisions)

1. **Trust source:** choose operator/use case and bundled/native/custom semantics, constraint/distrust representation or honest unsupported cases, plus provenance/license/security-update owner. Flat roots alone cannot promise native/browser policy equivalence.
2. **Identity:** choose validated A-label versus narrower NR-LDH-only input, Unicode support/mapping/version boundary, root-dot handling and wildcard support; keep opaque resolver input and SNI representation distinct.
3. **Wall time:** choose checked acquisition/sampling and explicit precision/bounds contract; resolve the RFC-inclusive versus OpenSSL-exclusive `notAfter` discrepancy without silently weakening verification or the exact-nanosecond time contract.
4. **Distribution:** choose exact provider/build/init/loader/CPU/entropy/environment profile; a private context and `NO_LOAD_CONFIG` alone are insufficient. #30 integration/backend/native safety remains open.

All runtime fixtures, extraction equivalence/subset proofs, ABI/build checks, wall-failure/boundary tests, ambient-input checks and native snapshot race tests are **future validation, NOT RUN**. Only this research file was written; no installs, builds, native experiments, OpenSSL CLI, handshakes, issue/spec/Serena edits, children, commits or pushes.
