# Compiler, standard-library and language-server repository layouts

Research date: 2026-11-16 UTC. This report supports the repository-setup interview. It does not approve a layout, implementation work or a reduced tooling scope.

## Scope and evidence

Rill's inspected baseline is `8934802f6974fcaeac8c3befc96a90586351ded6`. Its chronological prototype groups 01 through 23 are design examples and fixtures, not compiler or standard-library implementations. The compiler, standard-library and LSP implementation folders do not yet exist. Rust-first implementation and later, separate self-hosting remain the premise; LLVM 23 is already chosen. These are not questions this comparison reopens. [Prototype status](https://github.com/Reilley64/rill/blob/8934802f6974fcaeac8c3befc96a90586351ded6/docs/prototypes/README.md#L1-L12); [implementation language](https://github.com/Reilley64/rill/blob/8934802f6974fcaeac8c3befc96a90586351ded6/docs/adr/0001-emit-llvm-ir-directly.md#L1-L3); [backend decision](https://github.com/Reilley64/rill/blob/8934802f6974fcaeac8c3befc96a90586351ded6/docs/adr/0006-whole-program-monomorphization-on-llvm-23.md#L1-L3).

Source-contract approval and delivery acceptance remain separate. The language server design requires reuse of compiler front-end facts without LLVM executable generation. No server acceptance was recorded. That does not by itself establish an LLVM-free server build or distribution. ## Rust and rust-analyzer

### Observed source and sharing

Rust's root workspace includes `compiler/rustc` and tools, while `library/Cargo.toml` declares a separate workspace. `library/std` depends on sibling `core` and `alloc`; panic unwinding and compiler builtins are separate library components rather than one universal `runtime/` directory. LLVM is a Git submodule at `src/llvm-project`, with a branch declaration for Rust's LLVM fork. Cargo and backtrace are other explicitly recorded submodules. [root workspace](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/Cargo.toml#L1-L60); [library workspace](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/library/Cargo.toml#L1-L16); [std dependencies](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/library/std/Cargo.toml#L14-L38); [panic runtime](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/library/panic_unwind/Cargo.toml#L1-L16); [builtins dependency](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/library/alloc/Cargo.toml#L14-L23); [submodules](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/.gitmodules#L1-L41).

rust-analyzer develops in its own repository and Cargo workspace. Rust also contains ordinary in-tree source at `src/tools/rust-analyzer`, not a rust-analyzer entry in the inspected root submodule manifest. Rust bootstrap builds that copy with `SourceType::InTree`, `ToolRustcPrivate` and `in-rust-tree`; rust-analyzer has a scheduled `josh-sync` rustc-pull workflow. This is stronger evidence than assuming that a tool directory denotes a Git submodule. The exact bidirectional synchronization procedure was not established here. [in-tree build](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/src/bootstrap/src/core/build_steps/tool.rs#L1087-L1101); [sync workflow](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/.github/workflows/rustc-pull.yml#L1-L23).

The server's `hir-*` crates perform name resolution, macro expansion and type inference. `hir` provides a semantic API; `ide` adds editor operations and immutable analysis snapshots. `crates/rust-analyzer` implements LSP conversion and transport. Selected rustc-derived dependencies also appear in the workspace manifest. Thus "separate analyzer" does not mean "shares nothing with rustc", and "reusable IDE API" does not mean "the rustc front end". [semantic and protocol boundaries](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/docs/book/src/contributing/architecture.md#L153-L235); [compiler-derived dependencies](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/Cargo.toml#L84-L93).

### Observed builds, tests and releases

Rust's entry point is `x.py` and its bootstrap configuration, not a plain root `cargo build`. It downloads stage0 compiler/Cargo binaries and builds later compiler/library stages. Dependencies include Python, native C tooling and, when building LLVM, C++/CMake/Ninja or Make; supported configurations can download CI LLVM instead. Outputs belong under `build/`. [build entry and native dependencies](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/INSTALL.md#L7-L58); [bootstrap stages and outputs](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/src/bootstrap/README.md#L24-L45).

Compiler test modes include UI, codegen, MIR optimization and run-make. Library manifests own library-specific tests, including `library/std/tests`; `coretests` and `alloctests` are library workspace members. rust-analyzer separately owns parser vectors, semantic/IDE tests and LSP-boundary tests. Its fixtures can use a small `minicore` instead of loading the real standard library. These are different evidence owners, not one undifferentiated `tests/` collection. [compiler test modes](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/src/bootstrap/src/core/build_steps/test/compiletest.rs#L3-L28); [std tests](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/library/std/Cargo.toml#L138-L154); [analyzer test boundaries](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/docs/book/src/contributing/architecture.md#L392-L421); [minicore fixtures](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/docs/book/src/contributing/testing.md#L82-L87).

Standalone rust-analyzer uses `cargo build` and `cargo xtask install`; its manifest requires Rust 1.98 at this snapshot. Its release workflow produces date tags and a nightly tag independently of Rust's channel manifest, which includes rustc, rust-std and rust-analyzer components. Official analyzer installation documentation supports only the latest stable std source and advises a compatible older analyzer for older toolchains. This is not universal release lockstep. [standalone build](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/docs/book/src/contributing/setup.md#L5-L23); [build version](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/Cargo.toml#L1-L10); [release tags](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/.github/workflows/release.yaml#L211-L227); [channel components](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/src/tools/build-manifest/src/main.rs#L211-L244); [source compatibility](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/docs/book/src/installation.md#L11-L24).

Generated syntax/AST definitions have a code-generation owner in rust-analyzer. Rust bootstrap separately controls dependency vendoring and source-tarball vendoring; neither should be confused with compiler source or stage0 binaries. The inspection did not audit every transitive native dependency or establish that all analyzer build modes are LLVM-free. [generated syntax and vectors](https://github.com/rust-lang/rust-analyzer/blob/946b80a756ac1a1ef8882ec65e4f3199e38a23c7/docs/book/src/contributing/architecture.md#L90-L111); [build vendoring](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/bootstrap.example.toml#L395-L399); [distribution vendoring](https://github.com/rust-lang/rust/blob/5f4effd579500175af844241eb179e756190f1e7/bootstrap.example.toml#L1010-L1014).

## Gleam and its stdlib

### Observed source and sharing

Gleam is the closest inspected example of a Rust-implemented compiler and integrated LSP in one Cargo workspace. `compiler-core` parses, analyzes and compiles; `compiler-cli` supplies I/O and wraps the compiler/server; `compiler-wasm` is another client. `language-server` is a workspace crate with a direct path dependency on `gleam-core`. The stdlib is not a workspace member or bundled submodule in that arrangement; its own repository declares the Hex package `gleam_stdlib`. [workspace members](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/Cargo.toml#L4-L24); [component responsibilities](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/docs/compiler/README.md#L26-L43); [server dependencies](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/language-server/Cargo.toml#L1-L24); [separate library package](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/gleam.toml#L1-L11).

This is actual compiler reuse. `language-server/src/compiler.rs` wraps `ProjectCompiler`, retains compiled dependency information, requests `Mode::Lsp` and `Codegen::None`, and recompiles the root package into typed modules. It explicitly explains why normal build caches lack the typed AST needed by the server. The CLI's `gleam lsp` entry connects stdio transport to `LanguageServer`. [compiler wrapper and codegen policy](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/language-server/src/compiler.rs#L26-L79); [dependency compilation](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/language-server/src/compiler.rs#L103-L124); [typed root modules](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/language-server/src/compiler.rs#L165-L172); [CLI and transport](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/compiler-cli/src/lsp.rs#L13-L47).

"Standard library" here means real Gleam implementations under `src/gleam/`, plus target-specific helpers such as `src/gleam_stdlib.erl` and `.mjs`. It supports Erlang and JavaScript host environments. Separately, the compiler embeds `compiler-core/templates/prelude.mjs` and its TypeScript declaration template. The compiler prelude, Hex library and Erlang/JavaScript host runtimes are therefore different artifacts. [targets and runtime compatibility](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/README.md#L25-L34); [Gleam implementation with Erlang external](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/src/gleam/list.gleam#L48-L59); [Erlang helper](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/src/gleam_stdlib.erl#L1-L22); [JavaScript helper](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/src/gleam_stdlib.mjs#L1-L20); [embedded compiler prelude](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/compiler-core/src/javascript.rs#L34-L36).

### Observed builds, tests and releases

`make build` delegates to release Cargo build. `cargo test` runs Rust tests; `make test` additionally runs language, generated-code and project tests. Contributor prerequisites include stable Rust and Erlang, Elixir, Node, Deno and Bun for the documented test coverage. The repository documents Insta snapshots; server feature tests live under `language-server/src/tests`, distinct from compiler tests and `test/language`. [build and integration entry points](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/Makefile#L9-L37); [test prerequisites](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/CONTRIBUTING.md#L69-L87); [snapshot ownership](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/docs/compiler/README.md#L116-L142); [server feature tests](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/language-server/src/tests.rs#L1-L15).

The separate stdlib owns `test/gleam/*_test.gleam`; its CI runs `gleam test` across Erlang and JavaScript runtimes. Its manifest is version 1.0.5 with compiler constraint `>= 1.14.0`, while the compiler/server crates inspected here are 1.19.2. Those declarations establish independent package versioning, not exact release lockstep. Compiler release instructions explicitly update each Cargo manifest and build on `v*` tags. No stdlib publishing workflow or complete historical compatibility matrix was established. [library tests](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/test/gleam/list_test.gleam#L1-L28); [runtime test matrix](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/.github/workflows/ci.yml#L19-L51); [version constraint](https://github.com/gleam-lang/stdlib/blob/9816c72d28ac1fad9433e1ae851d1a3d4a17c64d/gleam.toml#L1-L7); [server version](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/language-server/Cargo.toml#L4-L12); [compiler release checklist](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/RELEASE.md#L6-L14); [release trigger](https://github.com/gleam-lang/gleam/blob/ec952b9138dbc3ba282237d588946a2b0b5b4f3d/.github/workflows/release.yaml#L1-L5).

## Zig and ZLS

### Observed source and sharing

Current Zig builds its compiler from `src/main.zig`, owns `lib/std/std.zig`, and supplies compiler runtime code at `lib/compiler_rt.zig`. `lib/c.zig` also selects bundled C-library implementation modules. The build installs the `lib` tree alongside the executable. The compiler's `build.zig.zon` explicitly says it is for testing, not for consuming the compiler as a package; its standalone-test dependency is a local path. [compiler root](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig#L909-L922); [library installation](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig#L164-L183); [runtime and standard-library roots](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig#L526-L560); [C support modules](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/lib/c.zig#L62-L84); [manifest purpose](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig.zon#L1-L13).

ZLS describes itself as non-official and lives in a separate repository. It owns `src/analysis.zig`, document/project state and LSP features. It reuses Zig's `std.zig.Ast` and AstGen/ZIR machinery, but this is not evidence that it embeds the compiler's full semantic analyzer. Its diagnostics can run `zig ast-check` as a child process or run AstGen in-process; its README explicitly calls comptime/semantic support work in progress. ZLS's own `Analyser` and compiler-generated diagnostics must not be conflated. [project status and semantic limits](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/README.md#L9-L29); [analyzer dependencies](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/src/analysis.zig#L10-L29); [in-process versus subprocess checks](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/src/features/diagnostics.zig#L280-L342).

### Observed builds, tests and releases

Zig documents CMake plus a C/C++ toolchain and LLVM/Clang/LLD 23.x for its full source build. It also documents a C-only bootstrap with limitations, and a prebuilt-Zig route requiring a sufficiently recent compiler and matching native libraries. `bootstrap.c` translates the checked-in `stage1/zig1.wasm` through `wasm2c`, then produces later compiler stages. This is a concrete self-hosting bootstrap burden, not an arrangement Rill needs before it has a compiler. [build alternatives and caveats](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/README.md#L44-L132); [Wasm bootstrap input](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/bootstrap.c#L147-L164); [later bootstrap steps](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/bootstrap.c#L199-L228).

`zig build test` connects behavior tests, compiler-runtime tests and standard-library module tests. Module-local data also exists under `lib/std`, with installation exclusions for compression/archive fixtures. ZLS separately uses `zig build`, `zig build check` and `zig build test`; its tests include source-local units, `tests/analysis` and `tests/lsp_features`. [compiler/library test routing](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig#L495-L562); [library fixture exclusions](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig#L164-L183); [server build and test commands](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/CONTRIBUTING.md#L11-L27).

Version coupling is explicit, not inferred from matching names. ZLS records minimum build Zig `0.18.0-dev.1151+8dfb7a7cc` and minimum runtime Zig `0.18.0-dev.897+117fd40fb`; its release checks require matching major/minor versions for tagged builds and allow a differing patch requirement. Dependencies use URL/hash declarations, and the manifest notes synchronization with Nix dependency metadata. Zig's own version comes from its build source and Git description, not the testing manifest's `0.0.0`. [build version and dependency pins](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/build.zig.zon#L1-L32); [runtime version](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/build.zig#L4-L8); [tagged compatibility checks](https://github.com/zigtools/zls/blob/37521c9834dc723108c28329c736f35e0e0743d6/build.zig#L722-L769); [compiler version construction](https://codeberg.org/ziglang/zig/src/commit/2e9bb03dff7425c5fdeeb205bd5be7e4bbd7b363/build.zig#L274-L355).

Generated parser-oracle output has an explicit generator/checker in Zig's build. ZLS generates version data and has explicit steps to regenerate `src/Config.zig` and `schema.json`. Neither the C-only bootstrap route nor ZLS's parser reuse proves that complete editor semantics or every server deployment is independent of LLVM. No end-to-end compatibility test between the two pinned development heads was run. ## Implications for Rill, not approved decisions

### Inferences from the comparison

The closest structural precedent is Gleam's Rust workspace with a reusable compiler core and an integrated server entry point. Rust-analyzer and gopls are stronger warnings against calling any folder named `analysis` a shared compiler front end. Their actual semantic implementations and reuse arrangements differ. Swift demonstrates that a separate server repository can still depend deeply on compiler/native libraries. Repository count does not determine semantic reuse, LLVM linkage or compatibility policy.

A second inference is that "stdlib" needs a Rill-specific ownership definition. The surveyed artifacts include source libraries, compiler-required runtime support, native shims, host VM APIs and declarations of APIs implemented elsewhere. Rill's chosen whole-program source build, trusted std origin and planned native providers are more relevant than borrowing TypeScript's `lib/` name or Gleam's package-release policy. This report does not revise those contracts. See the pinned Rill contracts in [Scope and evidence](#scope-and-evidence).

### Suggestions to test in the interview

- Prefer one repository initially unless independent ownership or release requirements justify another. A future Cargo workspace could keep Rust implementation crates together while treating Rill-language std source and native runtime inputs as distinct build inputs. This reduces cross-repository coordination but does not require one crate, one published package or one test command for everything. No workspace or directory creation is proposed for immediate execution.
- Treat reusable front-end semantics, IDE state/features, LSP conversion and LLVM code generation as separate responsibilities. Rill already requires semantic reuse and no executable generation for LSP analysis. Decide separately whether the server binary must build/install without LLVM, or merely avoid invoking its backend. Rust features and dependency direction would need verification once code exists; directory names cannot satisfy that requirement.
- Keep component-local unit tests with their implementation, and identify owners for language conformance, stdlib behavior, runtime/backend tests and language server protocol checks. Shared fixtures are useful only with explicit rule ownership and expected-versus-executed labels. Preserve groups 01 through 23 as chronological design evidence rather than silently treating them as passing compiler tests.
- Define the toolchain compatibility unit before choosing separate releases. A compiler/server executable, std source revision, native runtime ABI and LLVM build may need different identities even if distributed together. Bundling simplifies selection; separate releases need an explicit tested compatibility matrix. Neither arrangement proves that language server checks passed.
- Defer self-hosting artifacts until there is a working compiler and an approved migration plan. Rust stage0, Zig's Wasm bootstrap and TypeScript's last-known-good files answer real bootstrap needs. They do not justify empty bootstrap folders, downloaded binaries or a second compiler implementation in design-only Rill.

### Questions requiring user decisions

1. Should the future compiler, Rill std source, native runtime support and server have one repository owner and review boundary? What concrete requirement would justify a separately released stdlib or LSP?
2. Rill already specifies `rill lsp`. Should distribution be one LLVM-linked executable with analysis that never invokes code generation, or should an additional independently buildable LLVM-free analysis/server artifact be required? The latter is a new build/distribution constraint, not an established consequence of the current contract.
3. Which implementations belong to Rill std source, compiler intrinsics or native runtime/provider code? What toolchain identity makes an installed std source tree and native provider ABI trustworthy together?
4. Which suite owns cross-cutting rules and shared fixtures, and how should future executed conformance results link back to the chronological prototypes without rewriting their historical evidence?
5. Must compiler, std source and server releases match exactly, or will Rill support selected version combinations? Which supported host/target/client combinations must CI certify for the complete existing acceptance scope?
6. Should generated files be checked in, regenerated during builds, or shipped only in release source archives? What reproducibility/offline requirements would justify vendoring dependencies or later bootstrap artifacts?

## Limits

This is a source/build-organization survey, not a complete dependency/license audit, an exhaustive release-history study or a capability comparison. No upstream build/test command, Rill compiler run or language server integration test was executed. No conclusion about latency, correctness or production reliability follows from the inspected architecture.

The recursive GitHub tree responses for Rust and TypeScript main were truncated; Codeberg's tree response was paginated. Relevant file claims above were checked through direct pinned-file fetches rather than assuming a partial tree was complete. Missing candidate paths were not treated as proof of absent functionality. Swift's external dependency heads were not resolved into a fully reproducible whole-toolchain checkout. Historical compatibility matrices, every generated/vendor artifact, and complete LLVM-free dependency closures were not established. Specific narrower gaps are stated in the language sections.

This task added only this report. It changed no scaffold, build manifest, contract, issue, worktree or release configuration. The recommendations remain interview inputs, not approved repository decisions.
