# Cancellation-token models. C#/.NET and Tokio for Rill #33

**Status:** primary-source research input, **not approved token policy or an implementation plan**.

**Checked:** 2026-11-15 (UTC).

**Ticket:** [#33. Clocks, durations, deadlines and cancellable waits](https://github.com/Reilley64/rill/issues/33).

**Controlling direction:** the user's instruction, **"we should add cancellation tokens in the style of c# and tokio,"** supersedes the previously accepted no-token Q53. **Tokens are in scope.** This selects sources of design inspiration, not literal .NET/Rust APIs, exceptions, traits, a dependency, FFI or backend. The earlier [Jiff note's](0033-jiff-api-model.md#existing-rill-constraints-that-remain-in-force) statement that its research did not approve tokens is historical, not a reason to exclude them now. Exact integration with goroutine cancellation and typed operation outcomes remains unchosen. [B]

**Evidence boundary:** official documentation and static inspection of pinned upstream source only. No library execution, Rill implementation, backend investigation, concurrency/safety proof or scheduling experiment. Facts, possible adaptations and decisions are distinguished below; upstream implementation details are not automatically portable API guarantees.

## 1. Pins and authority: two materially different models

- **.NET 9.0.0:** `dotnet/runtime` tag `v9.0.0`, commit **`9d5a6a9aa463d6d10b0b0ba6d5982cc82f363dc3`**. The source includes API documentation for tokens, sources and registrations. Microsoft's explanatory documentation is separately frozen at `dotnet/docs` commit **`94b7dca39d8dca4374f326176874381661f4dd59`**; it is not represented as documentation shipped with the 9.0.0 release. [N1-N9]
- **tokio-util 0.7.16:** repository tag `tokio-util-0.7.16`, commit **`cf6b50a3fd44684d63fd758aae1ee2955f16c798`**, corroborated by its package manifest and versioned rustdoc. This is **`tokio_util::sync::CancellationToken`**, an additional-utilities crate type, **not a Tokio core `tokio::sync` type**. The official shutdown tutorial is separately frozen at website commit **`71cdb3858fbb943843e8cf0e8baf547fe22180f7`**. These are deliberate comparison pins, not claims about the newest releases. [T1-T3, T8]

| Question | .NET 9.0.0 | tokio-util 0.7.16 |
| --- | --- | --- |
| Who requests? | A `CancellationTokenSource` exposes `Cancel`/`CancelAsync`; its `CancellationToken` exposes observation/registration, not cancel authority. Anyone given the source can request; this is capability separation, not a special privilege of the original creating thread. [N1, N2] | Every token handle and every clone exposes `cancel(&self)`. Clones share the same cancellation state and authority. [T1, T2] |
| What does copying mean? | A readonly value-type token contains a reference to the same source, not an independent snapshot or independently owned resource. `None` is `default`, permanently noncancelable; `new CancellationToken(true)` is permanently canceled. [N1] | `Clone`, not Rust `Copy`, explicitly adds a handle to shared state. `new` and `Default` create a fresh, initially uncanceled **cancelable** token, not .NET's `None`. [T1, T2] |
| What does cancellation establish? | Request state, plus dispatch of registered callbacks according to the particular call; not completion of arbitrary token-consuming tasks. [N1, N2] | Request state and waking cancellation waiters, including descendant propagation; not completion of tasks holding/listening to tokens. [T2, T7, T8] |
| Does ordinary handle destruction stop work? | Source disposal releases resources; it is not `Cancel`. A token copy is not a disposable source owner. [N1, N3] | Ordinary token drop releases a handle, not a cancellation request. Separate armed guards request on drop. Neither operation joins tasks. [T2, T4–T6] |

**Design consequence, not a decision:** "like C# and Tokio" cannot by itself choose authority, default construction or destruction policy: the two models disagree on all three.

## 2. .NET facts

### Source, token copies and lifetime

A token's readonly struct representation does not make the cancellation state local to that struct: its `_source` reference is shared by copies. The reference keeps the managed source object reachable, but does **not** prevent explicit source disposal or keep a disposed wait handle usable. Source `Token` acquisition and token `WaitHandle` access check disposal; already-held token polling reads the source state. Do not translate managed reachability into a Rill borrow-free/lifetime guarantee. [N1, N2, N3]

`IsCancellationRequested` is only observation of a request, not proof that callbacks have finished or propagation has completed. `CanBeCanceled == false` guarantees the token will never become canceled. A canceled token never becomes uncanceled. Source/token members support concurrent use except for documented exceptions such as source disposal and `TryReset` racing cancellation. [N1-N3]

### `Cancel` versus `CancelAsync`: order, errors and races

- **`Cancel()` is `Cancel(false)`.** The winning cancellation call transitions request state before processing callbacks, then runs the registered callback list synchronously in **LIFO** order. Normally this is the calling thread; a registration that explicitly captured a synchronization context can use synchronous `SynchronizationContext.Send` to dispatch there. One callback throwing does not stop the default traversal: exceptions are collected and thrown as `AggregateException`. `Cancel(true)` instead propagates the first exception and skips remaining callbacks. Cancellation is not rolled back. [N2, N4]
- **`CancelAsync()` sets request state synchronously**, then, when there is a callback list to dispatch, schedules its processing on the default task scheduler. At this pin the same LIFO handler routine executes callbacks sequentially, not one concurrent job per callback; errors are aggregated in the returned task. It is not an asynchronous-callback-delegate API and does not discover/join work merely started by a callback. [N2, N4]
- **Important repeat-call boundary:** in 9.0.0, repeated `Cancel` does not replay callbacks or wait for another winning caller's dispatch. Repeated `CancelAsync` returns `Task.CompletedTask` if cancellation has already been requested, **even while that earlier callback dispatch is running**. Retain the winning returned task if its dispatch completion matters; a later call is not a universal callback join. Request idempotence is not join idempotence. [N2, N4]
- **Registering after cancellation is synchronous and reentrant:** the callback runs before `Register` returns, and its exception propagates from `Register`. A racing registration is either taken by dispatch or removed and invoked by the registering thread. This also means `CancelAsync` cannot promise that every later callback runs asynchronously or is covered by its task. LIFO is not a total order for arbitrary concurrently registered/late callbacks. [N1, N2, N4]

### Registration is an owned lifetime obligation, not just a callback pointer

`Register` returns a `CancellationTokenRegistration`. The source stores the delegate, state and captured context; keeping an ordinary source alive without unregistering can therefore retain callback environments. **Dropping a registration value is not automatic unregistration in C#: call `Dispose`, `DisposeAsync` or `Unregister` as appropriate.** Copies refer to the same registration identity, not distinct callback subscriptions. [N4, N5]

- `Dispose()` attempts unregistration; if another thread is executing that callback, it waits for that execution to finish. `DisposeAsync()` returns a `ValueTask` completing once the callback is unregistered without execution or finishes execution. **Self-disposal is an explicit exception:** a callback disposing its own registration does not wait for itself. Neither is a mechanism for forcibly stopping an executing callback. [N5]
- `Unregister()` attempts removal **without** waiting for an executing callback. Losing that race is not permission to invalidate callback data. Conversely, successful unregistration removes the future invocation obligation. [N5]
- **Deadlock is possible:** disposing a registration while holding a lock its running callback needs creates a wait cycle. Async disposal changes how the wait is represented, not the dependency cycle. Synchronous cancellation and synchronization-context dispatch can create additional reentrancy/wait problems; Microsoft's guidance is to keep callbacks fast and avoid manual thread/context coordination. [N4, N5, N8]
- Ordinary `Register` captures the current **`ExecutionContext`** and restores it for callback execution. Capturing `SynchronizationContext` is separately selectable and defaults off in common overloads. `UnsafeRegister` deliberately does not capture/flow `ExecutionContext`; that upstream name is not a proposed Rill unsafe escape hatch. An execution context is ambient managed state, **not** Rill's concrete closure capture/send/share evidence. [N1, N4]

### Linked sources and timed requests

`CreateLinkedTokenSource` constructs a separately cancelable source that requests cancellation when **any** input token does. It supports one-parent child-like behavior and multiple-input OR linking; directly canceling the linked source does not cancel input sources. Already-canceled input tokens synchronously trigger the link during construction through registration. Links do not join parent or child operations. [N4, N8]

At this pin the linked source **owns upstream registrations**, using `UnsafeRegister`, and disposes those registrations when disposed. Callback state references the linked source. This is concrete retention and unlinking machinery, not a weak name-based association: forgetting to dispose a linked source can retain it through a live upstream registration. Managed GC and these private subclasses are not a Rill ownership design. [N4]

`CancelAfter` starts a **relative countdown at that call** and schedules a cancellation request, not a hard task-completion deadline. Subsequent calls change the countdown only while uncanceled; the infinite timeout disables scheduling, not cancellation already requested. Constructor-delay overloads start during construction, with a `TimeProvider` overload available at this pin. A `CancelAfter`/`Cancel` race may leave a benign timer whose eventual notification has no further effect. None of this specifies a Rill absolute monotonic deadline, clock identity, suspend behavior or expiration-versus-completion winner. [N2]

### `TryReset` and source disposal: two misleading names

**`TryReset` does not uncancel a canceled token.** It can succeed only before cancellation, under a sole-owner discipline: the preceding operation is known complete, no one will try to cancel, and leftover registrations are considered erroneous. Success removes registrations and, when possible, disables a timer. Old token copies still observe the **same instance**, including later requests; this is not a new generation. Concurrent reset/cancellation is explicitly unsupported and can lose notifications. One-shot cancellation and restricted reuse of an uncanceled source are different propositions. [N3]

**Ordinary source `Dispose` neither requests cancellation nor joins token-consuming operations or all in-flight callbacks.** It releases timer/event/registration resources and marks the source disposed. It is generally not thread-safe against other source operations, even though the pinned implementation tolerates selected patterns involving cancellation/registration. Do not promote those tolerated races into a general disposal concurrency contract. **Linked-source caveat:** its override disposes upstream registrations, which can wait for an in-flight upstream callback under the registration rules. Thus neither "all source disposal joins callbacks" nor "every source disposal is nonblocking" is accurate. Source disposal and registration disposal have different contracts. [N3-N5]

### Poll, wait, throw, and task outcome are distinct boundaries

.NET supports polling request state, registering a callback, and waiting on the token's `WaitHandle`. `ThrowIfCancellationRequested` explicitly throws `OperationCanceledException` carrying the token. Waiting for the signal does not itself establish that the consuming operation has ended; operations decide where to observe and what to do, and may continue doing work after a request. The token wait handle is lazily allocated and belongs to the source, not to the caller to close independently. [N1, N8]

**Task cancellation is not simply task failure, and request state alone does not determine the outcome:**

- In the documented **delegate-backed Task** path, returning after noticing a request still means `RanToCompletion`. An `OperationCanceledException` acknowledging the task's associated, requested token produces `Canceled`; a mismatched/unrequested token or another exception produces `Faulted`. A canceled task's `Exception` property is null; blocking `Task.Wait`/`WaitAll` report cancellation using `TaskCanceledException` within `AggregateException`. [N6, N9]
- **Do not generalize that matching rule to every C# async task.** The pinned `AsyncTaskMethodBuilder<T>.SetException` uses `TrySetCanceled` for an `OperationCanceledException`, passing its token, without the delegate-backed path's associated-token/request check; other exceptions use `TrySetException`. Outcome classification is partly the producing API's contract, not an intrinsic property of a token. [N7]

**Possible Rill adaptation:** separate successful value, typed operation cancellation and ordinary typed failure where desired, but do not import exception matching, catchable panic or automatic flattening. Which token-aware operations expose a cancellation outcome remains a human decision, not a consequence of these .NET facts. [B, R1, R2]

## 3. Tokio-util facts

### Clones, children, propagation and retention

Every clone shares cancellation with the original in both directions. `child_token()` instead creates a distinct cancellation node: **parent cancellation reaches child and descendants; canceling the child does not cancel its parent or sibling branches**. Clones of that child still share its authority. A child of an already-canceled parent is returned canceled. The public API has no reset method or .NET-style multiple-parent `CreateLinkedTokenSource`. [T1, T2]

**Race boundary:** the public `cancel` documentation explicitly says propagation is **not atomic across the tree**: a parallel observer can see one child canceled and another not yet canceled. Once that `cancel` call returns, descendants have been canceled; this is a signal-state guarantee, not a guarantee that their tasks have run or finished. At the pin, child creation checks/inserts under the parent's lock, so creation racing parent cancellation either sees cancellation or joins the propagation structure. This is a source observation supporting the documented child behavior, not a Rill atomicity/safety proof or a promise of a tree-wide snapshot. Repeated cancellation of an already-canceled node is a no-op in the source. [T2, T3]

Tokens hold reference-counted tree state. In this implementation, dropping the last handle for an intermediate node reparents its children to the remaining ancestor, preserving propagation; dropping the last root handle disconnects children rather than canceling them. A child can thus outlive the parent's public handle without dangling, and retaining state does not imply retaining public cancel authority at every ancestor. These are pinned internal lifecycle observations, not a requirement to copy Tokio's tree or use Rust `Arc`. [T2, T3]

### `cancelled()` and `cancelled_owned()`

Both return futures completing with `()` when cancellation is requested, including immediately ready behavior when the token is already canceled. `cancelled()` borrows the token; `cancelled_owned()` consumes a token handle and its future owns it, avoiding that caller borrow. These wait for a **persistent request state**, not a one-consumer message that another waiter can drain. The implementation checks request state around notification polling to avoid lost wakeups. [T1, T2]

Both waits are documented **cancel safe**: abandoning a wait and waiting again does not consume the cancellation request. This says nothing about rollback/cancel safety of unrelated work selected against it. In particular, cancel-safe token observation is not proof that an in-progress receive, native operation or mutation can be abandoned without an ownership obligation. [T1, T2; R1, R2]

### Drop guards, `run_until_cancelled`, and completion

`drop_guard(self)` owns a token; `drop_guard_ref(&self)` borrows it. An armed guard requests cancellation on drop; `disarm` suppresses **that guard's** request and returns its token/reference without disarming other guards. Ordinary token drop is different. Guards neither wait for work nor enforce shutdown completion order. To use one for real shutdown, the request must happen while required state remains live, and a separate completion wait must finish before releasing that state. [T2, T4-T6; R1]

`run_until_cancelled` and its owned-token variant produce **`Option<F::Output>`**: `Some(output)` on work completion; `None` on cancellation, dropping the supplied future. At the wrapper's initial execution/poll, an already-canceled token returns `None` without polling work. The future value has **already been constructed and passed**, so this is not a guarantee that arbitrary work-construction effects were skipped. After that pre-check, simultaneous ready work/cancellation is **biased toward work completion**. The helper is cancel safe **only if the supplied future is cancel safe**. It does not flatten an output that is itself `Result`. [T1, T2]

These helpers contain/drop a future; they do not generically cancel and join separately spawned tasks or confirm release of external/native borrowers. Tokio's official shutdown guidance separates **decide to shut down → notify → wait for completion**, explicitly allowing cleanup after receipt. Its separate `TaskTracker` waits until it is both closed and empty; the pinned contract says tracked futures' destructors have finished when that wait returns. Dropping the tracker does not abort tasks. This is evidence that token signaling and task-completion ownership are distinct services, not a proposal to add a tracker API to Rill. [T2, T7, T8]

**Possible Rill adaptation:** awaitable/pollable persistent notification and directed child requests can be useful without adopting callbacks. Do **not** transfer Tokio's losing-future drop or completion-biased tie rule into the already accepted Rill deadline helper: Rill requires losing execution/cleanup to be joined and leaves simultaneous-ready ties unspecified. [B, R1, R2]

## 4. Rill invariants that adding tokens must preserve

The following are **existing constraints**, not newly chosen token integration:

1. **Cooperative cancellation is not fatal panic.** `stop(&routine)` requests cancellation and joins termination/cleanup; repeated/concurrent stops share completion, self-stop panics, and dropping `Routine` does not stop/join. Fatal panic remains immediate whole-program termination without cleanup, not a catchable cancellation exception. A token request must not be silently equated to `stop`'s complete request-and-join operation. [R1, R2]
2. **Request, delivery and cleanup completion are separate.** Delivery is deferred during disposal and mandatory cleanup joins, while suspension and normal completion remain possible. A pending request does not withdraw a **masked cleanup wait** or abandon its ownership obligations. Token-aware waits/links/registrations must respect this boundary if connected to goroutine cancellation; the exact connection is not yet chosen. [R1, R2, B]
3. **Sources survive actual use.** Scoped children finish before borrowed sources/guards are released. Trusted native operations retain buffers, callback data, handles and source obligations through completion or **confirmed abort**; request, token cancellation, handle drop or moving work to another worker is not release confirmation. Committed effects are not rollback promises. Required cleanup may wait forever. [R1, R2]
4. **Evidence remains concrete and pre-monomorphization.** `noBorrow`, `sendable`, `shareable`, copyability and invocation mode are separate properties. There is no general GC/public dyn/trait facility to assume for callback registries. Use Rill's explicit copy rules for shared ownership; a synchronized handle is not automatically implicitly copyable. Generic callbacks must retain capture/dependency evidence through storage, wrappers and disposal; an erased arrow cannot manufacture it. Background retention and scoped borrows have different requirements. [R1-R3, B]
5. **Accepted deadline helper, unchanged:** `Result<R, DeadlineError>`; once-callable/sendable work and sendable results, allowing valid scoped borrows rather than a blanket `noBorrow` constraint; no implicit error flattening; preflight expiration skips invocation; first-selected outcome, with unspecified simultaneous-ready ties; cancel/join losing work **before return**, also through cleanup. If `R` is itself `Result<T,E>`, it remains nested. These details are supplied by the current research brief, not claimed to have already been inserted into the checked local catalogue. Adding token input or a new outcome is a further decision. [B; R1, R2 for the underlying scoped/join obligations]

## 5. Possible adaptations and genuine open decisions

This is a **decision map, not a proposed API approval**. Each row states an unresolved choice grounded in the comparison or the Rill obligations above.

| Policy axis | Genuine choices / obligation |
| --- | --- |
| **Authority** | Separate read-only observation token and cancel-capable source (.NET-like), versus cancel authority on every explicit clone (Tokio-like). Decide whether authority itself is shareable/copyable; “token is synchronized” does not settle that. [N1, N2, T2; R1, R2] |
| **One-shot / reuse / default** | Fresh one-shot states versus restricted reuse/reset with a specified generation/old-observer contract. .NET `TryReset` is not uncancellation. Separately choose whether an inert never-canceled value exists and whether construction is explicit; neither upstream `Default` should be inherited silently. [N1, N3, T1–T3] |
| **Parent-child / linked ownership** | Directed child requests, multiple-input OR links, or both. Specify who owns link registrations/state, what dropping a parent/link means, behavior for an already-canceled input and concurrent creation, and whether any propagation-completion guarantee is per node or across descendants. Avoid unowned retained links/cycles; exact lifetime rules remain to be designed. [N4, T2, T3; R1, R2] |
| **Propagation and ambient state** | Explicit parameters/captures and explicit links versus any separately proposed automatic propagation. No ambient context has been approved: named functions cannot capture runtime state implicitly, and .NET `ExecutionContext` is not precedent for inventing it. A child's creation must not silently imply goroutine inheritance unless selected. [N1, N4, T2; R1, B] |
| **Observation surface** | Poll plus awaitable/waitable notification only, versus public callback registrations as well. Callbacks add decisions about invocation location, reentrancy, late registration, ordering, errors, unregister-versus-join, self-disposal and suspension. A scoped generic callback can preserve evidence; this does not prove a heterogeneous long-lived registry or authorize erased captures. [N1–N5, T2; R1, R2] |
| **Drop semantics** | Ordinary release only, explicit request-on-drop guards, or request-on-owner-drop. State clearly whether any disposer also joins; a signal-only guard cannot authorize release of borrowed/native resources. No token-drop choice changes existing `Routine` drop semantics by implication. [N3–N5, T2–T6; R1, R2] |
| **Request / delivery / join integration** | An operation may explicitly observe a token; alternatively an explicit scope/adapter could map it into goroutine cancellation delivery. Decide whether a token request ever delivers cancellation by itself, and which operation performs completion joins. Do not make observation itself an unmasking or force-kill mechanism. [N8, T7, T8; R1, R2, B] |
| **Borrow-free / send / share evidence** | Justify properties of each source, token, borrowed wait, owned wait, registration and link separately. Owned shared state may permit borrow-free handles, but does not erase borrowed callback captures. A link owner must retain all necessary state until unlink/in-flight completion; scoped registrations must finish before their sources expire. Background captures retain `noBorrow`/sendability requirements; scoped callbacks/jobs can use valid borrows with the necessary access evidence. [N4, N5, T2, T3; R1, R2] |
| **Typed outcomes / deadlines** | Decide which token-aware operations return ordinary typed cancellation outcomes, which participate in goroutine cancellation, and how external requests compose with deadline expiration and work errors. Preserve the accepted deadline helper until explicitly extended; do not silently put cancellation into `IoError`, flatten nested results or turn fatal panic into a catchable error. Distinguish observed request from the outcome ultimately selected after a race/commit. [N6, N7, T2; R1, R2, B] |

## 6. First human-interview frontier. Independent questions only

**Tokens are already included; do not reopen inclusion or ask for backend selection.** The following questions can each be answered without first selecting the others or inventing a signature. They are the first frontier, not one coupled all-or-nothing recommendation:

1. **Authority:** should ordinary recipients get observation-only tokens while a separate source requests cancellation, or should every explicit token copy/clone be able to cancel its peer group? The difference is authority delegation, not merely spelling. [N1, N2, T2]
2. **State lifetime:** should a cancellation state be permanently one-shot, requiring a fresh state for new work, or is reusable/resettable state a requirement worth specifying? Neither choice needs callback or goroutine-integration policy first. [N1, N3, T2, T3]
3. **Explicitness:** should cancellation state be passed/captured and linked explicitly, with no ambient token or automatic goroutine inheritance? This asks about propagation convenience, not whether tokens exist. No implicit context is currently approved. [R1, B]
4. **Observation capability:** is poll/wait observation sufficient, or are public user cancellation callbacks required too? Request a concrete callback use case before choosing ordering, registration types or callback failure rules. Both capability models support useful cancellation without copying the other platform's entire callback mechanism. [N1, N8, T1, T2]

**Next, after these answers:** choose child/OR-link ownership and drop behavior; then the explicit bridge among token requests, goroutine delivery and required joins; then operation-specific typed outcomes and any explicit deadline-helper extension. Callback execution/disposal contracts are needed only if callbacks are selected. This ordering avoids assuming an answer to a dependent integration question while interviewing about independent capabilities. It does not postpone any mandatory retention or cleanup invariant. [R1, R2, B]
