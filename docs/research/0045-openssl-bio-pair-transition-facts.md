# #45: pinned OpenSSL BIO-pair transition facts

## Authority, scope and limits

Facts-only research, not design approval, API selection, provider-mode amendment, conformance/security evidence or Rill/runtime execution proof. No tests or provider experiments were run. Only this new research document is owned by this task.

- Provider: OpenSSL **3.5.9**, commit **`45e844fa2a14ec92d146bd8f5778ac130b6625fb`**. All provider links below pin that commit, including the manuals shipped with it, rather than a moving online manual.
- #38 authority: published [public contract][public] and [closed private boundary][private] at **`15632ac1f88a7d1ca69cea66d083f6d61b897fb3`**. These were read with `git show`; their absence as local TLS files does not make the earlier research notes authoritative substitutes. Public sections 7–11 and private sections 3–6 govern the distinctions below.
- Context: [#45][issue45], [working #39 → #45 handoff][handoff], [earlier retry research](0039-duplex-progress-and-tls-retry.md), and [HTTP/1 compatibility research](0039-http1-compatibility-and-trailers.md). Working direction supplied for this research: single owner; whole TCP and TLS over eligible lower `D`; owned buffers; at most one pending read and one pending write; ordered flush; no split/raw escape; prepare TLS progress before handshake; bounded normal advance without external wait while retaining native jobs; caller controls outside `D` plus explicit terminal stop, not independent lane cancellation. **These directions do not freeze public signatures or establish an implementable scheduler.**
- Actual #30 runtime and #44 TLS delivery gates remain **OPEN**. Private boundary §5 explicitly allows native work to block and does not assert a hard CPU/return bound. A bounded/cooperative managed advance must not turn that into an assertion that a single OpenSSL call, crypto job or release is hard-bounded.

## 1. Transition/source matrix: permission is not symmetric

Here “retry” means continuation of the original native operation, not a fresh public request. “Feed/drain” means operations on the external half of the connected BIO pair while no SSL call is active. It is not another SSL application call. Everything remains serialized with immediate native result classification first.

| Pending native result | Direct BIO-pair work | Another SSL application I/O call | Handshake/shutdown/control implications and evidence |
| --- | --- | --- | --- |
| `SSL_write_ex` → WANT_READ | Feed bounded ciphertext to the external half; drain any generated output and hand it to lower transport. WANT_READ can coexist with pending output. | **Explicit permission:** `SSL_read[_ex]` when more data is available. The original write must subsequently be retried with its original data/length and required buffer identity. This permission does not complete or replace that write. | `SSL_get_error` WANT section grants the read exception; it does not grant arbitrary `SSL_do_handshake`, `SSL_shutdown`, fresh write, or control mutation. Reads can themselves enter handshake/control processing. [Error][error], [write][write], [pair][pair]. |
| `SSL_write_ex` → WANT_WRITE | Drain the external half to release output capacity; preserve lower unaccepted ciphertext tails. Local feed/drain does not call SSL application I/O. | **Explicit restriction:** do not perform any other operation that could trigger I/O except repeating the previous write. Thus no unconditional read/write alternation, fresh write, shutdown or explicit handshake as a yield mechanism. | Finish the constrained retry before proposing another SSL I/O operation; a later WANT_READ changes the applicable constraint, not the identity of the original write. [Error][error], [write][write]. |
| `SSL_read_ex` → WANT_READ | Feed input and drain existing output as needed. WANT_READ may occur with unprocessed local SSL/BIO input, especially with AUTO_RETRY off. | Manual says satisfy the BIO need and **repeat the read**. These sources do **not** supply an affirmative, all-states permission to issue a fresh write or other SSL I/O call in its place. Nor do they establish a blanket prohibition on every such call. | Read can transparently negotiate or process post-handshake messages. Need a state-specific justification for any additional interleave; the write-WANT_READ exception is not reciprocal evidence. [Read][read], [error][error], [records][records]. |
| `SSL_read_ex` → WANT_WRITE | Drain output to provide space; preserve input/output and original read continuation. | Manual again prescribes repeating the read after satisfying the BIO. It supplies no complete opposite-operation permission matrix. A read's WANT_WRITE is **not** the documented write-WANT_WRITE rule applied by changing the operation name. | The blocked write may be handshake/control output, not application plaintext. Calling an unrelated write/shutdown is not shown to finish that work safely. [Read][read], [error][error]. |
| Explicit handshake → WANT_READ / WANT_WRITE | Same feed/drain obligations; drain pending output before waiting only for input. | `SSL_do_handshake` manual prescribes retrying the handshake. Application read/write can negotiate implicitly, but that is not a documented license to replace an already pending explicit handshake arbitrarily. | #38 additionally withholds publication until authentication/policy checks **and final output handoff/flush**. Native handshake completion alone is insufficient. [Handshake][handshake], [pair][pair], public §7. |
| Fatal `SSL_ERROR_SSL` / `SSL_ERROR_SYSCALL` | Cleanup under the selected terminal policy, not attempted recovery. | No further SSL I/O; **do not call `SSL_shutdown`**. | #38 poisoning/disposal discards pending output, not a graceful-alert attempt. [Error][error], [shutdown][shutdown], public §§7,9; private §6. |

**What this matrix does not prove:** that one pending public read and one pending public write can always both enter OpenSSL, that all TLS 1.2/1.3 substates support a chosen interleave, or that bounded queues guarantee bidirectional liveness. Public pending commands and active native retry obligations need not be the same set. Preserve each admitted operation's state; an intervening read's result/error must not overwrite the saved write obligation.

`SSL_get_error` requires the same native thread as the immediately preceding SSL call, no intervening OpenSSL calls, and a previously empty thread error queue. Therefore **even a BIO pending/capacity query belongs after that classification**, not between the SSL operation and `SSL_get_error`. Capture bounded diagnostic facts before migration. [Error][error]; private §5.

### Handshake, control and shutdown are state transitions, not independent lanes

- Read/write manuals allow implicit initial handshake and transparent negotiation; client/server state must already be initialized. Source `ssl_read_internal` / `ssl_write_internal` checks initialization and handshake state. `ssl3_write_bytes` handles pending records before initiating locally queued KeyUpdate/extra-ticket work when appropriate; `ssl3_read_bytes` may re-enter the handshake state machine on handshake records. These source branches explain why protocol state matters; they are not a complete scheduler theorem. [Read][read], [write][write], [lib][lib], [records][records].
- AUTO_RETRY processes non-application records until input exhaustion or an application record with a nonblocking BIO. It is neither a scheduling-yield hook nor a per-call CPU bound. Disabling renegotiation/PHA under #38 does not eliminate required TLS 1.3 KeyUpdate/control handling. [Modes][modes]; public §6.
- `SSL_shutdown` initiates local close-notify and makes further application writes unavailable. Reads can remain available. It is not a cancellation primitive for a pending application write. The manual recommends reading remaining inbound application data while completing bidirectional shutdown; a subsequent shutdown completion attempt can fail if application data was not read. [Shutdown][shutdown], `ssl_write_internal` in [lib][lib].
- `SSL_SENT_SHUTDOWN` is set on an **attempt**, even if sending failed. It is not proof that notify was emitted into the pair or handed to `D`. With nonblocking I/O, preserve the actual result/WANT and output tails. #38 consuming close/local TLS 1.3 shutdownWrite requires local output handoff, not peer-notify waiting; TLS 1.2 shutdownWrite is pre-admission Unsupported, and peer-notify handling differs by version. Do not substitute the manual's generic close example or flag for those public policies. [Shutdown][shutdown]; public §9.
- Reset/clear/free, quiet shutdown, forced shutdown flags, initiating KeyUpdate/renegotiation, or changing modes are not sanctioned ways to retire a WANT obligation. Some have useful native purposes, but no generic safe-interleave rule for them was established here. Release belongs to the quiescent lifecycle, not the application retry matrix.

## 2. Retry arguments, storage and mode selection

| Question | Pinned fact / boundary |
| --- | --- |
| Write retry identity | The write warning requires **same arguments** after either WANT; input may have been partially processed. Without moving-buffer mode, preserve input address, bytes and length. With that mode, only address movement is relaxed: identical contents and length still required. Keep the original SSL engine and operation, not a suffix/new command. [Write][write], [guide][guide]. |
| Source checks | `tls_write_check_pending` checks pending size, pointer unless moving mode, and record type; `ssl3_write_bytes` also checks lengths against `wnum` and pending totals. Errors include BAD_WRITE_RETRY/BAD_LENGTH. The source does not compare all input bytes; lack of a check is **not** permission to change them or weaken the manual. [Records][records] lines 252–487. |
| Read arguments | Read manual says repeat the call but does not state the same explicit address/content rule as the write warning. The nonblocking guide says retry exactly the same operation. Retaining the original private destination/capacity is the conservative #38-compatible basis; no moving-read-buffer permission is established. Output count storage is shim-owned; no evidence here requires retaining a caller's `size_t*` address between completed synchronous C calls. [Read][read], [guide][guide]. |
| Partial-write mode | Default off. When enabled, a successful partial write **completes** that native operation; a new operation uses the unsent suffix. The manual describes a message block/record (16 KiB); actual fragment/pipeline configuration still matters and is not selected here. It **cannot be enabled in the middle of an incomplete write**. [Modes][modes], [write][write], [records][records]. |
| Moving-write-buffer mode | Default off. A mode available for retries, not a change of bytes/length or permission to hand OpenSSL movable managed storage. No reviewed transition here establishes mid-retry mode mutation as safe. [Modes][modes], [write][write]; private §4. |
| AUTO_RETRY | On by default since 1.1.1; this is an upstream default, **not evidence of a #38 explicit selection**. Nonblocking BIOs still require incomplete-operation handling. [Modes][modes]. |
| #38 selected modes? | The pinned public/private contracts require stable owned native retry storage, serialization and preserved identity/cursors, but **do not explicitly select ENABLE_PARTIAL_WRITE, ACCEPT_MOVING_WRITE_BUFFER or AUTO_RETRY settings**. Do not invent an approved bitmask from upstream defaults or from required KeyUpdate support. A concrete setting/timing/effective-bit inventory remains an explicit #38/#44 decision. |

Configuring chosen modes before first dependent I/O is a conservative implementation option, not a new selected API or a claim that OpenSSL forbids all later configuration changes. Only partial-write's mid-incomplete-write enabling prohibition above is explicit in the mode manual. OpenSSL `SSL_MODE_ASYNC`/async-engine retries are separate from #30's retained joined native jobs; #38's controlled profile disables engines. Retaining runtime jobs does not select OpenSSL async mode. [Modes][modes], [error][error]; private §§2,5–6.

## 3. Honest plaintext-prefix accounting

**A zero/WANT result is not an exact zero-effects report. In ordinary TLS, `*written` is specified on success, not as a cumulative native plaintext-prefix output on failure.**

At this commit `SSL_write_ex` delegates to `SSL_write_ex2`, which calls `ssl_write_internal` and maps negative results to zero. The wrapper does **not** universally initialize `*written` to zero. In `ssl3_write_bytes`, `*written` is assigned on successful completion; a record-layer failure/retry stores the completed internal total in `s->rlayer.wnum` and returns without assigning a failure-prefix result. [Lib][lib] lines 2523–2580, 2669–2682; [records][records] lines 274–487.

Consequently, **yes**: with partial-write mode off, an invocation can successfully process earlier record batches, increment internal `tot`, then encounter WANT on later output. It returns 0 through the public wrapper even though earlier ciphertext may already have been drained and accepted by the lower transport. If the shim initialized its output count to zero, it may still observe zero; that zero is **not an OpenSSL-exposed exact native plaintext prefix**. The same missing-prefix issue matters on a terminal failure after earlier record processing. Reading private `wnum`, inferring a prefix from ciphertext length, or parsing record structure is not an approved public byte-count API or #38 boundary amendment.

Partial-write mode provides a positive **successful** short-write count and a fresh-operation boundary. It does not transform every failure into an exact effects report, report ciphertext already accepted by `D`, or prove peer receipt/execution. In particular control records, partial ciphertext records and opaque provider state make cross-layer conversion invalid. The write manual's failure wording must be read alongside its partial-processing warning and source; do not interpret it as rollback or no observable effects. [Write][write], [records][records].

| Count/fact | What can be honestly known |
| --- | --- |
| Public Rill write acceptance | Exact current-input prefix copied/admitted into bounded TLS-owned staging, independent of the caller. #38 explicitly chooses this boundary. Retain that count on failure; never count earlier-call admission again. Public §8; private `AcceptPlaintext`. |
| Native successful write | Full requested chunk, or successful partial count if mode selected. Pending native retry may outlive public admission. [Write][write]. |
| Native write 0/WANT/error | Retry/failure classification and captured diagnostics; **no general exact cumulative plaintext-prefix output**. It can have partial internal/transport effects. [Write][write], [lib][lib], [records][records]. |
| Lower ciphertext acceptance | Exact layer-relative lower write prefix, plus retained unaccepted tail. Not plaintext acceptance, ACK, peer decryption or application execution. Public §8; private `TakeCiphertext`. |
| Actual peer effects | Generally opaque. Neither successful write/flush nor failure proves execution/nonexecution or replay safety. Public §§7–9. |

If a new #45 completion wants an exact count at a different boundary, that is an undecided policy/API requirement, **not** a reason to fabricate a native prefix. Engine-owned input admission can supply the already-approved exact public count while native effects remain unknown. Late public prefixes must reflect actual admission/append through joined completion, not guessed zeros or a reclassification after cleanup. Public §§8–9; private §6.

## 4. BIO bounds, EOF and lifetime are distinct facts

All provider facts in this section: [BIO-pair manual][pair] and [`bss_bio.c`][biosource].

- A connected pair has **two** write rings: internal-half writes become external-half reads (ciphertext egress); external-half writes become internal-half reads (ciphertext ingress). Capacity is per half, not one aggregate pool. `BIO_new_bio_pair` accepts both sizes; **zero means default 17 KiB, not zero capacity**.
- Configure sizes before pairing. `BIO_C_SET_WRITE_BUF_SIZE` rejects a connected pair with IN_USE and a zero size with INVALID_ARGUMENT. Constructor size arguments cross into a `long` control value; the shim must validate positive, representable sizes/counts before narrowing. Constructor failure cleans both provisional BIOs and returns null outputs. A capacity setter is not a safe connected-ring resize mechanism.
- A full ring write sets retry-write; an empty open-peer read sets retry-read. Writes exceeding free space are short. These are backpressure/pending, **not EOF, resource exhaustion or release**. The write guarantee is currently available capacity, not transport writability. Pair flush itself succeeds without sending anything to the network (`BIO_CTRL_FLUSH`); it is not `D.flush`.
- Read request is recorded when the opposite half's read failed on empty input, capped at ring capacity, and cleared on a successful read or a write satisfying even part of the request. It is a hint for feeding the BIO, not a requirement to wait for that many transport bytes, a full TLS-record guarantee, a wake registration, or proof the next complete SSL operation will succeed. Respect both actual free capacity and higher-level ingress budget, regardless of hints.
- `BIO_shutdown_wr(b)` closes **that half's writer**. The peer reads buffered bytes first, then EOF; subsequent writes fail. Merely empty is not EOF. Lower raw EOF may be represented to the SSL input BIO only after retained ciphertext tails are fed; it is still **not authenticated TLS EOF**. #38 rejects truncation without close-notify. Closing a local pair writer does not generate TLS close-notify.
- `BIO_destroy_bio_pair`/free is not shutdown-writer semantics: destruction disconnects both ends, marks them uninitialized and clears pending lengths. Both halves require ownership/release accounting even when `SSL_free` owns one half. No buffered-tail preservation or graceful delivery follows from freeing.
- Pair internals are not locked; normally both halves are operated by the same application thread. A serialized owner/native-job arrangement needs actual synchronization and no simultaneous pair/SSL access, not just two separately owned handles. No claim here proves safe worker migration or disposal races.

Application/progress queue capacity, clean terminal read result, lower EOF, pair retry, pair writer shutdown and native release must therefore be separate states. A full plaintext result queue cannot be treated as TLS EOF or permission to decrypt into unlimited overflow. A full write queue cannot erase an admitted native retry. #38 allows typed limit failure/poison for unsupported progress within bounds, not treating ordinary backpressure as failure. Exactly when to wait for consumption versus fail remains policy, not a BIO fact.

## 5. Existing budgets and closed copy boundary

Public §10 fixes **65,536 bytes each** for pending plaintext in/out and ciphertext in/out; the upgrade prefix is charged to ciphertext ingress. Bounded pairs partition these **existing** budgets, not four new rings added on top of full staging queues and not a bound on all OpenSSL allocations. Private §4 explicitly excludes a generic transient heap/stack proof.

Required accounting obligations, not a selected numeric partition:

1. Charge each pair ring's reserved capacity in the appropriate ciphertext direction; retain room in that same budget for lower read buffers, copied drain spans and unaccepted lower-write tails. Initial prefix shares ingress accounting. Do not call a BIO drain “free space” while its bytes still occupy another retained queue.
2. Partition plaintext staging between admitted pending input, stable native retry copies and authenticated output/result queues as applicable. Distinguish aliases from actual duplicates; a separate managed admission copy and native retry copy cannot both silently use the same capacity allowance. Temporary overlap during a copy needs explicit accounting/partition or a justified ownership transfer. Provider internal record/reassembly allocations remain separately audited; do not retroactively label all native internal allocations staging.
3. Managed ownership alone is **not pointer stability**. #38 private §4 requires managed input to be copied into bounded private storage **before foreign use**, with demonstrated native address/content validity across call/wait/retry/migration. No pointer into resizable `Bytes`/`List`, caller stack, expired temporary or movable Wasm memory may be retained by OpenSSL.
4. Ciphertext/plaintext output must be copied/adopted into owned validated representations before pointer invalidation/release. A pending lower job needs stable runtime-owned storage and retained lifetime. The closed shim catalogue, not generic FFI, owns these transitions; managed `D` operations remain outside C.
5. BIO non-copying interfaces (`BIO_nread0/nread`, `BIO_nwrite0/nwrite`) expose native ring pointers with consume/commit and wraparound constraints. Their existence **does not authorize** managed pointer leases, direct lower I/O into those pointers, public pinning, new callbacks or raw buffer escape. Native-internal use would still need reviewed private ownership/copy accounting; this research selects none of these APIs.

Whether “owned input buffer” is a managed command payload, a native retry allocation, or a transferred immutable runtime allocation must be explicit at each boundary. The selected #38 policy is copy-in/copy-out or validated owned adoption with no unapproved managed-pointer retention. A proposed zero-copy path is an amendment to justify, not a consequence of bounded BIO capacity.

### Failure categories under the existing policy

- Native reported allocation shortage constructing BIO objects/rings can be `NativeResourceLimit`, subject to actual native classification/capture. Source allocates ring storage with `OPENSSL_malloc` and returns failure. Constructor returning 0 **alone** does not prove allocation shortage: invalid configuration/in-use also fails. [Pair][pair], [biosource][biosource]; public §11, private §4.
- Queue full is retry/backpressure, not `NativeResourceLimit`. Exceeding an admitted profile/staging limit differs from native resource shortage; #38 specifies `LimitExceeded`/poison for unsupported bounded progress, not automatic allocation-failure classification.
- Rill/runtime allocation, bookkeeping, count/invariant, and error-construction failures remain **fatal** under #38; they are not made recoverable by routing an allocation through a BIO. Conversely a reported native shortage is not automatically fatal Rill bookkeeping.
- Mapping impossible shim sizes, connected-resize misuse, uninitialized/disconnected BIO access or unexpected constructor/configuration failure into existing `InvalidInput`, `ProviderFailure` or a fatal invariant requires identifying which side violated the approved contract. There is **no blanket approved rule “all BIO configuration failures are NativeResourceLimit”**, nor “every BIO construction failure is fatal.” Exact validated-input and failure mappings remain #38/#44 work; do not parse messages or invent a new catch-all category.

## 6. Explicit unknowns / undecided policy choices

1. State-specific interleave proof for pending **reads**, handshake and required TLS 1.2/1.3 control substates; the documented write-WANT_READ exception and write-WANT_WRITE restriction are facts, not a complete safe-alternation algorithm.
2. Effective partial-write/moving-buffer/AUTO_RETRY mode selections and allowed configuration lifecycle. No bitmask amendment is approved here.
3. Concrete ring sizes, per-direction staging partitions, transient copy overlap accounting, lower buffer/job ownership, and numeric ABI checks. Zero/default sizes must not accidentally bypass a partition.
4. Public admission/result/ordered-flush linearization, what may queue without entering SSL, terminal-stop selection and precise join/late-prefix handling. Independent lane cancellation cannot silently discard a native continuation. These are #45 policy choices constrained by #38, not selected signatures.
5. Behavior at plaintext-consumer backpressure and finite ingress exhaustion while a write's retry disallows SSL reads; whether to wait or report the approved typed bounded-progress failure in each state. **No universal liveness claim** follows from finite rings or one owner.
6. Exact construction/configuration error mapping after validated inputs, and any required private catalogue/data amendment. Native resource facts and fatal runtime bookkeeping must remain distinguishable.
7. Actual cooperative advance implementation, joined potentially blocking native work, wake generations/quiescence, release and all native-target acceptance remain #30/#44 obligations. Source/manual reading is not their execution evidence.
