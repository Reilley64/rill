# Error propagation and function overloading in Rill and other languages

This note compares Rill's documented design with upstream language references, library docs and source. The Rill syntax commitments and some semantic policies are confirmed, but [RFCs 0002, 0004 and 0008 remain Draft](../rfcs/README.md). The examples below are source comparisons, not compiler test results.

## Propagation, remapping and recovery

### Rill: a new cause node only when requested

```rill
let config = readConfig(succeed)?;
let config = readConfig(succeed) ? ConfigLoadFailed {};
```

These are alternatives from the [error prototype](../../prototypes/02-caused-by-errors.rill). Both evaluate the call once and yield its success value. On failure, the first returns the same `Err<E>` and requires the same canonical `E` in the enclosing `Result`. Postfix `?` also works on `Option`, where it returns `None` rather than constructing an error. The second form works only on `Result`. It evaluates the right-hand error value only on failure, constructs a new outer `Err` at the `?` token and returns it immediately. The complete inner wrapper becomes its retained cause, including its payload, origin and prior chain. The left and right error types can differ. Retention requires `display`, `noBorrow`, `sendable` and `shareable` evidence for the inner payload. [Postfix rules](../rfcs/0008-errors-propagation-and-caused-by-wrapping.md#postfix-propagation-and-normal-return) · [Wrapping and cause rules](../rfcs/0008-errors-propagation-and-caused-by-wrapping.md#infix-caused-by-wrapping).

The right operand is a value expression, not a function that receives the inner error. Use `guard ... else (cause)` with `Err(newValue, cause)` when the failure path must inspect that error before wrapping it. Draft `mapErr(result, mapper)` instead transforms the typed payload and leaves the result available locally. It preserves the old origin and any existing cause, but it does not keep the old wrapper as a new cause. [Explicit construction](../rfcs/0008-errors-propagation-and-caused-by-wrapping.md#closed-err-construction-and-typing) · [Combinators](../rfcs/0008-errors-propagation-and-caused-by-wrapping.md#consuming-combinators-and-borrowed-queries).

The [syntax annex](../grammar/v0-syntax-v1.md#question-marks-and-expression-starts) chooses infix if the next significant token can start an expression, and postfix otherwise. Spaces, comments, newlines and types do not decide. `read()? - 1i32` commits to wrapping with `-1i32`, while `(read()?) - 1i32` subtracts from the unwrapped value. Likewise, `value?()` commits to invalid infix syntax. Use `(value?)()` to call an unwrapped function. A failed parse or type check does not retry the other form.

### Rust, Roc, Zig and Gleam

| Language | Exact forms and failure behavior |
| --- | --- |
| Rust | `read()?` uses a postfix-only operator. On `Result::Err(e)` it returns `Err(From::from(e))`; that conversion may change the error type and does not promise to keep a cause. `read().map_err(remap)?` explicitly maps `Err`, then propagates it. `read().or_else(recover)` can return `Ok` and does not itself return from the caller. A typed wrapper can expose an underlying error through `std::error::Error::source`. With the `anyhow` library, `read().with_context(|| format!("read {}", path.display()))?` builds context only on failure, keeps the underlying error and returns an `anyhow::Error` on the error path. `.context(value)` takes an already-evaluated argument. [Rust reference](https://doc.rust-lang.org/reference/expressions/operator-expr.html#the-try-propagation-expression) · [`map_err`](https://doc.rust-lang.org/std/result/enum.Result.html#method.map_err) · [`or_else`](https://doc.rust-lang.org/std/result/enum.Result.html#method.or_else) · [`Error::source`](https://doc.rust-lang.org/std/error/trait.Error.html#method.source) · [`anyhow::Context`](https://docs.rs/anyhow/1.0.104/anyhow/trait.Context.html). |
| Roc | `U64.from_str(s)?` unwraps `Try` or returns its `Err` early. The return error type can include multiple propagated tags. Roc documents adjacent postfix `?` and spaced infix `?`. `U64.from_str(s) ? |_| InvalidPort` calls a handler on failure and returns `Err(InvalidPort)`, discarding `BadNumStr`. `U64.from_str(s) ? InvalidPort` uses the tag form and returns `Err(InvalidPort(BadNumStr))`. This keeps the original error as typed tag payload, not as a separate origin-bearing cause. `U64.from_str(s) ?? 8080` supplies a local default on failure. [Operator reference at the checked revision](https://github.com/roc-lang/roc/blob/63434e9847e74db8ffed7e9244bcb8317771c350/docs/langref/operators.md#L125-L166) · [Postfix rules](https://github.com/roc-lang/roc/blob/63434e9847e74db8ffed7e9244bcb8317771c350/docs/langref/operators.md#L205-L253) · [Tag wrapping fixture](https://github.com/roc-lang/roc/blob/63434e9847e74db8ffed7e9244bcb8317771c350/test/fx-open/issue_11097_bare_and_wrapped_try_runtime.roc). |
| Zig | `const n = try parseU64(s, 10);` uses prefix `try`, equivalent to `parseU64(s, 10) catch \|err\| return err`. `parseU64(s, 10) catch return error.InvalidPort` explicitly replaces and returns the error. `parseU64(s, 10) catch 8080` supplies a local default. An error set value has no payload for a retained cause. Zig's error return trace records return sites when enabled; it is not a chain of typed causes. [Error sets](https://ziglang.org/documentation/0.15.2/#Error-Set-Type) · [`try`](https://ziglang.org/documentation/0.15.2/#try) · [`catch`](https://ziglang.org/documentation/0.15.2/#catch) · [Error return traces](https://ziglang.org/documentation/0.15.2/#Error-Return-Traces). |
| Gleam | `use x <- result.try(read())` passes the rest of the block as a callback. `result.try` calls it only for `Ok(x)` and passes `Error(e)` through without calling it. This is ordinary callback composition, not an operator that returns from the enclosing function. `result.map_error(read(), remap)` changes only the `Error` payload. `result.try_recover(read(), recover)` calls a callback on error that may return `Ok`. Any old error data must be kept explicitly in the mapped value. [`use` expansion](https://tour.gleam.run/advanced-features/use/) · [`try`](https://hexdocs.pm/gleam_stdlib/1.1.0/gleam/result.html#try) · [`map_error`](https://hexdocs.pm/gleam_stdlib/1.1.0/gleam/result.html#map_error) · [`try_recover`](https://hexdocs.pm/gleam_stdlib/1.1.0/gleam/result.html#try_recover). |

Roc has the closest spelling. Its infix operator gives the old error to a handler or tag. Rill takes an error value and attaches the old wrapper separately. Rust's `with_context(...)?` is closer to Rill's lazy cause retention. It separates context attachment from early return and uses a common outer error type. Zig's `catch` makes recovery and early return differ by a visible `return`. Rill's shorter form needs parentheses at some postfix expression boundaries.

## Function overloading and web servers

### What Rill selects

A body-less declaration such as `function show<T>(value: &T): string;` establishes one canonical family and its shape. An `implement` body specializes that shape without changing its parameter count. Import aliases and re-exports identify the same family. All its bodies in the loaded graph contribute, even when the caller does not import the module that added a body. Unrelated files on disk do not contribute. Repeated paths to one body count once. Distinct bodies with the same canonical input pattern fail during collection, even if no call reaches them. [Family shape](../rfcs/0004-functions-overloads-and-generic-requirements.md#family-shape-and-canonical-patterns) · [Loading](../rfcs/0002-modules-and-program-loading.md#loading-and-cycles) · [Family collection](../rfcs/0002-modules-and-program-loading.md#family-collection-and-metadata-boundaries).

The ordinary orphan rule permits a body in the family owner or a module defining a nominal type anywhere in a parameter. A local type nested inside a foreign container counts. A local type appearing only in the result does not. This limits extension without guaranteeing coherence. [Placement rules](../rfcs/0004-functions-overloads-and-generic-requirements.md#collection-and-placement-permission) · [Separate conversion endpoint rule](../rfcs/0009-user-implementable-conversions.md#endpoint-placement-permission).

Ordinary ranking uses the whole static input vector. A pattern wins if its set of matching vectors is a strict subset of each other matching pattern's set. A sole match also wins. `(T, T)` is narrower than `(A, B)`. `(Point, T)` and `(U, Point)` are incomparable. A `(Point, Point)` call with both matches is ambiguous unless another match dominates both. Requirements and results do not rank candidates. If the winner lacks required evidence, the call fails rather than retrying a broader body. A whole-enum argument does not dispatch to a variant-only body according to its runtime tag. [Whole-vector ranking](../rfcs/0004-functions-overloads-and-generic-requirements.md#whole-vector-specificity) · [Selection order](../rfcs/0004-functions-overloads-and-generic-requirements.md#ordinary-call-selection).

### What other languages select

| Language | Mechanism and contrast with Rill |
| --- | --- |
| Kotlin / Ktor | Kotlin finds an applicable candidate set using scope and receiver priority, then uses type constraints to find its most specific member. For an explicit receiver, applicable members can exclude extensions before ranking, even if an extension has narrower types. Kotlin also has tie rules for genericity, defaults and varargs. Ktor uses real overloaded extension functions on `Route`, including `get(path, handler)` and `get(handler)` with different arities. [Kotlin specification](https://kotlinlang.org/spec/overload-resolution.html#call-with-an-explicit-receiver) · [Specificity rules](https://kotlinlang.org/spec/overload-resolution.html#algorithm-of-msc-selection) · [Ktor 3.3.3 source](https://github.com/ktorio/ktor/blob/3.3.3/ktor-server/ktor-server-core/common/src/io/ktor/server/routing/RoutingBuilder.kt#L119-L191). |
| Julia | A generic function has a method table. Dispatch uses the actual argument types at run time, even when compilation can resolve a particular call in advance. `g(::Float64, ::Any)` and `g(::Any, ::Float64)` cause a `MethodError` at their intersection unless a more specific method covers it. Defining `function g end` is possible but not required. A module can extend someone else's function with a qualified definition or explicit import for an unqualified definition. It need not own an argument type. Julia's style guide calls extending a foreign function on foreign types "type piracy" and advises against it. [Method tables and calls](https://docs.julialang.org/en/v1/devdocs/functions/#Function-calls) · [Ambiguity](https://docs.julialang.org/en/v1/manual/methods/#man-ambiguities) · [Module rules](https://docs.julialang.org/en/v1/manual/modules/#using-and-import-with-specific-identifiers,-and-adding-methods) · [Style guide](https://docs.julialang.org/en/v1/manual/style-guide/#avoid-type-piracy). |
| Roc | A nominal type declares methods in its `.{ ... }` block. `counter.increment()` selects `Counter.increment(counter)` using the receiver's static type. `where [a.to_str : a -> Str]` expresses a requirement on a type variable's own method. Roc can also select a method through a type variable without a value receiver, such as `Thing.default()`. This is type-associated dispatch, not competition among loaded bodies of a canonical free-function family. [Methods and calls](https://github.com/roc-lang/roc/blob/63434e9847e74db8ffed7e9244bcb8317771c350/docs/langref/static-dispatch.md#L16-L56) · [Requirements](https://github.com/roc-lang/roc/blob/63434e9847e74db8ffed7e9244bcb8317771c350/docs/langref/static-dispatch.md#L433-L491). |
| Zig | Zig does not have ordinary function overloading. A single `fn` can take `anytype` or a `comptime` type parameter and use compile-time branches to choose behavior. Different names or one explicit generic body replace overload discovery. That removes candidate-ranking rules, but the body can hide supported cases unless the API documents them. [Maintainer decision](https://github.com/ziglang/zig/issues/1251#issuecomment-405147513) · [Parameter inference](https://ziglang.org/documentation/0.15.2/#Function-Parameter-Type-Inference) · [`comptime`](https://ziglang.org/documentation/0.15.2/#comptime). |
| TypeScript | Overload signatures describe the allowed static call shapes of one implementation. The implementation signature is not directly callable. The function body, not a runtime overload table, must distinguish the inputs if they need different behavior. This can document a flexible registration API, but does not select distinct implementation bodies as Rill does. [Handbook](https://www.typescriptlang.org/docs/handbook/2/functions.html#overload-signatures-and-the-implementation-signature). |

### Keep route matching separate from function selection

Ktor's `post<CreateUser>("/users") { user -> ... }` selects a typed registration overload at compile time. That overload delegates to the path-based `post` and passes `call.receive()` to the typed callback after the route matches. Ktor matches request values with method and path selectors at run time. The payload type does not select the route. [Typed `post` source](https://github.com/ktorio/ktor/blob/3.3.3/ktor-server/ktor-server-core/common/src/io/ktor/server/routing/RoutingBuilder.kt#L143-L191) · [Route definition](https://ktor.io/docs/server-routing.html#define_route) · [Runtime resolver](https://github.com/ktorio/ktor/blob/3.3.3/ktor-server/ktor-server-core/common/src/io/ktor/server/routing/RoutingResolveContext.kt#L88-L176).

For a Rill server API, distinct names can express different registration arities without loosening family shape. A fixed-shape registration call with an explicitly typed decoder or options value gives overload selection an input type independent of the handler arrow. That fits [Rill's staged callback checking](../rfcs/0004-functions-overloads-and-generic-requirements.md#contextual-callbacks-and-function-values) better than asking the compiler to try several handler bodies to pick a route. Match HTTP method and path as request data, then decode in the selected handler. Keep route conflicts separate from build-time family ambiguities. Adding a module to the loaded graph can change a static winner or make a call ambiguous; it should not silently register a route. These are API design implications, not changes to the [standard HTTP server driver](../http-contracts.md#16-server-connection-driver).
