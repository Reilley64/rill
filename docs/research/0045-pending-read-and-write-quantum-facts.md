# ri-w0c: pending reads and candidate write-quantum facts

## Execution correction: the predicted TLS 1.2 `BAD_WRITE_RETRY` did not reproduce

A later pinned-source reference execution in [`0045-progress-reference/`](0045-progress-reference/) reproduced the stated setup—completed 227-byte application write, exactly 256 ciphertext bytes occupying the 256-byte external BIO ring, received post-handshake `HelloRequest`, observed warning-alert write callback and read `WANT_READ`—but a fresh one-byte `SSL_write_ex` **succeeded** after draining the external ring. Three immediate reruns produced the same result. Therefore this note's source-derived claim below that this path necessarily leaves record-layer `wpend_type=ALERT` and causes `BAD_WRITE_RETRY` is **rejected for the tested OpenSSL3.5.9 path**, not an executed counterexample.

The missing source fact was the handshake state machine's `ssl_init_wbio_buffer`: it pushes a buffering BIO and makes it the record layer's write BIO (`statem.c` around the handshake write transition; `ssl_lib.c:ssl_init_wbio_buffer`). A full external BIO-pair ring therefore did not prove a pending record-layer alert retry, and the later local application write was accepted.

A strengthened fixture then retained the full prior ciphertext instead of discarding it and delivered every ciphertext byte subsequently made available to the peer. It observed: warning-alert callback; post-read top write BIO already back to the BIO pair; 256 prior ciphertext bytes; a successful one-byte local write; only a 30-byte later application record; successful peer delivery of the prior 227 plaintext bytes; then peer `SSL_ERROR_SSL` with bad-record-MAC/record-layer failure before delivery of the fresh byte. The warning alert had advanced sender record state without corresponding ciphertext handoff. The exact temporary buffering internals were not exposed, but the end-to-end record consequence was executed. The explicit-stop fixture avoided the fresh write.

Thus the original derivation below remains a **falsified mechanism hypothesis**—not an observed `BAD_WRITE_RETRY`—while its safety conclusion is restored on stronger evidence for this tested TLS1.2 rejected-renegotiation path: continuation corrupts the peer-visible record sequence, so the progress profile should detect the event and terminally stop rather than continue application I/O. This does not prove every control substate or the production callback/shim mechanism. The corrected suite passed13/13 in memory and remains ReferenceExecuted, not Rill/TCP/provider delivery or a complete scheduler/security proof.

## 1. Result: a pending read is not an exclusive application-I/O lock, but WANT alone is insufficient

**A fresh application write after a read's WANT_READ is supported in specific established application states, including an upstream TLS 1.3 test that does exactly this after receiving a requested KeyUpdate.** Absence of a reciprocal sentence in `SSL_get_error(3)` is not proof of incompatibility. Conversely, **neither read-WANT_READ nor read-WANT_WRITE by itself establishes that a fresh write is safe in every reachable ri-irw state**. A pending warning-alert write is a concrete source-level obstruction even with TLS 1.2 renegotiation disabled. The distinction is shared outbound record state, not just which application operation ran last.

The manual explicitly permits read after write-WANT_READ, and explicitly restricts other I/O after write-WANT_WRITE. It does not supply the inverse blanket permission for pending reads. The following conclusions instead follow from the separate read/write implementation and actual upstream tests. They are narrower than a universal scheduler theorem. [Error][error], [records][records], [tests][tests].

### 1.2 Concrete source counterexample: NO_RENEGOTIATION does not eliminate control-write collision

A reachable TLS 1.2 **client** application state illustrates why “all pending reads can yield to writes” is too broad:

1. `SSL_OP_NO_RENEGOTIATION` is set; ordinary application ciphertext from earlier completed writes fills the outbound pair ring (or leaves too little free space for an alert). There is no active application write retry. The peer sends an encrypted, well-formed, empty `HelloRequest` after the initial handshake.
2. `SSL_read_ex` processes that handshake message. `tls_process_hello_req` calls `ssl3_send_alert(WARNING, NO_RENEGOTIATION)` and returns `MSG_PROCESS_FINISHED_READING` **without checking the alert-send result**. This rejects renegotiation; it does not perform renegotiation. [Client][client] L4044–4072.
3. Alert dispatch cannot complete into the full ring. `ssl3_dispatch_alert` retains `alert_dispatch = RETRY`, `wpend_tot = 2`, `wpend_type = ALERT`, and `wpend_buf = send_alert`. [Alert][alert] L108–136.
4. Client handshake write-transition from `TLS_ST_CR_HELLO_REQ`, with no renegotiation pending, goes to `TLS_ST_OK`; pre-work finishes the handshake. With AUTO_RETRY off and no additional application record available, `ssl3_read_bytes` returns its synthetic WANT_READ; with an empty open input it can also reach the ordinary input WANT_READ path. Thus **read-WANT_READ does not certify no pending control output**. [Client][client] L691–705, L782–784; [records][records] L1030–1067.
5. Even if the external BIO output is now drained, issuing a fresh application write immediately is not an alert retry. The application write hits the pending-type check first and fails BAD_WRITE_RETRY; the later alert-dispatch branch is not reached. Draining bytes cannot clear the native pending record by itself. [Records][records] L252–267, L337–378.

This is a source-path derivation, **not an executed reproducer**. The server-side rejection of an unsolicited renegotiation ClientHello similarly sends a warning and returns FINISHED_READING; no assertion that the entire client/server rejection coverage has been executed follows. [Server][server] L1504–1524. This counterexample does not require enabling renegotiation, PHA, tickets or async engines. Excluding it by assuming that the peer never sends a renegotiation request is **an extra profile/peer assumption**, not a consequence of disabling local renegotiation.

In particular, this investigation has **not** established that simply retrying the read after draining output always retires this queued alert. The ordinary application-read path is not a general pending-alert dispatcher. Nor is a zero-length fresh write established here as a control pump. The fact to carry forward is the collision and the need to account for it, not an invented recovery API.

### 1.3 Official examples/tests: what they actually demonstrate

- **`test_key_update_peer_in_read`**, [sslapitest.c L7173–7254][tests]: both role directions; new BIO pair of **512 bytes per half**; sender queues requested KeyUpdate and writes 515 application bytes, getting WANT_WRITE. Receiver calls `SSL_read`, gets WANT_READ after processing KeyUpdate and part of the application ciphertext, **then calls a fresh `SSL_write` successfully before its read is retried**. The pending sender write and receiver read are subsequently completed. This directly refutes a blanket incompatibility claim for read-WANT_READ. It uses legacy I/O wrappers over the same internals as `_ex`; it is not exhaustive coverage of TLS 1.2, all modes, alerts, padding, arbitrary fragmentation or ri-irw enforcement.
- **`test_key_update_local_in_read`**, [L7348–7440][tests]: receiver gets WANT_READ on a fragmented inbound application record, explicitly queues/sends its own KeyUpdate via `SSL_key_update`/`SSL_do_handshake`, then completes the read. Evidence that inbound partial-record state survives outbound control activity; not a fresh-write-after-every-WANT test or permission to introduce new public controls.
- **`test_key_update_peer_in_write`**, [L7078–7170][tests]: intentionally calls a read after an induced application write-WANT_WRITE, then retries the original write and sends a later response KeyUpdate. **This test goes beyond the manual's write-WANT_WRITE restriction.** It is evidence for that narrow source/test scenario, not a reason to override the published restriction in a general scheduler.
- Official [nonblocking client guide][guide] and [demo][demo] retry each write and then each read, preserving the operation. This is a sequential request/response example, **not** a general duplex interleave proof and not evidence against the supported interleave above.
- Official [`s_client`][s-client] L3120–3199, L3227–3275 contains an interactive event loop: read WANT_WRITE enables the SSL-write path; read WANT_READ can also enable it when stdin has supplied data. This shows upstream application practice, but it is a socket-based diagnostic program with broader controls, not a proof that all ri-irw pair/control substates are covered. The pending-alert check above remains real source behavior regardless of this example.

### 1.4 Retry storage and identity

Read retries and native write retries are separate obligations:

- For the ordinary non-async read path, the caller's destination is used for plaintext copying in the active synchronous call; partial ciphertext/handshake reassembly lives in SSL/record-layer state. The reviewed path does not store a caller read-destination pointer for later input reassembly. This is **source evidence**, not a manual promise that arbitrary read-buffer mutation is supported across all future modes. Keep a private destination/capacity/lifetime for the saved read continuation under ri-irw; never use caller-managed pointers or async-engine behavior to generalize it. [Lib][lib] L2305–2389; [records][records] L650–705, L790–842.
- After a write WANT, preserve the **original pointer, bytes and length** with moving-buffer mode off, even when the input has been encrypted already. Partial-write mode changes successful operation boundaries, not retry identity. `tls_write_check_pending` checks size/pointer/type; it does not compare all plaintext bytes. [Write][write], [modes][modes], [records][records] L252–360.
- A control write uses its own provider-owned `init_buf/init_off/init_num` or `send_alert` storage, but shares outbound record-layer pending state with application output. Do not overwrite those buffers, reset state, toggle modes, or infer that copying application bytes to staging clears the native continuation. [State-lib][state-lib] L76–124; [Alert][alert] L108–136.
- A read that returned WANT_READ may be waiting on an inbound handshake message. Starting a write can enter that same handshake and return WANT_READ too; preserve **both logical continuations**, without pretending the write has made application progress or discarding the read. The latest `SSL_get_error` cannot reconstruct the earlier saved result.

## 2. Candidate bounded native write policy — facts, NOT selection

Candidate only: partial-write mode from engine creation, moving-buffer mode off, AUTO_RETRY off, each native application write request at most **16 KiB**, and admission only with reserved egress capacity for worst application-record output plus necessary control output. ri-irw does **not** select these mode bits, quantum or partitions. The candidate cannot by itself solve the pending-alert counterexample or prove duplex liveness.

### 2.1 What the candidate changes, and what it does not

`ENABLE_PARTIAL_WRITE` permits a **successful** shorter write at a record/message-block boundary; the unsent suffix is a new native operation. It cannot be enabled midway through an incomplete write. With the selected AEAD suites, normal one-record fragmentation and a request no larger than 16384, success ordinarily accounts for that requested record (or a smaller configured fragment). A request bound alone does not specify fragment size, padding, pipelines, record-layer implementation or controls. All effective settings must be inventoried before using a size calculation. [Modes][modes], [write][write], [records][records] L380–487; [record-common][record-common] L1527–1551.

Partial-write mode does **not** make a partial ciphertext record a successful plaintext write. A full ring can leave part of the one record native-pending, returning WANT_WRITE, even when the request is ≤16 KiB. With moving-buffer off, retain the entire original request span unchanged until native success/terminal resolution. AUTO_RETRY off is not “one record of work per call”: it affects non-application record processing and can produce WANT_READ with locally buffered input; warning/empty-record loops and crypto/release costs are not converted into a hard work/time bound. [Read][read], [modes][modes], [records][records] L850–968, L1030–1067; [record-common][record-common] L1918–2035.

Initial/final handshake flights must already satisfy publication/handoff rules and have separate bounds. They are not bounded by an application-write quantum. TLS 1.3 sending-key update post-work uses BIO flush and changes the sending keys; a BIO-pair flush is not lower `D.flush`. Received repeated controls, fragmented handshakes, alert behavior and future reviewed key-use enforcement prevent treating “one small application write” as a bound on all protocol work.

### 2.3 Ciphertext lengths: conditional arithmetic, not a chosen reservation

For **one encrypted record**, no compression, the ri-irw suite inventory, and **no outbound TLS 1.3 padding**, let `n` be application content bytes in that record. Pinned source has a 5-byte record header, TLS 1.2 AES-GCM 8-byte explicit nonce, and 16-byte AEAD tags for the approved AES-GCM/ChaCha20-Poly1305 suites. TLS 1.3 adds one encrypted inner-content-type byte and no explicit nonce. [Constants][constants] L139–141, L177–210; [EVP constants][evp] L467–490; [TLS12 keys][tls12-keys] L168–195; [TLS13 keys][tls13-keys] L398–423; [TLS12 records][tls12-records] L138–156; [TLS13 records][tls13-records] L328–406.

| Record | Wire bytes under those conditions |
| --- | --- |
| TLS 1.2 AES-GCM application | `n + 29`; at `n=16384`, **16413** |
| TLS 1.2 ChaCha20-Poly1305 application | `n + 21`; at `n=16384`, **16405** |
| TLS 1.3 application, approved suites, no padding | `n + 22`; at `n=16384`, **16406** |
| TLS 1.3 KeyUpdate alone, no padding | 4-byte handshake header + 1-byte update type + 1-byte inner type + 16-byte tag + 5-byte record header = **27** |
| TLS 1.2 warning/fatal/close alert, approved suites | 2-byte alert content: **31** AES-GCM / **23** ChaCha20-Poly1305 |
| TLS 1.3 encrypted alert, no padding | 2-byte alert content + 22 = **24** |

These are **individual-record arithmetic**, not a total-output guarantee for an arbitrary native call. For the isolated no-pending-record TLS 1.3 path that sends one queued KU then one full application record, the no-padding sum is 27 + 16406 = **16433**. That number is an illustration, **not a selected required reservation**, nor a bound on all error/control/substate cases. Configured smaller fragments can produce more records unless successful partial mode stops after the applicable batch. Already queued ciphertext and partial native records need separate accounting.

Padding callbacks/block-padding/handshake-padding settings change small control-record sizes; ri-irw does not silently select a padding configuration here. `tls13_add_record_padding` caps padding against the record layer's max fragment length and adds it before the AEAD tag. The protocol-facing TLS 1.3 maximum ciphertext-content constant is **16384 + 256**, with the 5-byte header additional; this is a wider receive/envelope bound, **not** the no-padding emitted application-record size or a bound on a whole handshake flight. A reservation proof must pin actual padding, fragmentation, provider record method and any patches rather than reuse an allocator-overhead constant or this table unconditionally. [TLS13 records][tls13-records] L328–406; [constants][constants] L177–210.

### 2.4 A 16 KiB BIO ring is smaller than a full-size TLS record

A 16384-byte egress ring cannot hold even one of the full application ciphertext records above. Therefore:

- Even with ample *aggregate* egress budget reserved elsewhere, the first native write can fill the ring and return WANT_WRITE with its remaining ciphertext in OpenSSL's native record buffer.
- The external pair half may be drained into properly charged owned output storage; then **retry the same native write**, preserving stable input identity. `tls_retry_write_records` advances its native ciphertext-buffer offset/remaining count, using short `BIO_write`s until complete. This is normal partial-record transport progress. [Record-common][record-common] L1918–2035; [pair][pair].
- **Draining a BIO while the native application write is pending is not interleaving `SSL_read_ex`.** The manual's write-WANT_WRITE restriction still applies to other SSL I/O. Neither partial-write mode nor an aggregate reservation is a license to read at that point.
- A promise to avoid *all* WANT_WRITE in a single attempt would require enough immediately writable BIO capacity for the actual output, not merely free space in a separate queue. A cooperative strategy that drains/retries may work without that stronger property, but still needs retained jobs, wake/stop rules and accounting. No single native call's hard execution bound follows.

Ingress has the analogous framing issue: a ring smaller than a ciphertext record can be fed in pieces while OpenSSL reassembles it. A full plaintext result queue or native write retry that restricts reads can prevent further decrypting/feeding; free egress capacity does not prove ingress or consumer progress.

### 2.5 What egress reservation can and cannot establish

On the isolated established write path with no pending record/alert, no init requiring peer input, fixed one-record fragment configuration, no extra tickets, and an optional single queued KU, the source shows no peer-read step needed for ordinary application output. Sufficient **aggregate reserved owned capacity plus permitted repeated external drains** can address that path's BIO output pressure. That is a conditional storage argument, not a claim that every ri-irw write finishes without WANT_READ.

Remaining problems include:

1. **Shared pending control state:** enough capacity does not make APPLICATION_DATA an ALERT retry. The TLS 1.2 counterexample remains unless the mechanism prevents or handles that state by a justified method.
2. **Input-side init:** a read-WANT_READ may be waiting in a partially received control handshake. A fresh write enters the same state machine and can WANT_READ; output reservation supplies no missing input.
3. **Effective controls:** stock response KeyUpdate support is not ri-irw's complete mandatory key-use/epoch enforcement. Any maintained fixes/local enforcement must be included in output/work bounds and pending-state proofs. Ticket disabling is also not a demonstrated safe received-ticket discard implementation.
4. **Fatal outcomes:** malformed input, record/key-limit errors, native allocation or crypto errors can still fail; a reservation is not an infallibility or peer-effects guarantee.
5. **Reservation ownership and exhaustion:** preexisting ring bytes, copied drains, unaccepted lower tails and lower jobs consume capacity. Another read/control action must not consume a write's reserved output space unnoticed. Arbitrarily many received controls over time have no finite total-output bound independent of draining/consumption; a one-call/one-quantum budget requires an explicit state/work definition.
6. **Finite-input/consumer deadlock:** lower backpressure and plaintext consumer backpressure can exhaust bounded queues. No proof here establishes universal progress for a bidirectional streaming protocol or selects when to wait versus the approved typed bounded-progress failure. Ordinary ring-full is not allocation failure.

## 3. Exact acceptance and existing 64 KiB budgets

The **public exact current-input prefix is TLS-owned staging admission**, not an OpenSSL failure-prefix estimate. It must remain so regardless of quantum. A write WANT/failure is not an exact zero-effects report; success counts only the native chunk completed. Ciphertext drained or accepted by D does not give a public plaintext-prefix conversion or prove peer decryption/execution. Public §8; private `AcceptPlaintext`/`TakeCiphertext`; [write][write]; [records][records] L274–487. A small quantum and partial success do not authorize inferring effects from a failed record's ciphertext prefix.

Public §10 fixes **65536 bytes each** for pending plaintext-in, plaintext-out, ciphertext-in and ciphertext-out. The candidate introduces no new budget. Before selecting **any** numeric quantum or ring/queue partition, require an explicit ledger such as:

| Existing direction | Required named partitions / overlaps |
| --- | --- |
| Plaintext-out | Publicly admitted unsent staging; stable private native retry span (whether the same physical owned storage or a copy); remainder awaiting a fresh native operation; admission-to-native copy overlap. An alias is not a duplicate, but two actual copies must both be charged. |
| Plaintext-in | Private SSL-read destination/output staging; authenticated retained tail/result queue; copy/append overlap into caller-owned result; destination lifetime during joined native work. Consumer backpressure cannot justify hidden overflow. |
| Ciphertext-out | Egress pair ring **reserved capacity**; copied drain buffer(s); unaccepted lower-write tails; storage retained by outstanding lower jobs; temporary drain-to-tail copy overlap; any dedicated control/write reservation. A byte moving out of the ring is not freed while retained elsewhere. |
| Ciphertext-in | Ingress pair ring reserved capacity; upgrade prefix; lower-read buffer/job storage; unconsumed feed tails; temporary copy overlap into the ring. Native reassembly is separately audited, not silently mislabeled as managed staging. |

No numbers in §2 select these partitions. In particular, “16 KiB ring + up to 64 KiB queue” exceeds the existing direction's budget before copy overlap. Two pair rings are charged separately in their respective ciphertext directions. Native OpenSSL record/reassembly buffers exist; public staging budgets are **not** a proof of all provider transient memory/stack bounds. Private §4 explicitly requires that separate audit.

Private storage must be stable across call/wait/retry/worker migration. ri-irw requires managed input copied into bounded private storage before foreign use, and output copied or validated-owned-adopted before pointer invalidation. Do not add another uncharged shim-native copy on top of staging/native retry storage; distinguish the unavoidable provider record buffer from a newly proposed copy. BIO non-copying accessors do not authorize a managed pointer lease or direct lower I/O into native ring memory. No pointer into movable/resizable managed buffers, caller stack or Wasm memory may be retained. Lower I/O remains outside C with stable owned storage and proper joins. [Private] §§3–6; [pair][pair].

## 4. Facts/gates still needed before any safe-scheduler proposal

1. An implementable state distinction/retirement mechanism for pending **control output**, including TLS 1.2 rejected renegotiation, read-WANT_WRITE handshake continuations and read-WANT_READ with pending alert. Last WANT plus `SSL_is_init_finished` is insufficient; do not silently add raw OpenSSL internals to the closed private catalogue.
2. Effective from-creation modes, fragment/pipeline/padding/record-method settings, actual mandatory KU/key-use fixes and received-ticket safe-discard handling. Review any provider patch and then repeat state/size analysis against that exact source.
3. A proof or targeted selected-source fixture matrix covering both roles/versions, empty and fragmented input, inbound KU requested/not-requested, outgoing KU blocked at each point, warning-alert blockage, pending app-write identity, full/wrapped rings, retained lower tails, EOF/close/fatal outcomes and simultaneous public commands. Upstream tests identify useful cases, not complete ri-irw acceptance.
4. Explicit capacity equations and partitions for all four existing budgets, including transient copies/tails/reservations; prove worst applicable control-output bounds for the **admitted state**, rather than selecting 16 KiB or 16433 by assumption.
5. Public admission/result/ordered-flush semantics, preservation of both logical continuations, stop/poison/join/late-prefix behavior, and bounded advance/wake rules. Native execution can still block under private §5. A source-compatible interleave does not deliver ri-dej runtime cooperation or ri-ei7 TLS support.
6. Check the **complete proposed behavior**, not only a convenient request/response subset, against ri-n5i's general streaming goal. If control handling or finite-buffer progress remains unproven, record that counterexample/unknown and return to the mechanism/provider decision. Do not quietly redefine the goal to avoid the case, claim universal liveness, or treat a limited experiment as Rill/provider delivery proof.
