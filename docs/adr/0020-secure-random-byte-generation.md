# Secure random byte generation

Issue ri-w9z confirms secure-by-default `std::random` with owned generation and filling an existing exclusive `Bytes` owner. The Q1-Q15 interview and consolidated design were explicitly confirmed. [The public catalogue](../standard-library-contracts.md#13-secure-random-bytes) records the exact API; [prototype 15](../../prototypes/15-secure-random.rill) and its [case inventory](../prototypes/15-secure-random.md) are hand-checked design evidence, not an implemented library, executed provider tests, security/checker proof or accepted feature RFC.

## Complete success, not transactional mutation

Success means every requested byte was generated. Owned generation exposes no partial buffer; in-place failure/cancellation may modify contents and provides neither rollback nor a usable-prefix count. The buffer's logical length is unchanged. Empty requests succeed without consulting/initializing a provider. These are Rill adapter guarantees rather than an inference from platform zero-length behavior. Checked u64 lengths and bounded provider calls must not narrow/truncate; ordinary Bytes capacity/allocation failure remains fatal, separate from typed source failures. No arbitrary portable total-size limit is introduced.

RandomError exposes a portable kind and optional diagnostic native code, not generated bytes or destination contents. Its display/noBorrow/sendable/shareable contract follows ri-8n7's existing errors; ordinary origins/causes remain, not automatic propagation reports. Output is ordinary Bytes, with no implicit secret-storage/zeroization, uniqueness or nonzero-output guarantee.

## Chosen providers and trust

- **Linux.** Use getrandom with flags 0. Require secure initialization, account for positive short counts and retry EINTR with normal cancellation checks between attempts. No GRND_INSECURE, GRND_RANDOM, device-file compatibility fallback or Rill-managed generator fallback. Missing syscall/sandbox restrictions are reported where the running runtime receives an error; this facility is not available merely because some other Linux APIs work.
- **macOS.** Use SecRandomCopyBytes with kSecRandomDefault and checked status/size_t chunks, linked through the trusted runtime/system framework. Apple explicitly promises cryptographically secure output and supplies a status channel; arc4random_buf lacks a recoverable failure channel, while Apple's getentropy contract has a 256-byte cap and recommends other APIs for ordinary consumers. No undocumented macOS latency/EINTR/rollback promise is inferred.
- **wasm32-wasip1.** Use random_get under an explicitly supported trusted-host configuration supplying cryptographically secure output. Preview1's wording alone is not a proof that every host qualifies. Check u32 ABI lengths/offsets and provider-specific limits. Missing imports/instantiation failures and host traps cannot all be converted into RandomError. A dishonest/predictable host returning success cannot be detected by the guest or statistical tests. No Windows support is implied.

OS services may use cryptographic generators. The rejected substitution is weak, predictable, fixed or test output presented as secure success, not a correctly seeded CSPRNG inside a trusted provider. Changing/adding providers or compatibility strategies requires explicit support/security review, not a hidden fallback.

## Scheduling, cancellation and testing

Potentially blocking native calls use the existing runtime blocking facility, not an ordinary M:N scheduler worker. Bound provider work into checked chunks so normal fairness/cancellation can occur between calls; a stuck call is not interrupted by interface wording. Retain backing storage and exclusive access until actual completion or confirmed abortion. Cancellation/timeout/handle drop is not proof the native writer stopped; cleanup may wait indefinitely. Wasm imports may stall the single-threaded scheduler. They need independent validation of host pointers, reentrancy and memory.grow. Host staging/copy-back is a possible mechanism, not an established implementation.

rill test does not silently substitute deterministic entropy, unlike ri-7ap's intentionally empty environment inputs. Applications test their own consumers with explicitly supplied fake callables. Provider faults use a structurally separate private harness/linkage, not a public seed, environment switch, global override or user-replaceable secure provider. Randomness observations/uniqueness checks cannot certify unpredictability. Seeded PRNGs, numeric ranges, floats, shuffling, UUIDs/tokens, cryptographic algorithms and special secret buffers are separate designs.

ri-8n7 stays closed as core baseline; ri-irw must reconcile TLS provider entropy needs without assuming arbitrary entropy injection or adding weaker production configuration. ri-48g must formalize checked sizing/chunk progress, error mapping/origins, non-escaping partial owned output, source retention/cleanup and actual native/Wasm provider mechanisms; ri-dej's backend gates remain. An inconsistent necessary mechanism returns to the map instead of being called proven safe.

## Primary evidence and limits

- [Linux getrandom manual](https://man7.org/linux/man-pages/man2/getrandom.2.html): flags/init, short-count/EINTR rules and syscall availability. Its 32MiB-era limit is explicitly historical, not a universal current cap.
- [Pinned Linux syscall/output implementation](https://github.com/torvalds/linux/blob/23c62304dde29abe92013d85910d03a77dada35d/drivers/char/random.c) and [buffer import](https://github.com/torvalds/linux/blob/23c62304dde29abe92013d85910d03a77dada35d/lib/iov_iter.c): validate actual chunk/count behavior; a zero syscall request can still wait for initialization.
- [Apple SecRandomCopyBytes](https://developer.apple.com/documentation/security/secrandomcopybytes%28_%3A_%3A_%3A%29) and [public C header](https://github.com/apple-oss-distributions/Security/blob/main/base/SecRandom.h): secure bytes, size_t count and checked status. No short-count or error-time rollback contract is inferred.
- [Apple getentropy](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/getentropy.2) and [arc4random manual](https://github.com/apple-oss-distributions/Libc/blob/main/gen/FreeBSD/arc4random.3): alternative contracts, not the selected macOS baseline.
- [WASI preview1 random_get](https://github.com/WebAssembly/WASI/blob/wasi-0.1/preview1/witx/wasi_snapshot_preview1.witx) and [u32 size ABI](https://github.com/WebAssembly/WASI/blob/wasi-0.1/preview1/witx/typenames.witx): high-quality output, permitted blocking, status rather than a short count; not preview2's contract.
- [Pinned Wasmtime preview1 implementation](https://github.com/bytecodealliance/wasmtime/blob/c52bc6d8fc7ebf2ba3f7e39ab3203a3c13c1d272/crates/wasi/src/p1.rs), [host provider/limit configuration](https://github.com/bytecodealliance/wasmtime/blob/c52bc6d8fc7ebf2ba3f7e39ab3203a3c13c1d272/crates/wasi/src/ctx.rs) and [memory safety constraints](https://docs.wasmtime.dev/api/wasmtime/struct.Memory.html#memory-and-safety): host policies/limits and predictable provider configuration are not universal WASI guarantees, and guest offsets are not stable retained host pointers.

These are provider-contract facts and support requirements, not validation of Rill's syscall/FFI/scheduler/linker or supported-host implementation. No general user-facing FFI, deadline API or deterministic secure-test mode is authorized here.
