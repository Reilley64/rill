# Whole-program monomorphization through inkwell and LLVM 23

The compiler monomorphizes every generic function, because Rill values are unboxed with fixed layouts, there is no GC to free boxes, and every overload call inside a generic body resolves at compile time. For v0, it builds the whole program, including `std`, from source on every build. The language does not rule out separate compilation. ri-skb's orphan rule allows each module's overloads to be checked on their own. As in Rust, a module could store declarations and generic bodies as metadata so dependent modules can monomorphize them. Whole-program builds postpone the need for that metadata format and a module cache. Ownership is checked on generic MIR before monomorphization, so an error in a generic body is reported once, and inside a generic body `T` moves unless a `where copy(T)` clause allows `copy`. Code generation uses inkwell pinned to LLVM 23 and statically linked into `rill`, because `musttail` through the C API needs LLVM 18, RISC-V `musttail` with `byval` needs 23, and Wasm reference types changed shape in 23.

## Stack and target support qualification

[ADR 0014](0014-bounded-stacks-proper-tail-calls-and-backend-gates.md) qualifies ri-j33/#13's earlier tail-position claims: semantic proper-tail transfer needs no retained caller storage or post-call cleanup/joins. Pending obligations make a final-looking call ordinary; ABI inconvenience must not silently reclassify an eligible call. Honor eligible transfers in development and optimized builds or report actionable unsupported lowering. No early guard disposal or accumulating hidden heap activation chain.

The earlier LLVM tail-call plus Binaryen Asyncify composition is not the selected portable Wasm mechanism: the inspected Asyncify revision rejects tail-call instructions, and the [confirmed ri-dej follow-through below](#confirmed-portable-wasm-lowering-direction-30) selects explicit records/iterative dispatch as a direction only. ri-dej gates support on pinned reproducible target/build evidence, including ABI cases, probes/outgoing arguments, distinct Wasm addressable/saved/engine resources, memory growth and host borrowers, iterative cleanup and reclamation. A callee-only check or native-style guard-page assumption is insufficient. If remaining lowering cannot preserve the contract, return unresolved backend/scope to the map rather than weaken it or treat directional approval as completed validation. Exact lowering/checking remains ri-48g work; this ADR does not establish a working compiler/runtime.

## Considered options

- **Boxing every value (OCaml, Java).** Generic code is compiled once, but every value needs a heap allocation, which conflicts with fixed layouts and in-place reuse and needs something to free each box. Rejected.
- **Witness tables only (Swift's unspecialized generics).** Generic code is compiled once and receives a hidden table of size, copy, `dispose`, and the overloads its `where` clauses name. Smaller binaries, but every operation on `T` becomes an indirect call. Kept as a possible later fallback for code size, not for v0.
- **Raw `llvm-sys`.** Fewer layers, but every codegen call is `unsafe`. Rejected.
- **Textual `.ll` and external LLVM tools.** The simplest start, but users would need LLVM installed, and the text format has no compatibility promise. Rejected.

## Confirmed portable Wasm lowering direction (ri-dej)

Human-approved ri-dej follow-through (comment 6900825635) selects **compiler-owned activation/continuation records plus a nonrecursive dispatcher** for portable `wasm32-wasip1` lowering. This replaces the provisional Wasm tail-call/Asyncify composition: pinned Binaryen rejects its tail instructions and does not supply the required managed-region pre-write containment. The LLVM 23/inkwell pipeline, native fixed-stack/proper-tail direction, intended targets, source semantics and public interfaces remain unchanged.

Ordinary calls retain required caller continuations and stable addressable storage. Eligible tail transfers evaluate their target and arguments once, then replace the current record rather than append activation history. Suspension publishes the surviving function, PC and live state, then returns to the scheduler. Resume does not replay eliminated entry effects. The dispatcher schedules already-resolved functions/continuations, not runtime overload or result-type dispatch.

Retained descriptors, links, arguments/results, padding, live staging and activation-specific runtime metadata belong in the managed accounting and must be checked before writes. Addressable sources, initialized ownership, disposal and child/native join state must survive through actual completion/confirmed release; a temporary step frame cannot back a retained borrow. Preserve ri-636's separate 1 MiB per-routine addressable/Saved defaults and program-wide Saved override setting, distinct host-engine limits, ordinary-call eligibility exceptions and fatal exhaustion rules. No hidden heap continuation history, premature release, target drop or ABI-dependent ordinary fallback is authorized.

**Alternatives:** LLVM retcon remains optional frame-splitting machinery, not a required dependency or an automatic source-tail solution. Stock Asyncify, simply removing its rejection, JSPI and host-only fibers are not the selected portable baseline; none supplies this complete accounting/lifetime contract by itself.

**Acceptance boundary:** this is directional architecture approval, not a finished private typed/owned-value ABI, automatic MIR/liveness/checker transform, final layout/admission policy, performance result or backend acceptance. The [primary-source comparison](../research/0030-portable-suspension-candidates.md), [executed candidate report](../research/0030-portable-suspension-experiments.md) and [standalone probes](../../experiments/backend-30/portable/README.md) provide finite mechanism evidence, not Rill execution or a safety proof. Their header/packet sizes, 64 KiB runtime reservation, minima and maximum-backing policy are experimental constants, not approved final policy. The later [runtime-validation follow-up](../research/0030-runtime-validation.md) completes ri-dej's standalone mechanism experiments, including owned ABI shapes, native admission/M:N/cleanup/retention and terminal guest teardown. ri-48g still owns the complete ABI/layout/admission specification, acceptance of generated lowering/checker/runtime/provider implementations, and RFC work. Neither this direction nor mechanism-stage closure establishes production implementation readiness or RFC acceptance.
