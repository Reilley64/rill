# One toolchain repository with mise-managed development

[Accepted #46](https://github.com/Reilley64/rill/issues/46) keeps the Rust implementation, Rill standard-library source and target-runtime support in one repository so changes to semantics, editor behavior and toolchain inputs can be reviewed together. A private root Cargo workspace uses the short names `crates/{compiler,ide,lsp,codegen-llvm,cli}` and produces `rill` from `cli`. The shared semantic core depends on neither LLVM nor LSP; Rust IDE and LSP adapters reuse it rather than maintain a second checker.

Rill source belongs in `stdlib/`, with a future explicit `std.rill` facade, and target-runtime support belongs in `runtime/`. Their separation keeps language algorithms distinct from target and ABI machinery without creating independently versioned releases. The future installed toolchain contains `bin/rill` and `lib/rill/{std,runtime/<target>,toolchain.json}`. The selected toolchain, not the working directory, determines installed standard-library source. End users need no Rust installation. This chooses a distribution boundary, not an implemented installer or ABI.

mise is the primary developer-tool and task entry point; Cargo and uv retain dependency ownership. Pinned tools and committed locks avoid competing version authorities, so there is no `rust-toolchain.toml` or custom bootstrap wrapper. GitHub Actions calls the same tasks as contributors. This is simpler than a staged bootstrap system, but it does not make host SDKs, native linkers or first-setup network access disappear. No vendoring or air-gap guarantee is made.

Fast checks remain LLVM-free, and heavy tools belong to explicit tasks. The optional LLVM 23.1.5 route uses an explicit upstream prefix on Linux x86-64, Linux AArch64 and macOS AArch64, with a pinned source build for macOS x86-64. This avoids implicit Homebrew discovery and shared-LLVM fallback at the cost of a costly Intel Mac build and per-host validation work. Provisioning and static-link suitability have not passed validation. The first scaffold adds infrastructure and real CLI help/version only; it does not implement a checker, server, library or runtime, or close their existing acceptance gates.

[Development](../development.md) records setup, task status and host prerequisites. The [repository comparison](../research/compiler-stdlib-lsp-repository-layouts.md), [mise investigation](../research/mise-toolchain-management.md) and [LLVM provisioning research](../research/0046-llvm23-provisioning-options.md) remain historical decision inputs, not installation or product acceptance results.
