# Explicit TLS trust and a private provider boundary

Rill needs TLS for standard HTTPS and external database transports without introducing general native extensions or handwritten cryptography. Human-confirmed #38 Q1–Q80 and consolidated approval select `std::tls`: eligible owned canonical-I/O transports, controlled private OpenSSL3.5 LTS, explicit root/CRL/credential snapshots, TLS1.3 default and a hardened explicit TLS1.2 compatibility offer. [The public contract](../tls-contracts.md) and [private semantic boundary](../tls-native-boundary.md) are authoritative; [prototype27](../../prototypes/27-tls/README.md) is hand-checked, not executed.

The deliberate minimum excludes automatic OS/bundled trust, online status fetching/soft-fail, insecure overrides, session resumption/0RTT, dynamic credentials, encrypted key containers and independent TLS application-I/O halves. Strict full-path CRLs and explicit provisioning cost compatibility and deployment effort; one exclusive generic transport avoids pretending TCP halves make arbitrary TLS directions independent. Version-dependent closure, authenticated EOF, layer-relative plaintext progress and actual native completion remain explicit rather than hidden behind provider defaults.

Provider selection is conditional: the pinned source has current-conformance gaps and does not establish the required bridge, limits, ownership or secure target execution. [#44](https://github.com/Reilley64/rill/issues/44) gates TLS implementation/support/v0 readiness; #30 and #43 stay independently OPEN. Design closure and review-ready #28 RFC inputs are not implementation, accepted RFCs, security certification or a passed ABI. If the provider cannot meet the contract, return to the map instead of weakening verification or dropping targets.
