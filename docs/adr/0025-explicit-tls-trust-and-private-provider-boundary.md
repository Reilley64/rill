# Explicit TLS trust and a private provider boundary

Rill needs TLS for standard HTTPS and external database transports without introducing general native extensions or handwritten cryptography. Human-confirmed #38 Q1-Q80 and consolidated approval select `std::tls`: eligible owned canonical-I/O transports, controlled private OpenSSL3.5 LTS, explicit root/CRL/credential snapshots, TLS1.3 default and a hardened explicit TLS1.2 compatibility offer. [The public contract](../tls-contracts.md) and [private semantic boundary](../tls-native-boundary.md) are authoritative; [prototype23](../prototypes/23-tls.md) is hand-checked, not executed.

The deliberate minimum excludes automatic OS/bundled trust, online status fetching/soft-fail, insecure overrides, session resumption/0RTT, dynamic credentials, encrypted key containers and independent TLS application-I/O halves. Strict full-path CRLs and explicit provisioning limit compatibility and require deployment effort. One exclusive generic transport avoids assuming that TCP halves make arbitrary TLS directions independent. The contract specifies version-dependent closure, authenticated EOF, layer-relative plaintext progress and actual native completion rather than leaving them to provider defaults.

Provider selection is conditional: the pinned source has current-conformance gaps and does not establish the required bridge, limits, ownership or secure target execution. [#44](https://github.com/Reilley64/rill/issues/44) gates TLS implementation/support/v0 readiness; #30's [standalone mechanism stage](../research/0030-runtime-validation.md) is complete, while #28 retains production/formal backend acceptance and #43 stays OPEN for its separate provider integration. Design closure and review-ready #28 RFC inputs are not implementation, accepted RFCs, security certification or a passed ABI. If the provider cannot meet the contract, return to the map instead of weakening verification or dropping targets.
